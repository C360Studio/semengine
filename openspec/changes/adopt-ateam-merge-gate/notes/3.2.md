# Task 3.2 notes

- The binary is reached as `ateam` on `PATH` after `go install`, as `ci.yml`'s verify job already relies on
  (`setup-go` puts `$(go env GOPATH)/bin` on `PATH`), not through `ATEAM`. ateam's reference workflow sets `ATEAM` only
  because it builds into `$RUNNER_TEMP`.
- No `push` trigger: the old `ci.yml` job also ran on a push to `main` (rule 1 only). ateam's workflow runs on
  `pull_request` alone, and the spec delta names only the `pull_request` types, so the push run goes.
- The design's Migration Plan and Risks say this PR's own `Merge check` fails rule 1 until the ruleset edit. That is
  not what will happen on this PR. The workflow checks out the base commit, and on `main` today
  `scripts/merge-check.sh` is still the 270-line script, which ignores `ATEAM_REQUIRED_CHECKS` and checks only that
  `Required` is required. So until this PR merges, its own `Merge check` runs the old script: skipped while the PR is
  a draft, and after it is marked ready it passes rule 1 and fails or passes on the old `reviewed-by:` rule. The first
  run that exercises `ateam review gate`, and the first that fails rule 1 without the ruleset edit, is on the first
  pull request opened or updated after this one merges. Task 3.2's gate ("the PR's own Merge check run reads the
  forge and reports, rule 1 red until the ruleset edit") therefore cannot be observed on this PR as written; the task
  stays unticked for the owner or architect to restate.
- Ordering consequence for task 5.1: once the owner adds `Merge check` to the ruleset, every other open pull request
  lacks that check until it merges `main` after this PR lands (a pull request runs the workflows of its merge commit,
  and `main` has no `merge-check.yml` until then).
