# Task 3.1 notes: server, client writer, subject input, keep-alive, lifecycle

Choices the design leaves open, and what task 3.1 did not do.

## What the factory builds now

A subject configuration builds the component. Two configurations are still refused with an error that is not of the
invalid-config class, each marked `// shortcut:` in `output/websocket/websocket.go`:

- **Applied state** (the kv-watch of `ENTITY_STATES`, which is also the default `{}`): `errNotBuilt`, until task 3.3
  adds the view. `TestAppliedStateNotBuiltYet` replaces 2.1's `TestFactoryBuildsNothingYet`; 3.3 deletes it.
- **TLS enabled** in `Dependencies.Security`: `errTLSNotBuilt`, until task 3.2 loads TLS at `Start`. Without it, a
  deployment that asked for TLS would get plain HTTP on this port. `TestTLSNotBuiltYet`; 3.2 deletes it.

`TestRegisterDeclaresWhatTheFactoryResolves` now also compares the declarer with a built component's `InputPorts`
and `OutputPorts`, for a subject configuration.

## Only `Register` is exported

D7 S8. The component type is `output`, unexported; the factory returns it as a `component.Discoverable`.

## No run context in 3.1

D3 says connections run under the one run context `Stop` ends. In 3.1 nothing that continues after `Start` takes a
context: `http.Server.Serve` takes none, a client's reader and writer stop on a closed connection or a channel, and
the subscription handler's context is the NATS client's. Handing the run context to the handlers would need
`http.Server.BaseContext`, a closure that keeps the context inside a struct the component keeps, which the developer
contract lists as a disguised stored context. So `Stop` ends each client itself: it fences new attaches, closes each
client's `closing` channel (its writer sends close 1001 and closes the connection), and waits for every upgrade
handler through `internal/httpadmission`. ADR-113's observable holds and is tested: ending `Start`'s context stops
nothing (`TestStartContextEndingStopsNothing`, the suite's `StartContextEndStopsNothing`). Task 3.3's view loop is
the first work that takes a context; the run context arrives with it.

## One reader, one writer per client

The upgrade handler's goroutine is the client's only reader and a writer goroutine its only writer: frames, pings and
the close frame all go through the writer, so no write needs a lock. The handler returns only after the writer has
(it closes the connection first, which ends a blocked write), so `httpadmission`'s wait joins both.

- Client frames are read with `NextReader` and copied to `io.Discard`, so a large client frame is never held in
  memory (the pin read each into a buffer with `ReadMessage`).
- The read deadline is set once at connect (twice `ping_interval`) and extended only by a pong, as the spec says. A
  client frame does not extend it; a gorilla client answers pings while it reads, so a client that sends frames also
  answers pings.
- On a read timeout the connection is closed without a close frame.

## The client queue

A slice under the client's mutex with a one-slot `ready` signal, not `pkg/buffer` (D10: the websocket ring is no
longer its reader). The writer takes one frame at a time, so at most 256 wait plus the one being written. A frame
queued while 256 wait drops the oldest.

## Stop and a stalled client

`Stop` asks every writer to send close 1001 under a one-second write deadline (`closeWait`), then close. A writer
blocked in a data write (its client stopped reading and the socket is full) sees the request only once that write
ends, at most `writeWait` (10 s, the pin's) later, so `Stop` can take up to about 11 s with a stalled client
attached. No mechanism shortens it; the bound is declared here. `TestStalledClientDoesNotSlowOthers` closes its
stalled client before it calls `Stop`.

## Metrics

Only `semengine_websocket_messages_dropped_total{listener,reason}`, which 3.1's drop tests read, registered through
`metric.RegisterOrGet` on the injected registry (nil registry: registered nowhere). The rest of D6's metrics,
including `clients_connected` and `client_disconnections_total{reason="read_timeout"}`, come with task 3.2; until
then `TestSilentClientIsClosed` checks the client is closed and detached, and `TestStartContextEndingStopsNothing`
checks no client is attached after `Stop` through the component's own client set.

## Declared drops

One `drops.record` site counts and logs both reasons. The first drop per reason logs at once; later ones at most once
a minute per reason, with `dropped` the count since the last line. The `not_json` line names the subject; the
`client_queue_full` line counts the clients shed in one fan-out.

## Test ordering

- `TestSubjectFanOut` and `TestStalledClientDoesNotSlowOthers` read the counter and the log after `Stop`, which
  drains the subscription, so every handler call has returned. Neither relies on NATS delivering a subscription's
  messages in order. After `Stop`, each fan-out client's next read is close 1001 with no frame left, so the
  message that is not JSON reached no client.
- `TestStalledClientDoesNotSlowOthers` publishes 16 KiB frames one at a time, each read by the live client before
  the next, until the stalled client's queue is full (`fullestQueue` reads the queue lengths only to know when to
  stop), then two more, each of which drops one. On this Mac it finished in about 1.2 s.
- `TestQuietClientStaysConnected` uses `ping_interval` 300ms and waits for six pings (three read deadlines);
  `TestSilentClientIsClosed` uses 100ms and fails if six unanswered pings arrive before the close. Both wait on
  pings the client counts, not on the clock.
- `TestStartFailureReleasesPort` is a unit test: its NATS client never connected, so `Start` binds the port, then
  the subscribe fails.

## Generated checks and fuzzing

Generated checks: not used, as the design's "Tests" says for this component: the subject path has no state across
messages but each client's FIFO queue, whose one law (drop oldest at 256) `TestClientQueueDropsOldest` checks at its
boundary. Fuzzing: no target; the only exported symbol is `Register`, and the component parses no external bytes
(a message is checked with `json.Valid` and sent unchanged; client frames are discarded unread).

## Review fix: pings while the queue drains

The step-2 review (PR #592, comment 6801700128, HIGH) found the writer's drain loop checked only `closing`, so a queue
kept non-empty past twice `ping_interval` sent no ping, and a client still reading and answering pings was closed at
its read deadline (close 1006). The drain loop now also takes a due ping before the next queued frame. The single
writer, FIFO order with drop-oldest, and the stop check are unchanged; a ping and a stop both due are taken in either
order, and the stop is taken on the next pass.

`TestBusyClientKeepsPings`, adapted from the reviewer's probe, drives it through real NATS and a real WebSocket: a
client with a 32 KiB receive buffer reads one frame per 5 ms tick (its processing time, not an ordering) and answers
pings; after three pings, 1024 frames of 32 KiB are published, and it must receive six more pings while connected.
On the unfixed writer it failed with
`client closed after the burst after 0 pings and 106 data frames: websocket: close 1006 (abnormal closure): unexpected EOF`;
with the fix it passed, five runs in a row under `-race`, with `TestQuietClientStaysConnected`,
`TestSilentClientIsClosed` and `TestStalledClientDoesNotSlowOthers`.
