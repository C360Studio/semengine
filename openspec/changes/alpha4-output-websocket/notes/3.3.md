# Task 3.3 notes: the applied-state input

Choices the design leaves open, and what task 3.3 did not do.

## What changed from 3.1

- 3.1's `errNotBuilt` refusal and `TestAppliedStateNotBuiltYet` are gone: a kv-watch configuration (the default `{}`)
  builds. `TestRegisterDeclaresWhatTheFactoryResolves` now compares the declarer with a built component for both
  inputs.
- The run context arrives here, as 3.1 said it would. `start` creates it for applied state only, as graph-query does
  (`context.WithCancel(context.WithoutCancel(ctx))`), keeps the cancel and a `supervised` channel, and `cleanup`
  ends it. A subject instance still takes no run context: nothing it runs after `Start` takes one.

## One view per instance, reopened

`state.go`. `superviseView` follows `processor/graph-query/community.go`: open `ENTITY_STATES` through
`kvcatalog.OpenCatalogReader` (which never creates it), run one `graphview.View` until it returns, wait 5 s
(`viewRecheck`, graph-query's value), open again. The log rule and `shutdownFailure` are graph-query's, copied: the
function is unexported there, and a shared helper for two callers was not worth a new package.

The view's decode runs `graph.UnmarshalEntityState` and keeps a copy of the stored bytes (`bytes.Clone`, so nothing
depends on whether nats.go reuses a value's buffer) and the write time. A value it refuses is poison.

## Readiness: Health and 503

`applied` is one of catching up (from `Start`), live (`Hooks.OnCaughtUp`) or lost (`Hooks.OnWatcherLost`). Health
reports the first and last as the stuck states D3 names: "applied-state view catching up", "applied-state watch
lost, reopening". After a loss the state stays lost until a new view catches up, so a missing bucket after a loss
still reads as lost.

The upgrade handler attaches to the view (`SnapshotAndSubscribe`) before it upgrades. No view, or an attach the
view refuses, is answered 503 with the stuck state as the body. The view's own refusal is the gate, not `applied`:
Health can lag the view by one hook call, the gate cannot. A refusal matching `graphview.ErrWatcherLost` names the
loss even before the hook has run.

The subscription is attached under the request's context and unsubscribed when the handler returns.

## The writer

The step-2 lesson (record 6801700128) applies to every queue the writer drains, so the drain loop is now one
function, `drain`, used for the subject queue, the snapshot and each batch of changes: before each frame it takes a
due ping and a stop. `TestBusyClientKeepsPings` still drives it (mutant M13 below).

An applied-state client has no 256-frame queue. Its writer takes the next batch from the subscription only after it
has written the one before, so while it is behind, its later changes merge per key in graphview's pending buffer.
That merge is what `Hooks.OnFanOut`'s overwritten count reports, and it feeds `changes_coalesced_total` and the
`client_behind` warning through the same `drops.record` as the subject reasons. `drops` now holds one counter per
reason, resolved at construction, so `messages_dropped_total{reason}` samples exist at 0 from the start, as the
single-label metrics already did.

Snapshot frames are built one at a time as they are written, puts by key, then poisoned by key, then `synced`. A
large snapshot is not copied into frames up front.

## Closing

- A lost watch closes each client with 1013 and the new disconnection reason `watch_lost` (D6 does not list the
  reasons; 3.2's set was closed, so this adds one).
- `cleanup` ends the run context only after every client handler has returned, so a client is closed by the stop
  (1001), never by the view stopping under it. A subscription that ends for a reason other than a loss is closed as
  a stop.
- A view whose watch could not be stopped (`kvwatch.ErrDeliveryOpen`) is returned by the `Stop` that joined the
  supervisor only, as graph-query does.

## Counting input

`messages_received_total` and `DataFlow` count each write the view decodes, with its length. A delete carries no
value and is not counted. Choosing `OnApply` would count deletes but has no length.

## Timing measured here

- `TestWatchLossClosesAndRecovers` takes about 25 s on this Mac: about 20 s from deleting the bucket until nats.go
  closes the watch's update channel, then up to `viewRecheck`. The 20 s is the library's and not promised.
- `stalledAppliedState` (the `applied_state` case of `TestStalledClientDoesNotSlowOthers`) writes rounds of 32 keys
  of 64 KiB. The first merge came in round 4 in each of three runs. The test stops at 40 rounds, a round bound, not a
  deadline. It then reads the stalled client again; that client must start reading before its blocked write has
  waited `writeWait` (10 s). In these runs it took about 2 s.

## Generated checks and fuzzing

No generated checks, as the design's "Tests" decided: the order-dependent law belongs to graphview and is already a
generated history against a reference model (`TestViewHistoryMatchesModel`). What this task adds turns each batch
into frames, with no state across batches. The named boundary cases are each run: a key put twice, put then
deleted, put/poisoned/healed in one burst, and a client attaching mid-burst (`TestAppliedStateConverges`); a stalled
client beside a live one (`stalledAppliedState`); the bucket deleted and recreated
(`TestWatchLossClosesAndRecovers`). The folds are compared with the bucket read back and each key's last revision
with the bucket's history, not with anything the component computes.

No fuzz target: no new exported surface, and the only external bytes are stored values, which
`graph.UnmarshalEntityState` checks. That decoder is graph's, with its own tests.

## Uncovered

- A view that opens but whose `Run` fails at once, then reopens: no test makes `WatchAll` fail on an existing
  bucket.
- The supervisor reopening at all is shown by the recovery tests passing. A mutant that never reopens would hang
  them until `go test -timeout`, an inconclusive run, so it was not run.
- The `kvwatch.ErrDeliveryOpen` path of `Stop` needs nats.go to leave a watch's delivery open; no real trigger is
  known.
