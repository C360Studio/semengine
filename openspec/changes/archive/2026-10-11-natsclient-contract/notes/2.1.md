# Task 2.1: T3 and T4

Choices the design does not spell out.

- **The silent server.** `silentListener` (in `natsclient/client_connect_test.go`) listens on `127.0.0.1:0`, accepts
  every connection and never writes, so nats.go waits for the server's first line until its connect timeout. It keeps
  each accepted connection referenced until cleanup: a connection nothing refers to can be closed by the garbage
  collector, which would end nats.go's wait early and hide the failure on `main`.
- **"The listener accepts nothing" (T3).** The test checks for an accepted connection with a non-blocking receive
  right after `Connect` returns. With the fix there is no dial, so nothing can arrive later. On `main` the connection
  was accepted 5 s before the check.
- **T3 also checks the error class.** The spec delta says the error is transient, so T3 asserts `errs.IsTransient`
  beside `errors.Is(err, context.Canceled)`.
- **The 3 s wait (T4).** `awaitConnect` fails the test when `Connect` has not returned after 3 s, then still waits for
  it, so no `Connect` outlives its test. nats.go's connect timeout (5 s per address) bounds that wait, which is why the
  run on `main` shows the full 5 s and 10 s. In the "cancel once accepted" case the time is counted from the cancel.
- **The two-address case** uses the 100 ms deadline, as P18's two-silent probe did.

## Review stop 1: T4 reaches a dial in progress

Implementation review of 925afa3 (LOW): T4's listeners accept at once, so no case ended a dial in progress, and no
test set `netDial`.

- T4 has a fourth case, `deadline while dialling`. It sets the client's `netDial` to a stand-in that ends only when
  the `*net.Dialer`'s `Cancel` closes, or at the dialer's `Timeout`, as a real dial nobody answers would. The timeout
  bounds the wait in `awaitConnect` on a failing run (5 s, like the other cases); a channel closed at cleanup would not,
  because `awaitConnect` waits inside the test function, before cleanup runs. The URL is `refusedNATSURL`, so a
  client that bypassed its dialer would fail at once with a refused dial, not a deadline.
- `Connect`'s comment now says it "ends the dial, or closes the socket while it waits for the server's answer" (T4).
  `Dial`'s comment cites T4 for the cut reaching a dial through `Cancel`, and P23, P25 for the net package still
  honouring that field. The `netDial` comment cites T4.
- What the case does not show: that the net package honours `Cancel`. The stand-in honours it by construction. P23 and
  P25 measured it on a real dial. T8 (task 3.3) also uses a `netDial` stand-in, so design D1's "T8 pins the behaviour,
  so a Go release that stopped honouring the field would fail it" does not hold as the design describes T8. That is
  for the architect.
