# Task 2.3: T5 and its mutation check

Choices the design does not spell out.

- **The setup.** T5 (`natsclient/client_connect_test.go`) runs an embedded server on port -1. An echo responder on a
  connection of its own subscribes and flushes before the client connects, so the server holds its subscription
  before any request. The client is built with `WithHealthInterval(0)` and `WithReconnectWait(10ms)`; the short wait
  keeps T5 near 0.1 s instead of 2 s, and every reconnect still dials through the client's dialer.
- **Only the client is dropped.** T5 reads the client's id on the server (`GetClientID`) before the cancel and drops
  that one connection with `DisconnectClientByID`. P18 dropped every client, the responder included.
- **The drop error is reported with the wait, not required on its own.** With a cut left armed, the cut may already
  have closed the socket when the drop runs, so the server may no longer hold the client. Requiring the drop would
  give that wrong change two places to fail, and `task mutate:check` an inconclusive verdict. On correct code a
  failed drop still fails T5 at the wait, with the drop error in its message.
- **The wait.** `probe.Await` reads the native connection's reconnect count and whether it is connected, within
  `lifecycleBound` (10 s, a failure bound). nats.go counts a reconnect only once a reconnect dial has succeeded
  (`nats.go:3530`, v1.54.0), so a dialer that refuses every dial leaves it at 0.
- **Doc comments.** `Connect`'s comment now says the context does not bound later reconnects (T5), and the comment in
  `connectWith` cites T5.
- **What a lucky wrong change would need.** The armed cut runs as soon as the cancel lands; the reconnect waits
  `ReconnectWait` (10 ms) and nats.go's jitter before it dials. A cut that came after the reconnect would close the
  new socket and refuse every later dial, so the request would have to finish in between. That did not happen in the
  three runs below.

## Generated checks: not used, and why the examples suffice

Codex's stop-1 review (PR #177 comment 6111641674, MEDIUM F2) asked for the decision `docs/testing.md`, "Decide
whether generated checks are needed", requires: the outcome here depends on the order of Connect, a context's end, a
disconnect, a reconnect, repeated cuts, and Close.

**The decision: named examples, no generated checks.** The history that decides an outcome is short, and each step of
it is a fixed point in one call, which a test can reach deterministically:

- **The dialer has two states.** It is live until its first cut, and cut for good after it. A second cut does nothing
  and every later dial is refused, whatever came between. So a generated sequence of cuts and dials reduces to "before
  the first cut" and "after it": `TestSocketDialerRefusesADialAfterTheCut` (a dial after the cut, and a second cut).
- **Each Connect has its own dialer, and two sites can cut it**, each armed and joined inside one call. Connect's cut
  can fire only on a Connect that then fails, whose dialer is never installed, so Close never cuts a dialer Connect has
  cut. That is decided by code order, not by timing.
- **Where Connect's context ends**, one test per stage: before the call (T3, "no dial"); after Close (T3, "after
  Close"); during the lookup (T4, "host name resolved inside the dial"); during the dial (T4, "deadline while
  dialling"); during the handshake (T4, "deadline", "cancel once accepted", "two addresses"); between the dial and
  admission (`TestConnectRejectsCandidateWhenContextCanceledDuringDial`); after Connect returned, followed by a
  disconnect and a reconnect (T5).
- **Where Close comes**, one test per stage: before Connect (T3, "after Close"); during Connect's dial
  (`TestConnectRejectsCandidateWhenCloseWinsAdmission`, and `TestConnectCommitsCandidateWhenAdmissionRemainsOpen` for
  the order without it); during a held write (T1); during a held write with a `Subscribe` held behind it (T2); during
  a reconnect dial after a disconnect (T8); and between a `Subscribe`'s admission and its connection check
  (`TestSubscribeEndedByCloseIsConnectionClosed`).

What a generated check would add is the interleaving of these calls with nats.go's goroutines: which of the cut, the
read loop and the drain takes nats.go's lock first. A sequential reference model cannot test that (`docs/testing.md`,
"Check a history against a reference model"). The examples pin each such point with a channel, a proxy or a `netDial`
stand-in instead of hoping a run reaches it, and are repeated: `-race -count=20` per test in tasks 3.1 to 3.5,
`task test:repeat` (five shuffled runs at one CPU) in `task verify`. Those repetitions found the one ordering the
examples first missed (task 3.2's notes: nats.go reopens a closed connection's status after a drain was cut short).

**Left out on purpose.** Connect's context cannot end during a reconnect of Connect's own: Connect returns before
nats.go starts any, and T5 shows the context no longer reaches the connection after that. Close does not cut a dial
that a Connect still in progress started, because that dialer is not installed yet; such a Connect ends with its own
context or nats.go's timeout and is then refused admission. `TestConnectRejectsCandidateWhenCloseWinsAdmission` shows
the refusal with a stub dial; no example runs that order against a real socket.
