# Task 3.1: T1, Close ends a held write

Choices the design ("Tests that replace the probes") does not spell out.

- **The new file holds the proxy.** `client_close_held_test.go` has T1 and the helpers T2 (task 3.4) will reuse:
  `newHeldClient`, `holdPublish`, `startClose`, `within` and `heldProxy`.
- **How the proxy knows the publish has begun.** It forwards each client's bytes to the server until a read contains
  `heldSubject`, then reads nothing more from that client and closes `held`. `Client.Publish` adds trace headers, so
  the line is an `HPUB`; the proxy looks for the subject, not the verb. It keeps the last `len(heldSubject)-1` bytes
  of each read, so a subject split across two reads is still found.
- **Cleanup order.** `newHeldClient` registers the proxy's cleanup after `closeInCleanup`, so it runs first and closes
  both of the proxy's sockets. `startHeldProxy` also registers it when the proxy starts, so a test that stops before
  the client exists still closes it; `close` runs once.
- **`within` fails at once.** Unlike `awaitConnect`, it does not wait for the call after the test's wait has run out:
  the held call is released only by the proxy's cleanup, which runs after the test returns.
- **`holdPublish` fails at once** if the publish returns before the proxy holds it, so a refused publish (for example
  one over `max_payload`) is not reported as a missing hold.
- **What T1 asserts.** `Close` returns an error matching `context.DeadlineExceeded` within the test's 10 s wait
  (`lifecycleBound`); the held publish returns an error, any error, as the design's table says; and the native
  connection read before `Close` reports `IsClosed`.
