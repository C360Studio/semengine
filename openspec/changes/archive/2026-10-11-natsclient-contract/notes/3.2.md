# Task 3.2: Close cuts the socket of a connection the client dialled

Choices the design (D1) and the prototype (`fix-prototype.diff`) do not spell out, or that depart from them.

- **One spelling of arm, then stop or join.** `socketDialer.cutWhenDone(ctx)` arms `context.AfterFunc(ctx, cut)` and
  returns a stop that disarms it or waits for a cut that has begun. `connectWith` (task 2.2's inline form) and
  `cleanup` both use it, so neither can drop the join. The stop is called once at each site; a second call would wait
  forever, which its comment says.
- **The dialer is recorded at admission,** `m.socket = socket` beside `m.dialled = conn`, under the same lock. Neither
  is cleared, as `dialled` was not before. `Close` takes it only when `conn == m.dialled`, so a connection installed
  through `SetConnection` is not cut (design D1, "Costs").
- **Where `cleanup` arms the cut.** First, before `stopHealthMonitoring`, as the task says, and stopped by a `defer`,
  so it is joined on every return. The comment says why: no step may wait before the cut can end the wait.
- **`Close`'s doc comment** now says an ended context closes the socket and ends a reconnect dial on a connection the
  client dialled (T1; P17, P23), that a buffered message is not promised to reach the server, and that a
  `SetConnection` connection is not cut. T8 (task 3.3) is added to the citation when it exists.

## T1 awaits CLOSED instead of reading it once

T1 read `conn.IsClosed()` once, right after `Close` returned. With the fix it failed in 2 of 160 runs (eight batches
of `-race -count=20`), with the status `DRAINING_PUBS`. The cause is nats.go's, not natsclient's:

- in that interleaving the cut released the lock, and `Drain` took it before the read loop saw the closed socket, so
  nats.go started its drain goroutine;
- `drainAndCloseConnection` then saw the ended context and called `conn.Close()`, which set `CLOSED`;
- nats.go's drain goroutine sets `DRAINING_PUBS` without checking for `CLOSED` (`nats.go:6378-6381`), waits for a
  flush of up to 5 s (`:6384`), and closes the connection again (`:6390`). (nats.go v1.54.0; the line numbers here and
  in `requireClosed`'s comment were corrected at stop 2, NIT 1.)

So T1 now calls `requireClosed`, which waits with `probe.Await` (bounded by `lifecycleBound`) for `nats.CLOSED`. A
`Close` that never closed the connection still fails it: the reconnect loop would keep the status at `RECONNECTING`.
With the change, 160 of 160 runs passed; one batch took 9.4 s, the 5 s case awaited.

The same path exists on `main`: any drain that `Close`'s context cuts short can reopen the status this way. The
closed handler does not run a second time. An earlier version of this note said it did, possibly after a `Close` that
returned nil; the stop-2 review (MEDIUM 3) showed that wrong, and this paragraph is the correction. In nats.go
v1.54.0 the first close queues the closed handler and then the end marker of the connection's callback queue
(`nats.go:6244-6251`). The one goroutine that runs those callbacks returns at that marker (`:3654-3656`) and is started
once per connection (`:2019`). The drain goroutine's later `DRAINING_PUBS`, its flush error and its second close
(`:6378-6390`) queue their callbacks behind the marker, so none of them runs. A nil `Close` still means every handler
of the client has returned.

What is real is nats.go's own state, not a client callback: for up to 5 s after such a `Close`, a `*nats.Conn` kept
from `GetConnection` reports `DRAINING_PUBS` and `IsConnected() == true`, then `CLOSED` again. The stop-2 review
measured it with two scratch tests it removed afterwards; the developer has not reproduced it. Raw nats.go: the closed
handler ran once, and no async error callback ran. Through natsclient: a second `Close` returned nil, the native
status then read `DRAINING_PUBS` for 4.80 s, and the closed handler ran once, never after the nil return. The review
ruled it nats.go's behaviour, to be recorded and not filed. `Close`'s doc comment now states it, and `requireClosed`
already waits it out.
