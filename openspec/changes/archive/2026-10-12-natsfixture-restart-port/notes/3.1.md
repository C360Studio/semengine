# Task 3.1 notes: Codex's review findings

- **H1, the operation budget spent on fixture startup.** `TestIntegration_ClientHandleErrorLogsObservedSlowConsumerDropCount`
  made its 15 s context before `startFixture`, so a slow Docker start (30.5 s in Codex's run) left `Connect` an expired
  context. The fixture now starts first. `newCapacityTestClient` (`stream_capacity_circuit_integration_test.go`) had
  the same order with a 30 s budget and gets the same fix; a search of every integration test that starts a fixture
  found no third site.
- **Shown able to fail,** by hand (an integration test, #129), with the budget cut to 300 ms in place and restored:
  - old order, 300 ms: FAIL at `client_async_error_integration_test.go:33`, `Client.Connect: connection cancelled
    failed: context deadline exceeded` (the fixture took 0.63 s);
  - new order, 300 ms: PASS in 0.70 s, so the fixture's start no longer counts against the budget.

  Command for both: `SEMENGINE_DOCKER_ADMISSION_WAIT_SECONDS=1800 task test:integration -- -v -count=1 -run
  '^TestIntegration_ClientHandleErrorLogsObservedSlowConsumerDropCount$' ./natsclient/`.
- **M1, "a second failure returns both".** Narrowed in `Restart`'s doc comment, `design.md` and notes 2.1 and 2.3:
  only a failure in the second stop, start or port read is joined with the first; a connect or JetStream failure after
  a good second read is returned alone. The comment at the retry site (`restart.go`, "Both failures are returned")
  sits on the join itself and stays.
