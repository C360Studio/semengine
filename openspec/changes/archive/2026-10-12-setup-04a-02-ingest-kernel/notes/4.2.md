# Task 4.2 notes: reconcile at the caller's revision (#19)

Choices the task left to the developer, what the tests prove and what they do not. The change is in
`pkg/projection/mutation_types.go` (the field) and `pkg/projection/mutation_client.go` (`Reconcile`). graph-ingest is
unchanged. The tests are `pkg/projection/conditional_reconcile_test.go` (the typed client on a wire double) and
`TestCanonicalReconcileAtTheCallersRevision` in `processor/graph-ingest/canonical_mutations_test.go` (graph-ingest's
handler on the mock bucket).

## What changed

`ReconcileMutation` gains `ExpectedRevision uint64`, spelled as the wire request and `DeleteMutation` spell it. When
it is set, `Reconcile` sends it as the request's `expected_revision`. When it is zero, `Reconcile` sends the revision
of its own read, as before. The field's doc comment says what zero costs: a write between the caller's read and the
client's goes undetected.

graph-ingest already refused a request whose expected revision is not the one it reads, with code `revision_mismatch`
and detail naming `expected_revision` and `current_revision` (`processor/graph-ingest/canonical_mutations.go:333-337`).
Before this change the client could not send a revision the caller had read; it always sent the one it had just read.

## The choices

1. **The client still reads when the caller names a revision.** The read is there for `validateEntity`, which holds
   the stored entity to the contract's message type. graph-ingest's reconcile handler checks no contract, so without
   the read a caller could reconcile one contract's group onto an entity of another type that matches the entity
   pattern. The cost is one extra request. The client does not compare the caller's revision with the one it read:
   graph-ingest makes that comparison, and a second one in the client would be a second spelling of the same rule.
   When the two revisions are equal, the entity validated is the one written; when they differ, graph-ingest refuses.
   The comment at `mutation_client.go:196-199` says this.
2. **The concurrent-update scenario takes graph-ingest's comparison on its read, not the bucket's refusal.** The other
   writer commits R+1 before the reconcile is sent, so graph-ingest reads R+1 and refuses at `:333`, naming both
   revisions. The bucket's compare-and-set at `:350` covers a write that lands after graph-ingest's read; its refusal
   names `expected_revision` only. No re-read after that refusal was added. See "Open question" below.
3. **Where the tests live, and which proves what.**
   - "Concurrent update between read and reconcile":
     `TestReconcileAtAStaleRevisionIsARevisionConflict` proves the request carries the caller's R (not the R+1 the
     client reads), the receipt and the error are not committed, the error's kind is `MutationRevisionConflict` with
     code `revision_mismatch`, the detail the server sent arrives intact, and nothing is applied.
     `TestCanonicalReconcileAtTheCallersRevision`, first half, proves graph-ingest names R and R+1 and the bucket
     still holds the other writer's bytes at R+1.
   - "Unchanged revision": `TestReconcileAtTheCurrentRevisionIsVerifiedAtTheNewRevision` proves the request carries R
     and the receipt is verified at R+1. `TestCanonicalReconcileAtTheCallersRevision`, second half, proves a
     reconcile at the current revision R+1 applies at R+2 and the bucket holds the new value there.
   - The wire double (`reconcileServer`) is a model written from the requirement's text: it applies only at its
     current revision and otherwise refuses naming both. It is not graph-ingest's code.

Generated checks are not used. The input that matters is one revision against one current revision: equal, not
equal, or zero. Each has a named test (zero is `TestReconcileReadsExactRevisionThenMakesOneMutation`). No fuzz target:
the field is a number the client forwards; it parses no external bytes.

## Before adding the field

- Owner today: the wire request's `ExpectedRevision` (`graph.ReconcilePredicatesRequest`), which the client already
  filled from its own read. The typed request had no revision (`mutation_types.go:46-52` at `f3d5ae5`), so the field
  forwards an existing fact; it is not a sibling.
- Consumers at birth: semsource #215 and semconnect, named by the ruling (Q6 on #8, comment 5929656835). Nothing in
  this repository sets the field yet besides the tests.

## Open question

The requirement says that when the expected revision is not current, graph-ingest "SHALL return a revision-conflict
error naming the expected and the current revision". Read literally, that covers the bucket's refusal at `:350` too,
which names only the expected revision: the refused update returns no current revision. The scenarios and the
design's proving test (D8, row `#19 (Q6)`) cover only the comparison on graph-ingest's read. Naming the current
revision there would need a read after the refusal, and that read could return a revision later than the one that
won. This task did not add it. It is for the architect: narrow the requirement to the revision graph-ingest read, or
add the read after the refusal.
