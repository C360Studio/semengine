# Task 2.1 notes

`TestSubmitAfterRunCancelIsProcessed` and `TestRunCancelProcessesQueuedItems` are in
`internal/dispatch/shutdown_test.go`, each in `synctest.Test`, against the base API (`NewKeyedPool(ctx, cfg, deps)`,
`KeyOf`, `Process` returning an error).

Choices the design does not spell out:

- Each `Process` call records the item and `ctx.Err()` read at the call (`processCall`), so one equality checks the
  items, their order and that each saw the ended run context. The lane writes the slice; the test reads it only after
  `Shutdown` returned nil, whose join orders the writes before the read.
- `TestSubmitAfterRunCancelIsProcessed` calls `synctest.Wait()` after the cancel, so on the base the lane has taken its
  `ctx.Done()` arm before the submit: the failure is deterministic, not a race the test might lose.
- `TestRunCancelProcessesQueuedItems` holds the first item in `Process` until after the cancel; its own call records a
  nil context error, the 64 queued ones `context.Canceled`. The submits use their own live context, not the run context.
