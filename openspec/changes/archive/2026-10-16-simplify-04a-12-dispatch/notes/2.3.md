# Task 2.3 notes

Two queue-depth tests in `internal/dispatch/keyed_pool_test.go` (design D5), written against the base API and run at
base `49327b770027a2001536c6b9a03f288815ee0c52` with only the tests added.

## Choices the design does not spell out

- **Helpers.** `blockedPool` starts a one-lane pool whose `Process` holds the item `first` until a release channel
  closes, submits `first`, waits for it to enter `Process`, then submits the waiting items; `shutdownPool` releases and
  shuts it down under an hour's deadline on the bubble clock. Both tests use them, so each count is of items known to
  wait in the queue, not in `Process`.
- **The replacement pool.** It is made after both earlier pools are shut down, and holds four waiting items (a count
  neither earlier pool had), so a gauge that kept reading the first pool's queues (the `GaugeFunc` shape D5 rejects)
  reads 0, not 4.
- **`assert`, not `require`, for the gauge reads.** A failed `require` ends the test with the lanes still blocked in
  `Process`, and the bubble then panics with "deadlock" over the real failure. With `assert` the test goes on to
  shut every pool down and reports each wrong reading.
