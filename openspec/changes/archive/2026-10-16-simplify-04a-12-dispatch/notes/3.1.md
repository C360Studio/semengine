# Task 3.1 notes

One stop path (design D1, option (a)), in `internal/dispatch/keyed_pool.go`.

## Conformance to D1

| D1 statement | Where |
| --- | --- |
| Lanes read their queue until `Shutdown` closes it | `keyed_pool.go:246` (`for item := range ch`); `:334-337` (the drain closes each lane channel after `submitWG.Wait`) |
| The constructor's context reaches only `Process` | `keyed_pool.go:177` (handed to the lane), `:277` (to `Process`); no lane, `SubmitBlocking` or updater reads it |
| ADR-072 M3 submit/shutdown handoff kept | `keyed_pool.go:334` (`submitWG.Wait` before any lane channel closes), unchanged `SubmitBlocking` |
| `Shutdown` returns nil once the lanes exited, also under an ended ctx; `ctx.Err()` when ctx ends first | `keyed_pool.go:313-325`, mirroring `internal/cache/coalescing_set.go:203-208` |
| Nil ctx still refused | `keyed_pool.go:303` (unchanged) |
| No `context.Background`, `WithoutCancel` or `TODO` | none in `keyed_pool.go` |

## Choices the design does not spell out

- **The gauge updater's stop signal.** Deleting `drainCh` removed the signal `metricsUpdater` exited on, and D1 forbids
  it reading the constructor's context. Until task 3.3 deletes `metricsUpdater`, it exits on `stopMetrics`, a channel
  only it reads, closed by the drain once the lane channels are closed; it stays in the pool's wait group, so
  `Shutdown` still joins it. Without a `Shutdown`, the updater runs on, like the lanes (D1's stated cost). The field
  goes with the updater in 3.3.
- **Closing the lane channels is safe** because the drain closes them only after `submitWG.Wait()`: every submit that
  passed the stopped-check has finished its send, and every later one sees `stopped` and returns `ErrStopped`, so no
  send meets a closed channel.
- **Doc comments.** `NewKeyedPool`, `lane`, `Shutdown`, `drain`, `metricsUpdater` and the `submitWG` field now say the
  constructor's context reaches only `Process` and `Shutdown` is the only stop. `doc.go` is task 4.1's.
