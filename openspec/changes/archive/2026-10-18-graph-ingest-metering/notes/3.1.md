The test is `TestIntegration_DataFlowCountsInputMessages` in `processor/graph-ingest/dataflow_integration_test.go`. It
fails on the base, commit `98ef322`, by three assertions, after every precondition before them passed (the entity and
its type container landed, the older set was declared, the append reported two applied subjects, the create was
refused, the query answered):

1. `:91`, `entities_updated_total` rises by the append's applied subjects: expected 2, actual 0. On the base append
   counts nothing.
2. `:109`, `messagesProcessed` equals the four messages sent: actual 5. On the base the count is writes: the first
   message's merge, the containers its birth created, and the second message's merge that wrote nothing; the two

Choices the design does not spell out:

1. The component is built by `createTestComponentWithHierarchyConfig` on its own fixture broker and started, as the
   hierarchy integration tests do, with the merge test payload registered before `Start`.
2. "A message whose merge writes nothing" is the same entity's set sent again with a timestamp an hour older: the
   stored set is newer, so the set is declared on `stale_sets_total` and nothing is written (design D23). The test
   waits for that counter to rise, the only signal that the second delivery was handled.
3. The append's three subjects are the entity, its type container (both applied) and an absent local ID
   (`entity_not_found`). The `entities_updated_total` delta is read across the append alone.
4. The counters are read as the in-package fields `messagesProcessed` and `bytesProcessed`, which `DataFlow` divides by
   uptime; the rates themselves are wall-clock dependent and are not asserted here.
