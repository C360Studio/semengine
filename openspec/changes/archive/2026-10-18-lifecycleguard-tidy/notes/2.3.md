## Choices the design does not spell out

- `guard.go`: an unexported field `cleanup` is set in the same locked assignment as `used` and `startDone`, after the
  three refusals, so a refused Start records nothing. `Stop` copies it under the mutex in the section that sets
  `stopping`, then calls it unlocked, as before. The field is never cleared: once `terminal` is set, `Stop` returns
  before reading it, so clearing it would change nothing observable.
- The failed Start's rollback still calls the `cleanup` parameter rather than the field. It is the same function the
  field holds; reading the field would only add a lock.
- The two graph-ingest helpers (`leaveGuardCleanupPending`, `test_owner_support_test.go`; the cleanup in
  `TestLifecycleOwnerFailedCleanupRetainsExactHandlesForLaterStop`) remember their first call in a plain `bool`. The
  guard runs a cleanup one call at a time (the rollback ends inside `Start` before it takes the mutex; a concurrent
  `Stop` is refused before it reads the cleanup), and its mutex orders the calls, so `-race` reports nothing. Their
  assertions and test names are unchanged; each gains one doc sentence on the fail-once cleanup.
- `TestGuardStopRunsTheCleanupStartWasGiven`: the design names no failure line for the first Start or for Stop. They
  read "first Start = %v, want nil" (`t.Fatalf`, a precondition) and "Stop = %v, want nil" (`t.Errorf`, so the
  count lines still print). The second-Start line uses `t.Errorf` for the same reason. The other three lines are D2's,
  with B's count checked first.
- `TestGuardRollsBackAPanickingStart` counts cleanup runs: "a panicking Start ran its cleanup %d time(s), want one
  rollback" after `Start`, and "Start's rollback and a later Stop ran the cleanup %d time(s) in all, want 1" after
  `Stop`.
- `TestGuardStopBeforeStartRefusesLaterStart` loses its "Stop before Start ran cleanup" check: a `Stop` before any
  `Start` has no cleanup to run, since none was recorded.
- `TestGuardStopWaitsForAnInFlightStart` gives its counting cleanup to `Start`; both `Stop` calls take only a context.
  Its doc comment now says the waiting Stop runs the cleanup that Start was given.
- graph-ingest: `Component.Stop` is `return c.lifecycle.Stop(ctx)`. "component stopped gracefully" is logged at the
  end of `release`, after `clearLifecycleHandles()`. `Component.Stop`'s comment says Stop runs `release`, the cleanup
  Start gave the guard, and logs nothing itself; `release`'s says it logs once per success, for a Stop or a failed
  Start's rollback, and nothing on failure. graph-ingest's `Start` comment is unchanged (D5).

## Doc comments (D5)

The cleanup-once sentences 2.2 left: the package comment gains "The owner gives its cleanup once, to Start. A failed
Start's rollback and every Stop run that one function."; `Start`'s says it records `cleanup` and that a refused Start
records nothing; `Stop`'s first sentence is now "Stop runs the cleanup the admitted Start recorded and returns its
result." `Guard`'s says each Stop runs the recorded cleanup again. The #309 paragraph is unchanged and still true:
`stopping` is set before the cleanup runs and cleared only after it returns.
