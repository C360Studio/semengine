# Task 4.1 notes

## The loop test shown able to fail

`TestStatusMetricsLoopPublishesOnTheHeartbeat` (`processor/graph-ingest/readiness_loop_test.go`) passes on the base
too: with the override unset the loop already ticked at `statusMetricsInterval`. Its ability to fail is shown by two
`task mutate:check` runs against `processor/graph-ingest/readiness.go` as task 4.1 left it (uncommitted tree on
`58f1f81`, target SHA-256 `0a7d8475…4ba4d10` before and after each run). Both are detections: each of the three
mutant runs failed the named test with the expected line, and the run after passed.

| Wrong change | Command (`-expect-text`) | Line Go printed on the mutant | Verdict |
| --- | --- | --- | --- |
| Ticker built with half the interval: `time.NewTicker(statusMetricsInterval / 2)` | `after a heartbeat` | `readiness_loop_test.go:78: after a heartbeat: 3 publishes at [… 18:00:00 … 18:00:02.5 … 18:00:05 …], want 2 at [… 18:00:00 … 18:00:05 …]` | detection |
| The publish before the ticker removed (the first `c.refreshReadinessStatus(ctx)` in `statusMetricsLoop`) | `at start` | `readiness_loop_test.go:73: at start: 0 publishes at [], want 1 at [1999-12-31 18:00:00 -0600 CST]` | detection |

Each run was `task mutate:check -- -pkg ./processor/graph-ingest -test TestStatusMetricsLoopPublishesOnTheHeartbeat
-file processor/graph-ingest/readiness.go -mutant <copy> -expect-text '<text>'`; the full reports were written under
`$TMPDIR` (local only). Not covered by a mutant: a loop that keeps publishing after its context ends. The test asserts
no publish in the two heartbeats after `cancel`, but a loop that ignores its context also never returns, so the test
would stop at `<-done` before that assertion; no run was made for it, and what such a run reports is unchecked.

## Choices the design does not spell out

1. **The fake and the clock.** The test builds the component with `CreateGraphIngest` over an unconnected
   `natsclient.NewClient("")` (no nats.go connection, so the #156 rule for synctest does not apply) and sets
   `c.statusPublisher` to a publisher over a recording `readiness.StatusWriter`. The writer records `time.Now()` at
   each `Put`, which inside the bubble is the bubble's clock, so the test asserts exact publish instants: start, then
   start plus 1, 2 and 3 `readiness.DefaultHeartbeat`, then none in the two heartbeats after the context ends.
2. **The integration tests.** `awaitEnvelopeAfterTick` (`readiness_integration_test.go`) is the envelope counterpart
   of batch 2's `awaitHealthAfterTick`: each `probe.Await` observation calls `refreshReadinessStatus`, then reads the
   key. `PublishedAndCatchesUp`, `BacklogIsNotReady` (both waits), `NoStreamingPortIsHonestlyCaughtUp` and
   `ReadyImpliesTheWritesAreDurable` read through it; the two local `envelopeRead` types became one at file level.
   `ReadinessGaugesAreEmitted` uses the call's own result: one `refreshReadinessStatus` call sets the gauges
   synchronously, so the test reads `bootstrap_complete` once after it, with no wait. `AbsentKeyIsNotAFailure` set
   its interval through `startIngestForReadiness` only; its first wait needs only the publish at start, so it is
   unchanged apart from its comment no longer naming a 200 ms heartbeat.
3. **The gate grep.** `git grep -n -w -e statusInterval -e statusNowFn` as written also matches this change's own
   design, tasks and inventory, and an archived inventory; scoped to `-- '*.go'` (with `statusTickInterval` and
   `statusNow` added) it returns nothing.
