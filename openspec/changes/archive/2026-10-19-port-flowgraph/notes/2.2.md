# Task 2.2 notes

Choices task 2.2 made that the design does not spell out.

- `extractPortInfo`'s local variable `portInfo` is renamed `info`, so it does not shadow the type `portInfo` after
  R4's rename.
- `flowgraph.go` and `flowgraph_analysis.go` each carried a second copy of the package comment ("Package flowgraph
  provides flow graph analysis..."), which `go doc` printed after `doc.go`'s text. Both copies are removed; `doc.go`
  holds the one package comment.
- `doc.go` loses its architecture diagram (it named `componentNode`, now unexported, and listed five patterns) and
  its `ValidateStreamRequirements` example (it read `Severity` and `Issue`, removed by R4). Its two package links at
  the pin are replaced by plain text naming `composition` as the reader.
- `ValidateStreamRequirements`' doc comment in `flowgraph.go` carried the same two untrue statements the README and
  `doc.go` did: that the subscriber "will hang", and that the warning fires when a JetStream input is connected
  "only" to NATS publishers (the code warns for every plain NATS publisher edge into a JetStream input, whatever
  else feeds it). It also named `EnsureStreams`, which this tree does not have. The comment now says what the code
  returns, as the README does.
- The README and `doc.go` do not list the `Issue` values or how each is chosen; they point at the package's `Issue`
  constants. R10 (task 2.4) removes `IssueOptionalInterfaceUnused` and its heuristic, so a list would be undone
  there. They also do not describe the refusal text or its error class, which R14 (task 2.4) changes.
- The README does not say `BuildFromDeclarations` is the only way to build a graph: `NewFlowGraph` and
  `ConnectComponentsByPatterns` stay exported until R12 (task 2.3).
- The README describes how each pattern is joined as the code does today, including two things the pin README did
  not say: a watch or read edge can join a component to itself (`connectKVPorts` has no self-check, unlike the
  stream, request and store connectors), and request ports join whatever their direction.
- The pin README's "Thread Safety" paragraph promised the graph "should be treated as read-only" after analysis.
  The README and `doc.go` now say only that a `FlowGraph` has no locks and is built and read on one goroutine.
