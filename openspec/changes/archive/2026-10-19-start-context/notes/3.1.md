# Task 3.1 notes: metric (D5)

## Choices the design leaves open

- `TestServerServesAfterStartContextEnds` lives in `metric/lifecycle_test.go`, beside the adapter it uses for "nothing
  held". It sends two GETs in sequence after the Start context ends. A correct server gives the test nothing to wait
  for, so no signal exists to synchronize on; the second GET gives work that Start left waiting on its context (M5's
  closing goroutine) a full round trip in which to run. In every M5 run below the first GET already failed.
- The adapter's comment states why an empty, set `serveDone` means Serve has not returned.
- The README's GPSService example builds its run context with `context.WithCancel(context.WithoutCancel(ctx))`, the
  shape the lifecycle suite's clean double uses (`internal/harness/lifecycletest/refowner_test.go:112`). Its
  `Stop()` signature and the `time.Sleep` calls stay: they are issue #313.

## The adapter reading against `metric/handler.go`

At `5e8aa79`, Start makes `serveDone` with one slot and the Serve goroutine sends its one result, then closes the
channel (`handler.go:173-179`). Stop receives that result (`:240` or `:267`) and clears the field under `s.mu` (`:281`).
So while the field is set, an empty channel means Serve has not returned, and a waiting result means it has.

One gap against "exactly while Serve runs": inside a Stop, after Stop has received the result and while it waits for
admitted requests (`:271-276`), the channel is empty and still set, so the reading lists the serve goroutine though
Serve has returned. It over-reports only during a Stop call, and every Stop path clears the field before it returns,
so no suite check observes it (they read `Observe` between calls). Recorded, not changed.

field stays set after Serve returns, and M5 survives.

`TestServerServesAfterStartContextEnds` passes on the base as well (`go test -race -count=1 ./metric/` exit 0 at
`01e5ef2`, before the BaseContext removal): it is a regression guard, and M5 is its sensitivity.
