# Task 3.2 notes: graph-ingest (D6)

## Choices the design leaves open

- The run context is `context.WithCancel(context.WithoutCancel(ctx))`, the shape the suite's clean double and the
  metric README use (`notes/3.1.md`).
- `initStorage` takes both contexts, `initStorage(ctx, runCtx)`: the buckets are acquired under `ctx`, the entity cache
  is built under `runCtx`. No new field.
- The adapter's liveness reading for the status loop is a small `isClosed` helper in `lifecycle_adapter_test.go`: the
  loop is listed while `statusDone` is set and not closed.
- T-G2 reads `ENTITY_STATES` through the test's own JetStream handle (`js.KeyValue(ctx, graph.BucketEntityStates)`),
  not through `readEntity`, so the oracle is the bucket and not the component's read path. It publishes a
  `mergeTestGraphable`, the payload `registerMergeTestPayload` registers, as `TestIntegration_DataFlowCountsInputMessages`
  does. It also asserts that `statusDone` is still open after the query, before Stop.
- T-G3 builds its component on `newFixtureClient(t)` with no stream, so the consumer setup's `waitForStream` cannot
  succeed. It runs Start in a goroutine and reports a miss of the 10 s bound with `t.Errorf`, then joins Start
  (`waitForStream`'s own retries end it after about 50 s) so nothing Start logs outlives the test.
- T-G3 and T-G4 judge "holds nothing" through the suite adapter's `Observe` (`newSuiteOwner`).
- T-G4's subscribe function cancels the Start context on every call; only the first cancel has an effect.

## `setupSubscriptions` against the setup/submit split

At this commit every setup step in `setupJetStreamConsumer` takes the Start context: `waitForStream`,
`ValidateHeartbeatDeliveryPolicy` (checks the context once, retains nothing: `natsclient/delivery_settlement.go:150-153`),
`consumeStream` (setup only; handlers run under a context the client owns, `natsclient/stream.go:431-438`) and
`recordBindBacklog`. The consume closure uses only `submitCtx` and the pool it captured. Nothing there keeps the Start
context in continuing work.

One degrade the design does not name: if the Start context ends during `recordBindBacklog`, the read fails and is
declared (the Warn "bind-time backlog read failed", `bootBacklogPartial`), but the `ctx.Err()` check then fails Start
anyway, so no started component carries it.

## Uncovered

- The entity cache's expiry sweep under the run context (design D11): no test sees which context built it.
- The request subscriptions' setup wait is not cut short by the Start context (design D11). natsclient caps only the
  PONG wait at 5 s per subscription; a held connection write before it can last a minute or more
  (`natsclient/request.go:294-300`; ADR-112, probe P17). Not tested.
