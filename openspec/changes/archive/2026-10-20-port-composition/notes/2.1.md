## Choices the design does not spell out

- A third row in `TestDeclarationConflictWithMatchesAdmission`, "two clashes each way, the holder's claims are
  visited first". The design predicts that the two-claims case detects M2 (`ConflictWith` visits `d`'s claims
  before `held`'s). It cannot: with only one clashing pair, either loop order finds that pair. The third row has two
  clashing pairs, the candidate's first with the holder's second (port 9090) and the candidate's second with the
  holder's first (port 8080). Holder-first order names the 8080 pair; candidate-first order names the 9090 pair. The
  spec scenario's two-claims case is kept as written. Task 2.5 runs M2 against this row.
- `exclusiveResources` is renamed `checkSelfClash`, since it no longer lists resources. Its error's operation name in
  the errs prefix changes with it (`Registry.checkSelfClash`); the refusal text the tests check is unchanged.
- The defensive-snapshot test used to overwrite `ExclusiveResources[0]` in a snapshot. It now overwrites the
  listener fact's resource text in the snapshot and checks the registry's copy is unchanged.
- The tests obtain declarations through `Registry.Declare`, the path composition will use, not by building
  `Declaration` values by hand: `PortFacts` fields are unexported and only resolution sets them.
- Generated checks: none. `ConflictWith` reuses `claimsClash`, whose combinations are proven by
  `TestRegistryRefusesNetworkClaimsThatCannotBothBind` and `TestRegistryAdmitsNetworkClaimsThatCanBothBind`; the new
  tests prove the visit order and the text, which named examples cover (design "Generated checks", clash parity).
