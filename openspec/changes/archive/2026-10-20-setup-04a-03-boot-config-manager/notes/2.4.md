in design D5 was applied to the working tree at `140dc19` by a script, the named test run, and the file restored from
a `cp` backup kept outside the repository. Restoration is checked by SHA-256 of the file before the mutant and after
the restore, then the same test is run again on the restored file. go1.26.9 darwin/arm64, Docker NATS through
`natsfixture`.

Every run is `go test -count=1 -tags integration -timeout=180s -run '<regex>' ./config/`.

## Mutants applied to the code as it is now

- **Mutant 2.** D5 names a forwarder that does not select on a stop signal. Since task 2.2 the forwarder has no stop
  signal of its own: it ranges over its subscriber channel, and Stop ends it by closing that channel before it waits
  (`notes/2.2.md`, "Stop's order"). The equivalent mutant is Stop waiting before it closes the subscriber channels,
  which re-creates P1 (Stop waits for the forwarder, the forwarder waits for Stop). The test's one-second Stop
  context ran out, as P1 did at the pin.
- **Mutant 6.** The Manager has no refusal of its own: `Manager.Start` hands its work to `internal/lifecycleguard`,
  whose `Start` refuses a used guard. The mutant therefore removes that branch in `guard.go`; only the `config` test
  was run against it.

No watermark mutant is listed in D5, so the per-key applied revision that replaced the bucket watermark (Codex review
finding 2) is not part of this task. Its sensitivity is the before/after record of
`TestOtherKeyWriteDoesNotSuppressAnExternalUpdate` in `notes/2.2.md`.

## A subtest survivor, found and fixed

The first run of mutant 4 was not `-v`; a second run with `-v` showed the subtest `component writers` passing under
the mutant, so that subtest was a survivor even though the test as a whole failed. A probe test (an untracked file,
deleted after the run) printed what the writers did under the mutant: `PutComponentToKV("a.b")` wrote
`components.a.b` to the bucket and then failed in its in-memory apply ("invalid component key format"), and the
following `DeleteComponentFromKV("a.b")` deleted that key again. The subtest compared only the bucket's live entries
before and after the loop, which a put followed by its delete leaves unchanged, so design D3's "fails with no write"
was not proven for the writers.

Fix, test only: the subtest now also requires the bucket stream's message count (`KeyValue.Status(ctx).Values()`) to
be unchanged after the refused writes; every put and every delete adds a message. It passes on the unmutated code and
fails under mutant 4 (expected 4 messages, actual 6), recorded in the table above. No production code changed.
