### Choices the design leaves open

- **`Metrics` lifecycle.** Start and Stop go through `lifecycleguard.Guard` (D4, S3) with one cleanup: stop the
  server Metrics started (kept for the next Stop if its Stop fails), then the base service, errors joined. `ctx`
  goes straight to `metric.Server.Start` and `BaseService.Start`; no run context is derived (S1). The guard does
  not expose whether it was used, so the claim gate is a separate `lifecycleCalled` flag under `Metrics.mu`, set
  when the guarded start runs or when Stop is called with a live context (a refused nil or ended-context call leaves
  it unset, as the guard does). The pin's `running`, `stopping`, `terminal`, `cleanupPending`, `startDone`,
  `cancel` and the three test hooks are gone (S9); `testListener` stays.
- **`Metrics` health** (2.1 part 5, "For task 2.2"). `start` runs the base service's health check once itself
  after `BaseService.Start`, and `setManagerServerHealthy` runs it at once too, so `IsHealthy` and `Health`
  reflect the server when `Start` returns, with no override of either. `performHealthCheck` does nothing unless
  the service is running, so the manager's `setManagerServerHealthy(false)` after `Metrics.Stop` is harmless.
- **Logging** goes through the base service's logger (`deps.Logger`, P6), not the global `slog`.
- **`/graph/triples`.** The subject and predicate checks sit in `parseTripleQueryParams` (400 naming the
  parameter). `scanGraphTriples` sorts the listed keys before the scan; a key whose read reports not found is
  skipped with a Debug log and no metric: the entity no longer exists, so leaving it out is the answer, not a
  degrade (developer contract, "A skip, drop, or degrade is a declared event"; the reviewer may judge otherwise).
  Every other read error, and an entity `graph.UnmarshalEntityState` refuses, fails the scan with nil. The pin's
  file header named the `graph-gateway` component and three flows that are absent here; it is rewritten.
- **`TypeNameFromReflect`** (#349). Pointer: the element's name. Named type: its bare name, as at the pin. Unnamed:
  `list-X`, `array-N-X`, `map-K-V`, else `<kind>-<fnv32a of t.String()>` (an anonymous struct is
  `struct-xxxxxxxx`). Prefix form keeps nested shapes apart (`list-map-string-X` and `map-string-list-X`). Not
  covered: a named generic instance (`Foo[pkg.Bar]`) is cut at the last dot as at the pin and does not match the
  OpenAPI grammar; no registration passes one.
- **`decodeStrictServiceJSON`** decodes the document into `any` and runs `keycase.Check(doc,

### Choices the design leaves open

- **One guard.** `StartAll` and `StopAll` go through `internal/lifecycleguard`, as the design recommends: start is
  the sequence of D2, cleanup is `stopAll`, which a failed `StartAll`'s rollback and every `StopAll` run. The pin's
  three hand-written state machines (15 fields), its cleanup modes and `attributeShutdownError` are gone, so no
  generated history check is added for a hand-written machine. Each step of `stopAll` keeps the handle it did not
  release (a service's place in the composition, the publisher's cancel, a listener, the metrics server), so a
  repeat runs only what is left, and a repeat calls every started service's `Stop` again, as D2 says.
- **The rollback stops what started.** `stopAll` stops only services whose `Start` was called (including the one
  whose `Start` failed), in reverse registration order. The pin's rollback called `Stop` on every composed
  service; `TestStartAllMainBindFailureStartsNoService` requires none, and D2 says the rollback "stops what
  started".
- **Health listener and `StopAll`.** The health listener is not part of `StartAll`, so a `StopAll` before any
  `StartAll` (the guard runs no cleanup then) stops it after the guard returns; `stopAll` stops it too, in the
  pin's place (after the publisher, before the main listener), so a failed `StartAll`'s rollback stops it as the
  pin's did. `stopCalled`, set by the first `StopAll` given a live context, refuses a later
  `StartHealthListener`; `healthUsed` is set only after a bind succeeds, as at the pin.
- **The listener stop** (`stopHTTP`, shared by both listeners): close admission, `Shutdown(ctx)`; if that fails
  (its context ended), `Close`, which cuts every open connection and so ends each open request's context; wait for
  `Serve`; then `httpadmission.Requests.Wait(ctx)`. A repeat calls `Shutdown` on a closed server, which returns at
  once (probe C3), and waits for the handlers. (Removed in fix round 1.) `Shutdown` reporting `net.ErrClosed`
  means the listener's owner had closed it already and counts as stopped: tests that hand `startHealthListener`
  their own listener close it in a cleanup that may run before `StopAll`'s.
- **Readiness.** `stopAll` sets `stopping` and clears the commit under `mu` before any service stops. The pin's
  per-service stop records (`stopInvoked`, `stopCompleted`, `stopErr`) and `beginStopping`'s first-service mark are
  dropped: once `stopping` is set they added nothing to the snapshot. The snapshot's order of statuses is the pin's.
- **Health publisher.** Its first publish runs in its goroutine, as at the pin; its run context is created in
  `startAll` from the `StartAll` context without its cancellation and ended by `stopAll` (ADR-113). `startAll`
  refuses an ended context at the publisher start, after the full route set is built: the assumption of 2.1 parts
  4 and 5. An encode failure and a publish failure share one count and one Debug line; the encode path is not
  covered (#185).
- **Logger.** `NewServiceManager` sets `slog.Default()`, as `NewBaseServiceWithOptions` does; `ConfigureFromServices`
  replaces it with `deps.Logger` when one is given.
- **Mandatory service.** The pin's one-entry `mandatoryServices` list is `createComponentManager`.
- **Not carried:** the seven lookups (`GetAllServices`, `ListConstructors`, `HasConstructor`,
  `GetHealthyServices`, `GetUnhealthyServices`, `GetServiceStatus`, `GetAllServiceStatus`), `hasNATSAccess`,
  `completeHTTPSetup`, `Start`, `Stop`, `StopHealthListener`, `attributeShutdownError`; `publishComponents` is
  PR 3's. Stop errors name their step (`failed to stop service <name>`, `stop health publisher`, `stop health
  listener`, `stop main HTTP listener`, `stop metrics server`) with `fmt.Errorf`, not `errs.NewShutdownError`.

## Codex round 1 (review of record at `a74fc28`)

Two findings, each with a tracked issue; both fixed in one commit, tests first.

### BLOCKING: shutdown during a slow start later answered READY (#356)

- **Test.** `TestReadinessStaysClearedWhenStopAllExpiresDuringStart` (`service/service_manager_test.go`), Codex's
  reproduction from #356 renamed for the behaviour: a service's `Start` blocks, `StopAll` gets a live 25 ms context
  and returns `context.DeadlineExceeded` while the guard still waits for the start, the start is released and
  `StartAll` returns nil, then `/readyz` must answer 503 `NOT READY`.
- **On `a74fc28`** (`go test -race -count=1 -run TestReadinessStaysClearedWhenStopAllExpiresDuringStart
  ./service/`, exit 1):

  ```text
  --- FAIL: TestReadinessStaysClearedWhenStopAllExpiresDuringStart (0.03s)
      service_manager_test.go:812:
              Error:          Not equal:
                              expected: 503
                              actual  : 200
              Messages:       StopAll began, but /readyz answers "READY"
  ```

- **Fix.** The existing stop-request fact, `stopCalled` (set by `StopAll` only after its nil and ended-context
  checks), now governs readiness: `currentStartupSnapshot` reports `stopping` when `stopping || stopCalled`, and its
  final recheck reads `stopCalled` again beside the commit pointer, so a `StopAll` that enters while the health
  checks run also answers `stopping`. No new state. An already-ended context is still refused before `stopCalled` is
  set (`TestStopAllWithAnEndedContextStopsNothing` unchanged and passing), and the guard's bounded wait and retry are
  untouched: the test's cleanup `StopAll` stops everything and returns nil.
- **Choice not in the design.** A start that completes after a `StopAll` entry still commits its route set, as
  before; only readiness changes. Refusing the commit would turn a successful `StartAll` into a rollback, which is
  more than the finding asks and more than D2 states (D2 speaks of `/readyz` only). The `/services` startup snapshot
  reads `stopping` in that window, from the same function.
- **The pin.** It did not have the defect: its `StopAll` (`service/service_manager.go:838` at the pin) went straight
  to `stopAll`, whose `beginStopping` (`:950-952`) set `stopping` without waiting for a start in progress, and its
  readiness read `stopping` first (`:1796`). The window entered with the port, when `StopAll` began waiting for the
  start through `lifecycleguard` (ADR-113) before `stopAll` sets `stopping`.

### HIGH: `/openapi.json` wrote the internal descriptors, not OpenAPI 3.0 (#357)

- **Test.** `TestOpenAPIDocumentSerialisesBodiesAsOpenAPI3` (`service/service_manager_http_test.go`, beside
  `TestOpenAPIDocumentListsMountedRoutes`): a mounted service declares a `GET` whose 200 is an array of a `$ref`, and
  a `POST` with a required request body naming no content type, a 201 with a `$ref`, a 204 with a description only,
  and a 400 with a content type and no schema. The expected path item is literal JSON written from the OpenAPI 3.0.0
  Operation, Request Body, Response and Media Type objects, compared with `require.JSONEq`.
- **On `a74fc28`** (exit 1): the actual path item carried `request_body`, `content_type`, `schema_ref` and
  `is_array`, and no `requestBody` or `content`:

  ```text
  --- FAIL: TestOpenAPIDocumentSerialisesBodiesAsOpenAPI3 (0.00s)
      service_manager_http_test.go:169:
              Error:          Not equal:
              actual  : map[string]interface {}{"get":map[string]interface {}{"responses":map[string]interface {}{"200":map[string]interface {}{"content_type":"application/json", "description":"The widgets", "is_array":true, "schema_ref":"#/components/schemas/Widget"}}, ...
  ```

- **Fix.** `OpenAPIDocument.MarshalJSON` (`service/openapi.go`) translates each path's operations at the wire
  boundary into unexported OpenAPI 3.0 shapes: `requestBody` with `content[type].schema`, each response's
  `content[type].schema` as a `$ref` or `{type: array, items: {$ref}}` for `IsArray`. A request body naming no content
  type is `application/json` (the field's documented default); so is a response with a schema and no content type. A
  response naming a content type but no schema gets a media type with no schema, which OpenAPI 3.0 allows; a response
  with neither has no `content`. `PathSpec`, `OperationSpec` and `OpenAPISpec` keep their own JSON, so a registered
  spec's `MarshalJSON`/`UnmarshalJSON` round trip is unchanged.
- **New surface, the four questions.** One exported method, `OpenAPIDocument.MarshalJSON`, exported because
  `json.Marshaler` requires it. Owner today: nothing in this tree converts descriptors; the pin's converter lived in
  `cmd/openapi-generator` (`openapi_builder.go:95-170`), which was not admitted. Premise: measured true by the
  failing test. Caller: `handleOpenAPISpec` (`service/service_manager_http.go`), which encodes the document. No
  caller is asked to predict anything.
- **The pin.** It had the defect: its `generateOpenAPIDocument` (`service/service_manager.go:1615` at the pin)
  copied each `PathSpec` into the document and `handleOpenAPISpec` (`:1577`) encoded it as it was; only the static
  generator, `cmd/openapi-generator/openapi_builder.go:110-165`, translated. A pin defect fixed here, recorded as
  `adapt`. Two differences from that generator: a content type with no schema gets no invented `{type: object}`
  schema, and `text/event-stream` is not special-cased (no service here declares one).
- **Not covered.** `ParameterSpec.Schema` still writes `"type": ""` for a parameter that declares no schema; Codex did
  not raise it and no test here declares such a parameter.
