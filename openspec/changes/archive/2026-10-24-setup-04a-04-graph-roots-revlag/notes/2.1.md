## Choices the design does not spell out

1. **A third rename in `pinref_test.go`.** D8 renames only the type and the constructor. The pin also declares the
   unexported type `inflight`, and a port that keeps it (task 3.1 is the pin's code) would make the package fail to
   compile. So `inflight` is `pinInflight`. Comments were not edited, so they still say `Watermark`, `New`,
   `inflight` and `Indexed`. The pin's package comment is kept, with a blank line between it and the package clause,
   so the package does not get a second doc comment.
2. **Generated operations (D8).** Each step draws a key from `A`, `B`, `C` and one operation. The operations are:
   observe the next revision (gap 1 to 3; weight 2); the same with the zero commit time; observe a revision below the
   highest; observe again an already-observed revision under the drawn key; complete (weight 2). The re-observe uses
   a commit time not given before (`commitAt(r)` plus 1 to 999 ms), so a time kept from the earlier observation can
   be told apart from the one last given. The completion revision is drawn either from the observed revisions or
   from `0..highest+3`, which reaches observed, unobserved and zero revisions. A history has 0 to 60 drawn steps
   between the fixed prefix and the final drain. "Ascending" means no observation so far was at or below the highest.
   An observation of a lower revision, or a re-observation, ends the floor-never-falls check for the rest of that
   history.
3. **The record.** It is the highest observed revision and a map from each in-flight revision to its key. A Complete
   drains the key's entries at or below the revision. The record is written from the spec, not from either
   implementation. The test checks `Observed` against the pin's code only, not against the record, because D8 lists
   exactly two record checks.
4. **The seed.** Rapid v1.3.0 does not print its random seed on a passing run (`checkTB` in `engine.go` prints it
   only on failure). The test therefore logs the `-rapid.seed` flag value. `0` means Rapid drew a fresh seed. The
   run below fixes the seed.
5. **The concurrent example.** It uses 8 workers. Keys are `k0` to `k15` (`r % 16`), so one completion can drain a
   lower revision of its key that another worker is about to complete. An unbuffered channel hands each revision to
   the workers after its `Observe`. The reader's results are read after `reader.Wait()`. The final `IndexedAt` read
   comes after `writers.Wait()`, and a comment names each of those events.
6. **The retention example.** It makes 1,000,000 completions (D7's number). Under `-race` it takes about 1.6 s.
7. **No named example for "A revision observed again belongs to its last key".** D7 lists none. The generated
   check's re-observe draws reach this case, and both the comparison with the pin's code and the record check it.

## Commands (the stub and overlay are local only, under `/tmp/pr407stub/`)

The stub is the pin's `watermark.go` with lines 161 to 169 (`Indexed` and its comment) removed, which is the D3 API.
`overlay.json` maps `<worktree>/internal/revlag/watermark.go` to the stub.

```bash
go vet -overlay=/tmp/pr407stub/overlay.json ./internal/revlag/                       # exit 0
go test -race -count=1 -v -overlay=/tmp/pr407stub/overlay.json ./internal/revlag/ -rapid.nofailfile
go test -count=5 -cpu 1 -shuffle=on -overlay=/tmp/pr407stub/overlay.json ./internal/revlag/   # ok, 2.6 s
go tool revive -config revive.toml -formatter friendly ./internal/revlag/              # exit 0
scripts/lint-test-ports.sh                                                              # exit 0
```

The `-race -v` run passes all 19 tests (`ok ... 3.284s`). `TestWatermark_RetentionTracksInFlight` passes on the
pin's code: the live heap grew by -3,128 bytes (1.57 s). `TestWatermark_Concurrent` takes 0.30 s and
`TestWatermark_ConcurrentReadersAndWriters` 0.02 s.

## Rapid run

```bash
go test -race -count=1 -v -overlay=/tmp/pr407stub/overlay.json ./internal/revlag/ \
  -run '^TestPropWatermarkHistory$' -rapid.seed=20261024 -rapid.nofailfile
```

Rapid printed `[rapid] OK, passed 100 tests`. The test logged 100 histories completed, 77 of them not ascending. It
ran 2,745 step checks (2,600 with something in flight, 145 caught up), 559 floor-never-falls checks and 100 final
drains. It drew 777 next observations, 294 zero-time observations, 306 lower observations, 236 re-observations and
532 completions.

The stub's line numbers are the pin's below line 161; above it they are the pin's minus 9 (`:173` is pin `:182`,

run where it happens to be the highest, they could pass. The named test drains a single revision, so it fails on
every run.

(`retained = append(retained, drained...)` after `advanceCoveredLocked`). Only `TestWatermark_RetentionTracksInFlight`
fails, with growth of 8,091,240 bytes against the 1 MiB bound. D9's M6 targets task 3.2's new code and is run there.
