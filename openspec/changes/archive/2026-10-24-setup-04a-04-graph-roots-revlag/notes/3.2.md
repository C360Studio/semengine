# Task 3.2 notes: draining without a scan

Task 3.2 of `setup-04a-04-graph-roots-revlag` (design D5, owner ruling Q1 yes). `internal/revlag/watermark.go` now
keeps the in-flight revisions in an ascending `container/list` with a map from each revision to its list element
(`pending`), plus a map from each key to its in-flight revisions (`byKey`), all under the one existing mutex. The floor
is read from the front of the list, `Complete` visits only the completed key's revisions and unlinks each drained one
from all three at once, and the timestamp rules (`coveredRev`, `coveredAt`, `advanceCoveredLocked`) are the pin's.

This is the shape Codex's review of record prefers (PR #407 comment 6388455177): one mutex, pending work indexed by
key, an ordered list with direct lookup whose completed entries are removed immediately. No heap and no lazy deletion.
The tests of task 2.1 are unchanged (`git diff` touches only `watermark.go`).

## Cost of each call

| Call | Cost | D5 claim |
| --- | --- | --- |
| floor read (`indexedLocked`, so `IndexedAt` and the advance inside `Complete`) | constant: the list's front | 1: at most amortized logarithmic |
| `Complete(key, rev)` | proportional to `key`'s own in-flight revisions | 1 |
| `Observe`, ascending (the caller's precondition) | constant: appended at the back | not constrained |
| `Observe`, a revision lower than one in flight | proportional to the in-flight revisions above it (walks back from the back) | not constrained |
| `Observe`, a revision already in flight | proportional to its old key's in-flight revisions (it moves to the new key's list) | not constrained |

Retained state (D5 claim 2): one list element, one `inflight` record, one `pending` entry and one `byKey` slot per
in-flight revision, and one `byKey` entry per key with a revision in flight. `Complete` builds the key's kept slice
fresh, so a key's slice never keeps the capacity of an earlier peak, and a key with nothing in flight is deleted.

## Choices the design does not spell out

- A revision observed again while in flight keeps its place in the list and takes the newer key and commit time, as
  the pin's map overwrite did. It is dropped from its old key's list and appended to the new key's, so a key's list
  holds exactly that key's in-flight revisions, with no duplicate.
- The nothing-drained early return stays (`watermark.go:166-168`), so D9's S1 row stays; it is a survivor, as
  predicted (equivalent: with nothing drained, the rest of `Complete` changes nothing).
- Comments rewritten per D4's third bullet: the field comment on `order`, `pending` and `byKey` (`:49-57`, was pin
  `:47-50`), `advanceCoveredLocked`'s doc (`:179-190`, was pin `:144-159`), and `indexedLocked`'s doc (`:243-244`, was
  pin `:202-212`). The memory and commit-time trade on `coveredRev` (pin `:51-62`) is unchanged. `Observe`'s doc
  gains two sentences on a revision observed again and on the insertion cost; `Complete`'s doc gains one on what it
  visits.

## Benchmark (evidence, not a gate)

A throwaway test, not added to the tree, run through a Go overlay (`go test -overlay`) so the package's
`pinWatermark` (the pin's code, `pinref_test.go`) and the port run side by side. It observes n revisions, one key each
(graph-embedding's cold start), then completes them in a fixed-seed shuffled order (out-of-order pool workers), and
also observes n revisions in descending order. One run each, `go1.26.10 darwin/arm64`, on the developer machine (local only).

| n | Code | Observe n ascending | Drain n | Observe n descending |
| --- | --- | --- | --- | --- |
| 10,000 | pin | 0.69 ms | 958 ms | 0.38 ms |
| 10,000 | port, task 3.1 (the pin's code) | 0.46 ms | 940 ms | 1.07 ms |
| 10,000 | port, task 3.2 | 1.79 ms | 1.19 ms | 109 ms |
| 40,000 | pin | 2.31 ms | 16.84 s | 2.10 ms |
| 40,000 | port, task 3.1 (the pin's code) | 2.10 ms | 16.70 s | 2.15 ms |
| 40,000 | port, task 3.2 | 7.06 ms | 5.63 ms | 1.61 s |

Draining is now linear: 40,000 takes 5.6 ms instead of 16.8 s. Ascending observation costs about three times the
pin's (an allocation for the list element and the key slot), still a constant per call. Descending observation, which
the spec's ascending precondition rules out, is now quadratic: it walks the list from the back on every call (see Open
point). Codex's optional suggestion (record observation time beside drain time) is the "Observe" columns.

The throwaway test, `drain_timing_test.go`, overlaid into `internal/revlag` (indented with spaces here; `gofmt` restores
the tabs):

```go
package revlag

import (
    "fmt"
    "math/rand/v2"
    "testing"
    "time"
)

type wm interface {
    Observe(uint64, string, time.Time)
    Complete(string, uint64)
    IndexedAt() (uint64, time.Time)
}

func TestDrainTiming(t *testing.T) {
    for _, n := range []int{10_000, 40_000} {
        keys := make([]string, n+1)
        for i := 1; i <= n; i++ {
            keys[i] = fmt.Sprintf("k%d", i)
        }
        order := rand.New(rand.NewPCG(1, 2)).Perm(n)
        for _, impl := range []struct {
            name string
            w    wm
        }{{"pin", newPinWatermark()}, {"port", New()}} {
            start := time.Now()
            for i := 1; i <= n; i++ {
                impl.w.Observe(uint64(i), keys[i], commitAt(uint64(i)))
            }
            observed := time.Since(start)
            start = time.Now()
            for _, j := range order {
                impl.w.Complete(keys[j+1], uint64(j+1))
            }
            drained := time.Since(start)
            if f, _ := impl.w.IndexedAt(); f != uint64(n) {
                t.Fatalf("%s: floor %d", impl.name, f)
            }
            t.Logf("n=%d %s: observe %v, drain %v", n, impl.name, observed, drained)
        }
    }
    for _, n := range []int{10_000, 40_000} {
        for _, impl := range []struct {
            name string
            w    wm
        }{{"pin", newPinWatermark()}, {"port", New()}} {
            start := time.Now()
            for i := n; i >= 1; i-- {
                impl.w.Observe(uint64(i), "K", commitAt(uint64(i)))
            }
            t.Logf("n=%d %s: observe descending %v", n, impl.name, time.Since(start))
        }
    }
}
```

Run with an overlay file mapping `<worktree>/internal/revlag/drain_timing_test.go` to the copy:
`go test -count=1 -v -run '^TestDrainTiming$' -overlay overlay.json ./internal/revlag`.

## Open point

`Observe` of a revision below others in flight now costs time proportional to the in-flight revisions above it; the
pin's cost was constant. 40,000 observed in descending order take 1.6 s here, against 2 ms at the pin. The spec states
ascending observation as the caller's precondition and D5 does not constrain `Observe`, so this is the insertion
path for unusual observation orders that the review of record accepts. It is reported rather than changed.

D10's `dependencies_and_side_effects` reads `sync, time`; the port now also imports `container/list` and `slices`
(standard library). Task 4.1 writes the ledger row from D10 and should name them.
