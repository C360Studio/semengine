# Task 2.2 notes: `TestEntityCacheUseDuringStop`

Test: `processor/graph-ingest/entity_cache_stop_test.go`, `TestEntityCacheUseDuringStop` (design D7; spec delta
`graph-ingest-recovery`, scenario "Cache use during Stop"). Unit test, no NATS.

## What the test drives

- **Two entry points, three cache uses.** `handleQueryBatchNATS` with one ID already in the cache and one that is
  not: the first is a cache read (`fetchEntitiesConcurrent`, `query.go:487-488`), the second a bucket read followed by
  a repopulation (`repopulateEntityCacheEntry`). The exported `CreateEntity` of a new ID commits and invalidates its
  key (`invalidateEntityCacheEntry`). These are the three readers D7 and #306 list, reached through the handler and
  the exported call, not by calling the helpers.
- **The production cache.** The cache is built with `cache.NewFromConfig` and the same `Config` `initStorage` uses
  (hybrid, 5000 entries, 30 s TTL, 10 s sweep), so `Stop`'s cleanup closes a cache with an expiry goroutine, as it does
  in production. The bucket is the package's mock KV bucket (`createTestComponentWithMockKV`).
- **Reaching Stop without NATS.** As `lifecycle_owner_test.go` does: the test sets the cache and one consumer binding
  on the component, then `startGuardAcquiringNothing` admits one Start, so `Stop` runs `release`. The consumer is the
  package's `graphIngestLifecycleConsumeContext`, whose `drainSeen` and `closed` channels hold `Stop` inside `cleanup`
  before it closes and clears the cache.

## Ordering: what is ordered and what is left unordered on purpose

- The test starts `Stop`, waits on `drainSeen` (Stop is in `cleanup`, the cache still open and set), starts the two
  readers, then closes `closed` so `Stop` closes and clears the cache while they run. It joins the readers with a
  `sync.WaitGroup` and `Stop` with a channel before asserting. No sleep, no wall clock.
- The brief asked for the order between "reader has taken the handle" and "Stop clears it" to be set with channels.
  The test does not do that, and cannot while still failing at the base: a channel between a reader's read of
  `c.entityCache` and the clear is a happens-before edge, and the race detector reports only accesses no such edge
  orders. At the base a reader ordered after the clear reads nil and skips the cache (no failure); one ordered before
  it has finished using the handle. So the test leaves the read and the clear unordered, which the race detector
  reports whichever comes first in real time. Nothing else orders them either: the readers take the mock bucket's lock,
  the cache's own lock and `cacheGenMu`, none of which `Stop` takes, and the cache's `Close` takes no lock.
- After D7's fix both the reads and the clear take `c.mu`, so they are ordered and the race detector reports nothing.

## Outcome assertions

`Stop` returns nil; the batch query returns both seeded entities with nothing missing; `CreateEntity` returns nil.
The expected entities come from the seed, not from the code under test.

## Check against a D7-shaped fix (not committed)

To confirm the test needs no change once 4.2 lands, a copy of `component.go` and `query.go` kept outside the tree
(`go test -overlay`, nothing in the tree edited) applied D7's shape: each reader reads the handle once under
`c.mu.RLock` and uses the local copy, and `clearLifecycleHandles` sets it to nil under `c.mu.Lock`. The race-built
binary then passed 20 of 20 runs. That copy is a sketch for this check, not the 4.2 implementation.

## Generated checks

None. The history has one shape (readers overlap a `Stop` that closes and clears the cache), and the race detector
judges every interleaving of it, so named examples suffice.

## Not covered

- The prefix query (`handleQueryPrefixWithMaxPayload`) reaches the cache through the same `fetchEntitiesConcurrent`
  and is not driven separately.
- The poison-inventory invalidation (`poison_inventory.go:103`) and the delete and failed-write invalidations
  (`entity_writes.go:485`, `:501`) call the same `invalidateEntityCacheEntry`; only the commit path is driven.
- No reader is forced to start after `Stop` has returned: the readers run before, during or after the clear as the
  interleaving falls, which is what lets the race detector judge them.
