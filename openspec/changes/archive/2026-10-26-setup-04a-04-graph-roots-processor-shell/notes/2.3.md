# Task 2.3 notes: `TestCacheUsableAfterClose`

Test: `internal/cache/close_test.go`, `TestCacheUsableAfterClose` (design D7; spec delta `graph-ingest-recovery`,
scenario "A cache after Close").

## Choices the design does not spell out

- **Implementations covered.** "Every implementation" is read as every cache `NewFromConfig` builds: the four
  strategies of `memCache` (`simple`, `lru`, `ttl`, `hybrid`) and the disabled cache (`noopCache`, `Enabled: false`).
  The cache is built through `NewFromConfig`, the constructor graph-ingest calls (`processor/graph-ingest/component.go`,
  the `cache.NewFromConfig[graph.EntityState]` call). `CoalescingSet` is not a `Cache[V]` and stops with `Shutdown`, so
  it is out of scope.
- **What "works as before Close" means.** Literal expectations, not a comparison against a second unclosed cache: an
  entry written before `Close` is still read after it; `Set` of a new key reports `true` and the value reads back;
  `Set` of an existing key reports `false` and replaces the value; `Delete` reports `true` and the key then misses; the
  other key is untouched. The disabled cache misses every `Get` and reports `false` from `Set` and `Delete`, before
  and after `Close`.
- **Sequential, not concurrent.** The spec scenario is use after `Close` returned, so the calls run on the test
  goroutine after `Close`. Use while `Stop` (and so `Close`) runs is `TestEntityCacheUseDuringStop`'s scenario.
- **Named examples, no generated checks.** The input is one fixed sequence of three operations per implementation;
  there is no input grammar or order-dependent history to explore, and the claim is that `Close` changes nothing the
  existing suite (`testSuite`, `TestConcurrency`) already proves before `Close`.
- The TTL is one hour so no miss can be an expiry.
