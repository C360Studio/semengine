## T5's measurement (the premise design Tests rests on)

Measured with temporary `t.Logf` lines in T5 (three runs), removed afterwards; the file was restored from a copy and its
SHA-256 checked (`e84f869c...3392` before and after). In every run:

- The consume loop survived the cut: `Closed()` had not fired after the cut, after the cut tick, after the restore, or
  after the message published after the restore was applied. T5 keeps that last check as an assertion.
- A lookup under the cut, called with `t.Context()` (no deadline), failed after 5.000 s with
  `Component.observeOutstandingWork: look up stream ENTITY failed: context deadline exceeded`, while the caller's
  context was live (`ctx.Err() == nil`). That is nats.go's default API timeout ending its own derived context, so the
  tick stores the fault, not the shutdown path.
- The cut tick (`refreshReadinessStatus(t.Context())`) took 7.0 s (the lookup, then the readiness publish) and left
  `Health()` at `Healthy:false`, `Status:degraded`,
  `LastError:backlog observation failed for consumer ENTITY/graph-ingest-entity-wildcard`.
- After the restore, a fresh tick read healthy and the message published after it was applied.

The loop did not close, so T5's mechanism stands and nothing goes back to review before 3.1. The timings are what
was observed, not promised.

## Choices the design does not spell out

- **T2's "names the restart" moved to the last step.** The design's table has T2 check, after the stream is created
  again, that `LastError` names the restart, and also says T2 fails on the base at its last step. Both cannot hold:
  the base never writes "restart", so a check there fails at that step. T2 checks unhealthy, the consumer's name and a
  degraded `computeBacklogStatus` envelope after the stream is created again (all true on the base), and checks the
  restart text, with the consumer's name, at the last step. Because the base never writes "restart", a stale status
  tick cannot make that last step pass on the base.
- **T2 and T3 wait for the loop to end** (`awaitLoopEnded`, on the loop's `Closed()`, read from the component's
  binding in the test after `Start` and before `Stop`) before creating anything again. nats.go ends the loop
  asynchronously on the deletion's terminal status, and the scenarios are about a loop that has ended. On the base the
  wait passes in both tests, so this tree confirms probes d and f: deleting the stream, or the consumer, ends the loop.
- **T2's and T3's last step changed in task 3.2.** It first waited with `awaitHealthAfterTick`, which accepts the
  first matching observation. Task 3.2 found mutation M3 (a lost binding cleared by a good lookup) inconclusive under
  it: the status loop's own tick records the binding again just before some reads. The last step now runs a tick,
  reads `Health()` once and requires unhealthy, three times (`notes/3.2.md`).
- **The last step changed again after Codex's code review (PR #431, HIGH).** Each iteration also requires the
  envelope its tick computes to be degraded and not ready, so the lost binding alone is shown to keep readiness down
  once the lookup succeeds again (mutation M7, `notes/3.2.md`).
- **T3's last step** checks `!Healthy` and the consumer's name, as the design lists; it does not check the restart
  text.
- **T5 uses `newRelayedComponent`** (authority `c360.platform`) with `registerMergeTestPayload` before `Start`, so the
  message published after the restore can be decoded and applied. "Applied" means `readEntity` finds it.
- **T1 and T4** each carry `// Own server: restarts the server mid-test.` above their own `natsfixture.New` and use
  `openReconnectingClient`. Before the first tick after `Restart`, they wait until graph-ingest's own client can look up
  the ENTITY stream (`awaitStreamVisible`), so T1's unhealthy reading comes from a missing consumer on a live
  connection, not from a timeout while reconnecting.
