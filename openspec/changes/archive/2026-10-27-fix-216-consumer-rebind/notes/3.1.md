# Task 3.1 notes: the lost input binding

Base: `d055556` plus task 2.1's tests. The change is in `processor/graph-ingest/readiness.go`, `consume.go` and
`component.go` (`Health`).

## Where "Stop has begun" is read from

No new state holds it. `component.Lifecycle` already keeps it: its `running` field is set when `start` returns nil and
cleared, under the shell's lock, the moment `cleanup` begins, for a Stop or for a failed start's rollback, before
graph-ingest's `release` runs (`component/lifecycle_type.go`, `Start`'s cleanup wrapper). `Lifecycle.Health` with no
stuck state reports `Status: "stopped"` exactly when `running` is false, and its doc comment says it may be called at
any time and never waits for Start or Stop. graph-ingest reads it through a one-line unexported helper,
`Component.running()`, in `readiness.go`.

So there is no copy of the lifecycle state on `Component`, no field on the handle-bearing consumer binding, and no
exported change in `component`. The read is race-safe because `Lifecycle` guards `running` with its own mutex.

What it covers, against the requirement's words "while the component is running and its `Stop` has not begun":

- Before the shell is running. The status loop's first, up-front tick can run before `Lifecycle.Start` sets `running`
  (the loop starts inside `start`). An ended loop seen by that tick is not recorded; the next tick records it. That
  matches the requirement, which records only while the component is running.
- A failed start's rollback also clears `running`. The status loop starts after every step of `start` that can
  fail, so no tick runs during a rollback anyway.

## Read order (design review note, PR #431 comment 6443884766)

The tick reads the loop's end first (`<-bc.closed`, without blocking) and the running state second
(`observeLostBinding`). `Lifecycle` clears `running` before it calls `release`, so before `cleanup` issues any
`Drain`. The order of events in a clean Stop is: `running` cleared (lock released) -> `Drain` -> nats.go closes the
loop -> the tick sees `Closed()` fire -> the tick takes the shell's lock. The lock read therefore sees `running` false,
and nothing is recorded or logged.

The reverse order (running first, loop second) false-latches a clean shutdown: a tick reads "running", `Stop` begins
and drains, and the tick then sees the closed loop and records it lost. No test catches that interleaving; design
Tests lists it as mutation row M4, an expected survivor.

## Choices the design does not spell out

- **The lookup still runs for a lost binding.** The tick keeps reading the backlog of every bound consumer, a lost one
  included, so a failed lookup is still named ("backlog observation failed for consumer ..."), as
  `TestIntegration_HealthReadsLostConsumer` and T3's first step require. A lost binding sets `ObservationFailed` for
  the envelope on its own, so the envelope stays degraded after the lookup succeeds again (T2, T3 last steps).
- **Where the latch lives.** A `lost bool` on the `boundConsumer` readiness record, set under `boundConsumersMu` by
  `recordLostBinding`, which reports whether this call set it, so the Error line is logged once per consumer. Health
  builds its stuck state from the records (`lostBindingFault`), passed to `Lifecycle.Health` as a third stuck state
  beside poison and the backlog fault. `release` clears the records with the rest; after that `Health` reads
  "stopped" anyway, and graph-ingest is one-shot.
- **Text.** `LastError` part: `input binding lost for consumer <stream>/<consumer>: its consume loop ended; restart the
  process to consume again`. Error log: `graph-ingest: input binding lost; its consume loop ended and is not bound
  again until the process restarts`, with `stream` and `consumer` attributes.
- **Signature.** `registerBoundConsumer(stream, name, closed)`; `setupJetStreamConsumer` passes `handle.Closed()`.
  The record holds only that receive-only channel, never the handle (ADR-095).

## Test files outside task 2.1 that changed

The three-argument `registerBoundConsumer` and the new `handle.Closed()` call reach tests that existed before this
change. None of their assertions changed:

- `readiness_test.go`: `TestBoundConsumers_DedupedAndDeterministic` passes `nil` as the channel (a record whose loop
  never ends).
- `config_fields_test.go`, `guard_generation_test.go`, `statement_metadata_test.go`: their `consumeStream` stand-ins
  returned a nil `jetstream.ConsumeContext` with a nil error, which natsclient never does; `handle.Closed()` panicked on
  it. They now return the package's existing stand-in, `graphIngestLifecycleConsumeContext`, with open channels.

Production code gets no nil check for a handle natsclient does not return.
