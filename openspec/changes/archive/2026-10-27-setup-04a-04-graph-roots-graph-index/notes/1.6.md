# Task 1.6: #108's number, the initial rebuild at the pin and on the port

Design D13: measure, record, decide later. This note records numbers only; the decision on #108 is the owner's.

## What was run

The pin's `owner_filter_load_integration_test.go` writes its load straight into index buckets, so it never runs a
rebuild. The probe keeps its `ci` profile's shape (5,000 entities, each with one edge to one hub entity, one
predicate, one display name shared by all, plus 20 spread predicates on the first 20 entities; entity IDs
`acme.ops.load.graph.entity.%06d`, hub `acme.ops.load.graph.target.hub`) and writes it as 5,000 `ENTITY_STATES`
entries, so graph-index builds the indexes itself. Per entity: `robotics.assigned.hub` -> hub,
`robotics.status.ready` = true, `dc.terms.title` = "Owner Hotspot" (the display-name predicate both trees register,
used because a rebuild only indexes a registered name predicate); entities 0-19 also carry `robotics.spread.pNN` = true.

Then, through graph-index's public lifecycle only (`CreateGraphIndex`, `Initialize`, `Start`, the incoming query on the
hub every 5 ms until it answers, `Stop`):

- **initial:** fresh index buckets, `Start`, poll until the first answer;
- **restart:** `Stop`, a new component on the same buckets, `Start`, poll until the first answer.

The `index_not_ready` window runs from the `Start` call to the first answer; every refusal before it was checked to
be the classified `index_not_ready` code. KV writes are the sum of `LastSeq` over the five index buckets' streams
(OUTGOING, INCOMING, ALIAS, PREDICATE, NAME), read at the first answer and again after 2 s with no change (the same
both times, every run). Default config on both sides (one index worker).

Probe program: `pin_load_probe_integration_test.go` and `port_load_probe_integration_test.go` (one file each, in the
package under test, integration tag), posted on PR #414, comment 6442050008, beside the #108 comment (6442052435).
Not committed to either repository.

| | Pin `8b99efe9` | Port `812f28b9` (PR #414 head) |
| --- | --- | --- |
| NATS server | 2.14.4 (pin's `graphIndexNATSServerPin`, own container via `natsclient.NewTestClient`) | 2.15.0 (repo's `nats-image` digest, `natsfixture` shared server) |
| Entities in ENTITY_STATES | 5,000 | 5,000 |
| Initial: KV writes | 30,020 (OUTGOING 5,000, INCOMING 5,000, NAME 5,000, PREDICATE 15,020, ALIAS 0) | 30,020 (same per bucket) |
| Initial: `index_not_ready` window, run 1 / run 2 | 13.1 s / 18.0 s | 16.1 s / 48.9 s |
| Restart: KV writes | 10,000 (OUTGOING 5,000, NAME 5,000; INCOMING and PREDICATE 0) | 10,000 (same per bucket) |
| Restart: `index_not_ready` window, run 1 / run 2 | 18.8 s / 24.2 s | 30.0 s / 21.7 s |
| `Start` returned after | 10-16 ms | 15-41 ms |

KV write counts are identical across runs and sides. The windows are wall clock on one laptop (Apple M3 Pro, Docker
29.9.2) and vary widely between two runs of the same tree (port initial: 16.1 s, then 48.9 s); two runs per side do
not support a pin-versus-port timing comparison, and none is claimed. The server versions differ (2.14.4 at the pin,
2.15.0 on the port), as each repository pins its own.

## Reproduce

Copy the probe file into each tree as `processor/graph-index/zz_load_probe_integration_test.go`, then (Docker running;
`PROBE_ENTITIES` changes the count, default 5000):

```bash
# pin: gh api repos/C360Studio/semstreams/tarball/8b99efe9 > pin.tgz && tar -xzf pin.tgz --strip-components=1
go test -tags integration -count=1 -p 1 -run '^TestLoadProbe108$' -v -timeout 25m ./processor/graph-index
# port: git archive of PR #414's head, same command
```

Lines starting `RESULT` carry the numbers. Logs from these runs were local only (`/tmp/gi-measure/logs/`).
