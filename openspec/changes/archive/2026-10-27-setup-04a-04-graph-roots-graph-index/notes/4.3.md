# Task 4.3: lifecycle, Health and DataFlow

Choices design D4 does not spell out. The tests and the pin tests this task carries or drops: `notes/2.3.md`.

## Files

`component.go` (`Initialize`, `Start`, `start`, `Stop`, `cleanup`, `Health`, `DataFlow`'s doc comment) and two lines in
`index.go`: the follower field is now an `atomic.Pointer`. The integration test helper `startIndex` now builds the
component and calls `Start`, with `Stop` in the test's cleanup, instead of wiring the write path by hand.

## Choices

- **Two contexts, one root.** `start` makes the one run context with `context.WithCancel(context.WithoutCancel(ctx))`
  (ADR-113). The pool's lanes write under it. The follower's `Run`, the coalescer and the repair loop run under a child
  of it. `cleanup` ends the child first and joins the three, drains the pool with `Shutdown(ctx)` while the run context
  is still live, and then ends the run context. This is the order in `notes/4.2.md` with a single `WithoutCancel`
  root. graph-ingest does it the other way round: its pool context is a child of its run context. graph-index cannot,
  because ending the feeds must not end the context the lanes write under.
- **Order inside `start`.** `follower.Open`, then `openIndexBuckets`, then a check that Start's context is still
  live, then the contexts, the pool and the goroutines. Everything before the contexts holds nothing that needs
  releasing: readers and buckets are handles on the caller's connection, and the follower starts nothing until `Run`.
  A failed `Start` therefore holds nothing, and its rollback has nothing to release. The only step after the contexts
  that can fail is `dispatch.NewKeyedPool`, and the rollback then only ends the contexts.
- **The failed-cleanup branch of the `lifecycle-suite` rule has no graph-index case.** `cleanup` can fail only when
  its context ends, and a failed Start's rollback reaches `cleanup` with nothing to release, so no case exists. When a
  Stop's context ends first, `cleanup` returns that context's error and clears nothing. The next Stop picks up where
  it left off: the cancels do nothing the second time, `feeds` is already closed, and `Shutdown` returns nil once the
  lanes are done. The run context is ended only after `Shutdown` returned nil, so a Stop that timed out does not cut
  off work the lanes still hold.
- **Joining the goroutines.** A `sync.WaitGroup` covers the three goroutines, and one more goroutine closes `feeds`
  after `Wait`. `cleanup` selects on `feeds` and on Stop's context. That goroutine ends when the three have ended,
  which is the join itself.
- **`Run`'s error is logged, not returned.** `f.Run` returns an error only when the watch's `Stop` fails for a reason
  other than the watch already being gone. Returning it from `cleanup` would make every later Stop fail too, because
  the goroutine has already ended and the error never clears. It is logged at Warn.
- **`Health` reads the follower through an atomic pointer.** `Health` may be called at any time (component.Lifecycle),
  including during `Start`, which stores the follower. With a plain field that is a data race. After `Stop`, the
  follower stays stored: `Lifecycle.Health` ignores stuck states once the component is not running.
- **Handles cleared on a clean Stop:** both cancels, `feeds`, the pool and the coalescer. The follower is not a
  handle. The suite's adapter lists the five handles; the follower's watch is read from the server (design D11).
- **`Start` refuses a nil NATS client** before the shell is consulted, as graph-ingest does. `CreateGraphIndex` refuses
  one already, so only a zero `Component` reaches this check (`TestLifecycleBeforeStart`).

## Failing-first evidence

The tests were written first and run against a stub that adopted the shell without the write path: `Initialize` and
`Stop` as now, and `Start` calling `c.lifecycle.Start` with a start and a cleanup that did nothing. That is the
pin's lifecycle minus the follower. Run: `go test -tags integration -count=1 -run '<the six tests>'
./processor/graph-index`, log `/tmp/gi-43/failing-first.log` (local only). Every new integration test failed by
assertion:

- `TestGraphIndexLifecycleSuite/FailedStartHoldsNothing`: the must-fail owner started.
- `.../StartedOwnerReportsItsHandles`: "held while started = [], want [run cancel pool cancel pool lanes coalescer
  feeds]", and "the follower's watch on the server: … last observation 0".
- `TestStopWritesAcceptedWork`: "every entry delivered: … last observation 0".
- `TestSecondStartIsRefused`, `TestStartContextEndStopsNothing`: "open OUTGOING_INDEX: framework bucket
  "OUTGOING_INDEX" is not ready" (nothing was indexed).
- `TestHealthIgnoresErrorCountAndTracksStuckStates/a_latched_reset`: "last observation {Healthy:true … Status:running}".
  The failed-write subtest failed at its setup, because INCOMING_INDEX had never been created.
- `TestLatchBootstrap_ContinuousWrite`: "an envelope reporting bootstrap complete: … nats: bucket not found".

`TestLifecycleBeforeStart` (unit) passed against the stub. It carries the pin's unit tests of the shell, whose
behaviour did not change.

## Uncovered

- `TestLatchBootstrap_ContinuousWrite` relies on one lane indexing more slowly than one writer writes. It fails with

  anything. It passed in 5 of 5 shuffled runs (`/tmp/gi-43/repeat5.log`, local only).
