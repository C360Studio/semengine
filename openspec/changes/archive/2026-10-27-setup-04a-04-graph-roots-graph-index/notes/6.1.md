### M1: survivor, then detection by a new test

The first run, with the existing `TestFailedWriteWithholdsReadinessAndRepairClearsIt` and `-runs 1`, was a
**survivor**; the reach run showed the removed lines (373-375) are executed. With the check gone, `QueryReady` falls
to `compute`, which also returns not-ready while `failed > 0` (`follower.go:437`), so the refusal is the same until
`bootstrapped` has latched, and that test writes the failing entity before the latch.

The coordinator asked for a test that catches it. `TestFailedWriteAfterTheLatchWithholdsReadinessAndRepairClearsIt`
(`index_integration_test.go`) awaits the published envelope reading `BootstrapComplete` (`publishedEnvelope`, which is
written after the follower set the latch), then deletes `INCOMING_INDEX`, writes one entity (its write fails),
asserts `QueryReady` refuses, recreates the bucket, runs the repair, and asserts `QueryReady` answers. It uses the
package's shared server through the reset, no sleep and no hook. It passed 3 of 3 on the unchanged code
(`go test -race -count=3`). Failing-first was shown against the mutant, not against absent production code. Log:
`/tmp/gi-mut-61.wYaf/m1new.log` (local only).
