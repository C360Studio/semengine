## How the tests build the component

As before, each test puts a running component's handles in place by hand (pool, cancels, core subscriptions, the guard
through `startGuardAcquiringNothing`), so what each proves is unchanged. Only the JetStream input changed. It is bound
through the production path, `setupSubscriptions`, on a client of the test's own on the package's shared server
(`newFixtureClient`: `shared.Reset` and `natsfixture.Open` with `openFixtureClient`). No test starts its own server.
Helpers (`lifecycle_owner_test.go`): `newFixtureInputComponent` (component whose logger is a `pauseOnRecord` on
`"graph-ingest: poison message; terminating"`), `bindHeldInput` (binds, publishes undecodable bytes to `entity.poison`,
waits for the callback to be held), `awaitReleaseBegun` and `handlersReturned`.

Binding through `setupSubscriptions` also records the readiness bound consumer. So the failed-cleanup test now expects
`[runtime cancel consumers readiness bound consumers]` where it expected `[runtime cancel consumers]`. The ordering test
no longer sets `boundConsumers` by hand.

## The event that replaces `<-consumer.drainSeen`

A real handle shows nothing when `Drain` is called. Measured on this branch with a scratch test (not committed): on a
healthy connection, with the callback held, the handle's `Closed()` did not fire within 5 s after `Stop` began, three
runs out of three. So it cannot serve as the event. The tests wait for `Health` to report `"stopped"` instead
(`awaitReleaseBegun`). `component.Lifecycle` clears `running` immediately before it calls release
(`component/lifecycle_type.go`, the cleanup closure in `Start`). Each read goes through `readWithin`, so under the
shell-lock mutant (M7) the wait fails instead of hanging. From that point on, cleanup runs on another goroutine and cannot
pass `WaitConsumerHandlers` while the callback is held.

`TestLifecycleOwnerRunningStopPreservesEffectSettlementOrder` used to check that nothing had been canceled while the fake
stayed open. It now checks the order when each step runs. The test wraps `ingestSubmitCancel` and `ingestPoolCancel`;
when either runs, it asks whether every callback has returned (`handlersReturned`: `WaitConsumerHandlers` under a context
that has already ended, which returns nil only then) and whether the readiness observation is still there. The answer
does not depend on when the test releases the callback. The oracle is natsclient's own completion signal. graph-ingest
cannot observe a callback's return any other way, because the callback ends after `msg.Term()` inside `deliver`.

## What a real consumer cannot show

- **Drain replay.** The old tests counted `Drain` calls (`drains == 1` after a later Stop). Calling `Drain` a second
  time on a real handle has no effect the tests can see, so the "without replay" claim is now only `drainIssued`
  staying true after the failed Stop. A mutant that issues `Drain` again on every cleanup would survive; this is review-only.
- **Stop in place of Drain.** The adapter no longer counts "consumer stop", because no production code calls `Stop` on a
  consumer handle. A mutant that calls `binding.handle.Stop()` in place of `Drain()` would survive these tests (proposal,
  "Not covered"); this is review-only.
