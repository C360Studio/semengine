- **The failure-reason constants moved.** `normalizeFailureReason` (the pin's `storage.go:708-716`) switches on six
  unexported constants (`failReasonContentError` through `failReasonEmbedderError`) that the pin declares in

- **`TestRevisionGuardHistoryMatchesModel` is an integration test**, as design D9 lists it (on a real server through
  `natsfixture`). Task 2.2's text marks only `TestSaveDedupKeepsSameSpaceReplacesOther` as integration; the
  orchestrator fixes that wording in `tasks.md`.
- **`ScanFailed` stops its watch with `kvwatch.Stop`**, wrapped as "embedding: stop the EMBEDDING_INDEX watch". The
  pin called `watcher.Stop()` directly. With `kvwatch` in this PR for the #454 case, a plain `Stop` would be a second
  way of spelling the same stop in newly ported code (orchestrator ruling, 2026-10-28). If the delivery does not
  close, `ScanFailed` returns that error and no entries: a delivery still running is reported, never dropped. On
  every other path it returns the entries as the pin did, the partial seed on a cancelled scan included.
- **`SaveDedup` lost its `entityID` parameter.** At the pin its only use was the dropped `DedupRecord.EntityIDs` field
  (S13), so a kept parameter would have been an input nothing reads. Its only caller is the pin's `worker.go` (S20),
  ported in 3.4. D2 does not list this signature change; it follows from S13. Flagged for review.
- **The no-text removal** is `(*Storage).deleteAtRevision(ctx, entityID, kvRevision) (removed bool, err error)`.
  It returns `true, nil` when the record was removed, `false, nil` when the key moved or is gone
  (`ErrKVRevisionMismatch` or `ErrKVKeyNotFound`), and `false` with the error otherwise. Task 3.4 maps these to the
  Worker's outcomes.
- **Errors.** `saveError` returns `ErrRecordGone` and `ErrSupersededRevision` bare (as the pin did) and keeps an
  invalid-record error invalid. Everything else is wrapped transient, retry exhaustion included, so the result still
  matches `natsclient.ErrKVMaxRetriesExceeded` through `errors.Is`.
- **Comments.** Comments about SemStreams rolling upgrades and legacy records were dropped from `Record`'s fields
  (S17; owner, #91 comment 6109293267). `ContentFields` is gone (S14), along with its comment.
- **Entry validation (#467, Codex review of `66410b1`).** At the pin, entity IDs and dedup keys were checked only for
  emptiness. Now each of the six entity-ID entry points (`SavePendingGuarded`, `SaveGenerated`, `SaveFailed`,
  `GetEmbedding`, `DeleteEmbedding`, `deleteAtRevision`) calls `validateEntityID`, which uses
  `types.ValidateEntityID`. Both dedup-key entry points (`GetByContentHash`, `SaveDedup`) call `validateDedupKey`,
  which uses `natsclient.ValidateKVLiteralKey`. Each refusal is an `errs.WrapInvalid` error returned before any
  bucket call.
  - Entity IDs get no second `ValidateKVLiteralKey` check, unlike graph-index's `validateEntityLiteralKey`. A valid
    entity ID is already a valid KV key: at most 256 bytes, six tokens, first byte alphanumeric, the rest
    alphanumeric, `_` or `-` (`pkg/types/entity_id.go:193-238`). That is inside the key grammar: at most 1,024 bytes,
    64 tokens and 512 bytes a token, alphabet adding `/` and `=` (`natsclient/kv_key_contract.go:118-152`). A second
    check could never fail, so no test could show it failing.
  - `TestStorageRefusesInvalidIdentityBeforeAnyBucketCall` uses `countingKV`, which counts every bucket call. Each
    entry point is tried with these inputs:
    - entity IDs: empty, one part, five parts, seven parts, an empty segment, a wildcard byte, a `_` first byte, and
      six well-formed parts of 257 bytes;
    - dedup keys: empty, `*`, `>`, empty tokens, a space, and 1,025 bytes.
  - A valid input in the same test has to reach the bucket, which shows the counter can tell the two apart.
  - Mutation checks: for each of the eight call sites, a mutant with that site's validation removed:
    `task mutate:check -- -pkg ./graph/embedding -test TestStorageRefusesInvalidIdentityBeforeAnyBucketCall -file
    graph/embedding/storage.go -mutant /tmp/mut22/v_<Method>.go -expect-text "want an invalid-input error before any
    bucket call"`. Detection, 3 of 3, for all eight.

## The history test

`TestRevisionGuardHistoryMatchesModel` runs against real NATS. Each history gets a fresh `EMB_HIST_IDX_<n>` bucket,
deleted when it ends.

The model maps each entity to: present or absent, status, source revision, and the last KV revision observed. Its
rules come from D3:

- **Pending** is refused only over a generated record at the same or a newer source revision.
- **Generated and failed** return `ErrRecordGone` when the key is absent, and `ErrSupersededRevision` when the call's
  revision is below the stored one. Failed is also refused over a generated record at an equal revision.
- **The fenced removal** removes only at the KV revision it is given.
- **KV revisions:** a refused call leaves the key's KV revision where it was, and a write moves it forward.

Each call's result is checked against the model, along with the stored record and its KV revision, read directly
from the bucket. `history.apply` and `history.check` do this for both kinds of history below.

**Coverage comes from witnesses (#466, Codex review of `66410b1`).** The first version required each of the 17
outcomes to be reached by 50 random histories. That depends on the seed: `-rapid.seed=203` passed all 50 checks and
then failed the coverage assertion ("pending saved over an older generated record"). The test now runs these in
order:

1. **Witnesses.** There is one fixed, deterministic history per outcome (subtests `witness/<outcome>`), each checked
   against the model, and its last call must reach the named outcome. The 17 outcomes:
   - pending: saved; saved over a newer record; saved over an older generated record; refused over a newer generated
     record; refused at an equal revision;
   - generated and failed: saved; refused because the record is gone; refused as superseded;
   - failed refused over generated at an equal revision;
   - deleted;
   - fenced removal: at the current revision (removes); at a stale revision (keeps the record); of a removed key at
     its last revision; of a key never stored.
2. **Random histories.** Rapid generates up to 30 calls, over two entities and revisions 1-4. The draws are
   weighted, and `drawRevision` draws the stored record's revision on purpose. These histories explore orderings
   against the same model and make no coverage assertion, so no seed can fail for lack of reach.

Seed 203 needs no test of its own. Its failure was only the aggregate coverage assertion, which no longer exists, and
the witnesses reach every outcome whatever the seed. It is kept as a run of record. This command passed for
seeds 203, 20261028, 7 and 99:

```bash
go test -tags integration -race -count=1 -timeout=2m -v ./graph/embedding \
  -run '^TestRevisionGuardHistoryMatchesModel$' -rapid.checks=50 -rapid.seed=<seed>
```

Each run passed all 17 witnesses and printed `[rapid] OK, passed 50 tests`.

The witnesses fail on the guard mutants. Each command was:

```bash
go test -tags integration -overlay /tmp/mut22/<m>.json ./graph/embedding \
  -run '^TestRevisionGuardHistoryMatchesModel$' -rapid.checks=1 -rapid.seed=1 -rapid.nofailfile
```

The results:

- `w_pending_gt` (pending guard `>=` made `>`) failed `witness/pending refused over generated at equal revision`.
- `w_failed_equal` (`SaveFailed`'s equal-revision check removed) failed `witness/failed refused over generated at
  equal revision`.

`storage.go`'s SHA-256 was `f10d728c…` before and after.

The test bounds itself at 50 random runs: `TestMain` sets `-rapid.checks=50` unless the command line sets it. On
failure, Rapid prints the replay seed and the drawn sequence.

Model error found on the first run (`66410b1`'s history): the model assumed a key never stored could not be at KV
revision 1. On nats-server v2.15.1, `DeleteEmbedding` of a never-written key writes a delete marker at revision 1,
and the fenced delete at 1 matched that marker. A Worker's revision always comes from a stored record, never a
marker, so the model uses the last stored record's revision for an absent key, or 2^40 for a key never stored.
