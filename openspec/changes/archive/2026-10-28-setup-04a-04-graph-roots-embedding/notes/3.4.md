## How Run stops

`Worker.Run` (`graph/embedding/worker.go`) does this:

1. It refuses a nil context, and a second `Run` while one runs, with an invalid-input error, before anything starts.
2. It builds the keyed pool under `Run`'s own context. That context is handed to every item, so accepted items
   finish under it, ended or not.
3. It opens the watch under a context derived from `Run`'s. A watch that cannot open shuts the empty pool and joins
   it before returning.
4. `follow` reads the watch on `Run`'s goroutine, the single reader. It submits each put with `SubmitBlocking` under
   the derived context.
5. When `ctx` ends or the update channel closes, `follow` returns, and `cancel()` ends the derived context.
6. `pool.Shutdown(ctx)` begins the drain, and its result is ignored. `pool.Wait()` is the join.
7. `kvwatch.Stop(ctx, watcher)` runs, and its error is wrapped as "embedding: stop the EMBEDDING_INDEX watch".
8. `Run` returns `ctx.Err()`, or `errWatchLost` (the cache's error), joined with any stop error.

No detached context is created.

**The reader is `Run`'s own goroutine,** as in `VectorCache.Run`. D4 says the watch is read "on its own goroutine",
and the brief says "a single reader goroutine". `Run`'s goroutine is that single reader, and a separate one would
add a goroutine and a join with nothing gained. A read waiting on a full lane returns when the derived context ends,
because that context is the `SubmitBlocking` context. The entry it held stays pending in the bucket.

## Choices

- **Pool sizing.** The lane count is `WithWorkers` (default 5, floored at 1), as D4 says. D4 does not size the
  queue. It is `max(workerQueueCapacity/workers, 1)` with an unexported `workerQueueCapacity = 256`, which is
  graph-index's shape (a total split across lanes, `processor/graph-index/index.go:91`). 256 is the update buffer
  the pin's workers shared (nats.go v1.54.0, `jetstream/kv.go` WatchFiltered; not promised). Nothing exported
  changes. **Flagged for the architect.**
- **The pool is built per `Run`,** because `NewKeyedPool` takes the context handed to items. It is built before the
  watch so that a pool failure leaves nothing to stop. The pool has no metrics registry, because the package imports
  no Prometheus.
- **The pin's panic recovery stays in `handleKVEntrySafe`,** inside the pool's work function (D4). The pool's own
  recovery never fires, so `OnPanic` is nil.
- **`markFailed` takes the error, not its text.** Each call site wraps the cause with the pin's prefix (`text
  extraction failed: %w`), so the stored `ErrorMsg` reads as at the pin. The shutdown test is
  `errors.Is(cause, context.Canceled) && ctx.Err() != nil` (D7).
- **One text cap.** `textCap()` returns the configured cap, 8,000 when it is 0 or less, clamped to
  `MaxSourceTextLenCeiling`. Both lanes use it. The inline lane is now clamped too, which the pin did not do; above
  1,000,000 the pin's lanes already differed. `embedderIdentity` still folds the configured cap (0 stays 0), so no
  existing dedup key changes. Caps of 0 and 8,000 therefore key apart while embedding the same bytes. That costs one
  re-embed on a configuration change and nothing else.
- **No-text outcomes map from `deleteAtRevision`'s results:** removed → `OutcomeSkipped`; moved or gone →
  `OutcomeDeleted`; an error → not terminal, logged at Error. The fence is the revision of the watch entry being
  processed (`entry.Revision()`).
- **Retry exhaustion** is matched with `errors.Is(err, natsclient.ErrKVMaxRetriesExceeded)` in place of
  `ErrCASExhausted`.
- **`IncContentUnresolved`** is called directly. The pin's `contentUnresolvedMetrics` assertion is gone (D7).
- **`isExpectedShutdownError`, `Start`, `Stop`, `stopping`, `started`, `cancel`, `wg` and the `indexBucket`
  parameter** are not carried. `kvwatch.Stop` owns the stop-error rule.
- **Observed, not changed: the default KVStore budget versus its timeout.** Under constant conflict, ten jittered
  backoffs (10 ms doubling to a 1 s cap) can outlast the default 5 s `Timeout`. The save then ends on the deadline,
  not on `ErrKVMaxRetriesExceeded`, and the Worker treats it as a save failure (`markFailed`). D3 declares that the
  `Timeout` bounds retries. `TestCASExhaustionIsNotTerminal` uses `MaxRetries = 0`, so it never sleeps. This is not
  a defect: the Worker reports a timed-out save as a failure, which it is.

## Tests

**Unit (`worker_test.go`, synctest on fakes).** `worker_fakes_test.go` adds `watchKV`, a memKV whose `Watch`
replays the current keys, then nil, then every later write and removal in write order. Through it, the Worker sees
its own writes as it would on a real bucket. The unit tests:

- `TestWorkerRunRefusesNilContext`, `TestWorkerSecondRunRefused`, `TestWorkerRunLeavesNothingBehind`.
- `TestTerminalCallbackOncePerOutcome`: generated, failed, no text and deleted each fire the callback once.
- `TestCASExhaustionIsNotTerminal`: replaces the pin's `TestSaveAndNotify_CASExhaustedIsNotAFailure`.
- `TestFailureWithCanceledTextIsAFailure`: text only, through `Run`. It also calls `markFailed` with
  `context.Canceled`, once with a live context and once with an ended one.
- `TestBothLanesEmbedIdenticalBytes`: the expected text is worked by hand. 2,000 × "abcd " is cut to 1,600 words,
  7,999 runes.
- `TestKeyedCallbacksFollowRevisionOrder` and `TestWorkerSaveRefusedWhenNewerPendingArrives`.
- `TestNoTextDeleteFailureIsNotTerminal`.

**Two tests D9 lists as integration are unit tests here:** `TestKeyedCallbacksFollowRevisionOrder` and
`TestWorkerSaveRefusedWhenNewerPendingArrives`.

- In a bubble, `synctest.Wait()` while N's callback (or embedding) is held runs everything else that can run. So
  the pin's shared-channel shape fails every time, not by chance.
- Both are within `task mutate:check`'s reach, which does not build integration files. That matters for task 3.5.
- Neither needs the fence, which the fake cannot model. The two fenced no-text tests are integration tests.
- **Flagged for review against D9.**

**`TestKeyedCallbacksFollowRevisionOrder` fails N through the embedder,** not through a body fetch. The outcome,
`SaveFailed(N)` stored and `OutcomeFailed`, is the same. Callbacks are recorded in the order they *return*: the
defect is N's late callback completing after M's.

**Integration (`worker_integration_test.go`, shared server through the reset):**

slept in a retry backoff: a sleeping goroutine counts as durably blocked. Ending `Run` there turned the entry into a
shutdown. The fix is `MaxRetries = 0`, a single attempt with no sleep. After it, 50 runs passed, and m6 shows
detection, 3 of 3.
