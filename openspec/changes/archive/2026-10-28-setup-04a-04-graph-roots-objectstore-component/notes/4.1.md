# Task 4.1: tests for `Client.WaitConsumerHandlers`

Measured on the uncommitted tree over `6d43440` (Go 1.26.10, darwin/arm64, nats.go v1.54.0, the pinned NATS image).
Mutants and logs under `/tmp/5b-r2/` are local only; the commands below rerun them.

## The tests

All six are in `natsclient/wait_consumer_handlers_integration_test.go` (integration tag, `natsfixture`). Five use the
package's shared server through the reset; `TestWaitConsumerHandlersAfterConnectionLoss` starts its own, since it
restarts the broker under a running handler. The entry points are spread over the tests so each of the three
registration paths runs: `ConsumeStreamWithConfig` (running, context, unknown, nil context),
`ConsumeInternalStreamWithConfig` (connection loss), `ConsumeStreamWithConfigContexts` (after Close).

Choices the design does not spell out:

1. "The wait does not return until the handler is released" is asserted as a call under a 200 ms context
   (`heldWait`) that must end with `context.DeadlineExceeded` while the handler is held. The handler is held by a
   channel the test owns, so the outcome does not depend on the 200 ms; the length only bounds the run.
2. `…AfterConnectionLoss` cannot start a second consumer to show the claim released, because the client's
   connection is gone for good. It reads the client's claim table directly after the wait returned nil, as
   `waitForInternalClaimRelease` already does in this package.
3. `…RefusesNilContext` passes a live handle of the same client, so the nil context is the only thing that can be
   refused; `…RefusesUnknownHandle` gives each unknown handle a call under a 10 s context and requires an
   invalid-input error that is not the context's, so a call that waited instead of refusing fails.
4. The non-comparable value is `foreignHandle{tags []string}`, a struct with a slice: a map lookup or `==` on it
   panics, which `require.NotPanics` would report.

## Uncovered: a wait on `done` instead of `released`

Reviewer NIT, recorded as uncovered. The same-durable restart in `…WaitsForRunningHandler` (and the claim-table read
in `…AfterConnectionLoss`) cannot reliably tell a wait on `consumerOwnership.released` from a wait on
`ownedDelivery.done`: the ownership goroutine releases the claim microseconds after `done` closes. Measured with
`m4_released_on_done`, which closes `released` before `release` runs (the equivalent of waiting on `done`):

```bash
go test -count=3 -tags integration -overlay /tmp/5b-r2/m4_released_on_done.json \
  -run 'TestWaitConsumerHandlers(WaitsForRunningHandler|AfterConnectionLoss)$' -v ./natsclient
```

Survivor: both tests passed in all three runs. No test holds the release step open without a hook on production code,
which the design rules out (D8).
