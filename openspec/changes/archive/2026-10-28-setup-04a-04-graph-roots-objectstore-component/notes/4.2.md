# Task 4.2: `Client.WaitConsumerHandlers`

Choices the design (D11) does not spell out:

1. The record is `consumerReleases map[jetstream.ConsumeContext]<-chan struct{}` on `Client`, under its own mutex
   (`natsclient/client.go`), mapping a handle to its ownership's `released` channel; nothing else of the ownership is
   kept. `commitConsumer` records the handle on its success path only, after handing it to the ownership goroutine and
   before returning it, so a caller can never hold a handle that is not yet recorded. A setup that Close overtook
   returns no handle and records nothing.
2. A handle is recorded and looked up only when `reflect.ValueOf(h).Comparable()`; otherwise a map operation would
   panic. nats.go v1.54.0 returns a pointer (`*pullSubscription`, `jetstream/pull.go:228`, `:425`); a future
   non-comparable handle would be refused by the wait as unknown, which fails closed.
3. The wait checks `released` before it selects on `ctx`, so a finished handle returns nil even under a context that
   has already ended. The spec's "if ctx ends first" is the case where the handlers have not finished.
4. A context that ends first is wrapped as transient (`errs.WrapTransient`), as `commitConsumer` wraps its own setup
   context; `errors.Is(err, ctx.Err())` holds through it.
5. The client's stated rule for durable claims ("without retaining lifecycle handles", `client.go:73-74`) is unchanged;
   the new field's comment states that its handle is a lookup key only, as D11 records.
