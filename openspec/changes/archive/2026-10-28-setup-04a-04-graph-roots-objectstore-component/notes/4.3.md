# Task 4.3: the Component waits through natsclient

`cleanup` drains each JetStream input once, as before, then calls `natsClient.WaitConsumerHandlers(ctx, handle)` for
each, joining any error. `handlerJoin`, its `handlers` field, `newHandlerJoin`, the handler's `enter`/`exit` and the
Component's own late-delivery refusal (Error log and `CountError`) are gone; a late delivery is now refused, logged at
warn level and counted by natsclient (`late_delivery_refused`). `TestHandlerJoinWaitsForRunningHandlersAndRefusesLaterOnes`
is dropped. `TestStopJoinsHandlerAfterConnectionLoss` is unchanged and passes.

## Decision not in the design: the failed-cleanup test moves to integration

D11 did not name this test, but it used a stub consume loop (`stubConsumeContext`) with no NATS client. With the
change, `cleanup` asks the client about the handle, and the client knows only handles it returned, so a stub cannot
stand in (it would be refused as unknown, and the Component has no client to ask). Adding a seam for the wait would be
a back door (D8). The test therefore moved, unchanged in what it asserts, to
`storage/objectstore/lifecycle_integration_test.go`: its start function binds a real consumer through the Component's
own `bindJetStream` on the shared server and keeps the stub core subscription. The consumer's drain-once check reads
`consumers[0].drainIssued` after the failed rollback instead of a stub's Drain count; the later Stop now uses a 30 s
context instead of `t.Context()`. Task 2.1 lists this test among the unit tests (no Docker); that line is now out of
date, for the technical writer (task 5.2/6.1 records).
