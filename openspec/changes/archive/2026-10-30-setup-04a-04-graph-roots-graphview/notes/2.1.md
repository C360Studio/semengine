# Task 2.1 notes: the pin's unit tests on `Run`

Written with tasks 3.1 and 3.2, whose gate 2.1 shares. The pin's `integration_test.go` is task 2.4 and is not here.

## How the tests run

- Every test that runs a view runs inside `synctest.Test`. The fake watch's update channel is unbuffered, so a send
  returns once `Run` has received the entry; the `synctest.Wait` after it orders every later read after the apply.
  This replaces the pin's `OnApply` channel and its `time.After(testWait)` bounds, which are gone.
- A tick is `<-time.After(testTick)` then `synctest.Wait`. `testTick` is 100 ms of the bubble's clock, set through
  `WithTickInterval`. A wait of one period crosses exactly one tick of `Run`'s ticker, so each `tickNow` is one window.
  This replaces the pin's caller-driven tick channel (S6, removed) and its `OnTick` wait (`Hooks.OnTick`, dropped).
- Reads of what a delivery goroutine sent (`recvBatch`, `requireNoBatch`, `recvClosed`) call `synctest.Wait` and
  then receive without blocking, so a missing batch fails the test instead of hanging it.
- Hook calls are recorded in slices under a mutex (`recorder`) and read after `synctest.Wait`, not in buffered
  channels: the racing-attach test makes about 100 `OnSubscribers` calls, more than a fixed buffer holds.
- The fake source closes `Updates()` when the watch context ends (`context.AfterFunc`), as nats.go does (probe P11,
  PR #458 comment 6472856197); the pin's fake ignored the context (pin `harness_test.go:56`). The fake's `Stop`
  only counts calls.
- `TestNewValidatesArguments` and `TestRunRejectsNilContext` start no goroutine and do not use a bubble.
- Two goroutine-driven tests cannot call `synctest.Wait` while their other goroutine spins or reads, so they use raw
  blocking sends and receives and wait once the other goroutine has finished: `TestAppliedPairIsNeverTorn` (its
  reader never blocks) and `TestSnapshotDeltaSeamUnderConcurrentWrites` (eight readers block on `Deltas`, and only
  one goroutine may call `Wait`).

   - `TestWatcherLossFailsClosed`, `TestOnSubscribersReportsZeroOnWatcherLoss`,

2. The fake's context close is load-bearing. With `context.AfterFunc(ctx, w.lose)` replaced by `_ = ctx` (the pin
   fake's behaviour, copied in and restored by `cp`, SHA-256 `8a42247938…` matched before and after), the first test
   to end its bubble panics: `deadlock: main bubble goroutine has exited but blocked goroutines remain`, with `Run`

## Choices the design leaves open (3.1, 3.2)

- `Run`'s loop (`follow`) reads the watch and a `time.Ticker` in one `select`. A closed update channel is a loss only
  when `ctx.Err()` is nil at that read; otherwise it is a stop. `Run` cancels the watch context before
  `kvwatch.Stop`, as `graph/embedding.VectorCache.Run` does.
- A `WatchAll` that fails after `ctx` ended marks the view stopped, so later calls return `ErrViewStopped`; while
  `ctx` is live it marks the view failed (`failOpen`), so `WaitCaughtUp` returns the wrapped `ErrWatcherLost`.
- `stop` (was `Stop`) runs only on `Run`'s goroutine before `wg.Wait`, so the pin's `wg.Add` around its own
  `OnSubscribers(0)` call goes. `failClosed` keeps the pin's body without its already-stopped guard and returns the
  error `Run` reports.
- Doc drift (S10): `pkg/revlag.Watermark.IndexedAt` became `readiness.IndexStatusInputs.IndexedAt`, because this tree
  has no `revlag`; `graph.IndexStatusInputs` became `readiness.IndexStatusInputs`; `gh#579` and both `PR #583` mentions
  name SemStreams. `AppliedRevision`'s sentence on WatchAll ordering was not moved onto `Applied`: it is a library
  claim with no probe here.
- The `Hooks` doc says hooks run on `Run`'s goroutine or an attach's or detach's goroutine and that a blocking hook
  holds `Run`. The `OnSubscribers` doc says the last value is not promised to be the current count (D2).
