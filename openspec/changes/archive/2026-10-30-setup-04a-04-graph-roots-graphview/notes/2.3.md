# Task 2.3 notes: `TestViewHistoryMatchesModel`

The test is `pkg/graphview/history_prop_test.go`. No production code changed: the test found no defect in the package.

## What the test does

- **Generator.** Rapid (`pgregory.net/rapid`, as the other generated checks in this tree) draws a replay prefix of 0
  to 8 writes and a live history of 8 to 60 steps over three keys. A write is a put, a poisoned write (`POISON`), a
  skipped write (`SKIP`), a delete or a purge. A live step is a write, an attach with a snapshot
  (`SnapshotAndSubscribe`), a delta-only attach (`Subscribe`), an unsubscribe of a drawn live subscriber, or a tick.
  Every live history opens with one attach of each kind and ends with a tick, so the snapshot check runs in every
  history. The state check runs for each subscriber still attached at a tick; the generator can unsubscribe both
  opening subscribers before any tick, so a history can make no state comparison. The aggregate counts each run
  prints (`state` in the checks-run line) show the state check running (`docs/testing.md`, "Show that each assertion
  runs").
- **Model.** The last operation per key, filled only from the generated operations: a put holds its value at its
  revision, a poisoned write holds poison at its revision, a skip, delete or purge makes the key absent. It also keeps
  each key's last revision, whatever the operation. Nothing is read back from the view.
- **Checks.** A snapshot equals the model at the attach, and no key is both a value and poisoned. Each batch holds a key
  at most once, sorted by revision. Each delta's revision is above the subscriber's high-water for its key, which
  starts at the model's last revision for the key at the attach, so a change from before the attach or a stale one
  fails. At every tick each subscriber's state (snapshot, or the model at the attach for a delta-only subscriber, plus
  its deltas) equals the model, revisions included. After `Unsubscribe`, `Deltas` closes with a nil `Err`.
- **Harness.** The fake source and watcher of `harness_test.go` and its `decodeTest`. Each history runs in its own
  `synctest` bubble (Rapid calls `t.Deadline`, which a bubble refuses, as `internal/cache/coalescing_set_prop_test.go`
  notes) and stops its view, so the bubble's return proves nothing was left running. A write is an unbuffered send to
  `Run` then `synctest.Wait`; a tick is one tick period of the bubble's clock then `synctest.Wait`. A failed step is
  returned to the test goroutine as text naming the step index and the step, so no `require` runs off it, and Rapid
  shrinks the history and prints the seed.

## Runs

The default is Rapid's: 100 histories, a fresh seed each run, as `task test:unit` and `task test:repeat` run it. One
run takes about 40 ms of test time under `-race`; the whole package's `-count=5 -cpu 1 -shuffle=on` run took 0.32 s.

| Command | Completed checks (from `-v`) |
| --- | --- |
| `go test ./pkg/graphview -run '^TestViewHistoryMatchesModel$' -count=1 -race -v -rapid.seed=1320` | `[rapid] OK, passed 100 tests`; histories 100, steps 1954, snapshot 249, batch 798, revision 1379, state 1208, closed 148 |
| same, `-rapid.seed=7` | `[rapid] OK, passed 100 tests`; histories 100, steps 1798, snapshot 231, batch 622, revision 1085, state 1017, closed 152 |

Replay a failure with the seed Rapid prints: `go test ./pkg/graphview -run '^TestViewHistoryMatchesModel$' -count=1
-v -rapid.seed=<seed>`. Add `-rapid.nofailfile` so no `.fail` file is left under `testdata/rapid/`.
