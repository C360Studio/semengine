# Task 2.4 notes: the integration tests (D6)

All three are in `pkg/graphview/integration_test.go` (`//go:build integration`), on the package's shared NATS server
through `natsfixture.Open(t, shared.Reset(t), openClient)`. No `t.Parallel`, no sleep, no fixed port, no skip. Each
test opens one client, closed on `t.Cleanup`. No production code changed.

| Test | Spec scenario |
| --- | --- |
| `TestIntegration_GraphViewOverRealBucket` | none (the pin's real-bucket test, D6) |
| `TestRunLeavesNoWatchDelivery` | "Stopped with a backlogged watch" |
| `TestRunReportsLostWatch` | "The bucket is deleted" |

## Choices the design leaves open

- **The pin's test keeps its name and body.** The changes: `Start`/`Stop` become `Run` on its own goroutine, ended
  at the close, where it must return `context.Canceled`; the dropped `CaughtUp()` check goes (`WaitCaughtUp`
  returning nil is the same fact); the bucket comes from `natsclient.CreateKeyValueBucket` on the reset server, in
  place of the pin's `NewTestClient`.
- **Whose method shows "no delivery left".** `internal/kvwatch` has no integration test. The method used is the one
  `graph/follower`'s `TestFollowerRunReturnsAndLeavesNothing` and `graph/embedding`'s
  `TestVectorCacheRunLeavesNoWatchDelivery` use: 600 stored entries (above nats.go v1.54.0's 256-entry buffer), a
  hook that holds `Run` until the cycle's context ends (here `OnApply`), `natsfixture.AwaitNativeDeliveryBlocked`
  before the cancel, then `natsfixture.NativeDeliveryStacks` empty after `Run` returns, ten cycles on fresh views
  (a view runs once). It also checks no stack is in a `View` or `Subscription` method.
- **The 60 s bound.** `waitBound` bounds the wait on `Run` returning (a receive on its result channel, the ordering
  event), and every other wait. Every `Run`, each backlog cycle's included, starts through `startRun`, whose
  `t.Cleanup` cancels `Run`'s context and waits again, bounded, so a test that fails early leaves no `Run` behind
  when the fixture's cleanups close the client (they were registered first, so run last).
- **Cleanup after a wait ran out (Codex review, issue #481).** The first helper cached its whole timed wait with
  `sync.OnceValue`, so once a wait ran out the cleanup's wait returned that timeout at once and did not join `Run`;
  and the backlog test's cycles started `Run` by hand, with no joining cleanup on their `Fatal` paths. Now only
  `Run`'s own result is kept (it is written before a `done` channel closes), and each wait selects on `done` afresh.
  The backlog hook waits on a context derived from `t.Context`, which `testing` ends before cleanups run, so it never
  holds `Run` past the cleanup's cancel. Shown with a temporary test (in the package dir, deleted after; never
  committed) in `synctest` on the unit fake source: an `OnApply` hook holds `Run`, `stop`, the first `wait` runs out
  on the bubble's clock (`errRunHung`), the hold is released, and the second `wait` must return `context.Canceled`.
  It passed on the new helper; on the committed one (`9173734`, through `-overlay`) it failed:
  `second wait = run did not return within the wait bound; want context.Canceled`. The early backlog failure is a
  trace, not a run: each cycle's `startRun` registers its cleanup before any `Fatal` in that cycle.
- **The lost-watch test checks more than the spec line.** Beyond `Run`'s error, it checks the attached
  subscription's `Err` matches `ErrWatcherLost` (its `Deltas` has closed by the time `Run` returns; `failClosed`
  waits on it), `Get` refuses with `ErrWatcherLost` and `ErrNotReady`, and nats.go's delivery has ended. It does not
  check nats.go's unsubscribe goroutine as embedding's test does: the spec does not ask for it.
