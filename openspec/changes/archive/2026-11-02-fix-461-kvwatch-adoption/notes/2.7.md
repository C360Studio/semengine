# Task 2.7: flake #499, `TestSafeConfig_ThreadSafety`

Folded into this PR on the owner's word (2026-11-02), because `merge:check` refuses while a `class:flake` issue is
open.

The test gave up after a fixed 10 s and called that a possible deadlock. It now waits on its `WaitGroup` directly. A
real deadlock is still caught by `go test`'s own timeout, which also prints every goroutine's stack. The test's
assertions are unchanged.

## Reproduction, before and after

Same load both times: 36 copies of the compiled race test binary at once on a 12-core machine.

```bash
go test -race -c -o /tmp/cfg.test ./config
cd config
for i in $(seq 1 36); do
  /tmp/cfg.test -test.run '^TestSafeConfig_ThreadSafety$' -test.count=1 -test.cpu=1 &
done
wait
```

Before the fix, all 36 failed, each after 10.00 s to 10.84 s:

```text
--- FAIL: TestSafeConfig_ThreadSafety (10.01s)
    safe_config_test.go:88: Test timed out - possible deadlock
```

After the fix, all 36 passed with exit 0, each in about 14 s. So the work under this load takes longer than the old
limit, and nothing is deadlocked.

## Not covered

A real deadlock was not injected to watch `go test`'s timeout fire. The real timeout is `go test`'s default unless a
caller sets another.
