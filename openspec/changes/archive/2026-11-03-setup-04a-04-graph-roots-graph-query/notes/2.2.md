## Choices the design leaves open

- **Malformed `min_revision`.** The field is a `uint64` decoded by `encoding/json` in all eight decoders. A negative
  number, a fraction, an exponent, a string, a bool, an object, an array or a number above the largest `uint64` is a
  decode error, so the verb refuses it as class invalid, code `invalid_request`, before the readiness check. No new
  validation code was needed. This fails closed: the alternative, treating it as absent, would answer a request whose
  minimum was never checked.
- **`null`.** `{"min_revision":null}` leaves the field zero, so it means no minimum, as `encoding/json` treats null for
  any number. It states no revision to miss, so nothing is answered below a stated minimum.
- **Validation before the comparison.** An invalid request carrying a `min_revision` is refused as invalid. The spec's
  order is validation, `index_not_ready`, comparison; a latched reset, also from `QueryReady`, comes before the
  comparison too.
- **How "reads no bucket" is proved.** The five index buckets are deleted on the real server. The same request with a
  met minimum then answers `internal`, which shows a read cannot succeed, and the refused one still answers
  `revision_not_reached`. The eight read-first mutants show the order is what the test sees.
- **Not-ready fixture.** An unresolved write (`INCOMING_INDEX` deleted before the writes) withholds readiness at once;
  the lost-feed path took about 18 s when measured (comment in `TestQueriesAreRefusedWhileTheFeedIsLost`) and goes
  through the same `QueryReady` check.
- **`decodeEntityRequest`** now returns `entityRequest`, since the two entity verbs need both fields.
- **Examples, not generated checks.** Design D3 records this: one comparison, boundaries 0, R and R+1, plus the largest
  `uint64`.
- **No `Fuzz*` target.** The field adds no parser: `encoding/json` decodes it into a `uint64`, and the malformed table
  covers each class it must reject.
