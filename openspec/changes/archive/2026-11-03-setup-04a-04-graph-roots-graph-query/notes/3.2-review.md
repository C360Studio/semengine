## What counts as an error

- **What graph-index does.** Its query handlers count nothing, input or error: `processor/graph-index/query.go` has no
  `CountInput` or `CountError`. Its `CountInput` is per KV entry (`index.go:123`). Its `CountError` is per outcome of its
  own work, an entity whose writes failed or a reset (`index.go:248`, `:425`; `TestErrorCountCountsOutcomesNotOperations`).
  A refusal it sends a caller never moves `ErrorCount`.
- **The choice here.** A responder's refusal is not counted: the responder answered, and the forward did its work.
  Only a request with no answer is, which is graph-query's own failure. That is graph-index's rule, outcomes of its own
  work rather than what a caller is told.
- **Where this differs from graph-index.** graph-query counts its requests as input, because they are its only input
  and the finding asks for it. The shape is graph-ingest's nearest case, `meteredCanonicalMutation`
  (`canonical_mutations.go:39`): `CountInput(len(data))` on entry, and a refused request counts no error.
- **Where this differs from the pin.** `recordError` ran on every `RequestClassified` failure, refusals included
  (`pin:processor/graph-query/query.go:125-129`), so "no such entity" raised the pin's error count, and `recordSuccess`
  added the request and reply bytes together. Here only the request's bytes count, which is what
  `component.Lifecycle.CountInput` documents.
- **`ErrorCount` is not a stuck state.** It never lowers `Healthy` (ADR-109), so an outage shows in the count and `Health`
  stays running. `TestForwardCountsRequestsAndUnansweredOnes` asserts both.

A lost connection takes the same branch as the other failures with no answer. No test here produces one (`notes/3.2.md`,
"Every failure that is not a refusal gets one answer").
