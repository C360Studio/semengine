# Task 3.1: the request and the ranking

Developer notes on choices design D4 and D5 leave open, and the evidence behind the task's checks. Base `05ae5c2`.

## Premise

`pin:graphrag.go:2319-2397` read at `8b99efe9` (`gh api .../contents/processor/graph-query/graphrag.go?ref=8b99efe9`):
true as D4 and D5 state it. `filterEntitiesByQuery` lowercases, splits with `strings.Fields`, keeps a score at or
above the threshold and sorts with `sort.Slice` by score alone; `scoreEntityQuery` gives 1.0 for the type position
(`semtypes.ParseEntityID`, empty when the ID does not parse), else 0.5 for a substring of the lowercased predicates and
string values joined by spaces, over the term count. The pin's tests are `graphrag_test.go:347-458` at the pin.

## Choices

- **Where the terms live.** `decodeLocalSearchRequest` returns the request and its terms; the terms are in the order
  first typed, which the score does not depend on.
- **The level check.** The decoder calls `clustering.GroupKey` for the level, so the rule of which levels exist has
  one owner; the key is discarded here and read with the record in task 3.2. An `entity_id` error names
  `entity_id` (from `semtypes.ValidateEntityID`, run first), a level error names `level`, a query error `query`.
- **The text searched.** As the pin: each predicate and each string value, lowercased, joined by spaces. Since a term
  holds no white space, a match is within one predicate or one value, as D5 says. An object counts as a string only
  when it decodes as a JSON string; objects stay `json.RawMessage`, so a large integer is never converted.
- **A repeated ID** (#512) on a page is read once, its first copy, and counts once in `entities_scanned`.
- **An entity that does not decode** (for example triples that are not a list) refuses the whole ranking with an
  error, never a skip; task 3.2 classes it as a broken page.
- **The fit** is `fitLocalSearch(data, limit, encode)`: `encode` is the reply's own encoding (the envelope, in task
  3.2), and the answer is filled in for each candidate count, so `{n}` counts the entities kept. A reply shrinks as
  entities leave, so the count kept is found by bisection (about ten encodings at a 1,000-entity page, rather than one
  per entity). A reply that does not fit even with no entities is an error, for task 3.2 to class.
- **The answer's template (corrected after review M1 on `a51a09a`).** This corrects the owner-approved text of D5:
  `clustering`'s `summarize` (`graph/clustering/terms.go:104-122`) always writes a summary that already holds the
  member count and the themes, so the approved template printed both twice. The answer is now `Found {n} matching
  entities among {entities_scanned} read from {community_id}.`, then a space and the summary when set; with none,
  `It has {member_count} members.` and, with keywords, `Key themes:` and the first five. `{member_count}` is printed
  with `%d` (`7000`, not `7,000`). Design D5 and the spec requirement say the same.
- **JSON field shapes.** `community_summary` and `keywords` are `omitempty`, as on `clustering.Community`; `entities`
  is always a list (`[]` when nothing matches); `level` in the request is `omitempty`, so the zero value round-trips as
  omitted (level 0).
- **The pin's sort test** (`TestFilterEntitiesByQuery_SortsByScore`) ran at threshold 0. At the fixed 0.3 the sensor
  scores 0.25 and is dropped for "drone temperature"; the case keeps that query and adds "temperature sensor", where
  both are kept, the type match first.

## Generated checks

The score and the order are checked by named examples: their oracle is the pin's literal table and the probe log, and
the inputs do not interact beyond what the table covers. The decoder, which reads external bytes, has a native fuzz
target, `FuzzDecodeLocalSearchRequest`, whose invariant is: no panic; an accepted request has a valid ID, a level 0
to 2, 1 to 16 terms, each non-empty, without white space, within the lowered query, and not repeated. Seeds 0 and 1
are accepted, so the assertions run on seed replay. Seed replay passes in `task test:unit`. Exploration, separately:
`go test -run '^$' -fuzz FuzzDecodeLocalSearchRequest -fuzztime 20s ./processor/graph-query/` ran 992,147 executions
with no failure (local, Go 1.26 on darwin/arm64).

## Review fixes on `a51a09a`

- **H1, the query's cost.** `searchTerms` removed repeats over the whole query before the 16-term bound ran, a
  quadratic scan. It now iterates `strings.FieldsSeq` and stops at the 17th distinct term; the decoder's refusal is
  unchanged. Failing first, `TestLocalSearchTermsAreDistinctAndBounded` with a 1 MB query of distinct terms:
  `localsearch_test.go:168: searchTerms of a 1 MB query returned 144961 terms, want 17` (the test took 19.91 s).
  After the fix it returns 17.
- **M1, the template.** Failing first, `TestLocalSearchAnswerTemplate` and `TestLocalSearchFitKeepsTheBestThatFit`
  with the new literals failed against the old answer, for example `localsearch_test.go:279: answer with neither =
  "Found 3 matching entities among 40 read from acme.ops.src.docs, which has 7000 members.", want "Found 3 matching
  entities among 40 read from acme.ops.src.docs. It has 7000 members."`.
