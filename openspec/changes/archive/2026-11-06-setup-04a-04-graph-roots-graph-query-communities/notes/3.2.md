## Choices

- **Where the view lives.** `Component.communities` is an `atomic.Pointer` to the current view, nil while there is
  none. Only the supervisor stores it: before `Run`, and nil again once `Run` has returned, so a handler sees either
  no view or one whose `Get` reports its own state. The view's value type is `clustering.Community` (not a pointer), so
  a handler never shares a record with the projection.
- **The supervisor** (`community.go`) runs on its own goroutine under the run context; `start` begins it before the
  subscriptions, as graph-index starts its goroutines before subscribing. `cleanup` drains the subscriptions, ends
  the run context and waits for the supervisor under Stop's context; the handles are cleared only when all is
  released. The run context and a `supervised` channel are the two new handles; the lifecycle state stays in
  `component.Lifecycle`. The 5 s wait is a `time.Timer` that the run context ends, so a Stop during the wait does not
  wait it out. `TestStopEndsTheCommunityView/waiting_to_reopen` waits for the supervisor's first log record (logged
  just before the wait), then stops under a context of half the interval, marked `// Own deadline:` as the
  behaviour under test (`docs/testing.md`'s second reason). Review M2 on `49a6607`: the earlier version, with no
  bound, let a mutant whose wait ignored the context survive.
- **The supervisor's log** (review M4 on `49a6607`). Each failure is logged at `Warn` when it is the first, differs
  from the last one logged (compared by text), or follows a view that opened, and at `Debug` otherwise. This departs
  from the pin, which warned on every retry: until change 7 wires the writer, that would be one `Warn` every 5 s in
  every deployment. No metric: D6 puts no view error in `Health`, and task 3.3's counter is for truncation. Shown by
  `TestCommunityViewLogsEachNewFailureOnce` (first `Warn`, the same failure at `Debug` one interval later, a `Warn`
  for the lost watch after a view opened), through a capturing `slog.Handler` injected as `Dependencies.Logger`.
- **The decode** is `clustering.DecodeCommunity` with `keep` true; every key of `COMMUNITY_INDEX` is a record.
- **The page read** extends step 2's `readCountPage` to keep each row's bytes beside its ID (`countPage.rows`), so
  localSearch gets the same page checks as the counts, and the rows pass unchanged.
- **The record read happens before `min_revision`**, which happens before the page read (D2). The group key is
  recomputed with `clustering.GroupKey` after the decoder's check.
- **No record.** The entity read is `ask` on the entity verb with `{"id":...}`. Any success means the entity exists
  (index_not_ready); the reply is not decoded, since either outcome is a refusal. A refusal, or no answer, is returned
  as `ask` returns it, so no responder counts one error, as for the other composed verbs.
- **Errors.** A poisoned record and a reply that cannot be fitted to `max_payload` even with no entities, and a
  `MaxPayload` read failure, are graph-query's own transient `internal`, counted once (`unanswered`). A page that does
  not decode, or an entity in it that does not decode, is `brokenReply` naming the prefix subject.
- **The fit's encoding** is the envelope itself (`graph.NewQueryResponse` then `json.Marshal`), at
  `natsclient.Client.MaxPayload`: a success reply carries no headers (`natsclient/request.go`, the success path's
  `msg.Respond`), so the body is the whole message.
- **The `declaredRows` row for `localSearch`** names the prefix verb, its first downstream request once the view holds
  drone1's record. The five tests that send it (`TestHandlerBudgetEndsAForward`, `TestForwardedRefusalKeepsClassCodeDetail`,
  `TestNoRespondersIsTransient`, `TestQueryTimeoutIsRead`, `TestGraphQueryServesExactlyTheDeclaredVerbs`) publish that
  record through a real maintainer before Start (`withCommunityRecord`) and wait for the view with
  `awaitCommunityView`, a request far ahead refused `revision_not_reached`, which reads nothing downstream and counts
  no error. `startStack` was split so `startCommunityStack` can create the bucket before graph-query starts.
- **The lifecycle suite** adapter reports a "community view" handle while the supervisor is held; the failing owner
  now runs the component's own `start`, so its rollback releases the supervisor too.
- **`TestLocalSearchDuringBlockedTick`** writes the next record of one group straight to the bucket, as D3 lists.
- **`TestLocalSearchRefusesAfterWatchLoss`** deletes `COMMUNITY_INDEX` under a live view, twice. At the pinned nats.go
  the loss was seen about 20 s after the delete (log: `stream not found: recreating ordered consumer`, then the watch's
  channel closed); that delay is observed, not promised, and the test waits on the refusal, not on time.
- **Generated checks.** Not used: the view's history has four transitions (missing, caught up, lost, stopped), each
  driven by a named test, and the request's interacting inputs were 3.1's.

## Not covered

- A `Stop` whose context ends while the supervisor is in `Run`'s watch drain: the lifecycle suite's generic case covers
  a Stop that ends first; no test holds the drain itself.
- A view whose `WatchAll` opens but never catches up: refused `index_not_ready` by `graphview`'s own tests, not here.
- That deleting a bucket loses the watch is shown at the pinned versions by `TestLocalSearchRefusesAfterWatchLoss`;
  across versions it is not promised.

## Codex review

Codex's review of task 3.2 (PR #524 comment 6684534734) had two findings; both mutants it reported as survivors are
now detected.

- **HIGH: Stop discarded a watch-cleanup failure (#527).** `superviseCommunities` now returns what ended it:
  `shutdownFailure` (`community.go`) gives nil for a view that never opened, or one whose `Run` returned the
  cancellation alone (`Run` returns `ctx.Err()` itself), and `Run`'s error otherwise, the case where `Run` joined a
  `kvwatch.Stop` failure to the cancellation. The supervisor's goroutine stores that in `supervisorErr` before it
  closes `supervised`; `cleanup` reads it after the close and returns it wrapped with `%w`, so `errors.Is` finds both
  `context.Canceled` and `kvwatch.ErrDeliveryOpen`. The failure is reported by that Stop only: the handles and
  `supervisorErr` are cleared, so the next Stop returns nil, since the supervisor has returned and there is nothing
  to retry (in-house review of `325b3ff`, which kept the handles and so failed every later Stop; owner ruling Q4, #9
  comment 6278986482, the same case in `config/manager.go`). A watch lost as Stop cancels (`graphview.ErrWatcherLost`
  without `kvwatch.ErrDeliveryOpen`) is a clean end too, also from that review.
- **How the tests reach it.** No real path makes `Run` return a joined failure on demand: the trigger is the nats.go
  window of #454, not reproduced, and making it happen would need a seam in production code. So the joined error is
  reached two ways. `TestShutdownFailureKeepsAWatchCleanupFailure` (unit) checks the rule on a hand-built join and the
  three clean ends. End to end, Codex's own mutant of `pkg/graphview/view.go` (`return errors.Join(runErr,
  kvwatch.ErrDeliveryOpen)`) now fails `TestStopEndsTheCommunityView/a_view_running`, whose Stop must return nil, with
  the joined error at Stop's caller. That test now calls Stop twice and reports the first with `Errorf`, so under the
  mutant the second Stop runs too: it returned nil (the verbose overlay run below). No in-tree test drives a real
  joined failure through Stop.
- **MEDIUM: the Start-context check could not see an ended supervisor.** The lifecycle suite's adapter
  (`lifecycle_integration_test.go`, `Observe`) now reports the community view only while `supervised` is open, not
  merely set. Test code only; production is unchanged for this finding.
