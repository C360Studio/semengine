# Task 3.3: the truncation counter

Developer notes on choices design D6 leaves open, and the evidence behind the task's checks. Base `0971411`.

## Premises

Checked before coding. `processor/graph-query/localsearch.go` set `EntitiesTruncated` from the page's continuation and
from `fitLocalSearch`; `pathsearch.go` set `Truncated` in `walkPaths`; `processor/graph-index/metrics.go` is the
`RegisterOrGet` pattern; `component.Dependencies.MetricsRegistry` (`component/dependencies.go:44`) was not yet read by
graph-query. Issue #506 names "count cut-short searches in a metric" as the number that says when it is due.

## Choices

- **Which verbs.** `localSearch` only, as the spec counts "an answer with `entities_truncated` true" and #506 needs
  only it. A first version also counted `pathSearch`; review removed it as beyond 3.3.
- **When it counts.** After the reply is built, so a refused request or a failed encode counts nothing. `localSearch`
  counts the reply it sends, which is truncated if the page had a continuation or matches were left out to fit.
- **`fitLocalSearch` now returns whether the reply is truncated** (a second result), because the count kept is found by
  bisection inside it and the handler cannot tell otherwise whether matches were left out. Its unit test asserts it.
- **Nil registry.** The collector is built and counts but is registered nowhere (as graph-index does), so handlers never
  check for nil. The test shows the global registry gathers no such series.
- **Layout.** `metrics.go` (`queryMetrics`, `newQueryMetrics`), the component field `metrics`, built in
  `CreateGraphQuery`. A registration failure refuses construction.
