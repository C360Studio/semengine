# Task 2.1 notes: wire types

Choices the design leaves open:

- **Tags follow the pin.** `query`, `limit`, `entity_id` carry no `omitempty`, and `scope` does, as at the pin
  (`pin:processor/graph-embedding/query.go:52-81`) and as `TemporalRangeRequest.Limit` already does. Any request the pin
  accepted with these keys decodes the same way.
- **The counts are always sent.** `unreadable_records` and `failed_records` have no `omitempty`: the spec says they
  SHALL be the number, and a 0 is the answer that nothing was left out. They are `int`, like the tree's other limits
  and counts in `graph/query_*_types.go`.
- **Which unknown keys the test refuses.** `entity_id` sent to `search` and `scope` sent to `similar`, the one key each
  request has and the other lacks.
- **Trailing data is not tested here.** A struct cannot refuse bytes after its object; the responder's decoder does.
  `TestRequestsDecodeStrictly` in `graph` proves the type's half (every key round-trips under `DisallowUnknownFields`,
  `min_revision` included; an undefined key is refused by name). The trailing-data case of D1 needs the handler, so it
  goes with task 2.3's handler tests in `processor/graph-embedding`.
- **`graph/query_search_types.go:5-9`** (the file comment saying the responders arrive later and that `IndexedRevision`
  is theirs to settle) is left for task 3.1, which lists it; the responders arrive in 2.3.
