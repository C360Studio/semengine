## Choices the design leaves open

- **Where the gate runs.** `queryReady` runs after the entry checks and before the first read (the embedder, the
  bucket, the cache), as graph-index's `queryRevision` does. A malformed request is refused `invalid_request` whatever
  the readiness, and 2.3's never-started unit tests keep reaching only the entry checks.
- **The lost cache watch in the handler.** `search` would be refused by the cache itself after a loss (its view is
  stopped), but `similar` reads its source from `EMBEDDING_INDEX` before the cache and would answer
  `embedding_unavailable` or `internal` from a deleted bucket. So `queryReady` also refuses on the `cacheLost` latch,
  the same fact Health names. The latch is set before the log line, as for the Worker. Between the watch closing and
  the latch being set (the cache's `Run` returning), a `similar` can still read the bucket: that window needs
  nats.go's close timing and names no real-world trigger beyond an operator deleting the component's own bucket
  (#185); not promised beyond the latch.
- **Order inside `queryReady`.** The follower first (a reset is fatal and outranks a transient refusal), then the
  cache latch.
- **`failedMap.withheld`** walks the failures under the map's lock, as `repairTargets` does; it is called once per
  request, beside `workerFailures`, which takes the lock again. The two reads are not one moment; a reply's
  `failed_records` may be one entity off a concurrent hop-1 change. Not taken further.

Every cross-goroutine read waits on its event: a reply (`awaitAnswer`, `probe.Await` on the request), the floor
(`awaitIndexed`), the failed map (`awaitFailed`), the gated store's `opened` channel, or the lost-watch log line, which
the component writes after the latch under the log buffer's lock. No sleeps, no test deadline.

**The request in flight during Stop.** The `similar` request is held in the follower's `QueryReady` at its "query
deferred" debug line, through a `slog.Handler` given as `Dependencies.Logger` (the production seam), which holds that
one record and no lock. `search` is drained first, so `search` answering no responders says Stop is draining
`similar`. At that moment Stop has not returned and the Worker's body read has not seen the run context end; both are
deterministic for the code as written. Released, the request is answered (`index_not_ready`, the build being held),
not lost, and Stop returns nil.
