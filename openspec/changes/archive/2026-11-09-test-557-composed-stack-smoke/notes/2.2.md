# Task 2.2 notes: `TestSmoke_StackRestartKeepsAnswers`

Developer notes on the choices design D6, case 1, leaves open, the reindex counter (#108), and the "shown to fail"
run design D7 asks for.

## Choices the design leaves open

- **The restart reuses the first boot's ports.** The first run of the test gave the second child two newly picked
  ports and failed at its health read: `connection refused`. The second child's log shows why: it reads
  `Synced configuration from KV` and serves on the first child's ports. After the first boot, `config.Manager`
  takes the configuration from its bucket, not from the file, so a port changed in the file has no effect.
  "The same configuration" therefore includes the ports: `restartStack` boots the new child on the previous child's
  two ports, and refuses to start while the previous child is still alive. This is one more fact a product's own
  `main` has to know (task 3.3, adopter gap).
- **The platform ID is required to be the same after the restart.** The second child reads the minted ID from the
  configuration bucket (`Adopted platform identity`). The test fails at once, naming both IDs, if it differs.
- **The writes after the restart** are `newDrone` (`drone.009`, homed at `base.003`, which had no edge until then)
  and `editedDrone3` (drone 3 renamed, edge kept). `checkWritesAfterRestart` publishes both, waits on the order
  design D5 sets, checks health, and checks the answers: the first batch plus the two writes. Tasks 2.4 and 2.5 can
  use the same helper. Stale state cannot pass it: `awaitIndexed` reads the `ENTITY_STATES` revision after the two
  writes are acknowledged, so the `GRAPH_STATUS` envelopes the first process left, at a lower revision, are not
  enough. The new entity has no record from before, and the edited entity's record must carry the edit's
  `kv_revision`.
- **No answers are checked between the restart and the new writes.** There is no write to order such a check after,
  and the envelopes the first process left would read ready (design D5). The spec scenario checks the answers after
  the new writes, and that check covers the old answers too: `checkAnswers` reads every entity in the first batch.
- **Not checked:** the same exclusions as task 2.1.

## graph-index's reindex counter (#108)

Recorded, not asserted (design D4). `semengine_graph_index_reindex_events_total`, read from each child's
`/metrics` after its checks, in a passing run:

```text
first process:  {result="changed"} 12
second process: {result="changed"} 13, {result="unchanged"} 1
```

The counter starts at zero in each process. Its baseline, the last projection indexed for each entity, is held in
memory (`processor/graph-index/component.go:83-85`, `index.go:442-451`), so the second process counts the 12
entities it replays as `changed`, then the new entity as `changed`, and the edit as `unchanged`. The edit only
renames drone 3; the counter's projection did not change, which suggests `fleet.identity.name` is not one of
graph-index's name predicates. That reading is not checked here.
