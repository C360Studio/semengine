# Task 3.2 notes: `semantic` and `similar` in `checkAnswers`

Developer notes on the choices design D9 leaves open, and the "shown to fail" runs design D7 asks for.

## What #558 serves

PR #558 (67a8650) gave graph-embedding two verbs, `graph.embedding.query.search` and `graph.embedding.query.similar`,
which graph-query forwards as `semantic` and `similar` (`processor/graph-query/query.go:32-33`). Both answer from an
in-memory vector cache of `EMBEDDING_INDEX` (`graph/embedding/vector_cache.go`), drop every hit scoring 0
(`processor/graph-embedding/query.go`, `rank`), and claim no `ENTITY_STATES` revision: `indexed_revision` is always 0,
and `min_revision` above 0 is refused (change 5 PR B design D4).

## What is asserted, and why not scores

The BM25 statistics live in memory and depend on the order documents arrive (`graph/embedding/bm25_embedder.go:119-123`),
so a record embedded before a restart and one embedded after it are weighted against different statistics. No check
reads a score, a vector, or the order of two hits that both score above 0. What holds through a restart is which
entities score above 0: graph-embedding embeds only the name (`namePredicate` ends in `.name`), and an entity scores
above 0 exactly when its name shares a word with the query, since the IDF floor is 0.01, never 0
(`bm25_embedder.go`, `computeBM25Vector`). That rests on the fixture's words landing in distinct vector dimensions.
They do, at the default 384 dimensions (FNV-1a, computed for every word in every fixture name: falcon 296, kestrel 49,
osprey 107, harrier 270, merlin 26, hobby 23, lanner 141, saker 321, north 260, south 250, east 188, west 174,
field 359, peregrine 304, two 169, gyrfalcon 224). A new fixture name whose word shares a dimension shows as an extra
hit, a loud failure naming both entities.

`checkSearch` (`internal/smoke/smoke_integration_test.go`), called last in `checkAnswers`, so in every restart case:

- **Keywords.** Each entity, live or deleted, gets the last word of its name that no other entity's name holds:
  `falcon`, `north`, and for the edited drone3 (`Osprey Two`) `two`, which only its current record holds.
- **The wait.** One `semantic` on every keyword, limit 100, waited on until it answers exactly the live entities. This
  is the cache's ordering event: the reply claims no revision, so the earlier waits (graph-embedding's envelope at the
  `ENTITY_STATES` revision, the records read) do not order a read of the cache, which applies a record after it lands
  in the bucket. The cache exposes no position of its own; its answer is the only event, as graph-embedding's own
  tests use it (`processor/graph-embedding/query_integration_test.go:49-55`). Each keyword is held only by its
  entity's current record, so a reply holding every live entity and no deleted one is read after the cache applied
  every record `checkEmbeddingRecords` read and every delete. Before the cache's first snapshot the verb refuses
  `index_not_ready` and is asked again; a lost cache watch (`restart the process` in the refusal) fails at once.
- **Then one request each, no waiting:** the wait's reply names `bm25` with 0 unreadable and 0 failed records;
  `semantic` on each keyword answers that entity alone (so it is the top hit, unambiguously), and a deleted entity's
  keyword answers nothing; `similar` on each live entity answers the other live entities whose names share a word,
  compared as sorted sets (the four bases share `field`; every drone answers none), because their order depends on
  the statistics each record was embedded under; `similar` on a deleted entity refuses `embedding_unavailable`
  naming it.

Rank: only a single-hit answer is checked for order, where the corpus makes the top hit unambiguous. The order of
the bases under `similar` was not measured across restarts; it is read from the code as statistics-dependent, so
membership only.

## The `EMBEDDING_INDEX` read stays

The verbs report which entities match, not the revision a record was made from. `checkEmbeddingRecords` is the only
check that each record is the entity's current revision's (`SourceRevision` equal to the `entity` verb's
`KVRevision`) and that a deleted entity's record is gone from the bucket, not only from the cache. Design D5's
declared read stays.
