# Task 2.3 notes: the component

## Choices the design leaves open

- **Files.** `config.go` (Config, strict decode, `queriesPort`, as `processor/graph-query/config.go` does for its
  input), `component.go` (factory, `Register`, lifecycle, route, HTTP status), `resolve.go` (the four resolvers and
  their checks). The config schema variable is `configSchema`: `schema` is the GraphQL schema from task 2.2.
- **Subjects.** The factory looks up each root field's graph-query row in `graph.QueryVerbs()` and fails construction
  if one is missing, so no subject is spelled in the package and a removed row cannot leave a field unserved at
  request time.
- **Registration.** `Type: "gateway"`, `Protocol: "http"`, as the pin's (`component.go:445-455`).
- **Lifecycle.** `Start` acquires nothing: the shell's start function is a no-op and cleanup is `CloseAdmission`, then
  `Wait(ctx)`. The handler refuses with 503 while `Health().Healthy` is false; the gateway passes no stuck state, so
  that is exactly "not running" (before `Start`, and from the moment cleanup begins). Both refusals write the same
  text, `graph-gateway is stopping`, as plain text with `Connection: close`, as `httpadmission.Wrap` does.
- **Order of checks in the handler.** Admission (503), running (503), method (405 with `Allow: POST` and a GraphQL
  `errors` body), body decode (400: not one JSON object, or data after it), then `execute`. Variables are decoded with
  `UseNumber`, so gqlparser coerces an `Int` variable to `int64` exactly.
- **Deadline.** The request runs under `context.WithTimeout(r.Context(), query_timeout_ms)` and the same budget is
  passed to `RequestClassified`, as the pin did (`component.go:2131`, `:2214`).
- **Status mapping.** `classify` reads each resolver error: a `*errs.ClassifiedError` anywhere in the chain fills
  `extensions` with `class` and `code` (ADR-060). A request that got no reply is a `noAnswer` (unexported) naming the
  subject, wrapped as transient/`internal` like graph-query's own (`processor/graph-query/query.go`); it answers 504
  `request timeout` when it wraps `context.DeadlineExceeded`, else 500. A refusal the responder sent keeps its class,
  code and detail and answers 200. A failed D2 check answers 200 with the field null; `graph.UnmarshalEntityState`'s
  refusal keeps its `graph_state_reset_required` code in `extensions`. Each 500/504 counts one error on the shell;
  each POST counts one input (`ContentLength`, 0 when unknown).
- **400 from a resolver.** A null `predicates` item, or an `Int` outside 32 bits, is an `argumentError`; `classify`
  turns it into HTTP 400 and the answer drops `data`, as D6's 400 row (only `errors`). Nothing is sent. A single
  string where `[String]` is declared is coerced to a list of one (GraphQL input coercion).
- **Argument validation.** The gateway does not re-run the entity-ID, prefix or predicate validators: graph-ingest,
  graph-index and graph-query refuse at their entry with a classified refusal, which reaches the client with its
  class and code (`TestGatewayAnswersFourOperations`, "a field name inside an argument"). Validating here too would
  be a second interpreter of the same grammar.
- **Empty lists.** A reply's nil Go slice (graph-index's value filter answers `"entities": null` when nothing
  matches, `processor/graph-index/query.go:349`) answers `[]`: the typed reply is decoded first and the answer is
  built from it (D2), and a nil slice is Go's empty set. Proven by the `value: "nothing"` case.
- **Triple fields.** `timestamp` is RFC 3339 with nanoseconds; `source` and `confidence` are always present (the
  stored-value rule requires a source).
- **Paths.** `pathsOf` builds `paths[k]` as the path of the earlier entity `edges[k-1]` came from, plus that edge as
  the graph holds it. A reply with no start, an edge count other than one fewer than the entities, an edge not
  touching its entity, an edge from a later entity, or an entity listed twice is refused, never answered in part
  (`TestPathReplyBreakingAlignmentRefused`).
- **Lifecycle suite** runs in a unit test (`lifecycle_test.go`) with a client that never connects: the gateway holds
  no NATS state. Its adapter reports admitted requests; `TestStopWaitsForInFlightRequest` shows a started gateway
  reporting one ("Started owner reports its handles").
- **Tests added beyond the task's list:** `TestPredicatesRefuseANullItem`, `TestPathReplyBreakingAlignmentRefused`,
  `TestRequestBodyRefused`, `TestConfigTimeoutDefaultAndRange`, `TestRegisterAddsGraphGateway`,
  `TestCreateGraphGatewayRequiresNATSClient`, `TestLifecycleBeforeStart`.

## Generated checks

Not used. The one law with interacting cases is the path alignment (`paths[k] = paths[parent(k)] + edges[k-1]`): its
cases are the direction an edge is crossed (with and against, `TestPathsFollowEdgesBack` depth 1 and 2,
`TestGatewayAnswersFourOperations` outgoing depth 2) and each refused shape, one named example each. The projection
law is task 2.2's rapid check.

## Wall clock

`TestQueryTimeoutIsRead` asserts the 504 arrives within 20 s with `query_timeout_ms` 50: the timeout is the behaviour
under test, and 20 s is 400 times the configured value, well under the 60 s default a mutant falls back to. Every
other wait is on an event: `probe.Callback` for the held verb, `probe.Await` on the shell reporting stopped (cleanup
has begun), and Stop's return before the in-flight answer is read (Stop's wait observed the request's return, which
wrote the answer).
