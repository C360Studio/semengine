## Choices the design leaves open

1. `TestSingularFindsPlural` and `TestJoinedIdentifierIsNotHeld` now go through `Put` and `Search`: each writes one
   entity and requires the query to return exactly that entity (and `withretry` to return nothing), which is the
   spec's "the query returns the entity". `holdsAny` is gone from `tokens_test.go`.
2. A query in this task is built inside the package's tests (`plainQuery` in `index_test.go`, the distinct words of
   `Tokens`), because `ParseQuery` is task 2.3. `Search` with a zero `Query` matches nothing and returns no error,
   which agrees with the spec ("holds at least one plain word or phrase word"). Task 2.3 decides whether
   `ParseQuery` alone builds a `Query`; `Search` relies on its words being distinct.
3. `NameWeight` is 2 for now, the smallest value task 2.4 sweeps. The unit tests do not depend on the value:
   `TestSearchRanksByBM25` uses Body text only, and the model and `TestNameOutranksBody` read the constant. Task 2.4
   sets the measured value.
4. The sum of weighted lengths is kept as an integer that each write adds to and subtracts from. It is exact, so
   equal held sets give equal averages whatever the history (`TestPropRankingIgnoresHistory` compares scores with
   `==`), and the average is still worked out from it when the search runs. Entity count and each word's entity count
   are the sizes of the maps at search time.
5. An empty string inside `Scope` matches every entity and is not refused, as `graph.MatchesAnyIDPrefix` treats it.
   Every other prefix goes through `semtypes.ValidateEntityIDPrefix` before the lock is taken.
6. `TestSearchBreaksTiesByID` is an extra example: the spec orders by score, then ID, and the hand-worked test has no
   tie.

## Generated checks: decision

The index has an order-dependent history (replace, empty write, delete) and a stated law (results depend only on the
held entities), so both get generated checks against a test-owned model: `model` in `index_prop_test.go`, a
`map[id]Document` with BM25F worked naively by splitting on white space. The vocabulary is closed (lower case, no `s`
or `x`, never ending in `e`, no stopword), so tokenizing changes nothing and the model needs no tokenizer. Scope in the
model is its own dot-boundary match, not `graph.MatchesAnyIDPrefix`.

## What makes each assertion run

- `TestPropIndexMatchesModel`: 4 named witnesses before `rapid.Check` (a replaced document, an empty write and a
  delete, scope with limit 1 over an out-of-scope match, a tie broken by ID). Generated: up to 20 writes or deletes
  over 6 IDs in two scope families, then 1 to 4 queries of 1 to 4 words from 14 (4 never written), with one of 5
  scopes (none, a family, one ID, two prefixes, the empty prefix) and a limit of 1 to 8. Every query checks `Len`,
  `Matched`, the hit count and each hit's score and position; an empty answer still checks `Matched` against the
  model.
- `TestPropRankingIgnoresHistory`: 1 named witness (three entities, two extras written and deleted, each entity first
  written with junk) before `rapid.Check`. Generated: 1 to 6 final entities, a permutation of their write order, 0 to
  4 extra entities and a junk document per entity. Every query compares both answers exactly.
- `TestPropAbsentWordsMatchNothing`: 4 named witnesses (a word never written, a deleted word, a replaced word, an
  emptied entity's word) before `rapid.Check`. Generated: a history as above; the query draws only from words the
  model says no entity holds, never empty because 4 vocabulary words are never written.
- `TestSearchDuringWrites`: the two answers per query come from fresh indexes before any goroutine starts, and the
  test fails if a query cannot tell them apart. The writer starts first; the 4 searchers start after its first write
  and do 5,000 searches each, and the writer stops only when they are done, so every search runs while writes go on.

Each ran through `task mutate:check` on `graph/lexical/index.go`: 3 baseline, 3 mutant and 1 after-run, `-cpu 1

The split-lock mutant first survived three runs when the searchers did 500 searches each; at 5,000 it failed 20 of 20
by hand (`-cpu 1` and `-cpu 4`) and 3 of 3 under `task mutate:check`. Detection of a torn write stays a matter of
scheduling, not a certainty.
