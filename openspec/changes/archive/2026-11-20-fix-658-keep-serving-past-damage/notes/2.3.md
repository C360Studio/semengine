## Choices the design leaves open

- **Which count sets `truncated`.** The reply's own `damaged_entities`, the largest of every reply it was built from
  (task 2.2): the word search; for `searchGraph` at tier 1 the embedding search when its list was used; and the
  alias read or the walk of an honoured hint. A count from a hint read alone (word search at 0) still sets
  `truncated`, since the reply holds what that read gave; the test's "the alias read at 3" case holds it.
- **The hint is now read before the text is built,** so its count can set `truncated`. It is still read after the
  batch read, so a refusal of the word search or the batch still reaches the caller before any hint is read.
- **The truncation counter.** `semengine_graph_query_search_truncated_total` counts each reply sent with `truncated`
  true, so a reply truncated only by damage adds one, as every other reason does. While an entity is damaged the
  counter rises with every unscoped search, which is the design's stated cost of Q2. Counting damage apart would need
  a second counter, which the design does not ask for.
- **`searchGraph` answered from the embedding search alone** has `text` null, so no `truncated` to set; it carries
  the count (task 2.2).
