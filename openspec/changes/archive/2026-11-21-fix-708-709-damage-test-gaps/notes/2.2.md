# 2.2 notes: concurrent report and clear of one key

## Shape

`TestConcurrentReportAndClearOfOneKey` (`internal/damage/record_test.go`) raises GOMAXPROCS as the Health test of
task 2.1 does and stays out of `t.Parallel`. Eight goroutines wait on one channel, then each makes 100
`Report`/`Clear` pairs on key `k`. Every clear's bound is B = 1000. Worker `w` reports `B-w`, `B-w-8`, and so on,
falling; only worker 0 reports B itself. Each revision has its own refusal value. After `wg.Wait` the test asserts
the key is recorded at B with B's refusal, and `Len` is 1.

The rule checked holds in every order: once a report at or above B lands, no clear at B drops it and no lower report
replaces it. The layout is chosen so each wrong rule shows in every order, not only in some:

- No report is above B. With one above B, a `Clear` that drops entries at its bound would never meet an entry at B
  after the join, and that mutant would survive.
- Every worker ends with a clear, after its lowest report. A `Report` that lets a lower revision replace a higher
  one leaves the last report overall, always below B, as the entry, and a later clear drops it.

Generated checks: not used here. `TestPropRecordFollowsLatestEvent` already checks every order of calls against a
reference model one call at a time; this test adds overlap, and its assertion holds whatever the order.

## Mutation checks

Both with `task mutate:check -- -pkg ./internal/damage -test TestConcurrentReportAndClearOfOneKey -file
internal/damage/damage.go -mutant <copy> -expect record_test.go:226`, which runs `-count=1 -cpu 1 -race`.

- (a) `Report` keeps no highest revision: the `revision < current.Revision` early return removed (and `current`
  dropped so the copy builds). **Detection**, 3 of 3 mutant runs failed with `record_test.go:226: Get("k") = not
  recorded, want recorded at 1000`; baseline 3 of 3 and after-run passed. The first attempt left `current` unused,
  and the verdict was invalid (does not build); that copy was fixed and re-run.
- (b) `Clear` drops entries at its bound: `current.Revision >= below` changed to `current.Revision > below`.
  **Detection**, 3 of 3 mutant runs failed with the same line; baseline 3 of 3 and after-run passed.

## Not covered

Neither mutant needs overlap to be caught, by design: the test shows the rule holds while calls overlap under
`-race`, and the race detector covers unsynchronised access. Whether the calls actually overlapped on a run is not
measured. Older single-key tests in the file (`TestLowerReportIsIgnored`, `TestClearAtRecordedRevisionKeeps`)
may also catch these mutants; that was not run.
