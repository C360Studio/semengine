# Tasks 4.1 and 4.2 notes: graph-ingest on `damage.Record`

## The gauge (the choice the design leaves to the developer)

The gauge is set by `setEntityPoisonGauge` (`processor/graph-ingest/poison_inventory.go`), called only after a
`Report` that recorded a new key or a `Clear` that dropped one. It takes a graph-ingest mutex, `poisonGaugeMu`, reads
`entityPoison.Len()` and sets the gauge under it. Why this is enough: every change to the size is followed by its own
gauge write, so the last write in lock order comes after every change and reads the final size. Without the mutex, a
goroutine could read an older size, be overtaken by a newer write, and write its older size last.

Rejected: `Inc` on a new report and `Dec` on a drop. It needs no lock, but the gauge is shared through
`metric.RegisterOrGet`, so a gauge already holding a value from an earlier component on the same registry would stay
off by that value for good. A `Set` from the current size corrects itself on the next change.

## Other choices

- `dropEntityPoisonRecord(id, proofRev)` calls `Clear(id, proofRev+1)`: a proof at a revision covers that revision.
  A `proofRev` of the largest `uint64` would wrap to 0 and drop nothing, which keeps the entry (fails closed); KV
  revisions do not reach it.
- Health's message and `DebugStatus` both read `Sorted(0)` (see "Health departs from D4" below). The reason
  comes from `errors.As` on the stored refusal (`poisonContractError`), which is always the stamped
  `*graph.StateContractError` `recordEntityPoison` reported.
- The fast paths (Health, `writeFailed`, the three clear paths) check `entityPoison.Len()`, one atomic load.
- `component.go`'s `entityPoisonMu`, map and `entityPoisonSize` are gone; the boot sweep keeps `entityPoisonRecord`.

## Health departs from D4

Design D4 says the Health message comes from `Len` and `Sorted(10)`. Two reads let a report or repair land between
them, so the count and the named IDs disagree: review found it, filed as #705, and the owner ruled to fix it in this
pull request. `entityPoisonHealthMessage` now takes the count and the first 10 from one `Sorted(0)` read, as the
follower's Stuck sentence does (`notes/3.1.md`) and as the code before this change did under one lock. The cost is a
copy and sort of every entry per Health call while any is recorded, the same as before this change. The approved
`proposal.md` and `design.md` are left as approved; this note records the departure.

`TestHealthCountMatchesNamedIDsWhileChanging` (`poison_report_test.go`), adapted from the #705 reproduction, reads
Health while one key is reported and repaired 100,000 times with a second key recorded throughout, so every Health
read carries a poison message and the assertion runs on each one. It asserts the count equals the IDs named and no
"more" is claimed.

- At `9a39600720bec3be84d64604cfb9a4ff783b06c1` (two reads), with the test added:
  `go test -race -count=1 -cpu=4 -run '^TestHealthCountMatchesNamedIDsWhileChanging$' ./processor/graph-ingest`
  failed 3 of 3 runs, for example:

  ```text
  poison_report_test.go:145: Health count 1, 2 IDs named: "graph_state_reset_required: 1 poisoned entity
  (per-entity refusal; repair = delete + recreate): acme.ops.test.system.widget.anchor (unreadable_entity_state),
  acme.ops.test.system.widget.flicker (unreadable_entity_state)"
  ```

  At `-cpu=1` without `-race` it passed 3 of 3: the interleaving needs a second processor. `task test:unit` and
  `task test:repeat` both run at one CPU, so in those gates the test guards the fix only weakly; run it at
  `-cpu=4` to see it bite.
- After the fix, the same command passed 3 of 3, with `TestHealthNamesTenPoisonedEntities`.
