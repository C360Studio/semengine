# 2.2 Choices the design left open

- **The shared step.** `askBoth` (`processor/graph-query/merge.go`) sends both searches, awaits the word search,
  runs the caller's word-ID check before the embedding reply is awaited, and reads the embedding reply.
  `bothSearches.merge` merges or falls back to the word list; `declareMergeFailed` logs and counts. searchGraph's
  `mergedText` and mergedSearch's `mergedIDs` both call them. searchGraph passes `query_timeout_ms` as the embedding
  wait and no scope, so its requests and replies are byte-for-byte as before; its wait is #712.
- **The Warn.** Its message and reason are built from the verb: `<verb> answered the word list alone: the embedding
  search failed`, so searchGraph's text is unchanged and mergedSearch's names itself.
- **ID checks.** mergedSearch has no community level, so it checks hit IDs with `semtypes.ValidateEntityID` where
  searchGraph groups them (`groupAt`, which refuses the same IDs at the levels it accepts).
- **Word index not ready.** Results are the embedding list in its order, scored as a merge with an empty word list
  (1 / (60 + place)) and cut to the limit. An embedding hit with a broken ID there counts as the embedding search
  failing too, so the `index_not_ready` refusal is returned.
- **Tier 0.** The word search gets the request unchanged (its own limit, not 100), as searchGraph's tier 0 does.
- **Reply type.** `graph.MergedSearchHit` is new rather than reusing `graph.LexicalHit`, whose doc says its score is
  BM25F; a merged hit's score is not.
- **Registration.** mergedSearch is served whenever the table has graph-lexical's `search` row; it needs no batch row.
