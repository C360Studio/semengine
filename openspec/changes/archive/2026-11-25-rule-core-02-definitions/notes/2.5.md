## Choices the design leaves open

- **`Load` returns `*Rule`**, as the target-shape page sketches. `Rule` holds the definition with its conditions
  compiled and its action lists emptied, and five lists of checked actions, each with its `when` compiled and its
  firing-cap key. No field has a reader yet; the engine that fires rules reads them.
- **The checked action is the one `decodeAction(Body)` returns**, not the caller's: after the fields-to-`Body` check
  they say the same, and the decoded one has its own `When` slice and `Body` copy, so compiling it never reaches the
  caller's definition. Conditions are copied, then compiled one element at a time, so a refusal names
  `conditions[<i>]` or `on_enter[<i>].when[<j>]`.
- **Rule types.** `expression` gets the factory checks (at least one condition, field, known operator, logic `and` or
  `or`, cooldown a duration). `cron` disabled gets only the checks every rule gets. Any other type, empty included, is
  refused naming the type: the pin had no factory for it and skipped it with a log line.
- **Checks every rule gets**, enabled or not, cron included: the handler set, the ID as one KV literal token,
  `fire_every_n_events` 0 or more, `rerun_on_recovery` with an action to re-run, the entity pattern, the ADR-036
  condition-field check and compile of each condition, and every action.
- **Order inside one action:** body present, body decodes, fields equal to the body, `max_iterations` 0 or more,
  type in the set, the handler's `Check`, then each `when`. The first refusal is returned.
- **"Negative `max_iterations`"** in task 2.1 is read as the action's `max_iterations`, the one the spec bounds. The
  rule-level `max_iterations` is a value conditions read and is not checked, as the pin did not.
- **The condition-field check covers rule conditions and every action's `when`** (corrected by the review of record;
  see "Action guards and repeated keys" below). Inside one action the order is now: body present, body decodes,
  fields equal to the body, `max_iterations` 0 or more, type in the set, the handler's `Check`, then for each `when`
  condition the field check and its compile.
- **Case variants of rule keys are refused at decode** (ruling on step A's open question 1): after the strict struct
  decode, the top-level keys are compared exactly with `Definition`'s JSON tags (read by reflection, so the list
  cannot drift), naming the key as `json: unknown field "ID"`. Still matched without regard to case: keys inside
  `entity`, a condition, or a `when` condition (`"Field"` is taken as `field`). Open for the reviewer whether those
  get the same check.
- **Test predicates** are declared by `declareTestPredicates` in `builtin_test.go`, called at the start of each test
  that needs them, never from `init`; registering one again amends nothing.

## Step C: exact keys in entity, conditions and `when`

The open item above is ruled: the keys inside `entity`, each condition and each `when` condition are
compared exactly with their JSON tags, as rule keys are. A key spelt with another case (`"Pattern"`, `"Field"`,
`"Operator"`) is refused, naming the key and its position: `entity`, `conditions[<i>]` or `when[<i>]`. The key sets are
read from `EntityConfig`'s and `expression.ConditionExpression`'s tags by reflection, the same way the rule-level set
is. A `when` condition still names only `when[<i>]` at decode: the decode does not know the action's list position,
and `Load` names it.

## Action guards and repeated keys

The cross-agent review of record at `f9590256` found two ways past the load boundary, each reproduced with a probe
test.

**Action guards.** A predicate moved from `conditions` into `on_enter[0].when` loaded even when it was rule-opaque,
and the evaluator then matched the private value. ADR-036, which the design keeps, bars private content from every
condition a rule branches on, and a `when` is one. `loadAction` now runs `checkConditionField` on each `when`
condition before compiling it, and a refusal names `<list>[<i>].when[<j>]`.

The same check, not a narrower one, applies to both paths: a field starting with `$` is read from the message or the
rule's state and passes; any other field must be a declared predicate that is not rule-opaque. The declared-predicate
half applies to a `when` for the same reason it applies to a condition: a bare name the vocabulary does not know is
either a typo or a message field written without `$message.`, and the evaluator would read the entity's triples first.
No fixture or consumer rule in the tree has a bare undeclared name in a `when` (the semboids and rule-family packs
still load).

**Repeated keys.** `canonicalBody` decodes the body into `any`, which keeps the last of two equal keys, so the bodies
`{"type":"publish","properties":{"secret":1},"properties":{"other":2}}` and the same with `"secret":9` shared one
firing-cap key while the built-in decode saw different settings. The decode now refuses a repeated key in any object
at any depth (`notes/2.3.md`).
