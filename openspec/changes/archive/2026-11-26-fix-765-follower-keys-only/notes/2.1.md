# Task 2.1 notes: the keys-only field

## Shape

`follower.Config.KeysOnly`, a plain bool, off by default. When set, `follow` passes `jetstream.MetaOnly()` to
`WatchAll` (`graph/follower/follower.go`, `follow`). No functional option, no second constructor.

`observe` no longer branches on the mode for the value: it takes `entry.Value()` when it is non-empty and leaves
`Value` nil and `Bytes` 0 otherwise. So the value is absent because the library delivered none, and
`TestKeysOnlyEntriesCarryNoValue` fails if `MetaOnly()` is not passed (mutant 1 below). Had `observe` skipped the
value on the flag alone, the test would pass with the values still on the wire. The one change in values mode: a
stored value of zero length now reads as a nil `Value` instead of an empty slice. No stored entity is empty, and
every reader (`graph.UnmarshalEntityState` in graph-lexical, graph-embedding, graph-clustering) treats the two the
same.

## The library check (nats.go v1.55.0, the package's shared nats-server from natsfixture)

Read first: nats.go v1.55.0 `jetstream/kv.go`, the `update` closure of `WatchFiltered`. The operation comes from the
`KV-Operation` header (or the marker reason header), the revision and delta from the reply subject's metadata, and
the end-of-replay marker from the received count and delta. `MetaOnly` adds `nats.HeadersOnly()` to the ordered
consumer, which drops only the body. So all three facts should survive; the runs confirm it.

Command, run on the working tree that became the commit:

```bash
go test -tags integration -race -count=1 -v ./graph/follower
```

Result: `ok github.com/c360studio/semengine/graph/follower 54.115s`, every test passing, including:

- `TestKeysOnlyEntriesCarryNoValue` (new, keys only): three keys stored, one deleted and one purged before Run; the
  replay delivers entity 1 with `Deleted` false and the markers of 2 and 3 with `Deleted` true. Then a live put, a
  live delete and a live purge each arrive with the right `Deleted`. Every one of the six entries has `Value` nil and
  `Bytes` 0, revisions ascend in delivery order, no lost feed is declared (the watermark refuses a revision out of
  order), the end-of-replay marker arrives with the bootstrap target at the replay's last revision, `QueryReady`
  answers nil and the build latch is set.
- `TestFollowerSnapshotEndSetsBootstrapTarget/values` and `/keys_only`: the marker arrives right after the replay's
  last entry in both modes, so the bootstrap target is the replay's last revision and the latch waits for it.
- `TestEntryCarriesDeliveredValue` (values mode, unchanged): values and the delete marker as before.

Findings: with `MetaOnly`, a delete and a purge keep their operation, revisions ascend, and the end-of-replay marker
arrives. Nothing found that the follower cannot build on.

Not run in keys-only mode: the lost-feed, heartbeat, shutdown-drain and damage tests. They do not read the value or
the operation, and the damage test decodes values, which a keys-only plug-in never does.

## Show the test can fail

`task mutate:check` does not run tests in files built only with the integration tag (its classifier calls that
inconclusive), so the mutants ran through `go test -overlay`, which, like the command, builds the test with a copy
kept outside the repository in place of `graph/follower/follower.go` and edits nothing in the tree.
`follower.go`'s SHA-256 was `6e4574042aab7bdbc9e444e911b75679f9526a01e9237e1428e7dcdf1011127f` before and after.

```bash
go test -tags integration -race -count=1 -overlay "$M/<mutant>.json" -run '^<Test>$' ./graph/follower
```

| Mutant | Test | Outcome |
| --- | --- | --- |
| 1: `MetaOnly()` not passed under `KeysOnly` | `TestKeysOnlyEntriesCarryNoValue` | detected: `want Value nil and Bytes 0` for the two live and replayed puts (191 bytes each) |

The 2.2 mutants are in `notes/2.2.md`.

## Not covered

  the fix, measured in step 2 of the issue, not here.
- A plug-in that sets `KeysOnly` and still applies `Value`: only the doc comment guards it.
