# Task 2.2 notes: the initial build's progress line

## Cadence

The line is written in `publish`, which the heartbeat calls at once and then every `readiness.DefaultHeartbeat`
(5 s). No new timer. `publish` already computes the envelope; the line is written when that envelope reads the build
incomplete (`!status.BootstrapComplete`), before the envelope is written to GRAPH_STATUS. The build latch is never
cleared, so once an envelope reads complete no later heartbeat logs. `QueryReady` also computes the envelope but does
not log: the line follows the heartbeat only.

Fields: `key` (the follower's GRAPH_STATUS key, so graph-index's line is told apart from the other three),
`delivered` (entries handed to `Deliver`, a new unexported counter: nothing counted deliveries before; `completions`
counts `Complete` calls), `observed_revision` (the watermark's highest observed revision) and `indexed_revision`
(the envelope's floor).

## Test

`TestFollowerLogsBuildProgressUntilComplete` captures the follower's log through `Config.Logger`, a production field.
Two entities are stored and `Deliver` completes nothing, so the first envelope reads the build incomplete; reading it
from GRAPH_STATUS orders its progress line, written before it, before the check. The test then completes both
entries, waits for an envelope that reads the build complete, counts the lines, waits for the next heartbeat's
envelope and checks the count did not grow. Every ordering is an envelope read, never elapsed time. The test takes
one heartbeat period after the build completes, about 10 s in all.

Mutants, through `go test -overlay` as in `notes/2.1.md`:

| Mutant | Outcome |
| --- | --- |
| 2: the line written on every heartbeat (`if true`) | detected: `1 progress lines after the build completed; want none` |
| 3: the line never written (`if false`) | detected: `no progress line before the first envelope of an incomplete build` |
