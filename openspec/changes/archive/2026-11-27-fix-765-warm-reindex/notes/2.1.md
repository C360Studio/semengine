# Task 2.1 notes

The two failing-first tests, the oracle they rest on, the choices the design leaves open, and the red record.

## The tests

Both are in `processor/graph-index/record_integration_test.go` (build tag `integration`), on the package's shared NATS
server through its reset (`fixtureClient`), with the helpers of `index_integration_test.go`.

- `TestWarmRestartSkipsIndexedEntities` (spec "A warm restart over an unchanged store"). Five entities, carrying every
  row kind (outgoing, incoming, predicate, name, alias); one of them is deleted, and one written last orders the reads
  after every apply. graph-index indexes them and is stopped; a second graph-index, built on a registry of its own as a
  restarted process would be, starts over the same store. After its floor reaches the last revision and it answers
  queries, the test requires: no owner listing and no index row put or delete on its counter; no index bucket's stream
  sequence moved; `DataFlow` one message per live entity (four); the same reply data as before the stop for 29 public
  reads (outgoing and incoming of every entity, the deleted one included, every alias, every predicate by `predicate`
  and `predicateStats`, `predicateList`, `byName` of every name, and two `predicateCompound`); no failed entity.
- `TestLiveChangeUsesRecord` (spec "A live change"). Another entity links to `src`; `src` goes from A (an edge, a
  predicate, a name, an alias) to B (other values of each) while graph-index runs. The test requires no owner listing
  across the change, and that every public read answers B and nothing of A: outgoing, incoming of both targets and of
  `src` (the other entity's edge survives), `predicate` of each predicate, `byName` of both names, and `alias` of both
  aliases and the other entity's.

## The oracle

The counter is `semengine_graph_index_kv_operations_total` on the registry the component was built with
(`Component.metricsRegistry`), read through `PrometheusRegistry().Gather()`. The tests rely on two labels:

- `operation`: `list` is an owner listing; `put` and `delete` are row writes.
- `kv_bucket`: the index a row belongs to, `outgoing`, `incoming`, `predicate`, `name` or `alias`, spelled in the test
  from the bucket names (`indexRowLabels`), not taken from the code.

Listings are summed over every `kv_bucket` value, so a listing of any bucket counts, whatever 2.3 labels it.
Writes are summed over the five index labels only: the spec says "writes no index row", and a record write is not one.

Writes have a second oracle the component does not count: the last sequence of each index bucket's stream
(`natsclient.BucketLastSeq`), which every put and delete moves. Listings have none: a listing is a short-lived ordered
consumer (`natsclient/kv.go:656`), and stream info reports the consumers that exist, not those that existed. So a 2.3
that lists without counting would pass the listing assertions. Today both `KeysByFilter` calls on the write path count
(`owner_reconcile.go:46-47`, and the delete path at `index.go:644-645` after 2.2's lines); a reviewer of 2.3 checks
that this stays so. The query handlers' listings (`query.go:356`, `:456`) are not counted, and both tests read the
counter before they send any query.

## Choices

- **A deleted entity in the warm store.** Rule 6 says the clean empty record written after a tombstone is skipped on
  replay; a keys-only replay delivers the tombstone (`graph/follower/follower_integration_test.go`,
  `TestKeysOnlyEntriesCarryNoValue`). Today its delete path lists four times; after 2.3, nothing.
- **"As before" is anchored.** Comparing the second start's replies with the first's proves nothing if the first indexed
  nothing, so the test also requires first-start answers: one entity's outgoing, another's incoming (the deleted entity's
  edge gone), a name, and three aliases, the deleted entity's answering no ID.
- **Ordering.** The lane counts its KV operations and its `DataFlow` read before it completes the revision, so the
  floor reaching the last revision (`awaitIndexed`) orders the counter, sequence and `DataFlow` reads after every apply.
  The second start also waits for `QueryReady` before its reads.
- **The live change counts listings only.** Rule 3 writes the changed rows and the records, so a write count would test
  2.3's operation list, not the scenario.
- **Generated checks are not used here.** Each test is one fixed history whose expected answers are written out; the
  generated histories (values, cuts, re-offers, alias sets, a second writer) are `TestRestartConvergesFromEveryCutPoint`
  and `TestRecordMatchesListingOracle`, task 2.3.
