# Task 2.3 notes

The record (rules 1 to 6), the choices the design leaves open, the generated-check record, and the mutation record.

## Where it is

- `processor/graph-index/record.go`: the encoding, `recordFormat`, decoding (canonical form only).
- `processor/graph-index/owner_reconcile.go`: the ordered operations. `prepareApply` reads the record (and lists under
  rule 5) and builds the whole list; `runApply` runs it in order and stops at the first failure; `writeRows` retries
  (prepare, run) in place. `plannedRows` turns a plan into sorted (bucket, key, value) rows. `listOwnedRows` is the
  rule 5 fallback, the four owner listings of the old `reconcileOwnedRows` and `deleteFromIndexes`, still counted as
  `kv_operations_total{operation="list"}`.
- `processor/graph-index/index.go`: `indexEntity` and `deleteFromIndexes` go through `writeRows`; `lastProjections`,
  `computeIndexProjection`, `applyEntityIndexPlan`, `writeOutgoingIndex` and the per-index `reconcile*Index` are gone.

Rule 7 (too large) has its place in `prepareApply`, after the list is built and before it is returned: measure the
pending and clean records there, and replace the list with a record delete and a listing apply. Implemented by task
2.4 (`notes/2.4.md`).

## Choices

- **Encoding.** Every string field behind an 8-byte big-endian length, numbers as 8-byte big-endian: format, state
  (`pending` or `clean`), generation count then (bucket, creation time) sorted by bucket, row count then (bucket, key,
  32-byte hash) sorted by bucket then key. The bucket is its full name. `recordFormat` is `graph-index-record/1`.
  Decoding refuses another format, an unknown state, unsorted or repeated entries, a count the remaining bytes cannot
  hold, and trailing bytes, so whatever decodes re-encodes to the same bytes (`FuzzRecordDecode`, seeds only in
  `task test:unit`). A record that does not decode is unusable: rule 5.
- **Pending hashes.** A pending record carries the planned hash for planned rows, the earlier record's hash for its
  other rows, and 32 zero bytes for rows only a listing named. Nothing compares a pending record's hashes: from a
  pending record every planned row is put.
- **Rule 5's union** is the listed keys plus the entity's OUTGOING key, which no owner filter lists, so a delete with no
  record still deletes it ("not found" is done). A planned row a listing found is put again unless its value is empty
  (the marker buckets); NAME and OUTGOING always are.
- **A record that cannot be read** (not "not found") takes rule 5, and its pending put is a create: a record that does
  exist refuses it, a conflict.
- **A conflict is not retried in place.** `retryIndexWrites` returns at once on `errRecordConflict`, so the entity is
  failed and the repair pass starts from the stored record; without this the spec's "the entity is failed" after a
  second writer would not hold. Other failures are retried in place up to three times, each attempt reading the
  record again.
- **The first failed operation stops the apply** (rows included), so nothing is written after a failed record put and
  the clean record follows only a complete set of row writes.
- **The delete path** now retries in place like a write, and its failure is a Warn line naming the entity.
- **Metrics.** Record reads count `kv_operations_total{operation="get",kv_bucket="record"}`, record writes
  `{operation="put",kv_bucket="record"}` and `reconcile_operations_total{index_type="record"}`; the 2.1 tests count only
  `list` and the five index labels. `reindex_events_total` is `unchanged` exactly when rule 1 skipped. An unchanged
  entity counts `events_processed_total` but no `updates_total`.
- **What the tests call.** `TestSecondWriterFailsRecordWrite` and both generated tests drive an apply through its two
  production steps, `prepareApply` (the read) and `runApply` (on a prefix of the list for a cut), because a second
  writer or a cut must land between operations and nothing else orders it there. `TestRepairSkipClearsFailed` and
  `TestSecondWriterFailsRecordWrite` put the entity in the failed set with `markEntityFailed`, the lane's own mark for a
  failed read and for a conflict. Writers the tests drive are components that ran `openIndexBuckets` and nothing else
  (`openWriter`), with the alias set set on their fields as `plan_prop_test.go` does.

## A gap in the design's two-writer claim

Rule 2 says revision-checked record writes mean two graph-index processes on one store "cannot leave a row no record
names". The record check covers a second writer between an apply's read and its pending put, which the spec's
scenario names and the tests drive. It does not cover two applies whose row writes interleave after both pending puts.
A, applying an older value (plan P1), puts its pending record; B reads it, puts its own pending record (naming P1 and its
plan P2), deletes row X (in P1, not P2); A then puts X; B's clean put (P2) succeeds; A's clean put is refused and A is
failed. A's repair then reads the current value, plans P2, finds the clean record equal, and skips: X stays, named by
no record. The trigger is the design's own: two processes overlapping during a rolling update while an entity changes
twice. Not fixed here; it needs an architect ruling (declare two writers unsupported and name what refuses the second,
or another mechanism).
