# Task 2.1: the generated check, and the refusals' mutation checks

Scope: unit C's part of 2.1, the generated check of D3 (`TestFiringAndAskingAgree`, `processor/rule/matches_prop_test.go`)
and its two mutants, and the `task mutate:check` record for each refusal 2.1's head asks for. The named tests of 2.1
came with units A and B; their failing-first output and mutation checks are in `notes/2.3.md` and `notes/2.4.md`.

## Choices

- `pgregory.net/rapid` is already a dependency (`go.mod`: `pgregory.net/rapid v1.3.0`), used by PR 1's
  `TestPropConditions` and PR 3's `TestSubstitutionProperties`.
- The test has two subtests, `witnesses` then `generated`, through one check, `checkFiringAndAskingAgree`, which fails
  unless both matches error or both answer the same verdict with no error, and returns the shared answer. The five
  witnesses reach each answer by construction, before the generated run: conditions that hold (true), that do not
  (false), an absent required field (false, no error), `length_eq "abc"` (an error from both) and a value token that
  does not resolve (an error from both). Each asserts the answer it was written to reach, so the check's both-error
  and both-verdict branches each run on every run.
- The generator draws one to three conditions over five declared predicates, `and` or `or`, required or not; values
  are literals (numbers, text, `"abc"`, lists), templates filled from the entity (`$entity.id`, `$entity.instance`, a
  triple's bare, `.value`, `.length` and `.triples` forms, and `$entity.triple.x.y.missing`, which no generated entity
  holds) or a regex `Load` compiles; the operators are every registered one but `transition`. It never draws
  `transition`, `$state.`, `$prev.`, `$entity.lifecycle.` or `$message.`, in a field or a value, so `Load` accepts every
  draw and `Matches` refuses none. Entities are inside `matchPattern`, with zero to five triples whose objects are
  numbers, numeric text, text and lists in their Go and JSON-text forms. A bare `$entity.triple.<predicate>` the entity
  lacks also does not resolve, so the error answer is reached from two templates, not one.
- Reach, measured once with a throwaway tally (not committed), seed 20261127, 1000 checks: 66 true, 691 false, 243
  errors.
- The `-test` of each mutant run below is `TestFiringAndAskingAgree/generated`, so the detection is the generated run's
  and not a witness's.

## The generated run

`go test ./processor/rule -run '^TestFiringAndAskingAgree$' -count=1 -race -v -rapid.checks=1000 -rapid.seed=20261127`
printed `matches_prop_test.go:218: [rapid] OK, passed 1000 tests (307.331583ms)`. `task test:unit` and `task test:repeat`
run it with Rapid's defaults (100 checks, a fresh seed each run). No failure was found, so there is no failing input to
replay; each mutant run below prints its own shrunk input, replayable with `RAPID_SEED=1`.
