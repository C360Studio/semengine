# Tasks 2.2, 2.3 and 2.5: choices the design leaves open

Scope: unit A of the port, `ErrRequiredFieldMissing` (2.2), the entity match and `Matches` (2.3) and the `Load` check
(2.5), with the tests in 2.1 that prove them: `TestMatches`, `TestRequiredFieldMissing` (entity side),
`TestUnresolvedValueTemplate`, two `TestLoadRefuses` cases, and `TestErrRequiredFieldMissing` in
`processor/rule/expression` for the `rule-conditions` scenarios. The message match (2.4), the generated check and its
two mutants (rest of 2.1), the carried test sweep and comments (2.6, 2.7), ledger, PR body and docs are not here.

## A premise the design states that does not hold

`gt "abc"` on a number is not an error on main or at the pin. `gt`, `gte`, `lt`, `lte` and `between` go through
`compareValuesWithError` (`expression/evaluator.go:616-640`), which compares text when either side is not a number
and never returns an error; `eq`, `ne` and `contains` never error either. Probe P2's "no
match, nothing logged at Info" is that text comparison (`"5" < "abc"`), not a Debug-logged error. So the example in
D3, D4, tasks 2.1, the `rule-conditions` scenario "An operator failure is not a missing field" and the `rule-matching`
scenario "A comparison that cannot be made" names an input that gives `false, nil`. The tests use
`length_eq "abc"` instead, which fails in `coerceToInt` and is an `*EvaluationError` with `Err` set. The spec deltas,
tasks and inventory were corrected to `length_eq "abc"` in 9ec70200. The generated check of 2.1 needs the same
substitution for its "operator whose value cannot be compared".

## Choices

- `Matches` classifies a nil rule, context or state and a malformed entity ID as invalid (`errs.ErrorInvalid`), as
  `SubstituteVariablesWith` does for a nil context. A stateless refusal and an evaluation error are not classified;
  each is wrapped with the rule ID and keeps its `*expression.EvaluationError`.
- `Matches` checks `Enabled` although the entity match checks it too: the order puts a disabled rule (false) before
  the stateless refusals (an error). `TestMatches` has a disabled rule whose condition reads `$state.iteration` for
  this, and the same for a rule with no pattern and an entity outside the pattern.
- The firing match's failed lifecycle lookup is ignored, as the design says; the line carries a `// shortcut:` marker
  naming the limit, so the firing path that owns the lookup sees it.
- `substituteConditionValues` now returns `([]ConditionExpression, error)` and fills through the one scan
  (`ec.substitute`), which logs nothing. The error names the field, the value and every unresolved token of the first
  condition that has one; the entity match adds the rule ID. Its two existing tests (`TestSubstituteConditionValues`,
  `TestSubstituteConditionValuesLifecycle`) gained the error check.
- A regex condition is filled like any other. Skipping it was tried and survives a mutation check (below): `Compile`
  refuses a pattern holding a substitution prefix, so filling a regex value never changes its text and the kept
  compiled pattern still counts (`regex.go:83-86`). The doc comment says so. semteams' `02-plan-to-gather.json`, whose
  regex ends in `$`, matches through both paths.
- `expression.EnsureStatelessResolvable` keeps its `lifecycleResolved` parameter; `Matches` passes `false` and no
  production caller passes `true`. Only the message and the doc comment changed (2.3). Dropping the parameter is a
  signature change the design does not ask for; it stays for whoever carries a match with a lookup.
- One evaluator per match (`expression.NewExpressionEvaluator()`), as at the pin (F16, optional, left).
- `Matches` and the entity match live in `processor/rule/matches.go`; the entity match is `(*Rule).matchEntity`.
- The `Load` check is `checkConditionPath`, called from `checkExpressionRule` for each condition after its operator
  check, so it runs for disabled rules too. It reads `def.Entity.Pattern != ""`, the one spelling of which path a rule
  runs on (F2). `doc.go`'s Loading section gained one sentence on it.
- semteams' two research rules are in `processor/rule/testdata/semteams-research/` with a README (repository, commit
  `4df44ae877d0c711f769ec6b48b88100dbb267d1`, path `configs/rules/research/`, licence), byte-identical
  (`shasum -a 256` matched the downloaded copies). The test entity holds `coordinator.decision.subtopics` as a JSON
  list in a string, the form semteams' decide tool stamps, which both the regex and `.length` read.

## Seen to fail

Each test was run before the code it proves:

- `TestErrRequiredFieldMissing`: build failure (no `ErrRequiredFieldMissing`), then, with the variable declared and
  not wrapped, the four absent-field subtests failed on `errors.Is`.
- `TestLoadRefuses`, the two new cases: both failed, enabled and disabled, `Load` accepting the rule.
- `TestMatches`, `TestRequiredFieldMissing`, `TestUnresolvedValueTemplate`: build failure, then against stubs of
  `Matches` and the entity match returning `false, nil`, every true verdict and every expected error failed
  (18 subtests). The false-verdict subtests passed against that stub; each was then shown to fail by a mutation check.
