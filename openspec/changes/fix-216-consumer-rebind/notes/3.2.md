## M3, first found inconclusive, then closed by a test change

The first pass above found M3 inconclusive. A reading of the code, not measured: under M3 the record is cleared by
each tick whose lookup succeeds, but the loop's `Closed()` channel stays closed, so the next tick records it again.
When the status loop's own tick (every 5 s, `readiness.DefaultHeartbeat`) records it between a test tick's clear and
that observation's `Health()` read, `Health()` reads the lost binding, and `awaitHealthAfterTick`, which accepts the
first match, passed the last step. The passing mutant runs took 12.1 to 13.1 s against about 2.5 s for a baseline,
which fits a match found late in the wait.

On the coordinator's instruction, the last step of T2 and T3 (`health_integration_test.go`, no production change) now
drives one tick as `awaitHealthAfterTick` does (`c.refreshReadinessStatus(ctx)`), reads `Health()` once, and requires
unhealthy with the same text checks; it does this three times and requires every read unhealthy. With the fix the
latch is set by the test's own tick and never cleared, so the read after it is deterministic; under M3 the test's own
tick clears it, and only a background record landing in the gap before every one of the three reads lets it through.
