# Task 7.1: Codex's finding, the repeat list

Codex's code review of PR #419 at `63b1086` found that `test:repeat` read the `unit` list, so the repository guards
in `internal/harness/contract` still ran five times on every verify (54 of the repeat step's 58 seconds in Codex's
run). The owner's ruling (PR #419 comment 6429349207) keeps the guards in `contract`, run once per verify in
`test:unit` and never in `test:repeat`.

## The fix

- `scripts/test-pkgs.sh repeat` prints the `unit` list without `./internal/harness/contract`. The script names
  `contract` once, beside the tool list.
- `test:repeat` in `Taskfile.yml` reads `PKGS` from `scripts/test-pkgs.sh repeat`.

## Tests, shown failing before the code

- `TestTestPkgsLists` expects `repeat` to print `./a ./d ./e` in the planted module (no `contract`, no tool package),
  while `unit` still prints `./internal/harness/contract`. A planted module whose only unit package is `contract`
  must make `repeat` exit non-zero (empty list).
- `TestUnitInvocationsPinned`: `pinnedTestTasks` now requires `test:repeat`'s `vars` to be
  `PKGS: {sh: scripts/test-pkgs.sh repeat}`. The sensitivity case "test:repeat reads the unit list" plants the old
  `unit` line and expects a violation naming `test:repeat` and `scripts/test-pkgs.sh repeat`. The existing
  `test:repeat` cases plant the `repeat` line, so each still fails only on the fault it names.

`TestUnitInvocationsPinnedSensitivity` passed before the code too: its fixtures are built from `pinnedTestTasks`,
not from the real Taskfile, so the new case fails its fixture as soon as the pin says `repeat`. The empty-`repeat`
case also passed before the code, because the old script refused `repeat` with the usage error (exit 2); after the
code it exits 1 on the empty list. Neither is a detection of the fix; the two failures above are.
