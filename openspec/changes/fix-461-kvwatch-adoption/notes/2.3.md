# Task 2.3: `config` stopWatches stops through `kvwatch.Stop`

## Test

`TestStopWithABackloggedKeyFamilyLeavesNoWatchDelivery` (`config/manager_lifecycle_integration_test.go`, beside
`TestBlockedKeyFamilyHandlerHoldsStop`). A seeding Manager with a handler that does not block puts 600 members into
the `rules` family (above nats.go's 256-entry updates buffer) and stops. Then 10 cycles, each a fresh Manager on the
same identity and bucket, whose family handler blocks on its first entry (the watch's initial snapshot):

1. wait for the handler to be entered, then `natsfixture.AwaitNativeDeliveryBlocked`;
2. call `Stop` (30 s context) on a goroutine;
3. wait until the bucket's backing stream has no consumers (`awaitWatchConsumers(..., 0)`, the server-side count the
   lifecycle suite uses), then release the handler;
4. `Stop` returns nil, and `natsfixture.AwaitNoStacks` over `natsfixture.NativeDeliveryStacks` finds no delivery left.

## Choices the task left open

- **Release after the consumers are gone.** Releasing the handler as soon as `Stop` is called lets the handler, now a
  no-op, read the backlog out before `watcher.Stop` returns, and base passes. Waiting for the server to list no
  consumers orders the release after every watch's `Stop`. On base the run context ends right after, so the released
  `processFamily` returns after at most one read (its `ctx.Err` check) and the delivery stays blocked. The race
  between that release and the `cancel()` is why the test runs 10 cycles; base failed at cycle 0, 1 and 3 in three
  runs.
- **Context.** `release` passes its own `ctx` to `stopWatches`, which passes it to each `kvwatch.Stop`: `Start`'s on
  a failed `Start`, `Stop`'s otherwise (ADR-113). No context is stored; the teardown goroutine already outlives a
  `Stop` whose context ends first, and `kvwatch.Stop` bounds its drain to `kvwatch.DrainBudget` past that context.
- **Errors.** Still logged at Warn with the same message, never returned (ruling Q4). `kvwatch.Stop` already drops
  the benign "already gone" errors, so a second teardown's errors are quieter than before, not louder.
- **Docs.** `stopWatches` (unexported) says it returns once nats.go has closed each watch's delivery, for at most
  `kvwatch.DrainBudget` after ctx ends, and names the test. The exported `Stop` doc is unchanged: it already says Stop
  returns nil only once everything the Manager started is released. No exported signature changes or names
  `internal/kvwatch`.
- **No test fake.** `config` has no test watcher that stops without closing `Updates`; every config test watches a
  real server, so no `closeUpdates` helper was needed. `go test -count=1 ./config/`: 0.635s before, 0.518s after.
