## Choices the design leaves open

- **`resolver` returns `(value any, damaged int, err error)`** and `ask` returns `([]byte, int, error)`: the count
  comes from the envelope and is 0 for a bare row (`entity`, `prefix`). Two non-error returns, so no struct.
- **Only an answered field counts.** A field left null, by a resolver error or a reply that does not fit the schema,
  adds nothing: nothing of its reply is in `data`. This mirrors "a reply read but set aside adds nothing".
- **"Largest among the request's root fields"** is kept as `max` in `execute`, though a request names only one root
  field besides `__typename` (`prepare`), so today it is that field's count.
- **`extensions` holds only `damagedEntities`** and is absent when the count is 0, so an answer with no damage is
  byte-unchanged.

## Spec delta mismatch

The graph-gateway delta's scenario says "a client asks `relationships`". The gateway has no `relationships` root
field (`schema.graphql`: `entity`, `entitiesByPrefix`, `entitiesByPredicate`, `pathSearch`), and only
`entitiesByPredicate` and `pathSearch` read enveloped replies. The test uses `pathSearch` at 1 for the scenario and
`entitiesByPredicate` at 3; the scenario's wording should be corrected to `pathSearch` before the archive. The
design's "stubbed replies at 2 and 3 give 3" cannot be built here, since one request reads one reply.
