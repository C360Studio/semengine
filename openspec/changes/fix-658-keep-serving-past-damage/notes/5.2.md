## Choices the design leaves open

- Order: the report is made first, then the record is removed and the revision completed, all under `hop1Mu`
  (`removeRecord`, the path a delete and a textless entity take). A failed removal is marked `delete_failed`, so the
  verbs are withheld transient rather than answer from B's last good vector, and the repair lane re-reads B, finds it
  damaged again (no second count) and retries the removal.
- The error line is logged once per newly damaged entity, as ErrorCount counts, not on every repair read.
- The count is the larger of the record read before the vector cache is read and the record read when the reply is
  built, as graph-index and graph-lexical do (`5.1.md`). `similar` counts every damaged entity (it has no scope).
- `similar` checks the source's recorded refusal after reading the source record and before acting on that read's
  outcome: hop 1 reports before it removes, so a read that found the record gone already sees the report, and a record
  read before the report is the entity as it stood. The refusal returned is the one the follower recorded (fatal
  `graph_state_reset_required` with its reason), so an error reading the source never hides it.
- A repair clears the report when the Worker's terminal outcome completes the valid revision. The vector cache applies
  the new vector after that, so for a moment a search can miss the repaired B with no count; this is the same window
  any new write has, and the replies claim no `ENTITY_STATES` revision.
- The README and MIGRATION lines that still describe the reset (`README.md:130-131`, `:199`; `MIGRATION.md:72-75`,
  `:86`) are task 6.2's.
