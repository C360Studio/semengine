# 2.1 notes: the Health test runs its writer and reader in parallel at `-cpu 1`

## Choice

`TestHealthCountMatchesNamedIDsWhileChanging` raises `runtime.GOMAXPROCS` to `max(2, current)` at its start and
puts the old value back in `t.Cleanup`. The rest of the test is unchanged.

## Other tests in the package

GOMAXPROCS is process-wide, so the raise reaches anything running beside this test. `processor/graph-ingest` has
tests that call `t.Parallel` (for example `batch_unit_test.go`, `canonical_mutations_test.go`,
`entity_id_contract_test.go`, `entity_state_trusted_decode_test.go`, `query_contract_guard_test.go`). `go test`
holds every top-level parallel test until all the sequential top-level tests have returned, and this test is
sequential, so no parallel test runs while the raise is in force; the cleanup restores the value before the next
test starts. A goroutine another test left running would only get more processors, which changes its timing, not
its result. `-parallel` takes its default from GOMAXPROCS when the binary starts, so the raise does not change it.

## Failing at `-cpu 1`

The wrong change is the two-read Health: `total := c.entityPoison.Len()` and
`sample := c.entityPoison.Sorted(entityPoisonSampleCap)` in place of the one `Sorted(0)` read in
`entityPoisonHealthMessage` (`processor/graph-ingest/poison_inventory.go`).

```bash
task mutate:check -- -pkg ./processor/graph-ingest -test TestHealthCountMatchesNamedIDsWhileChanging \
  -file processor/graph-ingest/poison_inventory.go -mutant "$TMPDIR/mut21/poison_inventory.go" \
  -expect poison_report_test.go:152
```

It runs `go test -json -count=1 -cpu 1 -race`. Verdict: **detection**, 3 of 3 mutant runs failed at
`poison_report_test.go:152`, for example `Health count 2, 1 IDs named: "graph_state_reset_required: 2 poisoned
entities ... acme.ops.test.system.widget.anchor (unreadable_entity_state) (+1 more; enumerate via debug status)"`;
the 3 baseline runs and the after-run passed.

Also by hand, with the same mutant through `go test -overlay`:

- `test:repeat`'s flags, `-count=5 -cpu 1 -shuffle=on` without `-race`: 5 of 5 runs failed.
- The test without the raise, at `-race -count=1 -cpu 1`: 1 of 4 runs failed; at `-count=5 -cpu 1 -shuffle=on`:
  0 of 5 failed. Without the raise the test catches the regression only now and then, which is the gap.
