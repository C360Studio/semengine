# Task 2.3 notes: graph-index watches keys only and counts what it reads

## The owner's choice

`component.Lifecycle.CountInput(n)` counts one message and `n` bytes together; there is no bytes-only count. Moving
the bytes to graph-index's own read therefore moves the message count too. Three options went to the owner: move the
whole count to the read (no new surface), add a bytes-only method on `component.Lifecycle` (new framework surface,
Fable first), or leave the count on the delivered entry (bytes 0 for good under keys-only). The owner chose the first
on 2026-11-26, in the Enjoy session.

## What changed

- `processor/graph-index/component.go`: `follower.Open` gets `KeysOnly: true`.
- `processor/graph-index/index.go`: `deliver` no longer calls `CountInput`. `reconcileEntity` counts one input with
  `len(entry.Value())` after a successful `c.entities.Get`, and `reconcileNoncanonical` does the same after its own
  read, since that is also an entity graph-index reads. `watch_events_total` is untouched: it still counts every
  delivery by kind, before any coalescing.
- Nothing else in graph-index read `follower.Entry.Value` or `Entry.Bytes`; `deliver`'s `CountInput(e.Bytes)` was the
  only use. The other `.Value` reads in `query.go` and `index.go` are KV entries from graph-index's own reads.

## What a DataFlow message now means

One message is one entity graph-index read from ENTITY_STATES. Compared with one per delivered entry:

- Writes to one key that the coalescer folds into one apply count once, not once each.
- A delete counts nothing: its read finds no entity. It counted one message of 0 bytes before.
- A key the shared KV key validator refuses (`settleUnreadable`) is never read and counts nothing.
- A repair pass (`repairFailedEntities`) reads each failed entity again and counts each read.
- A failed read counts nothing; it marks the entity failed as before.

## Docs and specs reworded

- `docs/admission-ledger.yaml`, the graph-index row's adaptation (3): one input per entity graph-index reads, of that
  read's bytes, since its watch carries keys only; `watch_events_total` still counts each delivery by kind.
- `DataFlow`'s doc comment in `processor/graph-index/component.go`.
- A new delta, `specs/graph-index/spec.md`: "DataFlow counts deliveries" is renamed "DataFlow counts entity reads"

## Tests

- `TestDataFlowCountsEachDeliveryBeforeCoalescing` is renamed `TestDataFlowCountsEachEntityRead`. Its body is
  unchanged except one label: it already waited for each write to be counted before the next, so each write is read
  on its own.
- `TestDataFlowCountsReplayedBytes` (new): four writes over three keys, one written twice, before graph-index starts.
  Once the floor reaches the last write, `DataFlow` holds three messages and the summed lengths of the three values
  stored last. The oracle is computed from the stored bytes. The floor orders the read: a lane counts the read before
  it completes the revision.
- `startHeldBacklog` (`lifecycle_integration_test.go`) waited for `DataFlow().Messages` to reach the stored count
  as its signal that every entry was delivered. With one lane held, reads stop, so that wait would never end. It now
  waits on `watch_events_total{event_type="update"}`, which `deliver` increments before it submits, as `DataFlow` did.
