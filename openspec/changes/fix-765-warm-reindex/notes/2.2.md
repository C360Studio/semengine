# Task 2.2 notes

Choices the design leaves open, for the record bucket and the generations.

## The bucket

- `graph.BucketGraphIndexRecords = "GRAPH_INDEX_RECORDS"` (`graph/constants.go`), with the other graph-index buckets.
- Catalog row through the table's `derived` helper (`graph/kvcatalog/kvcatalog.go`), owner `graph-index`, like the five
  index buckets: class derived, owner-only writes, `RetentionNoLifecycle` (no TTL, no `MaxBytes`), History 1, one
  replica. A derived bucket in this catalog gets the same no-lifecycle retention as every other row
  (`TestKVCatalog_DeclaredPolicies` checks every row but the configuration family): a record evicted by age or size
  would be an entity whose rows no record names.
- Catalog tests: the row count goes from 17 to 18, the record bucket joins `TestIsFrameworkOwnedBucket_ProductionView`,
  and `TestKVCatalog_DeclaredPolicies` pins its class, owner and History.
- Opened in `openIndexBuckets` (`processor/graph-index/index.go`) through `kvcatalog.EnsureCatalogBucket`, as the owner,
  after the five index buckets; held in `Component.recordBucket`. A KV handle holds nothing to release, so cleanup is
  unchanged.

## The generations

- `Component.generations` is a `map[string]uint64` keyed by bucket name: `ENTITY_STATES` and the five index buckets.
  A value is the backing stream's creation time in nanoseconds since the Unix epoch, the spelling graph-ingest uses for
  its stream generation (`processor/graph-ingest/consume.go:92`). The map is built whole and set only when every read
  succeeded.
- `bucketGeneration` (`index.go`) reads it through the bucket's KV `Status`, as `readStream` does
  (`graph/follower/follower.go:546-556`), and refuses a zero creation time, as graph-ingest does (`consume.go:89-91`).
  A failed read fails Start, which then holds nothing.
- `ENTITY_STATES`' generation is read again here, not taken from the follower. The follower holds the same fact
  (`follower.go:123`, unexported); handing it out would be new exported surface on `graph/follower` for one caller,
  and design Decision 1 says to read it as `follower.go:546-556` does. The two reads are moments apart. If the bucket
  is deleted and created again between them, the follower's heartbeat sees a creation time other than its own and
  declares the feed lost (`follower.go:484-488`), so queries refuse until a restart, where both reads agree.
- The record bucket's own generation is not read: the design names `ENTITY_STATES` and the five index buckets. A
  record bucket deleted and created again is empty, so every entity has no record and is listed (rule 5).
