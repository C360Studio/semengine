# Task 2.4 notes

Rule 7, too large: the choices the design leaves open, the probe behind the allowance, and the mutation record.

## Where it is

`processor/graph-index/owner_reconcile.go`: `prepareApply` builds the list as before, then `recordsFit` measures its
pending and clean records against `MaxPayload()` less `recordPayloadAllowance`; when either is over, `tooLargeApply`
replaces the list. The new operation `opDropRecord` runs `dropRecord`, a `DeleteAtRevision` at the revision read.
`recoveryOps` is split so its row operations (`rowOps`) serve both the recovery list and the listing apply.

## Choices

- **The allowance is 1,024 bytes.** It covers the subject and the conditional header of a record put. The exact
  overhead is not promised; the test probes that a record of exactly `limit - 1024` bytes under a 256-byte entity ID is
  accepted by `Create` and by `Update` on the pinned server (nats-server 2.15.0 image, nats.go v1.55.0).
- **Both records are measured**, pending and clean, as the design says, although the pending one is never the
  smaller.
- **The listing.** A usable record that turns out too large has had no listing yet, so `tooLargeApply` lists then.
  With no usable record, the listing `prepareApply` already ran is reused. The listing apply's union is the listing
  alone, not the record's rows too: the listing finds every stored row, and only that entity's lane writes them.
- **A record that cannot be read** (not "not found") with a too-large plan fails the apply before anything is written:
  it cannot be deleted at a known revision, and a record left in place would name fewer rows than the listing apply
  writes. The error is transient, so the lane retries in place and the repair pass retries after that.
- **A delete refused because the revision moved** is `errRecordConflict`, like the record puts, so it is not retried
  in place. Any other delete failure (including "not found") is a failed write, retried in place; the retry reads the
  record again.
- **A deleted or damaged entity** whose listing is too large to record is deleted by listing and keeps no record, not
  the clean empty one. Each replay of its delete lists once more until a record fits. That is rule 7's declared cost.
- **Declared signal.** Each too-large apply logs at Info ("record too large to keep; the entity is applied by
  listing") and counts `reconcile_operations_total{index_type="record",operation="too_large",result="success"}`. The
  record delete counts `kv_operations_total{operation="delete",kv_bucket="record"}` and
  `reconcile_operations_total{index_type="record",operation="delete"}`.

## The test

`TestOversizeRecordFallsBackToListing` (`record_oversize_integration_test.go`) starts its own server with
`max_payload` 8,192 (`// Own server:` marker), so a record outgrows the limit while the entity's value still fits. One
entity goes small (recorded), grown (record between `limit - allowance` and the limit: the allowance alone keeps it
out), changed (record over the limit itself), shrunk (still applied by listing, since its listing finds the large
rows), shrunk again (recorded), and shrunk a third time (no listing). After each step it compares a listing of every key
of the index buckets with rows spelled from the key layouts, and checks the public `outgoing` read and the `incoming`
read of every target the entity ever held. The record sizes are checked by a test-side formula from the encoding
`record.go` documents, so a change in key layout that moves a step out of its window fails the test by name.
A last step gives a writer whose record reads are refused a too-large plan and requires a failed write with nothing
written.

Examples suffice, with no generated check: the cut points and histories are already generated in task 2.3's tests,
and rule 7 adds one branch whose inputs are the record size and whether a record exists or can be read. Each of these
is a named step.

## Mutation record

By hand (`task mutate:check` does not run integration tests), each on `owner_reconcile.go`, restored from a copy under
`$TMPDIR` with matching SHA-256 sums before and after (`c1d35ad8…`), at the tree that became the 2.4 commit:

| Wrong change | Outcome |
| --- | --- |
| no rule 7 (`recordsFit` treated as true) | detection: grown step has a record, no listing; changed step fails its writes, `index not ready` |
| the limit without the allowance | detection: grown step has a record (35 rows) and made no listing |
| no record delete before the listing apply | detection: the small clean record survives, and the shrunk step leaves 15 stale INCOMING rows |
| an unreadable record ignored | detection: the apply succeeds, rows are written, the clean record names rows not stored |

## Not covered

- A record within the allowance that the server still refuses: shown by reading (the put's error is a failed write
  through `putRecord`, as for any refused put), with no test, since no pinned server refuses it.
- A `DeleteAtRevision` refused as a conflict: no test drives a second writer between an oversize apply's read and its
  delete.
