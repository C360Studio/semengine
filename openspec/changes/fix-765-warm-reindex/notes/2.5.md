# Task 2.5 notes

Generations: what task 2.3 already enforced, the test, and the mutation record.

## What was already there

Task 2.3 already refuses a record of another generation: `prepareApply` (`owner_reconcile.go`) uses a record only when
it decodes and `maps.Equal(decoded.generations, c.generations)`, and `openIndexBuckets` (`index.go`) reads the
generation of ENTITY_STATES and of each of the five index buckets at start. A record of another format does not decode
(`decodeRecord` refuses it). No code changed in this task; it adds the test, which is also the first to check the
generation values a record carries.

## The test

`TestRestartRebuildsRecreatedIndexBucket` (`record_rebuild_integration_test.go`) indexes six sources linking to two
targets, checks every record's generations against each bucket's stream creation time read by the test from the
stream itself (`KV_<bucket>`, not through graph-index's own reader), stops graph-index and deletes `INCOMING_INDEX`.

- **The cut rebuild.** The spec says graph-index starts, is stopped during its rebuild, and starts again. A real start
  stopped at once would stop at an unknown point, so the rebuild is driven, as in task 2.3's tests, by a graph-index
  that opened its buckets (which recreates `INCOMING_INDEX` under a new generation) and runs its applies itself. Two
  sources are applied whole (`writeRows`), one is cut after its pending record and one row (`runPrefix`), and three
  are not reached. The test checks the cut is what it says: two records of the new generation, one pending, three of
  the old.
- **Then a real start.** Every incoming and outgoing read answers what it answered before the deletion, every record is
  clean, names exactly its stored rows, and carries the new generations, and nothing is failed.

Examples suffice, with no generated check: what decides the outcome is the record's state at the cut (rebuilt,
pending, old generation), and each state is a named case in the one history.

## Mutation and red record

By hand, each restored from a copy under `$TMPDIR` with matching SHA-256 sums before and after:

| Wrong change | Outcome |
| --- | --- |
| `prepareApply` ignores the generations (`owner_reconcile.go`, `175492d9…`) | detection: the rebuild under the new generation plans nothing ("starts with []") |
| `openIndexBuckets` keeps no index bucket's generation (`index.go`, `bc74b9cb…`) | detection: every record's generations hold only ENTITY_STATES |
| test edit: delete one rebuilt INCOMING row before the final reads (`record_rebuild_integration_test.go`, `ee2a724a…`) | red: the incoming read of that target lacks the source, and its clean record names a row not stored |

The first wrong change fails at the cut rebuild, which runs the same code as the later start, so it never reaches the
final reads; the red test edit shows those reads can fail.

## Not covered

- An index bucket deleted while graph-index runs. The generations are read once, at start, and the requirement and
  this test cover only the stopped case; what the running component does then is not tested here.
