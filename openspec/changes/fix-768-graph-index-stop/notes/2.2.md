# 2.2 notes: the stopping flag

- The flag is an `atomic.Bool` on `Component` (`stopping`), beside `failedCount`, the component's other atomic
  state. `cleanup` sets it just before `c.pool.Shutdown(ctx)`; `processWork` returns first when it is set. It is
  never cleared: a stopped component is not restarted (a second `Start` is refused), and a `Stop` retried after its
  context ended sets it again, which changes nothing.
- `TestStopWritesAcceptedWork` is removed: it proved only the old rule that every accepted entry is written before
  `Stop` returns nil. Its other checks (no `ErrorCount` change, no WARN or ERROR line) are in
  `TestStopDropsQueuedWork`.
- `TestStopInterruptedThenRetriedWritesAcceptedWork` is removed. What still holds, a `Stop` its context ends returns
  that error and a later `Stop` returns nil with nothing failed, is the order `TestStopDropsQueuedWork` runs (first
  `Stop` under an ended context, then a retried one). Its own setup depended on the drain outlasting a cancel, which
  the flag makes too short to rely on.
- The admission ledger's graph-index row names `TestStopDropsQueuedWork` in place of `TestStopWritesAcceptedWork`.
- Comments rewritten to the new rule: `component.go` (the run context in `start`, the `stopping` field, `cleanup`),
  `index.go` (`startIndexPool`, `processWork`), and the tests' `stopBound` and the unit test of an ended-context
  `Stop`.

## Review round 1: the cutoff moves to the start of Stop

The review at `24d4055f` (R1) found that `cleanup` set `stopping` only after every query subscription drain and the
feed join. A query handler still running at Stop holds that drain, and the lanes kept reading, writing and completing
the backlog meanwhile, against the requirement's "from the moment `Stop` begins".

- `cleanup` now sets `stopping` as its first statement, before the drains and the feed join. The write already in
  flight still runs under the live `poolCtx` and finishes whole. A failed Start's rollback also runs `cleanup`; the
  flag set there changes nothing, since a component is never started again.
- The comments on the `stopping` field, `cleanup` and `processWork` say the cutoff is where Stop begins.
- The spec delta says the drop holds from the moment `Stop` begins, even while it waits on query handlers, and names
  both tests. The admission ledger names the new test.

### The new history

`TestStopDropsQueuedWorkFromItsStart`: the same held backlog as `TestStopDropsQueuedWork` (both now build it with
`startHeldBacklog` and check it with `requireQueuedDropped`), plus a request handler on a test subscription, put
first in `c.subscriptions`, that is entered and held. `Stop` runs under a live context. The test waits until
`stopping` is set, then lets the lane go while the held handler still keeps `Stop` in its first drain, then lets the
handler go and joins `Stop`, which must return nil.

The wait is on the flag itself (`probe.Await` on the value): `component.Lifecycle` reports Health "stopped" before
it calls `cleanup`, so Health alone cannot order the lane's release after the cutoff, and a lane let go in that
window could take one queued entity and fail the test on a correct implementation.
