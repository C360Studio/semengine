# 2.2 notes: the stopping flag

- The flag is an `atomic.Bool` on `Component` (`stopping`), beside `failedCount`, the component's other atomic
  state. `cleanup` sets it just before `c.pool.Shutdown(ctx)`; `processWork` returns first when it is set. It is
  never cleared: a stopped component is not restarted (a second `Start` is refused), and a `Stop` retried after its
  context ended sets it again, which changes nothing.
- `TestStopWritesAcceptedWork` is removed: it proved only the old rule that every accepted entry is written before
  `Stop` returns nil. Its other checks (no `ErrorCount` change, no WARN or ERROR line) are in
  `TestStopDropsQueuedWork`.
- `TestStopInterruptedThenRetriedWritesAcceptedWork` is removed. What still holds, a `Stop` its context ends returns
  that error and a later `Stop` returns nil with nothing failed, is the order `TestStopDropsQueuedWork` runs (first
  `Stop` under an ended context, then a retried one). Its own setup depended on the drain outlasting a cancel, which
  the flag makes too short to rely on.
- The admission ledger's graph-index row names `TestStopDropsQueuedWork` in place of `TestStopWritesAcceptedWork`.
- Comments rewritten to the new rule: `component.go` (the run context in `start`, the `stopping` field, `cleanup`),
  `index.go` (`startIndexPool`, `processWork`), and the tests' `stopBound` and the unit test of an ended-context
  `Stop`.
