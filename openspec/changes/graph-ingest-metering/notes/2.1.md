Choices the design does not spell out:

1. Each row of the refusal table builds its own component, so its WARN count reads only its own request's log. The
   rows that need a stored entity create it by calling `handleCanonicalCreate` directly (`createCanonicalEntity`),
   before the test's logger is installed, so the seed is neither metered nor logged.
2. Revision mismatch is the read mismatch (`:296` reconcile, `:449` delete): the request names the created revision
   plus one. The CAS-lost sites (`:315`, `:455`) go through the same wrapper and are not driven here.
3. The `invalid_request` row is a create with no entity; the predicate row is a create with three triples whose
   predicates fail for two distinct reasons (`arity` twice, `segment_start` once), the case
   `mutation_rejection_metric_test.go:110` pins, so each reason must rise by exactly one.
4. Each row also asserts its WARN line's message and `reason=` attribute; the two revision rows also assert
   `subject=`. The authority row's message is the authority gate's
   (`graph-ingest: entity authority rejected`); its rejection reason is `authority_foreign` and its outcome
   `entity_id_authority_invalid`.
5. `TestMutationOutcomeCountedAtTheDecision` checks each reply's outcome before it checks the counts, so a count is
   never compared against a branch the request did not take. The append's third subject is a local ID no test
   creates (`acme.ops.robotics.gcs.drone.003`).
