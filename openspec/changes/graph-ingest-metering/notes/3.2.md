# Task 3.2 notes

`TestIntegration_DataFlowCountsInputMessages` (task 3.1) passes with this change; it failed on the base by assertion
(`notes/3.1.md`), so it needs no mutation check. The task gate
`git grep -n 'messagesProcessed' -- processor/graph-ingest ':!*_test.go'` shows four lines: the field
(`component.go`), the two increments (the consume callback in `component.go`, `meteredCanonicalMutation` in
`canonical_mutations.go`) and the `DataFlow` read.

Choices the design does not spell out:

1. The three increments (messages, bytes, last activity) are written out at each of the two sites, not put in a
   helper, so the task gate's grep finds exactly two increments.
2. `replaceEntity` (`entity_writes.go`) no longer returns the size of the value written. Its one caller,
   `mergeEntityOnLane`, used it only for the byte count that moved to the consume callback, so the return was dead.
3. Append's applied subjects count on `entities_updated_total` inside `addTriplesLane`, beside the commit that records
   the subject's revision, as merge and `CreateEntity` count at their writes. `handleCanonicalAppend` is that body's
   only caller.
4. `TestComponent_MetricsAtomic_MessageProcessing` (`metrics_test.go`), which the design does not name, asserted that an
   in-process `CreateEntity` counts one message and its stored bytes. It now asserts that it counts neither, and that a
   failed in-process write still counts one error and no message. A stale comment in
   `TestComponent_MetricsUpdate_EntityOperations` saying the append lane counts no updates is removed.
5. `TestComponent_DataFlow_ReturnsMetrics` sends one create request through `meteredRoute` (the wrapper
   `setupMutationHandlers` subscribes). Its error-rate step still fails an in-process `CreateEntity`, which counts an
   error but no message, so the rate is one error over the one request.
6. `DataFlow`'s doc comment and the counter fields' comment now say what is counted. The README paragraph is under
   § Health.
7. The `graph-ingest-recovery` ADDED delta was checked against the code and left as written: a delivery counts at the
   start of the consume callback, before the metadata check, so redeliveries and refused messages count; a mutation
   request counts when it reaches the wrapper (a request refused before `Start` completes is answered in
   `subscribeForRequests` and never reaches it); queries, in-process creates and container births do not count; and
   `ErrorRate` divides `c.errors` by the input count.
