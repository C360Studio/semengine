# ADR-112: natsclient Passes nats.go Through and Promises Only What Is Measured

## Status

**Proposed (2026-10-11)** on draft PR #177 (`Addresses #170`, `Addresses #168`), under the owner's ruling of
2026-10-10 (epic #9 comment 6098388541): a record of natsclient's contract over nats.go, before change 3. Measured at
nats.go v1.54.0 and nats-server v2.14.7 (`go.mod:12-13`, `.nats-image:5`) on darwin/arm64. Probes: P6 to P9 on PR #156
(comments 6098409783, 6098410018), Codex's blocked-write and denied-subscribe probes (PR #156 comment 6097783327),
P10 to P16 and the reviewer's p15b on PR #177 (task 1.3 records the comment ids). A line backed only by a posted
probe describes these versions. A "test" below is an in-tree test that drives the pinned nats.go against the pinned
server (embedded, or the `.nats-image` container) or a scripted one.

## Context

`transport-client` (from PR #48) promises that `Close` returns within its context. Nobody measured nats.go when that
was written, and it is false (#170, #168): nats.go takes one lock for every write on a connection, and a write the
server is not reading holds that lock until the write completes or nats.go's write timeout ends it
(`DefaultFlusherTimeout`, one minute, `nats.go:68`). natsclient sets no write timeout (`client.go:634-659`).

A correction to #168 and PR #156's P6: their "returned at 59.7 s after the server read again" timed the probe's own
`IsConnected` call, which waits for the same lock. A held call returns 0 to 29 ms after the server reads again
(P13, 16 of 16).

## Decision

natsclient passes nats.go's behaviour through. It adds no write bound, watchdog or reconnect logic over a held
write. A line below is a promise only where a probe or a test backs it; anything not measured is listed as not
promised.

### 1. Time

- The caller's context ends the wait for the server's answer: `Subscribe`'s PONG (or `DefaultRequestTimeout`), a
  request's reply, Close's wait for its drain (P13 idle; tests `subscribe_registration_test.go:296`, `:318`,
  `client_lifecycle_test.go:530`).
- It does not end a wait for nats.go's lock. While the server is not reading and the send buffer is full, every call
  that writes on the connection, `Close` included, waits for each held write ahead of it until the write completes or
  the write timeout ends it, one minute per write. No ceiling was observed (P13: released when the server reads;
  P14, server never reading: a 50 ms `Close` returned at 3 m 1.6 s in one run and was still held at 200 s in the other).
- `Connect`'s dial is bounded by `WithTimeout` (5 s by default), once per URL, not by the context; an ended context
  still dials (P12).
- Not promised: the connection's state after a write timeout has dropped bytes (in P11 and P14 it reported connected,
  and a later 10 s `Close` failed in 16 of 26 runs); timing on Linux; whether the ping timer detects a stalled server
  while a write is held.

### 2. What a nil return means

- `Subscribe`, `SubscribeForRequests`: the server has read the SUB (test `subscribe_registration_test.go:240`; P7),
  not that it accepted it. A refused SUB returns the subscription and nil (P8; Codex's denied-subscribe probe; #169).
- `Publish`: the message is in nats.go's buffer, not sent (P14: nil after 1 m 59.6 s with the server never reading).
- `PublishToStream`: the server stored it in the stream's storage class; on a memory stream it does not survive a
  restart (test `integration_test.go:109`).
- `Close`: everything the client owns has finished: handlers, its background work, the event handlers of a
  connection it dialled (tests `client_close_final_test.go:227`, `:835`, `:1328`, `:1399`, `:1442`). The async
  publish error handler is joined only as far as nats.go lets the client see it (`client.go:1630`; not measured).
- A KV write that returned an error may still have committed: `Put` (P15), `Create` and `Update` (p15b) returned
  `context deadline exceeded` while nats.go reconnected, and their values stood afterwards. Not promised: what an
  update loop does when the connection drops between its read and its write.

### 3. Error classes, by type and sentinel

- A class is read with `errors.Is` and `errors.As` (ruling N, #91 comment 6080973822; #146). natsclient returns
  `ErrNotConnected`, `ErrCircuitOpen` and `nats.ErrNoResponders` unwrapped, and `errs.IsTransient` is false for all
  three. It wraps as transient a failed `Subscribe` round trip, Close's drain timeout and Connect's dial error (P10).
- `errs.Classify` gives an unclassified error `ErrorTransient` (P10; #167), and a handler's unclassified error goes on
  the wire with that class (`errors.go:311-322`, read).
- Until #93 merges, `errs.IsTransient` also matches by text on `main`, so Close's refusal and eight nats.go sentinels
  read as transient there and not after it (P10, both trees).
- Two classifiers read nats-server's text on both trees: `isAlreadyExistsError` (`client.go:2335-2342`) and
  `isCircuitNeutralStreamCapacityError` (`client.go:528-541`). Their answers are not promised.
- `natsclient.ErrCircuitOpen` (`client.go:54`) and `errs.ErrCircuitOpen` (`pkg/errs/errs.go:79`) are two sentinels for
  one fact; `IsTransient` knows only the second (P10).

### 4. Ownership

A subscription or consumer the client created is the client's: `Close` stops it and joins its handlers, including
one on a connection `SetConnection` replaced. The replaced connection stays the caller's (tests
`client_close_final_test.go:1399`, `:1442`). A `Subscribe` that fails does not wait for its running handler; `Close`
joins it (test `subscribe_registration_test.go:390`). Once `Close` begins, new work is refused (test
`client_close_final_test.go:960`).

### 5. Reconnect

natsclient keeps nats.go's automatic reconnect, with unlimited attempts and `ReconnectWait` 2 s, natsclient's settings
(`client.go:344-345`). While
reconnecting, `Publish`, `Request`, `RequestClassified`, `Subscribe`, `PublishToStream` and `GetStream` return
`ErrNotConnected` at once. KV calls wait for their context, and their writes may commit after the reconnect (P15).
Not promised: reconnect pacing, the 8 MB reconnect buffer (`nats.go:64`), consumers across a reconnect, redelivery on
a file stream after a broker restart, failover between servers.

### 6. Where this record and other text disagree

This record holds. The `natsclient-contract` change cuts `transport-client` to match it. #168 corrects natsclient's doc
comments and README.

## Alternatives rejected

- A short `FlusherTimeout`: in nats.go's code a write that times out drops its bytes (`nats.go:2369-2372`; read, not
  measured, and P6's 1 s runs lost none), so a slow link could lose publishes that a minute would deliver.
- Closing the socket through the dial seam when Close's context ends: a new mechanism that covers `Close` only, and
  not a connection given through `SetConnection`.
- `ReconnectOnFlusherError` (`nats.go:1393`): covers the background flusher only, not a publish that flushes inline
  (`nats.go:2346-2347`); not measured.
- `ForceReconnect` (`nats.go:2622`) on a stall: natsclient would need a watchdog to see the stall.
- Releasing natsclient's lock before `IsConnected` in `subscribeOwned`: `Close` still waits for nats.go's lock behind
  the same write (P13 and P14 hold `Close` with no `Subscribe` running).
- Doing nothing: the spec keeps a promise that P13 and P14 contradict.

## Consequences

- A component's `Stop` that closes its client can be held for minutes by a server that stops reading. Change 3's
  design states its shutdown with that limit.
- A retry keyed on `errs.IsTransient` does not retry `ErrNotConnected`. A KV write's error is commit-unknown: re-read
  before retrying a write that is not compare-and-set. ADR-111 Decision 2's create-once write inherits this: an error
  other than `ErrKVKeyExists` may have written the outcome.
- Transport statements other records make are not covered here. ADR-110:192 (a watcher sees every revision; the
  pin's ADR-066 `:408-409` says a lagging watcher does not) is for ADR-109 (#110). Redelivery after a process kill is
  #93's task 4.4. Redelivery on a file stream after a broker restart (ADR-111 `:116-117`, #93's
  `graph-ingest-recovery` `:17-26`) is tasked nowhere and is not promised (§5).
