# Task 3.5: natsclient holds no lock of its own while it calls nats.go

Choices the design (D3) and the prototype do not spell out, or that go past them.

- **The three sites follow the prototype.** `MaxPayload` reads `m.conn` under the read lock and calls `IsConnected` and
  `MaxPayload` on its copy after releasing it. `SetConnection` calls `IsConnected` before taking the lock. In
  `subscribeOwned`, the lock-held check is `conn == nil` only; the work is admitted and the lock released, and then
  `IsConnected` runs. When it reports false, the work is uncounted (`finish`), and the call returns
  `nats.ErrConnectionClosed` (wrapped, "client closed") if `closing` is closed, else `ErrNotConnected`. The select
  reads the closing signal already in hand rather than taking the lock again.
- **The comments cite T2 and P21** at both moved calls (`SetConnection`, `subscribeOwned`), for the nats.go fact that
  `IsConnected` waits for the connection's lock.

## Is any other call made under natsclient's lock?

This awk script, run as `awk -f lockscan.awk $(ls natsclient/*.go | grep -v _test.go)`, flags a method call on `conn`,
`nc`, `m.conn`, `c.conn`, `js`, `m.js`, `sub` or `kv` made while a mutex named `mu` or `...Mu` is held, treating an
unlock followed by `return` as an early exit:

```awk
# Flags calls on nats.go values made while a natsclient mutex is held. An unlock
# followed by a return is an early exit and does not release the main path.
/^func /{held=0; pend=0}
pend { if ($0 !~ /^[ \t]*return/) held=0; pend=0 }
/[A-Za-z]+\.([a-z]+M|m)u\.(R)?Lock\(\)/ && !/defer/ {held=1}
/[A-Za-z]+\.([a-z]+M|m)u\.(R)?Unlock\(\)/ && !/defer/ {pend=1}
/^}/ {held=0; pend=0}
held && /(conn|nc|m\.conn|c\.conn|js|m\.js|sub|kv)\.[A-Z][A-Za-z]*\(/ {print FILENAME":"FNR": "$0}
```

On 2e25e09 (before this task) it finds exactly the four lines of D3: `client.go:410`, `:413` (`MaxPayload`), `:427`
(`SetConnection`) and `:1392` (`subscribeOwned`). On this task's tree
it finds only `socket.go:71`, the dialer closing its own `net.Conn` under its own mutex, which is not a nats.go call.
What it cannot see: a call made through a helper under the lock, and receivers with other names. One such site is
known and deliberate: `guardedConsumer.Info` and `CachedInfo` hold the handle's `infoMu` across the call, to guard
nats.go's unsynchronised cache field; that lock is per consumer handle, and `Close` does not take it.

## A test for the new error branch, beyond the task

T2 requires only an error from the held `Subscribe`, so no named test fails when the new branch returns
`ErrNotConnected` after `Close` has begun. Measured over 100 runs of T2 (a temporary log line, removed; the test file's
SHA-256 matched after), the `Subscribe` returned:

```text
  33 Client.Subscribe: client closed failed: nats: connection closed
  50 nats: connection closed
  17 nats: connection draining
```

The first line's text is shared by the new branch and the round-trip branch, so T2 cannot show which ran.
`TestSubscribeEndedByCloseIsConnectionClosed` does. A reconnect dial (T8's set-up, now `newReconnectDialClient`) holds
nats.go's lock until `Close` cuts it, and after the cut no reconnect can succeed, so the `Subscribe`'s connection
check runs after `Close` began and always fails. The test requires `nats.ErrConnectionClosed` and not
`ErrNotConnected`. T2 and the new test share `awaitSubscribeAdmitted`.

The other two lines are not this task's to change, and are reported to the orchestrator: when the native `subscribe`
step fails, `subscribeOwned` returns nats.go's error unwrapped (`client.go`, `if err != nil { finish(); return nil,
err }`), so a `Subscribe` that `Close` ended can return `nats.ErrConnectionDraining`. That path existed before this
change: `Close` could begin between the unlock and the native `subscribe` then too. The spec's error order starts
"when the round trip ends", which that path never reaches.

## What is not covered

`MaxPayload` and `SetConnection` have no test of their own, as the design names none: T2 covers `subscribeOwned`. No
test here shows that one of them, waiting in `IsConnected`, no longer holds `Close`; the scan above is the evidence that
neither holds the lock across a nats.go call.
