## M3 survives: why T3 does not distinguish it

M3 is reported as a survivor, not a detection, and it is not equivalent. What follows explains only why T3 cannot tell
it apart, read from nats.go v1.54.0's source (not promised across nats.go versions, ADR-112).

T3 builds the subscription first, then holds its handler, unsubscribes and begins `Close`. After construction a core
subscription records its delivery's end (`ownedDelivery.end`) from nats.go's closed handler (`natsclient/client.go:935`).
nats.go's `waitForMsgs` runs the callback, `mcb(m)`, inside its loop (`nats.go:3807`) and the closed handler,
`done(s.Subject)`, only after the loop exits (`nats.go:3829-3835`), on the same per-subscription goroutine. So while
T3's handler is held, `d.ended` is still false when `Close` begins, and M3 cancels exactly as the code does. The reach
run agrees: line 1187, inside the `closing` case, ran, and the test passed.

### Unmeasured: a connection close while the subscription is being built

`newSubscription` also records the end itself: when `sub.IsValid()` is false it calls `s.closeDone()`, which runs
`d.end` (`natsclient/client.go:936-939`). At v1.54.0 that state can hold with a handler running:

- `subscribeLocked` starts the delivery goroutine (`go nc.waitForMsgs(sub)`, `nats.go:5165`) before `Subscribe`
  returns, so a message can be delivered and its callback be running before `newSubscription` is called.
- A connection close marks every subscription closed (`s.closed = true`, `nats.go:6215`) and only signals the delivery
  goroutine; it does not wait for a running callback (`nats.go:6196-6227`).
- `IsValid` then reports false (`nats.go:5256-5262`), and `newSubscription` records the end with `running == 1`.

If `Close` begins after that point, or had begun and its drain timeout forced the close, the code's watcher
cancels the running handler's context and M3's watcher does not. No test drives this ordering: it needs a request to
arrive and a close to land between `conn.Subscribe` returning and the `IsValid` check, an interleaving the test cannot
choose without a hook in production code. It is recorded here as unmeasured, not as a defect: the code does the
right thing on that path, and only M3's survival leaves it unproven.

The watcher cancels when `Close` begins after delivery has ended both for that path and because it has the shape of
`ownConsumer`'s, where JetStream consumers reach that state too (`ownConsumer` calls `d.end()` itself,
`natsclient/owned_delivery.go:155`). Disposition (coordinator, task 2.3, narrowed after Codex's review of
`dea820f`): no test or code change; the result is recorded on the M3 line of `design.md` § Mutants.

## Generated checks: not used; named examples cover the orderings

`docs/testing.md` ("Decide whether generated checks are needed") asks for this decision because the change is a
shutdown history: what a handler's context does depends on the order of setup, requests, `Unsubscribe`, `Close` and
connection loss. This change uses no generated checks. The examples below name each ordering the design changes.

| Ordering | Test |
| --- | --- |
| Setup context cancelled, then a request arrives: the handler's context is live (T1) | `TestRequestHandlerContextOutlivesSetupContext` |
| Handler running, then `Close` begins: its context ends, and `Close` returns nil after it returns (T2) | `TestRequestHandlerContextEndsWhenCloseBegins` |
| Handler running, `Unsubscribe`, then `Close` begins: as T2 (T3) | `TestRequestHandlerContextEndsWhenCloseBeginsAfterUnsubscribe` |
| graph-ingest's Start context ends during the first query registration, or the first mutation registration (T4, T-G4's two rows) | `TestGraphIngest_StartFailsWhenItsContextEndsDuringHandlerSetup` `query`, `mutation` |
| A registration fails at the first query, or the first mutation, subject (T-G4's two rows) | `TestGraphIngest_StartReportsItsContextWhenHandlerSetupFails` `query`, `mutation` |
| The connection closes on its own (no reconnects left), then `Connect` is called (T5) | `TestIntegration_ReconnectionIsRedial` |
| graph-ingest's Start context ends after the last registration, before setup returns; a later `Stop` (T6) | `TestGraphIngest_StartFailsWhenItsContextEndsAfterHandlerSetup` |

Why examples suffice: the outcome turns on a few fixed points, not on accumulated state. The handler root ends on one
transition, `Close` beginning, and the only other input is whether a handler is running then, before or after
`Unsubscribe` (T2, T3). graph-ingest's `Start` registers in a fixed sequence, query handlers then mutation handlers
then a final context check, so the Start context can end at three places, and each has a test (T4's two rows, T6).
Nothing repeats, retries or replays, so there is no sequence length or combination for a generator to grow. The
remaining interleavings are between nats.go's delivery goroutine and a close, which a generated history could not
schedule without a hook in production code either.

Uncovered orderings:

- A connection close while the subscription is being built, with a handler running (above); M3 survives because of it.
- `Close` beginning while `SubscribeForRequests` is between admission and its round trip: no test this change adds
  drives it, and the change does not alter that path.
