## Inconclusive and repeated runs, and why

- **M15, first check: inconclusive.** All three mutant runs failed at `validate_document_test.go:104` with
  `Validate = <nil>, want an error naming tls.server.cert_file`, which is the intended failure. The verdict was
  inconclusive because the runner script that passed `-expect-text` turned the `_` in `cert_file` into a space, so the
  text named in the expectation matched no line. The second check named the location
  `validate_document_test.go:104` and gave detection. The test was not changed.
- **M10b, a stray first check: inconclusive.** A leftover line in the run plan ran the new M10b wrong change with the
  old expectation `mermaid_test.go:38`. The test failed at `:72`, so the verdict was inconclusive. The check that
  names `:72` is the one recorded above.

## M10 is an equivalent mutant

Dropping `ConnectionID` from `compareEdges` cannot change any output a test can observe, for three reasons:

1. Edges reach `compareEdges` already in a fixed order. `connectStreamPorts` visits connection IDs sorted
   (`internal/flowgraph/flowgraph.go:458-460`), and the projection is built from declarations sorted by instance name.
2. Within one pattern, flowgraph keeps one edge per port pair (the `seen` sets in the stream and request connectors).
   So two projected edges never agree on source, source port, target, target port and pattern while differing only in
   connection ID. In such a pair, the ID would be the only key that decides the order.
3. `slices.SortStableFunc` keeps input order among equal edges, and `Mermaid` never prints the connection ID.

The design predicted a detection here, and M10 survived. The key stays in the comparator: it keeps the order total if
flowgraph ever emits two such edges. M10b and M10c show that `TestMermaidIsDeterministic` detects a broken edge order
on keys Mermaid does print.

## Choices the design does not spell out

- **`TestMermaidIsDeterministic` gained the spec scenario's half.** The test checked equality only across five
  `Validate` calls, whose edges always arrive in the same order. It now also renders a hand-built `Graph` twice, with
  its nodes and edges reversed the second time, and checks the two renders are equal and hold every edge. Two of its
  edges differ only in their source, so an edge order that ignores `From` renders them in input order (M10b). The
  existing assertions are kept. This follows the coordinator's ruling on M10.
- **Mutants that would not build were avoided.** Removing M6's only use of `graphmutation` would leave an unused
  import, so `_ = graphmutation.SubjectFamily` keeps it used. M8 ranges over `declarations[:0]`. M10c keeps the
  `slices` import used with `_ = slices.SortStableFunc[[]Edge, Edge]`.
- **M10's test.** The design names no test for M10. Both determinism tests were tried. Their verdicts are in the
  table above.
