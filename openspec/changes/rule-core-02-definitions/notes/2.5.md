## Choices the design leaves open

- **`Load` returns `*Rule`**, as the target-shape page sketches. `Rule` holds the definition with its conditions
  compiled and its action lists emptied, and five lists of checked actions, each with its `when` compiled and its
  firing-cap key. No field has a reader yet; the engine that fires rules reads them.
- **The checked action is the one `decodeAction(Body)` returns**, not the caller's: after the fields-to-`Body` check
  they say the same, and the decoded one has its own `When` slice and `Body` copy, so compiling it never reaches the
  caller's definition. Conditions are copied, then compiled one element at a time, so a refusal names
  `conditions[<i>]` or `on_enter[<i>].when[<j>]`.
- **Rule types.** `expression` gets the factory checks (at least one condition, field, known operator, logic `and` or
  `or`, cooldown a duration). `cron` disabled gets only the checks every rule gets. Any other type, empty included, is
  refused naming the type: the pin had no factory for it and skipped it with a log line.
- **Checks every rule gets**, enabled or not, cron included: the handler set, the ID as one KV literal token,
  `fire_every_n_events` 0 or more, `rerun_on_recovery` with an action to re-run, the entity pattern, the ADR-036
  condition-field check and compile of each condition, and every action.
- **Order inside one action:** body present, body decodes, fields equal to the body, `max_iterations` 0 or more,
  type in the set, the handler's `Check`, then each `when`. The first refusal is returned.
- **"Negative `max_iterations`"** in task 2.1 is read as the action's `max_iterations`, the one the spec bounds. The
  rule-level `max_iterations` is a value conditions read and is not checked, as the pin did not.
- **The condition-field check stays on rule conditions**, not on an action's `when`, as the pin's was; a `when`
  is compiled only.
- **Case variants of rule keys are refused at decode** (ruling on step A's open question 1): after the strict struct
  decode, the top-level keys are compared exactly with `Definition`'s JSON tags (read by reflection, so the list
  cannot drift), naming the key as `json: unknown field "ID"`. Still matched without regard to case: keys inside
  `entity`, a condition, or a `when` condition (`"Field"` is taken as `field`). Open for the reviewer whether those
  get the same check.
- **Test predicates** are declared by `declareTestPredicates` in `builtin_test.go`, called at the start of each test
  that needs them, never from `init`; registering one again amends nothing.
