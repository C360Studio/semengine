# Task 3.13 notes: graph-ingest under the lifecycle suite

Choices the task left to the developer, and what the tests do and do not prove. The files are
`processor/graph-ingest/lifecycle_adapter_test.go` (the adapter, `suiteOwner`), `lifecycle_integration_test.go`
(`TestGraphIngestLifecycleSuite`) and `lifecycle_owner_test.go` (the carried test).

## The three choices

1. **Lane.** The suite runs in the integration lane. Its healthy owners need a Start that succeeds, and that needs a
   broker. There is one fixture broker holding the ENTITY stream, and each healthy owner is a fresh component on a
   client of its own (`natsfixture.Open`), so no client state crosses from one check to the next. An embedded
   nats-server in the unit lane was not used: its version is not the pinned image's.
2. **Calls.** Counted through the existing `consumeStream` test seam, which wraps each handle the client returns:
   `consumer bind`, `consumer drain` and `consumer stop`. No production hook was added.
3. **The failing factory's cleanup succeeds.** Its Start fails on the connection, before the component binds anything,
   and the rollback only cancels and clears. The suite's `FailedStartHoldsNothing` on that factory is the
   `lifecycle-suite` scenario "Cleanup succeeds after a failed start". The branch where the cleanup fails belongs to the
   carried test.

`Promise{}`: graph-ingest is one-shot. Under design D13 a Start after a Stop is refused with `ErrAlreadyStarted`.

## The refused broker

The must-fail client dials `refusingBrokerURL`: a loopback listener on an ephemeral port, kept bound for the whole test,
whose accept loop closes every connection before the server's INFO line. The client's Connect fails on the handshake.
The listener is closed, and its accept loop joined, in `t.Cleanup`.

Two other shapes were rejected:

- A port that was bound and then released (the first version of this task) can be handed to another process, whose
  broker would accept the dial. That is the flake class #89 removed in 89c878e.
- `newTestNATSClient` (`metrics_test.go:140`) builds a client with an empty URL. nats.go replaces an empty URL with
  its `DefaultURL`, `nats://127.0.0.1:4222` (nats.go v1.54.0 `nats.go:54`, `:2176`): a fixed address. A NATS server
  on that port on the host would accept the dial, and the factory would not fail.

## What Observe lists

Under `handlesMu`, one stable name for each handle `clearLifecycleHandles` clears: `runtime cancel`,
`ingest submit cancel`, `ingest pool cancel`, `ingest pool lanes` (the pool is cleared only after its Shutdown has
joined the lanes), `consumers`, `request subscriptions`, `status loop`, `status publisher` and `entity cache`. Under
`boundConsumersMu` (through `boundConsumerSnapshot`): `readiness bound consumers`.

The guard is not listed. It has no read-out (design D22), and every call on it either changes its state or returns
before reading it. The suite's checks reach its states through Start and Stop, as design D13 states them.

## The limit of Calls

Request-subscription drains, the pool's Shutdown and the cache's Close have no seam and are not counted. Their handles
are listed under Unresolved until a cleanup succeeds.

A cleanup that succeeded clears every handle, so a repeated cleanup would have nothing to call. Calls therefore cannot
catch a repeated cleanup on its own. It catches a refused second Start that binds a consumer, and a Stop that drains a
consumer again, and it backs up Unresolved.

## The added subtest

`StartedOwnerReportsItsHandles` is the `lifecycle-suite` scenario "Started owner reports its handles". After a Start it
asserts all ten names and at least one consumer bind; after a Stop that returned nil, no names and one drain per bound
consumer. The eight suite checks judge only what is left after a Stop, so they cannot see an adapter that leaves a kind
out.

## The carried test

`TestLifecycleOwnerFailedCleanupRetainsExactHandlesForLaterStop` cites `lifecycle-suite`, "Failed start whose own
cleanup fails" (design D7.3). It calls the guard's Start (design D22) with a start that fails and, as the rollback,
the component's `release` under a context that has already ended. Then:

- the error carries both causes;
- Observe lists `runtime cancel` and `consumers`;
- a following Start returns `ErrAlreadyStarted`;
- once the consumer double reports Closed, a Stop returns nil and Observe lists nothing;
- the double records one native Drain.

The pin's read of `drainIssued` is replaced by the double's Drain count staying at 1 after the later Stop.

## Mutation and omission records

The release mutation was run with:

```bash

  -test TestLifecycleOwnerFailedCleanupRetainsExactHandlesForLaterStop \
  -file processor/graph-ingest/component.go -mutant <copy> -expect <file:line>
```

The mutant: `release` clears the handles even when cleanup failed. The tree file's sha256 was `087673b0…` before and
after the runs; the mutant's was `02e48bd5…`.

- The test as it was at a4bd37f, which called `cleanup` and not `release`: **survivor**. Three baseline passes, three
  mutant passes; the reach run shows the test reached the mutant.
- The carried test, `-expect lifecycle_owner_test.go:153`: **detection**. All three mutant runs failed at `:153` with
  "held after the failed cleanup = [], want [runtime cancel consumers]", and the after-run passed.

The adapter omission was made by hand, because `lifecycle_adapter_test.go` is a test file and `task mutate:check`
does not apply. The `consumers` line was removed from Observe: the file's sha256 was `1d133fd1…` before, `b747d8e9…`
with the line removed, and `1d133fd1…` once restored. Results:

- All eight suite checks still passed, as the spec's "Adapter omits a retained kind (review check, not a test)" says
  they would.
- `StartedOwnerReportsItsHandles` failed: the list came back without `consumers`.
- The carried test failed at `lifecycle_owner_test.go:153`: "[runtime cancel], want [runtime cancel consumers]".

These records were taken at c40da61, before the refusal shape changed. That change touches only the must-fail factory's
URL; neither the adapter nor the carried test changed.

## Not covered

- The real `Component.Start` failing with a real rollback that also fails. Driving it needs the 5-second rollback budget
  (`pkg/lifecyclecleanup`) to run out against a consumer that never closes. The carried test makes the same guard call
  with `release` as the rollback instead.
- The must-fail owner's Start error is not inspected. The suite sees only that Start returned an error. The run log
  shows a connect attempt to the refusing listener with no "Successfully connected", and the check took 0.00s.
