# Task 4.1 notes: commit ambiguity reaches the caller (#20)

Choices the task left to the developer, what the tests prove and what they do not. The change is in
`pkg/projection/mutation_client.go`. The tests are `pkg/projection/commit_ambiguity_test.go` (wire doubles) and
`processor/graph-ingest/commit_ambiguity_integration_test.go` (`TestIntegration_TypedClientPreservesCommitAmbiguity`,
graph-ingest on a fixture broker).

## Where the fix is

graph-ingest already answers a key-value write it could not confirm with class transient and code `internal`
(`rejectFromError` → `rejectInternal`, `mutation_runtime.go`). The typed client read every classified reply as not
committed (`isDefiniteFailure`). So the fix is on the client, and graph-ingest is unchanged.

`isDefiniteFailure` now reads a classified reply as not committed only when it is class invalid or code
`graph_state_reset_required`. Every other classified reply reports commit-unknown. The transport rule (no responders, a
context already done before the call) is unchanged.

## The choices

1. **`graph_state_reset_required` stays not committed.** The spec's requirement lists three causes for not committed:
   an invalid request, a revision conflict and an entity not found. graph-ingest also sends this fatal code before its
   write, when the entity's state fails the state contract: the stored value on read, or the candidate at the marshal
   gate. The carried test `TestAppendDefiniteSubjectFailureIsNotCommitUnknown` holds it as not committed, so the
   change keeps it. The spec's list and that test disagree. One of them needs to change: either the spec adds a
   fourth cause, or the test is changed. That is a decision for the architect, not this task.
2. **Append's per-subject failure takes the same rule.** An append reports a subject's failure in the response body
   (`MutationFailed` with a class and code), not as a classified reply, and the client read every such failure as not
   committed. It now goes through `mutationFailure` as well. Without this, a transient `internal` on that path would
   still report not committed.
3. **Reads are unchanged.** `ReadAuthoritative` maps a classified reply to not committed, whatever its class: a read
   writes nothing. Reconcile's receipt for a failed read was already not committed. With the new rule applied to reads,
   the error would have said commit-unknown while the receipt said not committed.
4. **Commit-unknown keeps the reply's class, code and detail.** `unknownMutation` now builds on `newMutationError`, as
   the developer contract's NATS RPC rule asks ("without losing its class, code or detail"), and then sets the kind to
   `MutationCommitUnknown`. An unclassified error maps as it did before.
5. **How the fault reaches graph-ingest.** The test builds the component without `Start` and sets `entityBucket` to a
   `FaultKV` over the fixture's ENTITY_STATES (made by `kvcatalog.EnsureCatalogBucket`, the production spec). It then
   subscribes graph-ingest's own query and mutation handlers (`setupQueryHandlers`, `setupMutationHandlers`), as
   `TestIntegration_PrefixQuery_IndivisibleEntityTooLarge` already does. Setting the field after `Start` would race:
   the handlers' goroutines exist by then, and no lock orders the test's write before their read.
6. **The conflict is the bucket's own refusal.** A `_test.go` wrapper (`foreignWriteBucket`) over the `FaultKV`
   can write the key once more just before graph-ingest's next update. The update then carries a stale revision and
   the bucket refuses it. The log shows the branch after the write call ("concurrent modification"), not graph-ingest's
   earlier revision check. Not-found is a delete of an absent entity, which goes through the same predicate.
7. **Doc comments.** `CommitUnknown` and `MutationCommitUnknown` said "delivery without a valid reply"; a valid
   transient reply now reports commit-unknown too, so both comments were reworded.

Generated checks are not used. The input is a finite set: the classes and codes graph-ingest sends. The table in
`TestClassifiedReplyIsNotCommittedOnlyWhenRefusedBeforeWrite` covers each code across the four write operations.

## graph-ingest's write paths, checked

The rule: no failure after the bucket call is answered with class invalid, and no failure before it with a transient
class.

- **Create.** After `Create`: key exists → invalid `entity_already_exists`. The bucket refused, so this request wrote
  nothing. Any other error is transient `internal`. Correct.
- **Reconcile.** After `Update`: a revision mismatch or not-found → invalid, both bucket refusals; anything else is
  transient `internal`. Correct.
- **Append.** A failure after the write is transient `internal`, carried in the per-subject result. Correct; choice 2
  makes the client read it.
- **Before the write, answered transient (not changed).** Create with no payload registry (`rejectInternal`); a key
  value read failure in reconcile and delete (`readEntity` → `rejectFromError`); a candidate that fails to marshal
  for a reason other than the state contract. Each now reports commit-unknown. That is safe, but less exact than the
  pin. Making them not committed needs a code meaning "transient, nothing written", which the task forbids adding
  without a report, so none was added.

Found, not fixed (each needs more than a line):

- **`response_too_large` after a commit.** natsclient's request callback (`natsclient/request.go:455-470`) answers a
  handler's success response that exceeds the broker's payload limit with class invalid, code
  `response_too_large`. On a mutation that reply follows a commit, and the client reads it as not committed. The
  pin does the same. Telling it apart needs the code exported from natsclient (an exported-surface change) or a
  second spelling of it, so neither was done. The gap is declared in `isDefiniteFailure`'s doc comment. Whether a
  mutation response can exceed the limit, given ENTITY_STATES' value size, was not measured.
- **Append's retry loop.** `UpdateWithRetryRead` retries an update error that is not a conflict. If an earlier
  attempt's write stood, a later attempt's not-found or state-contract refusal is answered as not committed. Under
  `FailAfter` alone the retry reads its own write, deduplication declines, and the append reports unchanged
  (verified). That outcome is correct.
- **Bookkeeping after an unconfirmed write.** When `Update` returns an error, `committed` does not run, so the entity
  cache entry and a poison record are not invalidated, although the write may stand. Exact reads go to the bucket
  (`readEntity`), so commit resolution through `ReadAuthoritative` is not affected; cached queries may serve the
  older entry until its TTL.
- `pkg/lifecycle/graph_emit.go`'s `classifyEmitError` reads the same replies on its own: a classified reply other than
  the three named codes becomes `ErrEmitFailed`, with no commit state. It claims nothing committed or not, and it is
  outside this row.
