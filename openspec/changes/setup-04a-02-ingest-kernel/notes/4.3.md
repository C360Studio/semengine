# Task 4.3 notes: the applied-sequence record is keyed by stream generation (#15)

Choices the task left to the developer, what the tests prove and what they do not. The change is in
`processor/graph-ingest/keyed_ingest.go` (the record, the rule, the degrade) and `processor/graph-ingest/component.go`
(where the generation is read, the counter). The tests are `guard_generation_test.go` (processIngest and the consumer
setup, on the mock buckets) and `guard_generation_integration_test.go` (graph-ingest on the fixture broker).

## What changed

A **stream generation** is one lifetime of a JetStream stream (design glossary). The guard record for an entity and
stream now holds the generation the last applied input came from and that input's sequence. An input is dropped as a
redelivery only when it comes from the same generation at a sequence not newer than the last applied
(`guardRecord.covers`). An input from any other generation is applied, and its apply replaces the record.

## The choices

1. **The generation is the stream's creation time, `StreamInfo.Created`, read from the server.** graph-ingest already
   asks the server for the stream's info while it waits for the stream to exist (`waitForStream`, `js.Stream`); the
   wait now returns the creation time from that reply. It is read once per input port, in `Start`, before the consumer
   is bound, and every input the consumer delivers carries it, so no input arrives before it is known (task 4.17 adds
   a second read after the bind; `notes/cp4i-R3.md`). A stream that
   reports no creation time is refused and `Start` fails: with a zero time every generation would look the same.
   Why it is the generation: the server sets the time when it creates a stream, and keeps it when it recovers a
   file-backed stream after a restart (nats-server v2.14.7 `server/jetstream.go:1581-1583`), so a file stream that
   survives a broker restart is still the same generation, and a memory stream recreated after one is a new one.
   `TestIntegration_IngestGuard_FileStreamKeepsItsGenerationAcrossRestart` proves the first half on the fixture.
   Message metadata carries the stream name and sequence, not a generation, so nothing per message can replace this.
2. **The generation goes in the stored value, not the key.** The key stays `<entity ID>/<stream>`; the value is sixteen
   bytes, the generation then the sequence, each big-endian. With the generation in the key, every recreation of a
   stream would leave a full set of records behind, one per entity, and nothing could remove them: the bucket is
   operational state with no lifecycle (`kvcatalog.go:148`, `RetentionNoLifecycle`; a TTL is stripped at acquisition,
   `keyed_ingest_integration_test.go:35`). In the value, the first apply of an entity in a new generation replaces the
   record the old generation left; an entity never ingested again keeps one old record, as before. Generations are
   compared for equality, not order: they are creation times, and in a cluster two servers' clocks need not agree.
   D21 keeps holding: a value of any other length is refused, the spec's three-byte record among them
   (`TestCorruptGuardRecordIsRefused`, unchanged in logic). So is the pin's eight-byte record, a sequence with no
   generation. A bucket SemStreams wrote therefore refuses each entity's inputs until its key, or the bucket, is
   deleted; the design's text (D21, "cannot decode covers whatever value format that work chooses") gives no other
   reading, and nothing in SemEngine has written the old format outside tests.
   `TestGuardRecordOfAnyOtherLengthIsRefused` now tries 0, 8, 15 and 17 bytes.
3. **The no-bucket degrade logs and counts each input it applies as first seen.** The counter is
   `semengine_graph_ingest_unguarded_inputs_total`, registered through `metric.RegisterOrGet`, keeping the collector it
   returns (`registerMetrics`). The log is a warning per input, naming the entity, stream and sequence. Per input,
   because nothing repeats it: the input is applied and acknowledged, so there is no redelivery loop to flood the log
   (the reason D21 logs once per key), and only a component built without `Start` has no bucket. An input the lane's
   cache has seen is judged there and is neither logged nor counted.

## What is not covered

- A stream deleted and created again between graph-ingest's stream-info read and its consumer's creation, inside one
  `Start`. The consumer would belong to the new generation while its inputs carry the old one. Closing it needs a
  second read after the bind and a hold on inputs until the two agree; not done here. Task 4.17 does it (Codex
  interim review R3; `notes/cp4i-R3.md`), and leaves two cases open:
  - a single-server restore inside the window, which keeps the creation time (nats-server v2.14.7
    `server/stream.go:9331-9333`); a declared limitation by the owner's ruling (#91 comment 6112550268);
  - a pull that outlives its consumer's deletion and is later answered by a same-named consumer on a new stream
    (nats.go v1.54.0 `jetstream/pull.go:225`, `:740`).
- A stream recreated while graph-ingest runs. Its consumer is deleted with the stream and nothing binds a new one, so
  graph-ingest stops receiving until it is restarted; that was so at the pin and is outside #15.
- Two graph-ingest processes sharing the durable consumer. The guard already assumes one writer per key
  (`ingestGuardStampDurable`'s comment), and the generation does not change that.
- An input from an older generation than the record's is applied. With one graph-ingest it cannot arrive: its
  consumer was deleted with the older stream.
- Generated checks: not used. The rule has two inputs, generation equal or not and sequence above or not; the unit
  test covers each pair on both the cache and the stored record, so named examples suffice.
