# Task 4.4 notes: settlement (Q18)

Choices the task left to the developer, what the tests prove and what they do not. Task 4.4 has two parts; this file
holds part 1, the process-kill test and the durable-record failure test, and part 2's commit A, the consumer's
acknowledgement wait and the long-apply test's failing-first run.

## Part 1

Both tests are in `processor/graph-ingest/settlement_integration_test.go`, under the `integration` tag, on the fixture
broker with a file-backed `ENTITY` stream. No production file changed.

- `TestIntegration_Settlement_ProcessKilledBetweenApplyAndAck` holds `graph-ingest-recovery`, "Process killed between
  apply and acknowledgement" (design D8, "The settlement process-kill test").
- `TestIntegration_Settlement_FailedGuardWriteIsRedelivered` holds `graph-ingest-recovery`, "Durable record fails"
  (design D8, row "Settlement (Q18)").

Graph-ingest already settles in this order (`keyed_ingest.go:283-293`: the applied-sequence record is written, then
the input is acknowledged; a failed write is negatively acknowledged). Both tests pass on the code as it was, so each
is shown able to fail by a mutant (below), not by a failure before a change.

What the unit tests did not cover. `keyed_ingest_test.go`, `guard_record_test.go` and `guard_generation_test.go`
exercise a failed guard read (`TestGuardReadFailureIsNotARefusal`), a failed apply that writes no record
(`TestProcessIngest_DirtyStoredStateNaksAndInventoriesPerEntity`, `:313`) and an undecodable record. None makes the
record's write fail after the entity write succeeded, so "Durable record fails" had no test of any kind: neither the
negative acknowledgement on a real consumer nor the delivery that follows it.

### The choices

1. **The wrapper is installed through the `consumeStream` seam the component already has** (`component.go:383-391`,
   "Test-only acquisition seams"), not through a new setter. `Start` acquires the applied-sequence bucket in
   `initStorage` (`component.go:1141-1145`), starts the ingest lanes (`buildIngestPool`), and only then binds the
   stream consumer (`setupJetStreamConsumer`, which calls the seam). Assigning `c.ingestGuardBucket` after `Start`
   returns would race the lanes under `-race`: they were started before the write and nothing orders the write before
   their read. The seam runs on `Start`'s goroutine after the bucket exists and before the consumer binds; it
   re-acquires the bucket (`kvcatalog.EnsureCatalogBucket`, as `Start` does), assigns the wrapped store, and calls the
   real `ConsumeStreamWithConfig`, whose delivery is what hands inputs to the lanes. The assignment is the same
   `_test.go` field write as the foundation D4-A setter (`commit_ambiguity_integration_test.go:82-83`), made at the
   one point where it is race-free. No production failpoint and no new exported surface.
2. **The helper's state.** In: the fixture's URL, in `HELPER_NATS_URL`, through `prochost.Start`'s environment.
   Out: the helper creates a ready file (written, then renamed) under the test's temporary directory once `Start`
   returned; the test polls for it with `probe.Await`. Every wait on a helper stops at once and fails if
   `Process.Alive` turns false, so a helper that died is named as the cause. Everything else the test learns is read
   from the broker, not the helper: the entity bucket, the consumer's info, the applied-sequence bucket. The test
   confirms `Alive` before `Kill`, and reads `Wait`'s status (`SIGKILL`) before starting the second run. The first
   run's `Put` blocks on a channel nothing closes; it ignores its context, since `KVStore` gives it a five-second
   timeout (`natsclient/kv.go:40`) after which a context-bound wait would return and the input would be redelivered
   to the first run.
3. **The durable-record failure test runs in-process**, with a `natsfixture.FaultKV` over the applied-sequence bucket,
   installed through the same seam, and `FailBefore(KVPut, …)`. It refuses one write, not every write until the test
   clears the fault. Measured: graph-ingest's consumer delivers an input at most three times (`MaxDeliver: 3`, the
   default of `component.GetConsumerConfig`, `component/port_jetstream.go:130`), and a negative acknowledgement asks
   for the next delivery at once. With the fault held until the test cleared it, the three deliveries were spent within
   one second and the input was never delivered again: the broker reported `Deliveries:3 DeliveredStream:1 AckFloor:0
   AckPending:0 Redelivered:1` twenty seconds after the fault was cleared. So the refused write clears the fault itself
   and waits on a channel until the test has read the broker (the entity written, the input delivered once and pending
   acknowledgement), then returns its error. The redelivery's write reaches the bucket (`FaultKV.Calls`, one `put`)
   and the redelivery is acknowledged. In-process because what is tested, the order on a real bucket and a real
   redelivery, needs no process boundary; the process-kill test covers that.
4. **What "equal to one application" compares.** The state after one application is read from the broker while the
   record write is held (the process-kill test) or refused (the failure test), and compared with the state after the
   redelivery's acknowledgement, over every key of `ENTITY_STATES`. Two things are left out:
   - `UpdatedAt`. The design says it "is the store's write time, not a statement; it stays the clock" (D15,
     "Statement metadata"), and a merge sets it to the clock (`entity_writes.go:225`).
   - The position of one statement set among the others. Measured on the first run of the process-kill test, which
     compared exactly: it failed only because the content statement moved from first to second, behind the indexing
     profile. `graph.ReplaceBySource` keeps the stored sets an arrival does not carry ahead of the sets it applies
     (`graph/helpers.go:49-50`), so an input applied again moves its sets to the end. The comparison groups statements
     by their (subject, predicate, source) set with a stable sort, so the order inside a set, which `GetTriple`'s last
     tie-break reads, is still compared.

   Reviewer: the second exclusion is a reading of the spec's "equal to the state after one application", which names
   no statement order; `graph-entity-writes` speaks of sets. If order across sets is state, graph-ingest breaks the
   spec on every redelivery and the fix is production work (stop and report), not this test.

### What is not covered

- M1's first detection depends on the broker having processed the early acknowledgement before the test reads the
  consumer; in every run above it had. Had it not, the later delivery-count assertion (`:294`, `:384`) is the one that
  fails, since an acknowledged input is not delivered again. That second path was not observed.
- A broker restart. The requirement names a process or broker restart; the scenario, and this test, a process kill.
- The delivery limit. Three refused record writes in a row leave the input unacknowledged and never delivered again:
  its effect is applied, its record is not. Parking it where it can be seen is `internal/maxdelivery`, change 7 (design
  D8, the paragraph after the process-kill test).
- A stale premise, not changed: `component.go:1137-1138` says the applied-sequence bucket's lack of a TTL is "correct
  for MaxDeliver=0 (unlimited redelivery)"; the consumer's limit is 3.
- If more than 30 seconds pass between the first delivery and the kill, the first run is delivered the input again (it
  queues behind the held write). The test allows it: it requires at least two deliveries, not exactly two.
- Generated checks: not used. Each test drives one input through a fixed sequence of events; there are no interacting
  input cases, so named examples suffice.

## Part 2, commit A

Commit A gives graph-ingest's consumer the port's `ack_wait` and reads `heartbeat_interval` (design D8, "Long apply",
bullet "Configuration"). Settlement is unchanged: nothing sends `InProgress` yet. Commit B, which runs each input
through `natsclient.ConsumeDeliveryWithHeartbeat`, follows.

- `defaultIngestAckWait` (`component.go:1360`) is 30 s, passed to the consumer, so natsclient's fallback
  (`natsclient/stream.go:908`) is never reached. `ingestDeliveryTiming` (`:1367`) returns the port's pair, or 30 s and
  a quarter of the wait in effect. `setupJetStreamConsumer` passes the wait to the consumer (`:1439-1450`) and checks
  the pair before it creates the consumer (`:1451-1460`).
- Test: `TestConfigAckWaitAndHeartbeatInterval` (`config_fields_test.go:238`), through the `consumeStream` seam as
  `startStreamLane` uses it.

### The choices

1. **The check at Start calls `natsclient.ValidateHeartbeatDeliveryPolicy` itself**, so the ceiling of half the wait
   is spelled once, in natsclient. That function requires a work function, and Start has none to give it: the work is
   one input's. Setup passes `checkOnly` (`component.go:1454`), which is never run, and discards the policy. The
   error names the port and the pair and wraps natsclient's.
2. **A negative or zero `ack_wait` never reaches graph-ingest.** The port's own validation
   (`component/port_codec.go:385-394`, `validatePositiveDuration`) refuses both when `CreateGraphIngest` decodes the
   configuration, and `Port.Facts()` refuses them again; `PortDefinition.MarshalJSON` will not even encode one. So a
   zero in `ConsumerConfig.AckWait` means "not declared", and the test's "negative wait" case writes `-2s` into the
   JSON and asserts that `CreateGraphIngest` refuses it. That case passes on the base; the design's "a negative ack
   wait fails Start" was already true, one step earlier than Start.
3. **The interval is read from `ingestDeliveryTiming`, not from the seam.** In commit A the interval reaches nothing
   setup hands on, so the test reads it from the function setup calls, on the component's own port
   (`component.GetConsumerConfig`). Commit B's tests see it in use.
4. **Not settled by the design: an `ack_wait` under 4 ns.** A quarter of it is zero, which natsclient refuses
   ("heartbeat interval must be positive"), so for such a wait the design's "`ack_wait` alone never fails Start" does
   not hold. Not handled; any wait of 4 ns or more holds it.

### The long-apply test's failing-first run

The test is `TestIntegration_Settlement_LongApplyIsNotRedelivered`, written as design D8's developer detail describes
it: a 2 s `ack_wait` and no `heartbeat_interval`; the application held at its applied-sequence write; the oracle, a
durable pull consumer of the test's own on `ENTITY` with filter `entity.>`, a 2 s wait and `MaxDeliver` 3, created
only after the write began and fetched without acknowledging until it had delivered the input three times; every
delivery to graph-ingest counted for `InProgress` through the `consumeStream` seam; no sleeps. It cannot be committed
while it fails (`task verify` must pass), so it is kept outside the repository at
`/tmp/pr93-briefs/4.4-longapply-test.go` (this machine only; SHA-256
`359923fd0bc15bd4c491b545d9231337d9a90d4afdfa494dcbe50baf129b2b6e`). Commit B restores it as
`processor/graph-ingest/long_apply_integration_test.go`.

Two choices in it the design does not spell out:

- **Its held write is a new type, `heldApplyBucket`.** The process-kill test's `heldWriteBucket` neither reports its
  arrival nor ever makes the write. The new one closes `entered` on the first write, then waits for the test's
  release, when it makes the write, or for its context to end.
- **The replaced applied-sequence store has no operation timeout** (`NewKVStore(held, ...Timeout = 0)`). `KVStore`
  gives every write five seconds (`natsclient/kv.go:40`, `applyTimeout` at `:69-74`). The hold lasts about four
  seconds past the write's start, so the write's context would end near the oracle's third delivery, and on release
  the real write would fail on that ended context: the input would be negatively acknowledged and delivered again in
  the run that should pass.

Run on the tree that became commit A (`component.go` SHA-256 `5a3a69de…`, `keyed_ingest.go` `4c3d47c9…`), with
`task test:integration -- -run='^TestIntegration_Settlement_LongApplyIsNotRedelivered$' -v ./processor/graph-ingest/`,
four times; each run failed the same way, in 4.7 to 5.1 seconds:

```text
long_apply_integration_test.go:163: graph-ingest's consumer: {Deliveries:3 DeliveredStream:1 AckFloor:0 AckPending:1 Redelivered:1}; in-progress signals: 0; the oracle's delivery counts: [1 2 3]
long_apply_integration_test.go:165:
    Error:      Not equal:
                expected: 0
                actual  : 1
    Messages:   the input must not be delivered again while it is applied
```

So graph-ingest's delivery was redelivered (`NumRedelivered` 1) with no `InProgress` sent, by the time the oracle had
delivered the input three times. By then graph-ingest's consumer had made all three deliveries its `MaxDeliver`
allows. This measures the design's premise P2: without `InProgress`, graph-ingest's delivery is redelivered, and
counted, no later than the oracle is redelivered twice. Each run's teardown released the write and logged
"component stopped gracefully".

### What is not covered

- The interval's use: nothing sends `InProgress` in commit A. Commit B's long-apply test (at least one signal) and its
  interrupted-work unit test observe it.
- The long-apply test's mutants: none yet. It fails on commit A by design; its mutants are run by hand on commit B
  (#129).
- Generated checks: not used. The configuration test's cases are the design's five named ones; the pair's rules are
  natsclient's and tested there.
