# Task 4.5 notes: a failing payload on the Graphable lane is poison (Q13)

Choices the task left to the developer, what the tests prove and what they do not. The requirement is
`graph-ingest-recovery`, "A failing payload is poison, not a redelivery loop" (spec delta lines 71-81), and design D8,
row Q13.

## What changed

- `processor/graph-ingest/component.go:1593` `decodeEntity`: a deferred `recover` turns a panic in payload code (its
  `UnmarshalJSON` inside `Decode`, its `Validate`, and `EntityID`, `Triples`, `StorageRef` or `IndexingProfile` during
  extraction) into `errs.WrapInvalid(...)`, and `baseMsg.Validate()` runs before extraction, as SemStreams PR #1437
  does. Both errors name the payload type and the subject.
- The consume closure (`component.go:1455-1476`) terminates every `decodeEntity` failure that is not a statement

- `component.go:1137-1141`, the guard bucket's comment: the no-TTL reason no longer depends on the delivery
  limit (folded in from `notes/4.4.md`, "What is not covered", its stale-premise item). Comment only.
- Comments that said a poison message is acknowledged now say terminated: the D15 refusal's comment in the closure
  (`component.go:1457-1459`) and two in `readiness_integration_test.go` (`:82`, `:95`).

## The three choices

1. **The poison count is `c.errors`** (`component.go:487`), the count the poison branch already raised
   (`component.go:1471`). Health reports it as `ErrorCount` (`:829`) and `DataFlow` reads it (`:861`); it is the "error
   count its health reads" the next requirement in the same spec names. No new metric. The `poisoned_entities` gauge is
   a different thing: stored entities whose state cannot be read.
2. **The test-registered payload type** is `fenceTestPayload`, message type `test.fence.v1`, the PR's type with its
   modes. The option `withFenceTestPayload` (in `fact_lane_fence_test.go`) registers it in `deps.PayloadRegistry`, the
   registry `testDependencies` builds with `payloadfixture.NewWithSubset`; the factory then builds the component's
   decoder from it, as it would for a product's type. The `mode` field on the wire picks the failure: `invalid`
   (`Validate` returns an error), and a panic in `UnmarshalJSON`, `Validate`, `EntityID` or `Triples`. No `agentic`
   import. The entity ID is under `c360.test`, the authority the fence fixtures build under, so the authority gate
   admits the conforming message. The stream-lane test rebuilds `c.decoder` from `c.payloadRegistry` after
   `startStreamLane`, which installs the merge-test decoder.
3. **Tests adapted and left out.**
   - `TestDecodeEntity_ValidateFailureRejectsBeforeIdentity`, `TestDecodeEntity_FencesPayloadPanics`,
     `TestHandleMessage_RejectionsLandOnPoisonAccounting`: adapted. The class is read with `errors.As` on
     `*errs.ClassifiedError` (the PR used `errs.IsInvalid`), and every error must name the payload type and subject.
   - `TestDecodeEntity_MalformedLoopExecutionEntityIsInvalid`: left out. It needs `agentic`, which SemEngine does not
     have; the path it drives (a payload's own `Validate` refusing before `EntityID` runs) is the first test's.
   - `TestIntegration_FactLane_PoisonLoopExecutionEntityIsAckDropped` becomes
     `TestIntegration_FactLane_InvalidPayloadIsTerminated`: the same refusal by `Validate`, on the fence type.
   - `TestIntegration_FactLane_PanickingPayloadIsAckDropped` becomes
     `TestIntegration_FactLane_PanickingEntityIDIsTerminated`: the panic moves from `Validate` to `EntityID`, the
     spec's scenario, and the test also requires that the next message on the stream is applied.
   - New: `TestStreamLane_FailingPayloadIsTerminated`, the consume closure over a real keyed pool with a recording
     message, so a unit test sees the disposition, the count, the log line and the next message's application.

## The acknowledgement became a termination

The PR keeps ack-drop; the spec requires termination, so the lane terminates. It is one branch: every `decodeEntity`
failure that is not a statement refusal (design D15, already terminated) is terminated, including an undecodable
envelope or an unregistered type, which were acknowledged before. Telling those apart from a payload's failure would
mean classifying errors by kind for no difference in outcome: both are this message's own fault and are never
retried. The closure serves every JetStream input port, so the import lanes are terminated too.

The integration tests see the termination on the broker: it publishes a `MSG_TERMINATED` advisory for a terminated
message and none for an acknowledged one. Each test subscribes to it before publishing and requires the poison
message's stream sequence, on its first delivery.

## Other choices the design does not spell out

- `wireMessageType` (`component.go:1621`) reads the envelope's `type` field again, only on a panic: a panic inside
  `Decode` leaves no decoded message to ask, and the spec requires the type in the log. `message` exports no reader of
  the wire type (its `wireFormat` is unexported). Its present consumer is the fence; nothing else should adopt it.
- The log's `subject` is `msg.Subject()`, the delivered message's subject, where the closure logged the port's filter
  subject (`entity.>`), which names no message. The same subject goes into `decodeEntity`, so its errors (the D15
  refusal's included) name it too. Text only; the unit and integration suites pass with it.

## What is not covered

- A panic in `StorageRef` or `IndexingProfile`: the recover covers them by construction (they run inside
  `decodeEntity`), but the fence type implements neither, so no test drives one.
- An undecodable envelope or an unregistered type is now terminated; no new test asserts that disposition.
- `handleMessage` has no message to settle; it counts and logs, as before.
- A terminated message is gone; nothing parks it where an operator can see it (`readiness_integration_test.go:305`
  names gh#742 for that visibility).
- Fuzzing: not applicable under the contract's rule, which binds new exported surface; `decodeEntity` and
  `wireMessageType` are unexported, and the envelope decoder is `message`'s, unchanged.
- Generated checks: not used. The failure modes are a fixed list of the payload methods the lane calls; they do not
  interact, so named examples suffice.
