## Choices the design does not spell out

- **Stop's order.** `release` (the guard's cleanup, run by Stop and by a failed Start's rollback) takes the
  watchers, the run-context cancel and the subscriber channels under `mu`, closes the channels and marks the Manager
  closed, then stops each watcher, then ends the run context, then waits on every `workDone` channel under Stop's
  context. (Since the Codex review fixes below, the watcher stops and the cancel run on a goroutine in `workDone`.)
  The pin waited first and stopped the watchers after. Two reasons:
  - The model-registry forwarder ranges over its subscriber channel. Closing the channels before the wait is what
    ends it; waiting first is P1 (Stop waits for the forwarder, the forwarder waits for Stop). So the forwarder's
    stop signal is its subscription closing, not a separate signal. For task 2.4, design D5's mutant "forwarder not
    selecting on the stop signal" is, in this code, "Stop waits before it closes the subscriber channels", which
    `TestStopWithAModelRegistryWatcherReturnsPromptly` must catch.
  - The watches are opened under the run context. nats.go v1.54.0 unsubscribes a subscription in the background
    when its context ends (`js.go:2063-2068`). Stopping each watcher before ending the run context makes the
    explicit Stop the unsubscribe that deletes the consumer, so its error (logged at WARN, not returned, Q4) is never
    the background unsubscribe's leftover. No `did not stop` line appeared in a `-v` run of every integration test.
  A family handler that blocks still holds Stop: its goroutine is not done, so Stop returns its context's error and
  the next Stop waits again (`TestBlockedKeyFamilyHandlerHoldsStop`). The watchers are already stopped by then.
- **Stop before Start.** `lifecycleguard.Stop` runs no cleanup when no Start was admitted. `Manager.Stop` calls
  `release` after the guard returns nil, so channels requested before a Start that never came are closed and their
  forwarders joined. Every step of `release` is a no-op the second time, so this costs nothing after a normal Stop.
- **Start's context bounds opening the watches.** The run context is `context.WithCancel(context.WithoutCancel(ctx))`
  (ADR-113, as graph-ingest). A watch opened under it has no deadline, so Start registers
  `context.AfterFunc(ctx, cancel)` until it commits: if `ctx` ends during Start, the run context ends with it and the
  watch request returns. The AfterFunc is deregistered (`stop()` returned true) before the handles are published; if
  it already fired, Start fails and the rollback stops the watches. After Start returned, ending `ctx` stops nothing
  (`TestStartContextEndingKeepsDelivering`, the suite's `StartContextEndStopsNothing`).
- **Every watch must open.** The pin skipped a Manager pattern whose watch failed (Debug log) and failed only when none
  opened. The port fails Start on any watch that does not open, as it already did for a family. A skipped pattern
  was an undeclared degrade: updates to that key would never be seen.
- **The encode check is `encodePush`.** `pushToKV` builds its whole list of writes with `encodePush` before the first
  `Put`, version last. Start calls the same function on the file configuration (`checkPushable`) before acquiring
  the bucket, so a refused name or an unencodable value writes nothing, not even the identity record. Push encodes
  again at write time because the platform section carries the established identifier by then. A platform, nats or
  model-registry value that fails to encode now fails the push; the pin skipped it silently.
- **The name check is `sectionKey`.** It applies the space mapping, then `natsclient.ValidateKVLiteralToken`, and is
  used by `encodePush`, `PutComponentToKV` and `DeleteComponentFromKV`, each before any store access.
- **Version and sync read through `KVStore`.** `getKVVersion` and `syncFromKV` take the `*natsclient.KVStore`, whose
  `Get` maps both not-found states to `ErrKVKeyNotFound` and whose `Keys` maps an empty bucket to none. A missing
  `version` is `0.0.0`; any other read failure fails Start. A stored version that is not a JSON string still reads as
  `0.0.0` with a Warn, as at the pin.
- **Stored nats check.** `rejectStoredNATSKeys` decodes the stored value and runs `rejectUnappliedNATSKeys` on it
  wrapped as `{"nats": ...}`, only in `syncFromKV` (Start). A runtime watcher update is not checked: design D4 keeps
  runtime writes logging and skipping, and an unapplied key has no `NATSConfig` field to land in.
- **`stopped` and `shutdownCh` are gone.** Their checks in `handleUpdate`, `notifySubscribers`, the forwarder and
  `processFamily` are replaced by the closed flag under `mu` (no send after the channels close) and the run context
  (`processFamily` returns when it has ended). `processWatcher` now returns when its update channel closes, which
  the pin never handled because it left on `shutdownCh`.

- **1, Stop honours its context during watch teardown.** `release` no longer stops the watchers itself. It starts
  one goroutine through `goLocked`, so it is in `workDone`, which stops every watcher and then ends the run context;
  Stop then waits on `workDone` under its context, as before. A Stop whose context ends first returns its error, and
  the guard leaves the cleanup pending, so the next Stop runs `release` again: it finds no watchers and no cancel,
  starts nothing, and waits on the same teardown goroutine. The test proves both halves: Stop under 100 ms returns
  `context.DeadlineExceeded` in under a second, and a later Stop under 30 s returns nil. Q4 stands: a failed stop is
  logged at WARN and not returned. Not asked by the review: the watchers stop concurrently (`sync.WaitGroup.Go`,
  joined inside the tracked goroutine), so a teardown the server does not answer takes one consumer-delete timeout
  instead of one per watch (five Manager watches: 25 s measured before, about 5 s after). The order inside the
  teardown is kept: every watcher stops before the run context ends.
  - **Own server.** The test starts an embedded nats-server (the module's pinned `nats-server/v2` v2.15.1, as
    `natsclient/client_lifecycle_test.go` does) with one user whose publish permissions deny
    `$JS.API.CONSUMER.DELETE.>`. The shared Docker fixture (`natsfixture`) has no option for server permissions
    (its only option is `WithMaxPayload`), and adding one would be harness code for one test. It does not call
    `natsfixture.New`, so the `// Own server:` guard does not apply; the reason is in its doc comment. Host
    `127.0.0.1` with `Port: -1` is an ephemeral port (`TestNoFixedAddressesInTests` forbids only `nats://` URLs with
    a fixed host and the fixed ports). Cleanup is bounded: server shutdown 5 s, client close 5 s, Stop 30 s.
- **2, the applied revision is per key.** `engineHighWaterRev` (one atomic for the bucket) is replaced by
  `appliedRev map[string]uint64` under `revMu`. `applyRevision(key, value, rev)` applies and records under the lock
  unless the key already has a revision at or above `rev`; `handleUpdate` and `PutComponentToKV` call it, and
  `pushToKV` records each key it wrote (`recordRevision`). The watcher now also records what it applied, so a
  `PutComponentToKV` whose own apply runs after the watcher applied a newer external write to the same key keeps the
  newer value; the pin's bucket watermark could not tell those apart either. A delete still records nothing (the
  API returns no revision), as at the pin. The test also checks the same-key protection the review asks to keep:
  a late event for `components.local` does not overwrite a newer applied revision. The reconcile unit tests set
  the key's revision instead of the watermark.
- **3, one name for a service or component.** The KV direction cannot recover a space from `_`, so the one
  consistent name is the key's. Start now re-keys the file's services and components by `sanitizeNATSKey` (`nameByKey`,
  one `SafeConfig.Mutate` after `checkPushable`, skipped when no name has a space). File state, the push, the
  watcher, the sync and the component writes then all name `a b` as `a_b`. **Observable change beyond the pin:**
  `GetConfig()` after a first boot names a file component `a b` as `a_b`; at the pin it said `a b` until the next
  bucket-selected boot, where it already said `a_b`. To make the re-keying safe, `encodePush` now refuses two names
  that map to one key (`a b` and `a_b`), naming both, before the bucket is acquired; at the pin both were pushed to
  one key and the last write won. New subtests `TestNameThatIsNotOneKeyTokenIsRefused/{service,component} names
  sharing a key`; shown able to fail by disabling the check in a scratch copy (`cp` backup, SHA-256
  `7a696850155fc0067c398bde7659a9ffcffff5f6344dd40258d2fd99b994890c` before and after the restore): both subtests
  failed at `manager_arbitration_integration_test.go:121` ("An error is expected but got nil").
- **4, family values are left to their owner.** `applyConfigKey` checked size and JSON nesting before its `switch`
  decided whether the key is the Manager's. The checks moved into `decodeConfigValue`, which each Manager section
  (`services`, `components`, `nats`, `model_registry`) calls to decode its value, so an ignored key, a family's
  included, returns `errNoConfigChange` before its value is looked at. Fail-closed decoding of those four sections
  is unchanged. Side effect: a stored `platform` (a published mirror, never applied), `version` (read by
  `getKVVersion`) or identity-record value is no longer depth-checked by `syncFromKV`, which never applied them.
