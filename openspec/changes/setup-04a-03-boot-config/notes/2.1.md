## New tests (`load_test.go`), and choices the design does not spell out

Every new test runs against both loaders through one `loadPaths` table. A rule that only one loader enforces fails one
of the two rows.

- `TestLoad_RefusesUnappliedNATSKeys`: one row per D2 key. Each row checks that loading fails, that the `Config` is
  nil, that the error names the dotted key, and that it contains `not applied`. One extra row is `"token": ""`, because
  D2 refuses a key "when present", whatever its value.
- `TestLoad_AcceptsAppliedNATSKeys`: the control. `urls`, `jetstream.enabled:false`, `max_memory` and
  `max_file_store` load, and their values arrive.
- `TestLoad_RefusesNATSCredentialEnv`: each of the three variables set to `x` fails the load, and the error names the
  variable. A control row sets each variable to `""` and checks that the load succeeds, per the spec's "set and not
  empty".
- `TestLoad_EnvOverrideNames`: all four `SEMENGINE_` overrides together replace the document's values, and `org`
  (which has no override) keeps the document's value. This kills the "prefix reverted to `STREAMKIT`" mutant.
- `TestLoad_RefusesMalformedDocument`: the two spec scenarios. The error must carry the decode text: `urls` for the
  string-for-list case, and `unknown field "name"` for the service entry.
- `TestLoadFromBytes_RoundTrip`: "round trip" is read as two checks. First, each value the document writes comes back
  on the `Config`; the expected values are the literals in the document. Second, `json.Marshal` of the loaded `Config`
  loads again through `LoadFromBytes` and gives an equal `Config`.
- Generated checks are not used. Examples suffice, as D5 says: each rule is a fixed list or one branch.

## What task 2.2 must satisfy that the design does not say

- **Refusal error text.** The refusal error must contain the full dotted key (for example
  `nats.jetstream.replication_factor`) and the words `not applied`. The env refusal must contain the full variable name.
- **Decode errors.** They must be wrapped or included in the error text, so that `urls` and `unknown field "name"`
  appear in it.
- **`getDefaults()`.** It stays unexported under that name. `TestLoader_Defaults` reads it.
  `validateAuthorityPair`, `validateDeclaredAuthorityPair` and `maxDeclarableAuthorityPairBytes` keep their pin names.
- **The round trip.** It requires that a marshalled `Config` carries no key that loading refuses. So the D2 fields must
  be removed from the structs, not only refused, and no default may set them. The scratch run passed only once the
  fields and the `MaxReconnects`/`ReconnectWait` defaults were gone.
- **`README.md`.** `readme_example_test.go` reads `config/README.md`, so 2.2's gate (`go test -race ./config/`) fails
  without it. D4 and task 3.1 cut the README. Task 2.2 either carries the pin's README for now (its platform block
  loads; checked on the scratch copy) or writes 3.1's cut early. This is a sequencing gap in `tasks.md`.
- **`TestLoader_Validation`.** Its three documents must load without error. The `components` entry with
  `"name": ""` must decode under D3's fail-closed merge, and the refusal must come from `Validate`. On the scratch D3
  version it does.
