## Choices the design does not spell out

- `LoadFile` no longer goes through a layer list. It does the work inline, as `LoadFromBytes` does, and both end in
  `applyEnvAndReserve`. That function checks the credential env vars, applies the overrides, then applies the declared
  pair reserve. With `Load` and `AddLayer` gone (D1), nothing else needed the list.
- `parseDurations` is removed whole, not just its `graph` branch. Its only other branch converted
  `nats.reconnect_wait`, which is now refused before it would run.
- The commented-out legacy `GraphConfig.UnmarshalJSON` block at the end of the pin's `config.go` goes with the custom
  `Config.UnmarshalJSON` that D2 removes.
- The refusal tables are `unappliedNATSKeys`, `unappliedJetStreamKeys` and `unappliedNATSEnv`. They follow the shape
  of the pin's `removedPlatformFields`. A key is refused when present, whatever its value. A nats block that is not an
  object is left to the decoder, which D3 then refuses.
- The error texts:
  - for a key: `config key nats.<key> is not applied yet: remove it` (or `nats.jetstream.<key>`);
  - for a credential variable: `environment variable SEMENGINE_NATS_<X> is set, but NATS credentials are not applied
    yet: unset it`;
  - for a decode failure: `failed to load <path>: …` or `failed to parse config: …`, wrapping the decoder's own error.
- `mergeFromMap` lost its `override == nil` early return. Merging an empty override gives the same result.
- `streams.go`'s duplicate package comment ("configuration management for SemStreams") is removed. `doc.go` carries
  the package comment.
- `security.go:85`'s comment now says what the check does: `os.Stat` follows links, so a link to a regular file is
  accepted. The `..` check at `:49` is unchanged, per D4.
- The default URL stays `nats://localhost:4222`. That is production code, which the fixed-address guard does not scan.

## Review fix: key letter case (pre-Codex review of `4b6e820`, MEDIUM)

`encoding/json` matches field names in any letter case, so the pin decoded `"TLS"` and `"Token"` into their fields. The
first version of `rejectUnappliedNATSKeys` looked keys up exactly, so `{"nats":{"TLS":{"enabled":true}}}` and
`{"nats":{"Token":"x"}}` loaded with no error. Now the top-level `nats` key, the keys inside `nats`, and the
`jetstream` level all match with `strings.EqualFold`, and the error names the canonical dotted key. A document can
carry more than one case variant of a key (for example `nats` and `NATS`), so every match is checked.

Four rows were added to `TestLoad_RefusesUnappliedNATSKeys`: `"TLS"`, `"Token"`, a top-level `"NATS"` block carrying
`"token"`, and `"JetStream":{"Domain":…}`. Each runs through both loaders. Before the fix, all eight new subtests
failed (`go test -count=1 -run TestLoad_RefusesUnappliedNATSKeys ./config/`): `LoadFile/nats.tls#01`,
`nats.token#02`, `nats.token#03`, `nats.jetstream.domain#01`, and the same four under `LoadFromBytes`. After the fix,
all pass.

There is one related problem this fix leaves alone: in the merge, a case-variant top-level `"NATS"` block loses its
URLs to the defaults. That is a defect in the pin's merge, and the coordinator is filing it as an issue.
