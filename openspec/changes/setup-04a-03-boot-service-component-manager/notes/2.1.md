# Notes: task 2.1 (tests first)

Status: not started. One section per unit of `tasks.md` 2.1. Each section names its files, the pin lines it carries
(SemStreams `8b99efe9`, `service/` unless another path is given), the design sections its brief cites, and the names
its tests call in the port. The developer fills "Choices the design leaves open" and "How the tests fail on the base".

Rules for every unit (design D7): a manager is built through `NewComponentManager` with a test `component.Registry`
and a `config.Manager` holding the test components, never as a struct literal; no test writes or reads a lifecycle
field the guard replaced (`initialized`, `lifecycleUsed`, `cleanupPending`, `lifecycleTerminal`, `stopping`,
`startDone`, `cancel`, `componentRuntime.cancel`/`startDone`/`terminal`), and none touches a record's state value or
the pin's `components`, `mu`, `storeProvided` or `updateComponentState`, which the state shape replaces (design D2);
assert outcomes instead (what `Start` and
`Stop` return, `GetComponentStatus()[name].State`, what a component recorded). No `time.Sleep`, `Skip`, fixed port, or
`t.Parallel` in an integration file. Measured for building without a broker: `config.NewConfigManager` over an
unconnected `natsclient.NewClient` returns a manager whose `GetConfig()` is non-nil (go1.26.10, a probe outside the
repository; the test names an address the fixed-port guard accepts).

## 2.1n The Start/Stop model check

- Files: `service/component_manager_prop_test.go` (new, `TestPropComponentManagerStopHistory`).
- Design: Generated checks (first bullet), D2.
- Names the tests call: `Start`, `Stop`, `GetComponentStatus`; `pgregory.net/rapid` (in `go.mod`); scripted
  components from 2.1a's helpers.
- Choices the design leaves open:
  - Composition: one to four components named from `comp-a`..`comp-d`, each one's role (provider or consumer)
    drawn apart from its name, so a consumer often sorts before a provider and launch order differs from name
    order. The first `Start`'s outcome is drawn first (clean, provider phase fails, consumer phase fails) and the
    composition built to reach it: a failing outcome forces one provider and one consumer, the forced component
    fails, and any other eligible one fails one time in three. Independent draws were measured first: a local run
    of the generator alone (`/tmp/pr3stub/2.1n/sim`, local only) left "provider phase failed" unreached in 3 of
    300 runs of 100 checks. With the outcome drawn, 20,000 runs reached every branch, the rarest at least 6 times
    a run.
  - History shape: one time in four a live `Stop` comes before any `Start`; then the first `Start`; then
    `rapid.Repeat` over `Start`, `Stop` live, `Stop` with an ended context, and clear. Nothing else can come
    first: clearing before `Start` is the same as drawing no `Stop` failure, and a `Stop` with an ended context
    is not drawn before `Start`, because the design does not say whether it uses the manager up. D2 says it
    returns the context's error and stops nothing; the guard checks the context before it marks itself used
    (`internal/lifecycleguard/guard.go:109-117`), while "Generated checks" says "a `Start` after any `Stop` is
    refused". This is for 2.2 and the reviewer to settle; the test does not decide it.
  - "Clear the armed failures" clears the queued `Stop` failures only. A `Start` failure is fixed by the
    composition: the first `Start` runs before `Repeat`, and every later one is refused.
  - Scripts: each component holds a queue of zero to two fresh `Stop` errors, one popped per `Stop` call
    (`cmPropStopScript`, behind its own mutex, since the manager calls `Stop` on its own goroutines), wired
    through `lifecycleTestComponent.onStop`. The model reads each queue before an action to predict what fires
    (`nextStopFailures`, passed to `expectStops`). For `Start` that read must come before `cm.Start` is called:
    a failed `Start`'s rollback runs inside `Start` (design D2, "A failed `Start` rolls back once"; the guard runs
    it within `Guard.Start`), so when `Start` returns, the rollback has already popped the failures it fired.
    The first version read the queues after `Start` returned, so it expected the next queued failure. It failed
    against 2.2d's manager with seed `10059235893143844472` ("component comp-a is failed, want stopped"): the
    model was wrong, not the manager, which had popped and reported exactly the failure the script armed. The
    2.2d developer found it (`/tmp/pr3stub/2.2d/prop_peek_before_start_test.go`, local only); the fix here reads
    the same snapshot, passed as an argument instead of a closure variable.
  - Oracles: `Start`'s and `Stop`'s errors are checked with `errors.Is` for each failure that fired, rollback
    failures included in `Start`'s; `Start`'s also names `component "x"` for each failed `Start` (D2). The text
    of a `Stop` failure is not checked (the pin wrote `component 'x'`). A `Stop` with an ended context must
    satisfy `errors.Is(err, context.Canceled)` and call nothing, whatever came before, a nil `Stop` included (D2
    states the ended-context rule first; the guard checks it first). Visits are compared exactly, in order,
    through the shared `lifecycleCallLog`.
  - States, checked after every action: `StateInitialized` until launched (as 2.1c asserts), `StateStarted`,
    `StateStopped` with no last error once a `Stop` returned nil (a failed `Start` whose rollback `Stop` returned
    nil included), and `StateFailed` with `LastError` matching, by `errors.Is`, the latest failure. Each
    component's `Start` count is 0 or 1 as the model says. Health: `healthCheck()` is nil exactly when no
    component is failed; otherwise it contains `component "x" failed` for each failed component, in name order,
    matching each one's last error by `errors.Is`, and names no component that has not failed.

  - Not checked here: which context each component's `Stop` got (the design's model list does not name it, and
