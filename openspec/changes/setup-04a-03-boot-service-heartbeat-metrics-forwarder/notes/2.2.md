## P-1

`service/heartbeat.go` (199 lines; pin 280), `serviceDuration` in `service/service_configs.go`, and the `heartbeat`
line of `RegisterAll` in `service/register.go` (its doc comment names the heartbeat and says it serves no route, so
no OpenAPI spec is registered for it).

Against the pin, by design item:

- D1: module path rewritten; the pin's `component` import is gone, since `Start` asserts `*ComponentManager`. Dropped:
  `HeartbeatConfig.Validate` (folded into an unexported `applied()`), `componentHealthGetter`,
  `newHeartbeatServiceForTest`, the `config` and `startTime` fields and the file's package comment. The loop's
  comment says why the first round runs at once. The logger is `deps.Logger.With("service", "heartbeat")`, or
  `slog.Default()` with the same attribute, as storage observability's; the base service gets `WithLogger(deps.Logger)`.
- D2: composes `lifecycleguard.Guard`; the pin's `ticker`, `stopChan`, `stopOnce`, `wg` and `loopDone` goroutine go.
  `start` looks up `componentManagerName`, asserts `*ComponentManager`, starts the base service, then the run context
  `context.WithCancel(context.WithoutCancel(ctx))` and one goroutine that closes `loopDone` when `run` returns.
  `run` makes the ticker, emits once, then once per tick until the run context ends. `cleanup` cancels, waits on
  `loopDone` or returns the wrapped `ctx.Err()` (keeping the channel, so the next `Stop` waits again), then stops the
  base service. `runCancel` and `loopDone` take no lock, as storage observability's (doc comment).
- D3: `decodeStrictServiceJSON`; nil `deps` and nil `deps.ServiceManager` are checked before the decode; every
  refusal is `errs.WrapInvalid` naming its input. `applied()` calls `serviceDuration("heartbeat", "interval", ...,
  30s)` and refuses under 1s. Only the applied interval is kept.
- D4: one Info record "System heartbeat" with `uptime` (`GetStatus().Uptime.Round(time.Second).String()`, the pin's
  string form), `goroutines`, `components_healthy`, `components_total`.
- `serviceDuration(service, field, value string, fallback time.Duration)` replaces `storageDuration`; with
  `service = StorageObservabilityServiceName` its two messages read exactly as before. Storage observability's two
  calls switched.

Choices the design left open:

- The two `Start` refusals for a missing or foreign component manager are plain errors, as at the pin, not invalid
  data: they are a composition fault found at `Start`, and the design names no class. The texts are
  `heartbeat requires the component-manager service` and `heartbeat requires the framework's component-manager, got
  <type>`.
- An unexported `heartbeatServiceName` constant (`"heartbeat"`) names the service in the constructor, the base
  service, the config messages and `RegisterAll`, as storage observability's name constant does.
- The service logs "heartbeat started" (with the interval) and "heartbeat stopped" at Info, as storage observability
  does; the pin logged "Heartbeat service started" and "Heartbeat service stopping". Neither is the held record.

## P-2

`service/metrics_forwarder.go` (295 lines; pin 461) and the `metrics-forwarder` line of `RegisterAll` in
`service/register.go` (its doc comment names the heartbeat and the metrics forwarder, and says neither serves a route,
so no OpenAPI spec is registered for either).

Against the pin, by design item:

- D1: module path rewritten. Dropped: `MetricsGatherer`, `MetricsForwarderConfig.Validate`,
  `newMetricsForwarderWithPublisher`, `newMetricsForwarderForTest`, `newMetricsForwarderForTestWithMockRegistry`, the
  `natsPublisher` assertion, the `config` field and the file's package comment. The forwarder holds the
  `*natsclient.Client` and the `*metric.MetricsRegistry` it is given and gathers `PrometheusRegistry()` each round.
  The logger is `deps.Logger.With("service", "metrics-forwarder")`, or `slog.Default()` with the same attribute; the
  base service gets `WithLogger(deps.Logger)`. The loop's comment says why the first round runs at once.
- D2: the heartbeat's shape (P-1): `lifecycleguard.Guard`; `start` starts the base service, then the run context
  `context.WithCancel(context.WithoutCancel(ctx))` and one goroutine that closes `loopDone` when `run` returns;
  `cleanup` cancels, waits on `loopDone` or returns the wrapped `ctx.Err()` (keeping the channel), then stops the base
  service. The pin's `ticker`, `stopChan`, `stopOnce`, `wg` and `loopDone` goroutine go.
- D3: nil `deps`, nil `deps.NATSClient` and nil `deps.MetricsRegistry` are checked before the decode;
  `decodeStrictServiceJSON`; `serviceDuration("metrics-forwarder", "push_interval", ..., 5s)`, so an empty
  `push_interval` takes 5s. Every refusal is `errs.WrapInvalid` naming its input. Only the applied values are kept
  (`interval`, `includeGoMetrics`, `includeProcMetrics`).
- D4: `metricSamples` is one plain function; `metricSample` carries `Subject` (`json:"-"`) and the six payload fields
  with the pin's map keys as JSON tags, so the round encodes each sample directly. Two small helpers keep the pin's
  value and type switches (`metricValue`, `metricTypeName`).

Choices the design left open:

- An encode failure and a publish failure share one path, as the service manager's health publisher does
  (`service/service_manager.go:668-682`): one Debug record `failed to publish metrics to NATS` with `subject` and
  `error`, and one `RecordError("metrics-forwarder", "metrics_publish")`. The pin logged an encode failure as `failed
  to marshal metrics entry`; the design counts both on `metrics_publish`.
- A failed gather logs `failed to gather metrics` at Debug, records `metrics_gather` and skips the round. The pin's
  nil-gatherer branch goes with the interface: the constructor refuses a nil registry.
- One `time.Now()` per round, not per sample (the pin called it per sample): the samples of one gather share a
  timestamp.
- The subject is built by concatenation, not `fmt.Sprintf`; the result is the pin's `metrics.<component>.<name>`.
- The `GAUGE_HISTOGRAM` type maps to `untyped` through the `default` arm; the pin's explicit `UNTYPED` arm folds into
  it.
- An unexported `metricsForwarderServiceName` constant and `defaultPushInterval`, as the heartbeat's.
- The service logs "metrics forwarder started" (with the interval) and "metrics forwarder stopped" at Info.
