# Task 2.1 notes: the startup tests on the real component manager

## What changed

`service/component_startup_test.go` drops `componentStartupDouble` and its `var _ componentStartup` assertion. No other
file referenced the double. The three tests now drive a `ComponentManager` built by `newTestComponentManager`, with the
existing helpers `newBarrierTestComponent` (a lifecycle component whose `Start` can be held or fail),
`newStartupDiscoverable` (a plain component whose health the test sets) and `awaitStartupAnswer`. No production file
changed.

Choices the design does not spell out:

- `gatewayComponent` now embeds `baseDiscoverable` instead of spelling the four methods.
- The double's private reads (writer handed before `Start`, the startup prefix) are replaced by what an operator sees:
  the `starts_invoked` gauge reads 1 while the gated component's `Start` is held, which only happens if the component
  manager held the writer before its components started; `/components/list` answering proves the `/components` prefix.
- The readiness cases are subtests, each on its own composition, because "starting", "failed" and "stopping" cannot
  be reverted to READY on a real manager as the double's cases were.
- The old case "an admitted component missing from health" is gone: D2 removes the check it exercised, which the real
  manager cannot reach.
- The "failed" case waits for `/services` to report `failed` with `probe.Await` (new local helper
  `awaitStartupStatus`): the component manager records the sibling's outcome after its `Start` returned, and no channel
  marks that write. The sibling's `startReturned` channel is awaited first.
- `TestConfigureRefusesACompositionWithoutAComponentManager` uses `newStandInComponentManager` where it used the double.
