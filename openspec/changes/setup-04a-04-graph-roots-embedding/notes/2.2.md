## Placement and wording

- **The failure-reason constants moved.** `normalizeFailureReason` (the pin's `storage.go:708-716`) switches on six
  unexported constants (`failReasonContentError` through `failReasonEmbedderError`) that the pin declares in
  `worker.go:1106-1113`, task 3.4. They are now declared in `storage.go`, next to `normalizeFailureReason`, with
  their doc comment unchanged in meaning. This changes where they are declared, not what they do. Task 3.4's
  `worker.go` uses them from `storage.go` (orchestrator ruling, 2026-10-28).
- **`TestRevisionGuardHistoryMatchesModel` is an integration test**, as design D9 lists it (on a real server through
  `natsfixture`). Task 2.2's text marks only `TestSaveDedupKeepsSameSpaceReplacesOther` as integration; the
  orchestrator fixes that wording in `tasks.md`.
- **`ScanFailed` stops its watch with `kvwatch.Stop`**, wrapped as "embedding: stop the EMBEDDING_INDEX watch". The
  pin called `watcher.Stop()` directly. With `kvwatch` in this PR for the #454 case, a plain `Stop` would be a second
  way of spelling the same stop in newly ported code (orchestrator ruling, 2026-10-28). If the delivery does not
  close, `ScanFailed` returns that error and no entries: a delivery still running is reported, never dropped. On
  every other path it returns the entries as the pin did, the partial seed on a cancelled scan included.
- **`SaveDedup` lost its `entityID` parameter.** At the pin its only use was the dropped `DedupRecord.EntityIDs` field
  (S13), so a kept parameter would have been an input nothing reads. Its only caller is the pin's `worker.go` (S20),
  ported in 3.4. D2 does not list this signature change; it follows from S13. Flagged for review.
- **The no-text removal** is `(*Storage).deleteAtRevision(ctx, entityID, kvRevision) (removed bool, err error)`.
  It returns `true, nil` when the record was removed, `false, nil` when the key moved or is gone
  (`ErrKVRevisionMismatch` or `ErrKVKeyNotFound`), and `false` with the error otherwise. Task 3.4 maps these to the
  Worker's outcomes.
- **Errors.** `saveError` returns `ErrRecordGone` and `ErrSupersededRevision` bare (as the pin did) and keeps an
  invalid-record error invalid. Everything else is wrapped transient, retry exhaustion included, so the result still
  matches `natsclient.ErrKVMaxRetriesExceeded` through `errors.Is`.
- **Comments.** Comments about SemStreams rolling upgrades and legacy records were dropped from `Record`'s fields
  (S17; owner, #91 comment 6109293267). `ContentFields` is gone (S14), along with its comment.
- **Entity IDs are checked only for emptiness, as at the pin.** They are not checked with
  `natsclient.ValidateKVLiteralKey`, because the design adds no entry validation. `DeleteAtRevision` validates its
  key itself.

## The history test

`TestRevisionGuardHistoryMatchesModel` uses Rapid. It is sequential and runs against real NATS, with fresh
`EMB_HIST_*` buckets each run, deleted when the run ends.

The model maps each entity to: present or absent, status, source revision, and the last KV revision observed. Its
rules come from D3:

- **Pending** is refused only over a generated record at the same or a newer source revision.
- **Generated and failed** return `ErrRecordGone` when the key is absent, and `ErrSupersededRevision` when the call's
  revision is below the stored one. Failed is also refused over a generated record at an equal revision.
- **The fenced removal** removes only at the KV revision it is given.
- **KV revisions:** a refused call leaves the key's KV revision where it was, and a write moves it forward.

Each call's result is checked against the model, along with the stored record and its KV revision, read directly
from the bucket.

How the generator reaches each boundary:

- `drawRevision` returns the stored record's own revision half the time, so equal-revision cases are reached by
  construction.
- The ops are weighted (pending 3, generated 2, failed 2, delete 1, fenced removal 2).
- At the end the test fails unless each of the 17 outcomes the model distinguishes was reached at least once. This
  check showed that unweighted draws never reached "failed refused over generated at equal revision"; that is why
  the draws are weighted and the equal revision is drawn on purpose.

The test bounds itself at 50 runs: `TestMain` sets `-rapid.checks=50` unless the command line sets it.

Run of record:
`go test -tags integration -race -count=1 -v ./graph/embedding -run TestRevisionGuardHistoryMatchesModel -rapid.seed=20261028`
printed `[rapid] OK, passed 50 tests`. Every outcome was reached; for example "failed refused over generated at equal
revision" 11 times, "pending refused over generated at equal revision" 24, "pending saved over a newer record" 30,
"fenced removal present=true current=false" 25. On failure, Rapid prints the replay seed and the drawn sequence.

The first run failed on a model error. The model assumed a key never stored could not be at KV revision 1, but on
nats-server v2.15.1 `DeleteEmbedding` of a never-written key writes a delete marker at revision 1, and the fenced
delete at 1 then matched that marker (seed 20261028, replay `-rapid.seed=20261199`). A Worker's revision always
comes from a stored record, never a marker, so the model now uses the last stored record's revision for an absent
key, or a revision no run reaches (2^40) for a key never stored.
