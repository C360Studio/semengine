# Task 3.0b notes

Choices the design (D1, D4) does not spell out:

- `Wait` is `<-p.stopDone`: the channel `drain` already closes after every lane has exited. It adds no field, no
  context and no goroutine. Its doc comment says it blocks forever if nobody calls `Shutdown`, as
  `sync.WaitGroup.Wait` does.
- `TestKeyedPoolWaitJoinsAfterShutdown` sits in `internal/dispatch/shutdown_test.go` beside the other `Shutdown`
  tests, in a `synctest` bubble. Its oracle is the list of items `Process` records: one item is held inside `Process`
  and one is queued behind it. `Wait` must not have returned before `Shutdown`, nor after `Shutdown` under an ended
  context while the item is held (each check follows `synctest.Wait`); after the release it returns and both items are
  recorded. The final `p.Wait()` after the join would be a bubble deadlock if it blocked.
- Mutation check: `Wait` with an empty body (returns at once),
  `task mutate:check -- -pkg ./internal/dispatch -test TestKeyedPoolWaitJoinsAfterShutdown -file
  internal/dispatch/keyed_pool.go -mutant <copy> -expect shutdown_test.go:273`: detection, 3 of 3 mutant runs.
- Generated checks are not used: `Wait` has one input (when it is called relative to `Shutdown` and the drain), and
  the named orderings (before `Shutdown`, during the drain, after the join) are each covered by an example.
