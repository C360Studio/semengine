# Task 3.3 notes

Choices the design (D4, D5, D9) does not spell out, for task 3.3 and the cache's share of task 2.3.

## How Run stops

`VectorCache.Run` (`graph/embedding/vector_cache.go`) stops in this order once its context ends or the watch's update
channel closes while the context is live:

1. The loop stops reading.
2. `withdraw` takes the cache's write lock, sets it not authoritative and drops the vectors. From here `FindSimilar`
   answers `(nil, false)`.
3. The context the watch was opened under, derived from `Run`'s, is cancelled.
4. `kvwatch.Stop(ctx, watcher)` stops the watch and drains it until nats.go closes the channel. Its error is wrapped
   as "embedding: stop the EMBEDDING_INDEX watch".

`Run` returns `ctx.Err()` if the context ended, or `errWatchLost` if not, joined with the wrapped stop error when there
is one. When the watch cannot open, it returns `ctx.Err()` if the context has ended, or a transient error otherwise.
A nil context and a second concurrent `Run` both get an invalid-input error before any watch opens. The running flag
is an `atomic.Bool`, cleared when `Run` returns, so `Run` can be called again.

## Choices

- **Each Run starts empty.** `follow` begins with a new map, so a decode failure withdraws the cache only for the rest
  of that `Run`. The pin's withdrawal lasted for the `Storage`'s lifetime. Under the pin's one-shot
  `StartVectorCache`, the two are the same thing.
- **Decode failures are not logged.** An undecodable record withdraws the cache, and the only signal is
  `FindSimilar`'s `false`, which sends callers to the bucket. This is the same as the pin. The cache has no logger,
  and adding one would be new surface. Flagged for review against the declared-degrade rule.
- **`keep` runs under the read lock**, as at the pin. Because of this, withdrawing the cache waits for a read already
  in progress (`TestVectorCacheInvalidationLinearizesWithActiveRead`). It also lets the integration test use a
  blocking `keep` to hold `Run`'s loop. `FindSimilar`'s doc says `keep` must not call the cache.
- **A limit of 0 or less returns `nil, true`** without scoring anything (S21).
- **`errWatchLost` is unexported.** Task 3.4's Worker can use the same error.

## The unsubscribe goroutine's frame

This frame was measured from a stack dump taken during `TestVectorCacheRunReportsLostWatch`, with a live watch, on
nats.go v1.54.0:

```text
goroutine 101 [chan receive]:
github.com/nats-io/nats%2ego.(*js).subscribe.func3()
    .../nats.go@v1.54.0/js.go:2066 +0x4c
created by github.com/nats-io/nats%2ego.(*js).subscribe in goroutine 117
```

The test matches on `github.com/nats-io/nats%2ego.(*js).subscribe.func3(`. A stack dump escapes the dot in the
module path's last element. Before deleting the bucket, the test checks that a goroutine with this frame exists, so
the test fails if a nats.go upgrade renames the frame.

**A correction to the design's wording.** D4 and the spec delta say the derived context releases this goroutine. At
v1.54.0, `js.subscribe` waits on a child context of its own (`js.go:1911-1913`), and nats.go cancels that child when
the subscription is unsubscribed (`nats.go:5553-5564`). So stopping the watch releases the goroutine too, without the
derived context. Mutant m9 below shows this: the watch was opened under `Run`'s own context, and the goroutine still
went away. The derived context stays because D4 and the background-work spec require it, but no test can show it is
needed. The spec's sentence "released by that context, not joined" is true but incomplete. That is for the architect.

**Library timing, not promised.** After the bucket is deleted, nats.go v1.54.0 took about 20 s to close the watch's
update channel. That is 20.0 s for this test and 20.2 s for `TestFollowerDeclaresLostFeed/deleted`. The test waits up
to 1 min.

## Tests

Unit tests are in `vector_cache_test.go`, on fakes behind `natsclient.NewClient("").NewKVStore`. `feedKV` hands the
test the watch's unbuffered channel, so each send returns only after `Run` has received the entry, and
`synctest.Wait` orders each assertion after `Run` has applied it.

- `TestVectorCacheRunRefusesNilContext`
- `TestVectorCacheSecondRunRefused`
- `TestVectorCacheRunLeavesNothingBehind`
- `TestVectorCacheNotAuthoritative`: before the snapshot, after an undecodable record (and still after a later good
  one), and after `Run` returned
- `TestVectorCacheFollowsRecordStatus`: pending, failed, delete and purge each remove a vector, and a generated
  record with no vector never enters the cache
- `TestFindSimilarOrderAndLimit`: the expected orders are worked out by hand from the vectors
- Ported from the pin onto the production path, replacing the pin's writes to private fields:
  - `TestFindSimilarFromCache_DeterministicTopKAtEqualSimilarity` (`similarity_determinism_test.go`)
  - `TestFindSimilarFromCache_ScopeFilter` (`storage_scope_test.go`, which now also checks that `keep` saw all four
    IDs)
  - `TestVectorCacheInvalidationLinearizesWithActiveRead` (`storage_cache_health_test.go`). The pin's 100 ms
    negative wait is replaced by `probe.Await` on a stack dump showing `Run` in `[sync.RWMutex.Lock]`. That
    assertion runs outside a bubble, because a goroutine waiting on a mutex is not durably blocked.

Integration tests are in `vector_cache_integration_test.go`, on the shared server through the reset:

- `TestVectorCacheRunLeavesNoWatchDelivery`: 600 records and ten cycles. A `FindSimilar` whose `keep` blocks until
  the cycle's context ends holds the read lock, so `Run`'s loop stalls and the delivery backs up. The test calls
  `natsfixture.AwaitNativeDeliveryBlocked` before cancelling. After each cycle it checks that no stack is in a
  `VectorCache` method and that `natsfixture.NativeDeliveryStacks` is empty.
- `TestVectorCacheRunReportsLostWatch`

`go test -tags integration -race -count=3 -run 'TestVectorCache|TestFindSimilar' ./graph/embedding` passed: `ok`,
67.3 s. `go test -count=5 -shuffle=on -cpu 1 ./graph/embedding` passed.
