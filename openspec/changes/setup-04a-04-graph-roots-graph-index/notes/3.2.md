# Task 3.2: `graph/follower`

Choices the design (D3, D5, D11) does not spell out.

## Tests on the real clock, not in a bubble (deviation from D11's labels)

D11 marks `TestFollowerRunReturnsAndLeavesNothing` and `TestFollowerPublishesOnEveryHeartbeat` as `synctest`, and D5
says the tick test runs inside `synctest`. Both need a follower, and `Open` needs a real client and a real
`ENTITY_STATES` (no fake reader, #186). A bubble's clock advances only when every goroutine in it is durably blocked;
nats.go's read loop waits on a socket, which is not, so the fake clock would never reach a heartbeat. A scripted
`net.Pipe` server, as natsclient's bubble tests use, cannot serve JetStream KV, and an in-process server goes against
keeping NATS in Docker. The orchestrator's brief directed real-clock suites. So both run as integration tests:

- Leaves nothing: after `Run` returns, a `runtime.Stack` dump of every goroutine holds no `follower.(*Follower)`
  frame (the heartbeat goroutine and the watch loop are both `Follower` methods), and the stream's consumer count
  reaches 0 (`probe.Await`). nats.go's own subscription goroutines are not the follower's and are not checked.
- Heartbeat: commit times of three envelopes, read from a watch on the key. The first is before one heartbeat from
  `Run`; each later gap is at most `2 x DefaultHeartbeat`, which catches a tick lost behind the parked `Deliver`. The
  orchestrator dropped the developer's lower bound (`DefaultHeartbeat - 1s`): a slow write commits late and the next
  on-time tick then lands under one heartbeat after it, so the bound would fail on a loaded runner (#392). The test
  takes about 10 s.

Heartbeat independence (the spec's "a blocked Deliver never delays a heartbeat") is in the heartbeat test: its
`Deliver` parks until `Run`'s context ends.

## Follower

- `Open` reads the stream's creation time once, from the status handle, after the bounded wait; `Run` starts the
  watch. A bucket recreated between `Open` and `Run` is then read as a lost feed at the first heartbeat: a false
  positive, on the safe side.
- One private `readStream` reads the last sequence and the creation time from one `Status` call (D3: "one read
  site"). It does not call `natsclient.BucketLastSeq`, which would make a second read for the generation.
- The pin's `statusTargetMu` around the target read is not kept: the pin gives no reason for it, and a KV `Status`
  call is a stream info request, safe from several goroutines. Only the stuck detector's progress record is under a
  mutex.
- A status read that fails is not a lost-feed trigger; the envelope reads `degraded` (D3's three triggers only). After
  a delete, the envelope is therefore degraded before trigger (ii) fires.
- A lost feed sets the envelope's `ready` false as well as `degraded`, as the failed override does: after a recreate,
  the target is the new stream's sequence and a floor from the old one cannot be compared with it. The envelope
  carries no `reason` for it; `Stuck` names it.
- The lost-feed mark is logged once, at the transition, at error level, with its cause. The envelope's `degraded`
  state (and its gauge) is the metric.
- `QueryReady`'s reset refusal wraps a `*graph.StateContractError` with the reason and the pin's remedy text, so
  `graph.IsStateContractError` matches it in process.
- `Reset` latches whatever reason it is given, an empty one included; no caller passes one.
- `Logger` nil takes `slog.Default()`; `StartupAttempts` and `StartupInterval` zero take `internal/resource`'s
  defaults (10 x 500 ms), as the resource watcher already does. A nil `MetricsRegistry` registers nothing, as
  `Gauges.Register` already allows.
- `Stuck`'s sentences: `graph state reset required: <reason>`, `<n> index writes unresolved`,
  `ENTITY_STATES feed lost; restart the process`.

## Not covered here

- Trigger (i), `WatchAll` failing: its real trigger is the bucket deleted between `Open` and `Run`, a window the test
  would have to choose. No test; review checks the branch.
- The 30 s stuck-watermark detector: wall-clock, ported from the pin unchanged; no test in this task.
- The failed-count override and `failed_count` on the envelope: proven with graph-index's write path (task 4.x,
  `TestHealthIgnoresErrorCountAndTracksStuckStates`).
- `TestLatchBootstrap_ContinuousWrite`: the follower spec names it beside `TestFollowerSnapshotEndSetsBootstrapTarget`,
  D11 lists it as a ported graph-index test, and task 2.2 does not list it. Not written in this task.

Generated checks: none. The follower's history is a watch delivering in stream order; the named cases are the
triggers and latches the design lists, each one example.

## Orchestrator decisions (2026-10-26)

- Real clock instead of `synctest` for the two D11 tests above: accepted. The reason is the one stated (nats.go's
  socket read keeps a bubble's clock still; no fake reader, #186), and the brief directed it.
- `TestLatchBootstrap_ContinuousWrite` belongs to task 2.3: D11 lists it as a ported graph-index test, and it drives
  the latch through graph-index's continuous writes.
- Trigger (i), a watch that cannot start, has no test: its one real cause is the bucket deleted between `Open` and
  `Run`, a gap only a test could time. Recorded as an uncovered case, checked in review.
