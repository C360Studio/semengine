# Task 4.4: query handlers, QueryReady, the reply envelope

Choices design D5 and D6 do not spell out. The tests and the pin tests this task carries or drops: `notes/2.3.md`.

## Files

`query.go` (new: the eight handlers, the subscription walk over `graph.QueryVerbs()`, the read-side key helpers),
`component.go` (the `subscriptions` field; `start` subscribes last, `cleanup` drains first and clears them),
`lifecycle_integration_test.go` (the suite adapter lists "query subscriptions").

## Choices

- **One readiness-and-revision step.** Every handler validates its request, then calls `queryRevision`, which asks the
  follower's `QueryReady` and, only when it answers nil, reads `Indexed()`. That read is the reply's
  `indexed_revision` and comes before the handler's first bucket read (D6). Validation stays first, as at the pin, so
  a malformed request is refused as invalid even during the replay.
- **Producer.** `graph.ResponderGraphIndex` (`"graph-index"`), the responder name the verb table uses, through
  `graph.NewQueryResponse`; its empty-producer refusal is unreachable here and maps to an internal error if it ever
  fires.
- **Subscriptions last in `start`.** Everything a handler reads (the follower, the five buckets, the ENTITY_STATES
  reader) is set before the first subscription, so graph-ingest's `startCompleted` guard is not needed. A failed
  subscription is the last step that can fail; the rollback's `cleanup` drains the ones already made. `cleanup` drains
  them first, before the feeds and the pool, so no handler is running when the buckets' work stops; a Stop whose
  context ends during a drain returns its error with the subscriptions kept, and `Subscription.Drain` rejoins the same
  drain on the next Stop.
- **No `subscribeForRequests` field** (S12, #186): `subscribeQueries` calls `natsClient.SubscribeForRequests`
  directly.
- **Internal errors carry their cause** (`internal error: %w`), as graph-ingest's handlers do; the pin sent a bare
  "internal error".
- **Incoming order.** Sorted by source then predicate, then `slices.Compact` (the pin used a seen-map before the sort).
  Name keys are sorted and compacted before the 2,000-membership budget, as at the pin.
- **Compound.** One count per entity across the listed predicates' deduplicated sets; AND keeps entities counted once
  per listed predicate. A predicate listed twice therefore still intersects correctly. Same answers as the pin's
  set intersection and union.
- **Kept from the pin:** the 5 s handler timeouts and predicateList's 10 s (S6, optional item kept); the
  `nameQueryMaxHydration` budget of 2,000; the value filter reads ENTITY_STATES through the kept `CatalogReader` and
  fails the whole query on a read or decode failure other than not-found, rather than answer part of it.

## Review fixes at code stop 3 (#429, #430)

Codex's review of `733139c` (PR #414 comment 6441772113) found two MEDIUM defects in `query.go`.

- **#429, name ranking.** `nameRankCompare` subtracted priorities, which overflows for extreme ints (vocabulary
  priorities have no narrower range) and reversed the order. It now compares directly with `cmp.Compare`, as the pin
  did, with the entity ID as the tie-break through `cmp.Or`.
- **#430, malformed stored rows.** The five skip sites (incoming key; predicate key in the exact read and in
  predicateList; name key and name value) now call one method, `skipMalformedRow`, which logs a warning naming the
  index, key and reason and increments `query_rows_skipped_total{index_type}`, registered through
  `metric.RegisterOrGet` beside `aliases_skipped_total` (design D10). The label is the index only, a bounded set; the
  key and reason go to the log. The predicate read's `stored != predicate` case counts as malformed: the exact filter
  fixes the first three tokens, so only a key that fails to parse reaches it. A name row deleted after the listing is
  still skipped without a signal: it is not malformed. `predicateSummaries` stays a pure function and returns the
  malformed keys for its caller to declare.
