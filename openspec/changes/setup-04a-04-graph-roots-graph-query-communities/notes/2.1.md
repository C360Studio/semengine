# Task 2.1: the record's revision

Developer notes on choices design D1 leaves open, and the evidence behind the task's checks. Base `3fd6240`.

## Premises

Checked on the tree before coding, all true: `graph/clustering/maintainer.go:120-161` (Upsert and Delete),
`:240-272` (plan, which builds each record), `:390` (an entity's three group IDs); `storage.go:55-68` (get, the
decoding `GetAllCommunities` runs), `:107-110` (`communityKey`).

## Choices

- **Where the mark lives.** On the in-memory `group` (`revision`), so it goes when the group is deleted at zero
  members: "a removed group takes its mark with it" needs no separate bookkeeping. `raise` lifts it only for a group
  that exists after the delivery is applied, and marks the group dirty only when it rose.
- **A raise past a refused or never-held entity.** `raise` parses the ID itself (`types.ParseEntityID`), since a
  refused value and a delete of an entity never held have no contribution to read groups from. An ID the parser
  refuses has no group and raises nothing. In `Upsert` this parses a valid ID twice (once outside the lock in
  `newContribution`, once under it); the cost is a string split, kept for one plain path.
- **The mark is a maximum, not the last write.** `revision > g.revision`: with the ascending feed the caller owes,
  the two agree; out of order across keys, the maximum is what the spec's "highest revision" says.
- **"The maintainer uses them".** The maintainer has group IDs, not entity IDs, so it does not call `GroupKey`.
  Both share the two pieces `GroupKey` is made of: `groupIDs(eid)` (the `:390` derivation, now one function used
  by `newContribution`, `raise` and `GroupKey`) and `communityKey` (used by `save`, `plan`, `GroupKey` and
  `DecodeCommunity`). `GetAllCommunities` calls `DecodeCommunity` for each entry.
- **Errors.** `GroupKey` and `DecodeCommunity` return `errs.WrapInvalid` with component `clustering`;
  `DecodeCommunity`'s error names the key. `GetAllCommunities`' read error is unchanged (transient, names the key).
- **`DecodeCommunity` does not refuse a level outside 0 to 2** when the key matches it (`5.x` holding level 5).
  The spec names three refusals and this keeps to them; `GroupKey` never produces such a key, so a reader that
  finds its key through `GroupKey` never reads one. Say if it should refuse.
- **`TestTickCost` changed one step.** "Same value at a newer revision" expected no write; under D1 ("a write that
  changes no count, word or representative now writes its records once") it writes that entity's three records.
  The step now expects them; the "unchanged graph" step still expects nothing.
- **`TestUnchangedRecordAddsNoRevision`** is now two subtests on fresh buckets: "nothing applied" (a tick with
  nothing applied, then an obsolete upsert at the applied revision and a tick: the bucket stays at sequence 3) and
  "same-content upsert" (sequence 3 to 6, then a second tick leaves 6; `GetAllCommunities` reads revision 2).
- **`TestHistoryOrderIrrelevant`** masks the encoded `"entity_revision":N` with a regular expression and compares
  the rest of the bytes, so the comparison stays byte-level apart from that one field. Its histories ascend per
  entity only, so the masked field may differ, as the spec allows.
- **Fuzz targets** `FuzzGroupKey` and `FuzzDecodeCommunity` (new exported surface that parses strings and decodes
  bytes, developer contract). Oracles: `GroupKey` against `strings.Split` and `types.ParseEntityID`;
  `DecodeCommunity` against the key re-built from the accepted record.
- **`TestRecordNamesItsLatestWrite`'s recreated group** is recreated at revision 8, below the delete at 9 that
  emptied it, by an entity seen for the first time (its own feed still ascends). Only a revision below the last
  delete tells "the mark ends with the group" from a kept mark; at a higher revision both give the same number.
  The step also checks that record as literal JSON, which shows `entity_revision` is always encoded.
