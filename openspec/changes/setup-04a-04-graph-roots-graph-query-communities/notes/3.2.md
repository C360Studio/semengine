## Choices

- **Where the view lives.** `Component.communities` is an `atomic.Pointer` to the current view, nil while there is
  none. Only the supervisor stores it: before `Run`, and nil again once `Run` has returned, so a handler sees either
  no view or one whose `Get` reports its own state. The view's value type is `clustering.Community` (not a pointer), so
  a handler never shares a record with the projection.
- **The supervisor** (`community.go`) runs on its own goroutine under the run context; `start` begins it before the
  subscriptions, as graph-index starts its goroutines before subscribing. `cleanup` drains the subscriptions, ends
  the run context and waits for the supervisor under Stop's context; the handles are cleared only when all is
  released. The run context and a `supervised` channel are the two new handles; the lifecycle state stays in
  `component.Lifecycle`. The 5 s wait is a `time.Timer` that the run context ends, so a Stop during the wait does not
  wait it out (`TestStopEndsTheCommunityView/waiting_to_reopen`).
- **Every reopen logs one `Warn`** naming the error and the 5 s wait: the declared signal of D3's refusal while the
  bucket is missing or lost. No metric: D6 puts no view error in `Health`, and task 3.3's counter is for truncation.
- **The decode** is `clustering.DecodeCommunity` with `keep` true; every key of `COMMUNITY_INDEX` is a record.
- **The page read** extends step 2's `readCountPage` to keep each row's bytes beside its ID (`countPage.rows`), so
  localSearch gets the same page checks as the counts, and the rows pass unchanged.
- **The record read happens before `min_revision`**, which happens before the page read (D2). The group key is
  recomputed with `clustering.GroupKey` after the decoder's check.
- **No record.** The entity read is `ask` on the entity verb with `{"id":...}`. Any success means the entity exists
  (index_not_ready); the reply is not decoded, since either outcome is a refusal. A refusal, or no answer, is returned
  as `ask` returns it, so no responder counts one error, as for the other composed verbs.
- **Errors.** A poisoned record and a reply that cannot be fitted to `max_payload` even with no entities, and a
  `MaxPayload` read failure, are graph-query's own transient `internal`, counted once (`unanswered`). A page that does
  not decode, or an entity in it that does not decode, is `brokenReply` naming the prefix subject.
- **The fit's encoding** is the envelope itself (`graph.NewQueryResponse` then `json.Marshal`), at
  `natsclient.Client.MaxPayload`: a success reply carries no headers (`natsclient/request.go`, the success path's
  `msg.Respond`), so the body is the whole message.
- **The `declaredRows` row for `localSearch`** names the prefix verb, its first downstream request once the view holds
  drone1's record. The five tests that send it (`TestHandlerBudgetEndsAForward`, `TestForwardedRefusalKeepsClassCodeDetail`,
  `TestNoRespondersIsTransient`, `TestQueryTimeoutIsRead`, `TestGraphQueryServesExactlyTheDeclaredVerbs`) publish that
  record through a real maintainer before Start (`withCommunityRecord`) and wait for the view with
  `awaitCommunityView`, a request far ahead refused `revision_not_reached`, which reads nothing downstream and counts
  no error. `startStack` was split so `startCommunityStack` can create the bucket before graph-query starts.
- **The lifecycle suite** adapter reports a "community view" handle while the supervisor is held; the failing owner
  now runs the component's own `start`, so its rollback releases the supervisor too.
- **`TestLocalSearchDuringBlockedTick`** writes the next record of one group straight to the bucket, as D3 lists.
- **`TestLocalSearchRefusesAfterWatchLoss`** deletes `COMMUNITY_INDEX` under a live view, twice. At the pinned nats.go
  the loss was seen about 20 s after the delete (log: `stream not found: recreating ordered consumer`, then the watch's
  channel closed); that delay is observed, not promised, and the test waits on the refusal, not on time.
- **Generated checks.** Not used: the view's history has four transitions (missing, caught up, lost, stopped), each
  driven by a named test, and the request's interacting inputs were 3.1's.
