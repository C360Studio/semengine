# Task 3.1: `pathSearch`

Choices designs D2, D3 and D4 leave open.

- **The start read is not a hop.** Its refusal reaches the caller unchanged, not wrapped to name the entity. D3 says a
  hop's refusal names the hop's entity; the caller named the start, the entity verb's `not found:` message names it, and
  `TestForwardedRefusalKeepsClassCodeDetail` holds each row's first downstream refusal to its exact message.
- **A start reply is read only for an `entity`.** Not JSON, no `entity`, or `null` is transient `internal`. The stored
  value is not judged: `ExactEntityReader`'s stored-value rule refuses fatal, against the spec's transient, and the walk
  reads nothing from it.
- **Filling the limit does not stop the walk, finding one more does.** Truncation must be exact, so the walk reads the
  entities it holds until an unseen one has no room, or none are left. That is what keeps the bound: one read per
  direction per entity held.
- **No row-level dedup step.** The requirement is that a repeat cannot affect the limit. After the sort the walk's seen
  check takes the first of any neighbour, so a repeated row, a second predicate and a self loop all add nothing. Witness:
  "a self loop and repeated rows add nothing".
- **A reply with a producer and no `relationships` key is not refused.** The pin's "missing relationships" check covers
  `{}`, `null` and `{"data":{}}`; here `decodeIndexReply` refuses all three, since they name no producer, and
  `TestPathSearchRefusedMidWalk` holds them. A body naming a producer with the key missing reads as no edges, as on the
  `relationships` verb. No responder here builds one: `graph.QueryResponse` is built by graph-index with a non-nil list
  (`processor/graph-index/query.go`, `index.go:305`), so this is left as is, not a new mechanism.
- **`outgoingEdges` and `incomingEdges` split** into `outgoingRows` and `incomingRows` plus the envelope, so the walk and
  `relationships` read an index reply one way. `relationships` behaves as before.
- **Direction spellings stay unexported.** The design's export list has no direction constants; a caller writes the wire
  string.
- **Bytes after the request are refused.** D2's "decoded strictly" is read to cover it: `json.Decoder` alone stops at
  the first value.
- **A walk that loses its responder** uses a raw NATS subscription with `AutoUnsubscribe(2)`, in
  `TestComposedVerbsCountAsForwardsDo`, since nothing else makes a real third hop find no responder.
- **Fuzzing: none.** The new exported names are types and constants, with no parser. The unexported decode is
  `encoding/json` then `ValidateEntityID` and `ParsePredicate`, whose packages fuzz them (`FuzzParseEntityIDRoundTrip`,
  `FuzzParsePredicateNeverPanics`), and `TestPathSearchRefusesBadRequests` holds the classes.

Generated check: used, as D3 asks: direction, filter, depth and limit interact. `TestPathSearchMatchesTheModel` holds the
walk to a model written from the requirement as levels (distances by relaxation, then each level by who reached it). It
runs 17 named witnesses with literal JSON and a 120-entity star for `max_nodes` 0 before `rapid.Check`, so nothing
depends on what the generator reaches. The limit's two boundaries, exactly the entities in reach and one fewer, are drawn
by construction. Seed 1: `[rapid] OK, passed 100 tests`. Every run reaches each assertion: `checkWalk` fails on a walk
error, and `max_depth` is at least 1, so the walk always hops.
