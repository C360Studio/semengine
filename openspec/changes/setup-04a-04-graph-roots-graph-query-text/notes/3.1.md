# Task 3.1 notes

## Generated checks

Named examples suffice, decided before the tests were written (`docs/testing.md`, "Decide whether generated checks are
needed"). `chooseRoute` is a table over a handful of hint kinds (a path start, a time range, an area, path words with
no start, path predicates, a similarity, a ranking, an aggregation), so its interacting cases are D1's rows; each row
of D1's table and each question the design and spec name is a named case, through the real keyword classifier, plus
the two path-predicate rows the keyword tier never sends, through `chooseRoute` directly. The order of the refusals
(two filters, then an aggregation, then a hint beside a filter) is the spec's and is held by the rows that carry more
than one (`how many pumps connected to pump-42 in the last 2 hours` is two filters, `how many sensors are connected to
pump-42` an aggregation). `FuzzDecodeGlobalSearchRequest` already routes any accepted query; it gains the text
strategy's invariant (each unhonoured hint is `path`, `similarity` or `ranking`) and seeds for a level, a text
question and a hint beside a filter. There is no history.

## Choices the design leaves open

- **What the text branch returns until task 3.2.** `globalText(level)` refuses transient `index_not_ready`, no error in
  `Health`, when graph-query has no community view or the view is catching up, lost or stopped (`ListCounted`'s
  readiness errors), the spec's "The text tier refuses an index it cannot read". With a readable view it refuses
  transient `internal`, "the text tier does not answer yet", marked `// shortcut:`, counting no error, since nothing
  failed; 3.2 replaces it with the answer and adds the empty-level refusal with `TestTextTierRefusesAnEmptyLevel`.
  Until change 7 writes `COMMUNITY_INDEX` the first is what every deployment sees, so it is what the integration tests
  hold (`requireTextTierReached`). More than `graph.MaxSearchTerms` terms is 3.2's (D3), checked there before the view.
- **The route reaching text is tested at the route and the handler.** `TestGlobalSearchRoutesByHints` holds each text
  row's `unhonoured` list at `routeGlobalSearch`; the reply field `unhonoured_hints` is 3.3's (`TextSearchData`), so
  `globalRoute.unhonoured` has no reader in production until then. `TestGlobalSearchUnknownWordIsSearched` and
  `TestGlobalSearchUnknownIDIsSearched` hold `index_not_ready` naming the missing view; 3.2 tightens them to the reply
  (`strategy` `text`, its query that word).
- **Refusal wording.** An aggregation: "the question asks for an aggregation (max of retries), which global search does
  not compute; ask without it", naming the operation and, when the classifier found one, its field. A hint beside a
  filter: "the question names a ranking beside a path from pump-42, which no strategy answers together; ask with one",
  the filter spelled as step 4's two-filter refusal spells it. Neither carries a detail.
- **`entityNotFound`.** `entityByAlias` and a global search named start build the same refusal through one helper in
  `query.go`, so the spec's "One resolver reads an entity reference" holds by construction.
- **A start whose entity is gone** passes the entity verb's `entity_not_found` as it came (its message, not
  `not found: <start>`): the spec's "A refusal from the alias or entity verb SHALL reach the caller with its class, code
  and detail".
- **`readHints`** now types every key it reads (`aggregation_*` strings, `use_embeddings` and `ranking_intent` bools,
  `limit` an int, `path_predicates` a `[]string`); a `limit` alone reads as a ranking. `classifier.go` is unchanged.
- **Tests renamed or removed.** `TestGlobalSearchDecodesStrictly` is `TestGlobalSearchRequestKeys` (the spec's name);
  `TestGlobalSearchUnknownReferenceFallsThrough` is split into `TestGlobalSearchUnknownWordIsSearched`,
  `TestGlobalSearchUnknownIDIsSearched` and `TestGlobalSearchUnknownPathStart`; `TestGlobalSearchTextTierRefusal` is
  removed. The ledger's `processor/graph-query` test list names them; its contract prose, `README.md`, `doc.go:49` and
  `.agents/skills/query-pattern/SKILL.md:89` still describe `text_search_unsupported` until task 5.1, which lists each.
- **`TestComposedVerbsCountAsForwardsDo`'s globalSearch steps.** "a request it refuses" sends `level` 3 (1 is now
  valid); "a question for the text search" is now "a count". Counts unchanged.
