## Choices the design does not spell out

- `StoredMessage.MarshalJSON` marshals a fixed wire struct instead of the pin's `map[string]any`. The keys and values
  are the same; only key order on the wire differs, which no JSON reader depends on. `UnmarshalJSON` uses the same struct.
- `RegisterPayloads` sets no `Builder` (S31: `buildStoredMessage` is not carried); the doc names the composition root
  as the caller (#33).
- The factory is `newComponent` and the declarer `declarePorts`, both unexported (D6). Tests call `newComponent`
  directly: `Registry.ListFactories` withholds factories, and `CreateComponent` is the component manager's seam.
- Carried from the pin's `resolveObjectStorePorts` unchanged in meaning: the `api` input refusal, core NATS or
  JetStream only, one subject per port, unique names, the derived `store-provide` output. The pin's per-kind and
  per-subject maps are not carried; task 3.3 derives what binding needs from the ports' facts.
- `planObjectStoreInputBindings` (consumer names, duplicate-binding and collision refusals) is not in this unit; task
  3.3 carries it with its tests, since those refusals are about binding inputs.
- Skeleton: `Component` holds the config, the resolved ports and a `component.Lifecycle`; `Health` and `DataFlow`
  answer through the shell. `Initialize`, `Start`, `Stop`, `ProvidedStores`, the dependencies (NATS client, logger,
  decoder, metrics registry) and the write lane are absent, left for tasks 3.3 and 3.4. The factory ignores its
  dependencies until then.
