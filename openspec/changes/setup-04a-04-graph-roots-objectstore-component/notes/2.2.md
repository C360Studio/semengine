## Choices the design does not spell out

1. The shared server moved into package `objectstore` (`fixture_integration_test.go`, exported as `SharedServer`): the
   Component's tests read unexported handles, both test packages build into one binary, and only one `TestMain` may
   exist. `store_integration_test.go` takes `shared = &objectstore.SharedServer`; it still reaches the server only
   through the reset.
2. `Observe` reports no `Calls`: the Component has no acquisition seam to count through (D8), so the suite's no-op checks
   compare empty maps and what a call left held is read from `Unresolved`.
3. `checkDone` stays after a successful cleanup (above). It is a closed channel and carries no authority.
4. The watched inputs are owned by the check's goroutine (handed over at `go`), and Health reads one
   `atomic.Pointer[string]` the check replaces each time it runs to its end; graph-ingest keeps a mutex-guarded list
   because its readiness envelope and Health both read it, which this Component has no need for (D2: no envelope).
5. The lookup is `js.Consumer(ctx, stream, name)`, one call; graph-ingest also reads `Info` for its backlog, which this
   Component does not report.
6. `inputCheckInterval` is `readiness.DefaultHeartbeat` (5 s), importing `graph/readiness`; `graph` was already a
   dependency through `component`.
7. The failed-store error is wrapped with `errs.Wrap` (unclassified, `%w`), so `errs.IsFatal` still finds the Store's
   fatal class (`errors.As`); the pin's `startStoreError` is not carried. No test here drives a fatal Store at Start.
8. `waitForStream` is kept as D2 says (30 lookups, doubling from 100 ms to 2 s, the pin's), although
   `ConsumeStreamWithConfig` also waits up to 5 s for stream visibility itself.
9. A deleted consumer ends the consume loop only when the server's deletion notice answers a pull request waiting at the
   server (nats.go v1.54 `jetstream/pull.go:740`, read; observed once in one failing run, not promised: the shuffled
   full-package run
   deleted the consumer before the first pull and the loop kept running 30 s later). In that window the lookup still
   reads the loss, so Health is unhealthy naming the consumer, but not the restart. The test waits for
   `NumWaiting > 0` before deleting. D2's "A deleted consumer ends the consume loop" holds for a running input with a
   waiting pull; for the architect.
10. The binding plan runs in the factory only, as at the pin; `declarePorts` does not plan, so a configuration with two
    inputs on one subject is declared and then refused at construction.
11. A JetStream port's declared `consumer_name` is not read, as at the pin and in graph-ingest: the plan's name wins.
    `ack_wait` is not passed either (pin), so natsclient's default applies.
12. Until task 3.4 the handlers count each delivery (`CountInput`); the core handler drops it and the JetStream handler
    acks it.

## Not covered

- Clearing the stuck state after a later lookup succeeds (design D2: stated, not tested).
- The check's read order (loop end, then running) during a Stop: no test drives a check concurrent with release.
- The integration mutants ran once each, not three times with an after-run as `task mutate:check` does.

### Choices the design does not spell out

1. A Component with an input and no payload registry is refused at construction (`newComponent`), as graph-ingest's
    factory does (`processor/graph-ingest/component.go:292`); otherwise every message would be refused. A store-only
    Component needs none. Test: `TestComponentRefusesInputWithoutPayloadRegistry`.
2. The handlers take the `*Store` that `start` opened as an argument (closures built in `start`), not
    `c.store.Load()`: a handler still finishing during release never sees the cleared pointer, and the Store has
    nothing to close.
3. The stored output's subject and kind are read once in the factory (`storedTarget`); `resolvePorts` makes `stored`
    the first output whenever there is an input.
4. A failed `Ack` (stored and published, but the server not told) is logged at error level and counted: the
    redelivery it causes stores the body again. A failed `Nak`/`Term` is logged; the delivery's error is counted once.
5. Every non-Ack is logged at error level, including a NAK because the handler's context ended (D4); the pin logged
    a cancelled one at Debug.
6. The decode failure, the not-`ContentStorable` refusal and the marshal failure are wrapped `errs.WrapInvalid`, so
    they terminate; `StoreContent`'s own classes pass through; a publish failure is wrapped `errs.WrapTransient`.
7. The pin's comment that a ContentStorable redelivery overwrites (`pin:…/component.go:1046-1051`) is not carried;
    `write`'s doc says a redelivery after a failed publish stores the body again under a new key (D4).

### Not covered

- A transient `StoreContent` failure on a JetStream input (NAK, then a stored redelivery): no failure from the real
  server reaches it deterministically; the transient path is proven through the publish failure.
- The shutdown NAK (a handler whose own context ended mid-write): natsclient owns that context; only the classifier
  test covers the row.
- A delivery past `MaxDeliver` (stated, not reported, #36).
- The failed-settlement and failed-ack log lines.
