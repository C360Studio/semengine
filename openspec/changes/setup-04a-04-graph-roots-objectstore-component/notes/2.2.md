# Task 2.2: integration tests for task 3.3

Measured on the uncommitted tree over `9099777` (Go 1.26.10, darwin/arm64, nats.go v1.54.0). The logs under
`/tmp/5b-u2/` are local only; the commands below rerun them. This note covers the integration tests of task 3.3 (the
lifecycle, input binding, the run context and the lost-input check). `TestStartContextEndKeepsBothLanesWriting`,
`TestWriteLaneStoresBodyAndEmitsReference`, `TestWriteLaneRefusals` and `TestStoredEmitFailureNaksThenRedeliveryStores`
land with task 3.4 and are recorded here then.

## Tests

All in `storage/objectstore/component_integration_test.go`, package `objectstore`, on the package's shared server
through the reset, except the memory-restart test, which starts its own.

| Test | Proves |
| --- | --- |
| `TestObjectStoreLifecycleSuite` (`core`, `jetstream`) | the lifecycle suite on a core-NATS input and on a JetStream input; `Observe` lists the input check while its goroutine runs, so "nothing retained after Stop" proves Stop joined it and "Start context end stops nothing" proves it outlives the Start context (design D5). The must-fail owner names a bucket NATS refuses (`not.a.bucket`), so its Start fails at the Store |
| `TestFailedStartReleasesBoundInputs` | Start binds a core input, then fails waiting for a JetStream input's missing stream when its 2 s context ends: Start returns `context.DeadlineExceeded`, `Observe` lists nothing, Health is `stopped`, and the client's subscription count is back to what it was before Start |
| `TestProvidedStoresUnderObjectstore` | nil before Start; one Store under `objectstore`, stamping `objectstore`, usable through the map, while running; nil after Stop |
| `TestSecondComponentRefusedAtStart` | a real `service.ComponentManager` composing two objectstore Components (store-only ports) fails Start naming `instance "objectstore"` |
| `TestLostJetStreamInputReportsUnhealthy` | the input's durable consumer deleted while running: Health becomes `degraded`, naming the input `"js-write"` and the restart |
| `TestMemoryInputLostAtBrokerRestartStaysUnhealthy` | own server, restarted keeping its URL: the memory stream is created again, Health is unhealthy naming the consumer, before and after a publish, and the consume loop Start began has not ended |

Waits: every assertion on what the input check writes waits on Health with `probe.Await` (30 s bound; the check runs
every 5 s). The lost-input test also waits for a pull request waiting at the server before it deletes the consumer (see
"Choices", item 9). No `time.Sleep`, no `t.Parallel`.

Oracles: the consumer name the tests delete and look for is spelled as a literal
(`objectstore-objectstore-objectstore-test-write`, the pin's legacy format), not computed by the plan under test; the
subscription count comes from the nats.go connection; the store-registry refusal comes from the component manager.

Generated checks: not used. Each test is one named scenario with no interacting inputs; the cross-delivery history is
task 3.4's (design D9).

## Choices the design does not spell out

1. The shared server moved into package `objectstore` (`fixture_integration_test.go`, exported as `SharedServer`): the
   Component's tests read unexported handles, both test packages build into one binary, and only one `TestMain` may
   exist. `store_integration_test.go` takes `shared = &objectstore.SharedServer`; it still reaches the server only
   through the reset.
2. `Observe` reports no `Calls`: the Component has no acquisition seam to count through (D8), so the suite's no-op checks
   compare empty maps and what a call left held is read from `Unresolved`.
3. `checkDone` stays after a successful cleanup (above). It is a closed channel and carries no authority.
4. The watched inputs are owned by the check's goroutine (handed over at `go`), and Health reads one
   `atomic.Pointer[string]` the check replaces each time it runs to its end; graph-ingest keeps a mutex-guarded list
   because its readiness envelope and Health both read it, which this Component has no need for (D2: no envelope).
5. The lookup is `js.Consumer(ctx, stream, name)`, one call; graph-ingest also reads `Info` for its backlog, which this
   Component does not report.
6. `inputCheckInterval` is `readiness.DefaultHeartbeat` (5 s), importing `graph/readiness`; `graph` was already a
   dependency through `component`.
7. The failed-store error is wrapped with `errs.Wrap` (unclassified, `%w`), so `errs.IsFatal` still finds the Store's
   fatal class (`errors.As`); the pin's `startStoreError` is not carried. No test here drives a fatal Store at Start.
8. `waitForStream` is kept as D2 says (30 lookups, doubling from 100 ms to 2 s, the pin's), although
   `ConsumeStreamWithConfig` also waits up to 5 s for stream visibility itself.
9. A deleted consumer ends the consume loop only when the server's deletion notice answers a pull request waiting at the
   server (nats.go v1.54 `jetstream/pull.go:740`, read; one failing run measured it: the shuffled full-package run
   deleted the consumer before the first pull and the loop kept running 30 s later). In that window the lookup still
   reads the loss, so Health is unhealthy naming the consumer, but not the restart. The test waits for
   `NumWaiting > 0` before deleting. D2's "A deleted consumer ends the consume loop" holds for a running input with a
   waiting pull; for the architect.
10. The binding plan runs in the factory only, as at the pin; `declarePorts` does not plan, so a configuration with two
    inputs on one subject is declared and then refused at construction.
11. A JetStream port's declared `consumer_name` is not read, as at the pin and in graph-ingest: the plan's name wins.
    `ack_wait` is not passed either (pin), so natsclient's default applies.
12. Until task 3.4 the handlers count each delivery (`CountInput`); the core handler drops it and the JetStream handler
    acks it.

## Not covered

- Clearing the stuck state after a later lookup succeeds (design D2: stated, not tested).
- The check's read order (loop end, then running) during a Stop: no test drives a check concurrent with release.
- The integration mutants ran once each, not three times with an after-run as `task mutate:check` does.
