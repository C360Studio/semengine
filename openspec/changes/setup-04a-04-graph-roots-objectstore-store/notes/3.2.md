# Tasks 3.1 to 3.4: choices the design does not spell out

- **A client with no JetStream is invalid input.** `client.JetStream()` errors when the client never connected; the
  constructor wraps that as invalid input, as design D4 says (the pin wrapped it transient).
- **A nil `ContentStorable` is refused** as invalid input, after the nil-context check and before any read.
- **Only non-empty content is refused, binary fields included** (coordinator, applying the ruling at PR #432 comment
  6447702631: "non-empty" governs binary fields too, since an empty one loses nothing). A binary field is refused as
  `binary "<field>"` only when its data is non-empty; an empty one beside a body stores the body
  (`TestStoreContentRefusesExtras`, "empty binary field beside a body is stored"). An empty `title` beside a body
  likewise stores the body (`TestStoreContentReferenceOpensToBody`). The spec scenario and design D4 and D9 now say
  "non-empty binary field".
- **The refusal names fields sorted**, so the message is the same for the same payload. A non-body role that names
  the body's own field is refused as `role "<role>" (field "<field>")`, one entry per such role (#433); a non-body
  role on any other field is refused by that field's name alone, as before.
- **The content key keeps the pin's local-time partitions** (`time.Now()`, not UTC), only swapping the `UnixNano`
  suffix for a UUID (design D4, S11).
- **Metrics.** `read_operations_total` and `write_operations_total` keep the pin's `operation` label (`get`, `open`;
  `put`, `store_content`); `delete_` and `list_operations_total` carry only `bucket`. Latency is observed on success
  only, as at the pin; `operation_errors_total` counts each call that returned an error, refusals before any I/O
  included (nil context, nil content, invalid entity ID, refused content; #434): each operation defers the count on
  its named error result, so there is one place per operation and no path is missed. Refusals add no operation count
  and no latency; those stay with calls that reach the bucket. A `Delete` of a missing key returns nil and is not
  counted as an error (`TestRefusalsCountAsOperationErrors`).
- **The retention guard's fail-closed test uses a fake JetStream** (`deniedUpdateJS` in `store_test.go`, a unit
  test). A stream update NATS refuses cannot be produced on the fixture's cooperative server, so the pin's fake-based
  fatal case is ported as it was. Design D9 lists `TestRetentionGuardFailsClosed` among the integration tests; it
  needs no server.
- **`TestStoreMethodsRefuseNilContext` uses a bucket handle that answers every call with success** (`okObjects`), set
  through the Store's unexported field from the package's own test. Production code is unchanged; a missing check
  shows as a nil error and a counted call rather than a panic.
- **Object names are not checked by the shared key validators** (`natsclient.ValidateKVLiteralKey` and kin). They
  are ObjectStore names, not KV keys, and the design asks for no check; noted for the reviewer.
- **`TestStoreHistoryMatchesModel` is held at 50 runs by setting `-rapid.checks` from the test**
  (`boundRapidChecks`), unless the command line or `RAPID_CHECKS` chose a count: Rapid v1.3.0 has no per-test
  setting.
- **`doc.go`** states only what ships. Task 4.3 owns its final text, the `README.md` and `ExampleNewStoreWithConfig`.
