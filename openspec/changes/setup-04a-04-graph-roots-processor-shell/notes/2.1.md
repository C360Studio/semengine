## Choices not in the design

- **A real-clock bound on every read.** D10 says that inside the bubble "a read that blocks deadlocks the bubble and
  fails the test". That holds for a read waiting on a channel, not for one waiting on a `sync.Mutex`: a bubble does
  not count a mutex wait as durably blocked, so the binary hangs until `go test`'s timeout. Probe (Go 1.26.10,
  scratch module `/tmp/pr409stub/probe`, local only): a bubble goroutine locking a mutex another bubble goroutine holds
  while waiting on a channel ran until `panic: test timed out after 8s`, with no deadlock report. So `read` takes
  both reads on a goroutine and waits for them, or for the `Done` channel of a 10-second real-clock context made
  outside the bubble (`realDeadline`; it must be made outside, since a `Done` channel first touched inside a bubble
  cannot be closed by a timer outside it: the probe's first form failed with `close of synctest channel from outside
  bubble`). A read still waiting at the deadline ends the test with `Fatalf`: the next call on the shell (a count,
  another read) would wait on the same lock, and the cleanups let the held functions go, which frees it. The bound
  only bounds failure; a read that does not wait returns at once and the test never waits on the real clock.
- **Held functions are let go, and their calls joined, in cleanup.** `newHeld` registers its release, and `goCall`
  registers "let the holds go, then wait for the call to return". `stopAtEnd` is registered first, so it runs last:
  the terminal `Stop` (a fresh one-minute bound) never runs beside a held `Stop`. Without the join, the row "stop
  cleanup held open" failed with `concurrent Stop is unsupported`.
- **The phase table reads in three stages per history**, each with no stuck state, one empty stuck state, and
  `"poison", "", "backlog fault"`: at 2 s with nothing counted; at 2 s after two `CountError`s and no input (so
  `ErrorRate` stays zero and `Healthy` is unaffected by errors); at 4 s after four 100-byte inputs counted at 2 s. The
  expected values are D4's table (`wantHealth`) and literal numbers (1 message/s, 100 bytes/s, error rate 0.5 while
  running; zero rates otherwise; `Messages` 4, `Bytes` 400 and `LastActivity` 2 s in every history).
- **The rollback's held cleanup stays inside the rollback's 5 s budget** (`pkg/lifecyclecleanup`): the table moves the
  clock 4 s in all.
- **A panicking start** is in `TestLifecycleFailedStartNeverRuns` (the spec's "fails or panics"). The test accepts
  either a panic out of `Start` or an error, since D3 promises neither; it asserts only that the shell is not running
  afterwards.
- **The refusal before `Initialize`** is asserted as any non-nil error, since D3 names no error class.
- **`TestLifecycleSuiteCatchesWorkUnderTheStartContext` runs the check twice in one bubble**: on an owner whose worker
  runs under its own run context (it must pass) and on one whose worker runs under the Start context (it must report
  `stopped holding [worker]`). The pass on the first shows that the failure on the second comes from the Start
  context.
- **Every input is counted before `Start` in the failed-start test**, so no count runs while a start or cleanup is
  held open.

## Mutants on the stub

Each mutant was one edit to a copy of the stub (`/tmp/pr409stub/M<n>/`), run with
`go test -count=1 -timeout 120s -overlay=/tmp/pr409stub/M<n>/overlay.json -run 'TestLifecycle|ExampleLifecycle'
./component/`. All were detected; none hung. M6 is graph-ingest's (`TestEntityCacheUseDuringStop`) and has no
shell mutant. The graph-ingest tests D10 also names for M3, M4, M7 and M8 were not run here. These are scratch
runs on a stub; the recorded mutation checks are task 6.1's, through `task mutate:check` on the real file.

| Row | Mutant | Tests that failed |
| --- | --- | --- |
| M1 | `Healthy` drops the running term | `ReadsInEveryPhase` (all 8 non-running rows), `FailedStartNeverRuns`, `StartBeforeInitializeIsRefusedAndLeavesItUnused` |
| M2 | `Healthy` also requires zero errors | `ReadsInEveryPhase/running` |
| M3 | running cleared after `cleanup` returns | `ReadsInEveryPhase/stop_cleanup_held_open` |
| M4 | `Start` skips the Initialize check | `StartBeforeInitializeIsRefusedAndLeavesItUnused` |
| M5 | running set before `start` returns | `FailedStartNeverRuns`, `ReadsInEveryPhase/start_held_open` |
| M7 | lock held across `start` and `cleanup` | `ReadsDoNotWaitForStartOrStop`, `FailedStartNeverRuns`, `ReadsInEveryPhase` (3 held rows); each after the 10 s bound |
| M8 | `Messages` zero when not running | `ReadsInEveryPhase` (all 8 non-running rows), `ExampleLifecycle` |

M7 is detected only through the real-clock bound above. Each failing test costs 10 s, well inside
`task mutate:check`'s default 2-minute `go test` timeout.
