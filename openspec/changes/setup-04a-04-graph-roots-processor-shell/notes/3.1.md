| Change | Why |
| --- | --- |
| Doc comments on the type and every method | D1-D5: the type's comment defines the coined term (ADR-108's processor shell), says a `LifecycleComponent` holds a `Lifecycle` to answer the lifecycle half (D2a), names what the component supplies (D2) and what the shell does not own (D3, D5: no context or cancel, no release order, no readiness, no metrics), zero value and no-copy (D1). | Start before Initialize is `errs.WrapFatal(errors.New("component not initialized"), "Lifecycle", "Start", "initialization check")`; the stub used `WrapInvalid` | D3 names no class; D4 says the rules are graph-ingest's moved, and this is graph-ingest's spelling and class today (`processor/graph-ingest/component.go:970`), so graph-ingest's Start keeps its error class when it delegates (task 4.x). The test asserts only non-nil |
| `Health` reads `time.Now()` inside the lock; the stub read it before | With the stub's order a read could take `now`, then `start` return and set `startedAt` later than `now`, then the read take the lock and report a negative `Uptime`. Inside the lock, `startedAt` is never after `now` |
| `DataFlow` reads the clock inside the lock (`time.Since`) | Same reason; `secs > 0` stays as the guard against dividing by zero |
| Field `errors` renamed `errorCount` | Reads plainly beside the `errors` package import |
| A field comment on `mu` and on `running` | Records the one concurrency rule (the lock is never held across `start` or `cleanup`, so reads never wait: D4, `TestLifecycleReadsDoNotWaitForStartOrStop`) and D3's running window |

atomics for its counters, but one short lock keeps the type to one rule and nothing it guards is held across a call
out). `running` set inside the guard's `start` wrapper after `start` returns nil and cleared at the top of the
`cleanup` wrapper, so a rollback and a `Stop` both end running before cleanup runs (D3). No method added beyond D2.
