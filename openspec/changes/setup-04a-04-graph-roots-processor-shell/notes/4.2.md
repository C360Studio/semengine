# Task 4.2 notes: #306, the entity cache handle stays valid through Stop

Design D7, done with task 4.1 as one unit on the working tree over `61fbc66` (both edit graph-ingest's `Stop` path).

## The fix

One unexported helper, `entityCacheHandle` (`processor/graph-ingest/component.go:2283-2291`), reads `c.entityCache`
under `c.mu.RLock` and returns the copy. Who owns this today: nothing; the handle was read bare at each site. It is
called by the three sites below only; it is not a pattern for other packages.

The three reader sites, each reading the handle once and using that copy:

| Site | Was (`61fbc66`) | Now |
| --- | --- | --- |
| cache read in `fetchEntitiesConcurrent` (batch and prefix queries) | `query.go:487-488`, read twice per ID | `query.go:478` reads once before the ID loop; `:488-489` use the copy |
| `invalidateEntityCacheEntry` | `component.go:2370, 2376` | `component.go:2273-2281` |
| `repopulateEntityCacheEntry` | `component.go:2396, 2402` | `component.go:2310-2318` |

The two writers take `c.mu`: `clearLifecycleHandles` clears the handle under `c.mu.Lock` (`component.go:1071-1073`),
still only after a cleanup that succeeded, and `initStorage` sets it under `c.mu.Lock` (`component.go:1105-1107`).
Setting under the lock is not in D7's text; without it a `CreateEntity` running during `Start` would race the set the
same way. `cleanup`'s own read before `Close` stays bare: only `start` and `clearLifecycleHandles` write the field,
and all three run under the lifecycle guard one at a time. `c.mu`'s field comment now says it guards the handle.
