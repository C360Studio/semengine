# Task 2.3: the Worker under the run context, and its lost watch

Base `8fc0aaa` (branch `claude/change5-graph-embedding`, PR #550). Files: `processor/graph-embedding/component.go`,
`hop1.go` (a doc comment), `hop1_integration_test.go`, the new `worker_integration_test.go`, and this note with its
wrong changes in `notes/2.3-mutants/`.

## What changed

`start` builds an `embedding.Worker` over the component's storage with a BM25 embedder (the pin's 384 / 1.5 / 0.75,
`BM25Config{}`'s defaults), `workers`, `max_text_len`, `embedder_type`, the store registry when one is admitted, and
`WithOnTerminal(c.onTerminal)`, and runs its `Run` on a goroutine under the one run context, after the follower's.
`cleanup` joins it (the `worked` channel) after the follower's `Run` and before the coalescer. When `Run` returns
while the run context is live, the goroutine latches `workerLost`, then logs an error; `Health` adds
`embedding worker watch lost; restart the process` to the follower's stuck states. Nothing clears the latch: the
component is one-shot.

## How the watch is lost

`TestHealthNamesLostWorkerWatch` deletes `EMBEDDING_INDEX` on the test's NATS server (`js.DeleteKeyValue`) under a
running component, after the Worker has generated one record. nats.go then closes the Worker's watch, and `Run`
returns `errWatchLost` with the run context live (`graph/embedding`'s `TestWorkerRunReportsLostWatch` drives the same
trigger against the Worker alone). How soon nats.go closes the watch is its timing, not promised; `go test -timeout`
is the deadline. The test then recreates the bucket and writes a new pending record into it: Health still names the
loss, since nothing rebinds the watch. No hook was added; the trigger is the bucket.

## Edge values

- **Run returns nil vs an error while the context is live.** The goroutine decides on `runCtx.Err()` alone, never on
  `Run`'s error, so both latch. Only the error case is reachable: `Worker.Run` documents that it returns
  `ctx.Err()` when its context ended and an error otherwise (`graph/embedding/worker.go:272-275`), so a nil return
  with a live context would need a fake Worker, which `Component` has no seam for (and adding one would be a back
  door, #186). `m3`'s opposite (latching regardless of the context) is the check that the condition is the context.
- **Run returning because Stop ended the context.** `TestStopJoinsWorker` checks no lost-watch line is logged by the
  time Stop returns (the latch precedes the line, and Stop's join orders the read); `m3` fails it.
- **Stop before, or without, a successful Start.** `TestLifecycleBeforeStart` ("Stop before Start") and the lifecycle
  suite's must-fail owner, whose Start fails in the follower's `Open`, cover it: `worked` is nil there and `cleanup`
  skips it.
- **A failed Start after the Worker launched.** Not reachable: the Worker is launched as the last step of `start`,
  after the coalescer (the last step that can fail), so no failure follows it. Were a later step added, `cleanup`
  already joins `worked` and keeps it when Stop's context ends first (the lifecycle suite's
  `StartedOwnerReportsItsHandles` now lists `worker` among the held handles).
- **A pending record written before Start.** `TestPendingRecordBeforeStartIsEmbedded` writes the entity and its
  pending record (through `embedding.Storage`, as an earlier process would have) before Start; the Worker embeds it
  and its revision completes. Hop 1's replay may also rewrite the pending record; either order ends generated.

## Choices the design leaves open

- **Holding the Worker in tests.** With the Worker running, a pending record no longer stays pending for a test to
  read, and the 2.2 tests that called `onTerminal` in the Worker's place now let the Worker do it. Where a test must
  hold a revision at hop 2, the entity's body is offloaded to a test store (`gatedStore`, registered through the
  injected store registry, the production path) whose `Open` waits until the test releases that key. Where a test
  reads an inline pending record, `"workers": 1` and one held offloaded entity keep the Worker's only lane busy
  (`holdWorker`). `TestReadinessWaitsForHopTwo`, `TestRestartCompletesGeneratedRevision` and
  `TestCoalescedRevisionsComplete` read the offloaded record's identity text where they read source text before.
- **`TestStopJoinsWorker`'s ordering.** The store's `Open`, once Stop ends the run context, waits for the test to let
  it go. The test waits for the follower's goroutines to leave the stack dump (Stop joins them first), then checks
  Stop has not returned; only then does it let the read go and require a nil Stop, by which time the read has
  returned. A stack read right after a join can still see a goroutine that has finished (#490), so the test never
  asserts that the Worker's goroutines are gone at that instant.
- **No `WithMetrics`, no `WithOnGenerated`.** The pin wired both (pin `component.go:1017-1027`); D2 names neither,
  and the collectors they feed are not ported yet (`notes/2.2.md`, "content_unresolved_total"). The Worker's own
  unresolved-store warning and count therefore go to the log only.
- **The latch before the log line,** so a test that saw the line reads the latch through the log buffer's lock.

## Not covered

- A watch that cannot open at all (`Run` returning at once with its transient error) latches through the same branch,
  but no test drives it: `start` ensures `EMBEDDING_INDEX` just before, so no real trigger makes the open fail.
- The follower's readiness envelope does not reflect a lost Worker watch; D2 asks only for `Health`. A revision whose
  pending record is never embedded holds the floor, so readiness reads not ready, and degraded after 30 s with no
  completion (D1).
