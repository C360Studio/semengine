## What changed

- `follower.Config.Failed` returns `(count int64, reasons map[string]uint64)`. `envelope` calls it once and sets
  `FailedReasons` only when the count is above zero. `Stuck` and `QueryReady` read the count only. graph-index
  passes `func() (int64, map[string]uint64) { return c.failedTotal(), nil }`.
- `IndexStatusResponse.FirstFailureAt` is removed, with its test fill. The failure-detail case now checks that
  `first_failure_at` is absent.
- `failedMap` (`failed.go`) holds each entity's latest terminal outcome: success or failure, its revision, its
  reason, and whether it is stranded. The Worker's outcomes go through `onTerminal` (the failure is recorded before
  the revision completes). Hop 1 calls `mark` on a failed read, delete or pending write, and `queued`, `ended` or
  `absent` when it converges. Start seeds the map from `Storage.ScanFailed` before the follower publishes.
- The repair lane (`repairLoop`, `repair` in `hop1.go`) runs on its own goroutine under the run context. Every
  30 s it passes each entity whose failure is one of the three hop-1 reasons through `reconcileEntity`. `cleanup`
  joins it (`repairs`) after the follower's `Run` and before the Worker's. The task-2.4 `// shortcut:` stubs are
  gone.

## Choices the design leaves open

- **Any hop-1 convergence clears a stranded failure.** That includes a follower delivery or a coalesced batch, not
  only a repair pass. D3 says "by the repair lane", but the spec delta's requirement ("cleared only by a later
  successful hop-1 convergence of that entity") does not restrict the lane, and neither does the pin
  (`clearStranded` on every hop-1 convergence, `component.go:1694-1701`). Every lane runs the same
  `reconcileEntity` under `hop1Mu`. Holding the mark after a delivery has converged would keep readiness degraded
  for up to 30 s more, with nothing left to repair. The Worker never clears a stranded failure, which is what
  `TestStrandedWithoutRevisionClearsOnlyOnRepair` checks. **For the orchestrator to confirm.**
- **Successes are kept.** The spec's scenario "A late failure for an older revision" (7 generated, then a failure
  for 5: not counted) needs the latest success revision, which the pin's map forgets (`f8_successes_forgotten`
  shows the difference). The cost is one entry per entity embedded or tombstoned (a key and a revision). An entity
  that hop 1 finds absent, and whose record it removes, is forgotten, because no revision was read. A later Worker
  failure for that key would count, but `SaveFailed` on a removed record returns `ErrRecordGone`, which the Worker
  reports as skipped.
- **Stranded is a flag, not a revision.** The generated run at seed 24 failed against a first draft that treated
  any entry at `^uint64(0)` as stranded. A Worker failure at that revision then became unclearable by revision. That
  failure is unreachable today, but the first draft let it happen. It is now a named witness ("a Worker failure at
  the highest revision is not stranded") and `f7_never_stranded`. The pin has the opposite gap: a Worker drain at
  `^uint64(0)` clears a stranded mark there (`sourceRevision < held.strandedAt` is false at max). Here no Worker
  outcome clears one (witness "no Worker outcome clears or replaces a stranded failure").
- **A seed that cannot be read fails Start.** The pin logs and continues. A short map would let readiness read
  ready over failed records, so this fails closed instead.
- **No failed-count gauge.** The pin's `failedGauge` is not ported. D3 names none, and the follower's readiness
  gauges carry the count.

## Generated checks

`TestFailedMapHistoryMatchesModel` compares histories against a reference model the test owns, written from D3 and
the spec, not from `failed.go`. A history has an optional Start seed, then 1 to 30 steps drawn from: Worker failure,
Worker success, hop-1 failure, queued, ended, absent. The steps use three entities, revisions 0 to 3 and
`^uint64(0)`, Worker reasons `timeout`, `content_error`, `unknown`, and the three hop-1 reasons. Because adjacent
revisions are one draw apart, every step can land below, at or above the held revision. After every step the test
checks four things: the count and reasons against the model, nil reasons at count 0, the repair targets, and that
editing the returned map leaves the next read unchanged. Ten named witnesses run first, one per edge value below.
Recorded run: `go test ./processor/graph-embedding -run '^TestFailedMapHistoryMatchesModel$' -count=1 -race -v
-rapid.checks=1000 -rapid.seed=24` printed `[rapid] OK, passed 1000 tests`. The failure the generated run found is
described under "Stranded is a flag". Its rapid failure file was moved out of the tree, and the case is now a named
witness.

## Edge values

- A failure below a held failure is not stored. A success below a failure keeps it; a success at or above clears
  it. A late failure below a success is not counted. Seed: failures present and none. Count 0 returns nil reasons.
  These are covered by witnesses, and seeding also by `TestStartSeedsFailedMap`. In the follower, count 0 with nil,
  empty or stray reasons, and count 2 with an empty map, each publish no `failed_reasons`
  (`TestGraphIndexEnvelopeUnchanged`).
- A terminal outcome for a stranded entity does not clear it. `TestStrandedWithoutRevisionClearsOnlyOnRepair`
  sends generated, skipped and deleted outcomes at a higher revision and at `^uint64(0)`, plus a failure, through
  `onTerminal`. The same case is a witness.
- A read that succeeds before a write that fails re-marks the entity. Covered by `TestRepairConvergesStranded`
  and a witness.
- A repair that succeeds after the entity was deleted meanwhile. In `TestRepairConvergesStranded`, B's tombstone
  delete fails, and the repair pass finds B absent and removes its record.
- A Worker-side reason is not re-driven. In `TestRepairConvergesStranded`, the absent entity `gone` failed with
  `timeout` stays counted. A re-drive would find it absent and clear it.
- Stop while a repair pass is in flight: **not tested**. A pass's reads and writes run under the run context, which
  `cleanup` ends before it joins `repairs`. A pass that is cancelled marks its entity again (`entity_read_failed`)
  and stops at the next `ctx.Err()`. Holding a pass mid-flight needs a NATS read the test can hold, and no real
  trigger holds one. The lifecycle suite checks that the handle is released (`repair lane` in
  `StartedOwnerReportsItsHandles`). Removing the join while keeping the handle would survive.

## How the failures and the repair are driven

There are no hooks (#186). The test changes its own NATS server's stream configuration:

- `AllowDirect` off on `KV_ENTITY_STATES` makes the component's `Get` fail. Its handle was bound with direct gets,
  so nats.go v1.55.0 keeps sending them (`jetstream/stream.go:579-594`, `kv.go:1606`) and gets no responder.
- `MaxMsgSize` 1 on `KV_EMBEDDING_INDEX` makes pending writes and delete markers fail, while reads still answer.

Each test observes the failure before relying on it. Both behaviours are shown against the fixture's pinned
nats-server image and are not promised beyond it. The 30 s interval is a constant. The tests call `c.repair`, the
tick body, directly, as graph-index's tests call `repairFailedEntities` and the pin's tests call `repairStranded`.
No test waits on the ticker, and the cadence itself is **not covered**. A tick that fires during a test that runs
longer than 30 s would only repeat a pass; the assertions that must not see a repair are made while the trigger
still fails.
