# Task 2.1 notes: contract and readiness

Choices the design leaves open:

- **An ended context returns the context's error.** When a read fails and `ctx.Err()` is set, `Fuse` returns
  `ctx.Err()`, not the read's error, whatever the reply said (index_not_ready, fatal, or other): D1 checks this row
  first. The spec says "during any read", so the check also covers the two reads D1's table does not list: `Names`
  (a miss's suggestions; any other `Names` error is still swallowed, F16 kept) and the body reads (`Lens.Hydrate`,
  `BodyResolver.ResolveBody`; any other failure is still a `BodyReason`). A read that succeeds after the context ended
  does not stop the call.
- **`Node.RelationsTruncated` lands here, partly.** `TestFatalWalkReadSkipped` asserts it, so 2.1 adds the field and sets
  it only when a relation target's read failed and was skipped. Its doc says exactly that. Task 2.2 adds the cap, the
  skipped relations `Neighbors` read and the target read as absent, and rewrites the doc.
- **Stubs of 2.3 so 2.1 compiles.** `hydrate.go` is carried as at the pin (the engine's `BodyResolver`); its tests,
  the nil-context refusal and the `storeregistry` assertion stay 2.3's. The body-failure counter is not carried yet:
  no `metrics.go`, no `WithMetrics`, and `reportBodyFailure` only stamps the reason (it used
  `prometheus.DefaultRegisterer`, F5). `NewEngine(graph, body)` and the `WithSignals` builder keep the pin's shape
  until 2.3 replaces them. `fakeStore` lives in `engine_lens_test.go`; 2.3's `hydrate_test.go` port must not declare it
  again. `TestEngine_NilBodyResolver` keeps its `BodyReason` assertions; its counter assertions return with 2.3.
- **Docs touched beyond the list.** `Response.Deferred` named the removed `Index`, so it is rewritten; with it the
  `DeferReason` doc (a 3.1 item) now names the two values left. 3.1 should check it, not redo it. `doc.go` described
  the `Fuse` path, which is not carried; it now describes the lens engine. `RetrievalClient`'s doc no longer names
  `GraphQueryClient` or a status subject.
- **The facets return an error.** `computeImpact`, `computePaths`, `computeGraph` (and their helpers `neighbors`,
  `nameOf`, `pathOf`, `collectIncomingGraphEdges`) now return an error, only ever the context's. The path stop (F12,
  `nameOf` falling back to the ID) is unchanged: it is 2.2's.
- **Pin tests not carried.** `engine_health_gate_test.go` exercised the removed gate and `IndexStatus` projection;
  its one gate-free test, `TestFuse_AnsweredResponseIsNotMarkedDeferred`, moved to `contract_test.go`. From the rest:
  `TestEngine_NotReady_EmptyEnvelope`, `TestGraph_ViewRevision` and the readiness file's two re-sample tests went with
  the status read. `TestEngine_ReadinessTransient_Degrades` became `TestDeferredOnIndexNotReady`;
  `TestGraphProjection_ResponseJSONRoundTrip` became `TestGraphProjectionRoundTrip`, which also asserts the graph JSON
  has no `view_revision`. `TestEngine_NeighborGenuineError_Swallowed` stays until 2.2 replaces it. The pin's
  `semantictest.Predicate` fixture comes from `internal/harness/semantictest`.
- **What "equal-score group" means here.** Entities sharing a name that matches no query and carrying no signals do not
  score exactly equal: the resolve base still separates them by position. What they share is that nothing but resolve
  position separates them, so their expected order is resolve order, which is the oracle the generated test uses. An
  exact tie between different names needs the weights, so it is a named witness written by hand from the documented
  weights (`exact tie keeps resolve order`: resolve base 12, 8, 4; the third name contains the query, +8). It runs
  before the generated cases and is what catches an inverted tie-break.
