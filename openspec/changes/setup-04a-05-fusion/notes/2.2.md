# Task 2.2 notes: labels and counts

Choices the design leaves open:

- **One site copies the search counts.** `Fuse` resolves, then `fuseSeeds` builds every response; `Fuse` copies
  `UnreadableRecords` and `FailedRecords` onto whatever `fuseSeeds` returns (nodes, a miss, an all-seeds-unhydrated or
  index_not_ready deferral), and only when the lens chose `ResolveModeNL`. A symbol or prefix client that reports counts
  anyway is ignored, so "both always omitted" holds by the engine, not by the client. A failed `Resolve`, or an ended
  context afterwards, returns an error and no response, so no counts.
- **`Resolution` fields are `int`**, like `graph/query_search_types.go:58-59`.
- **Edges are ordered in two places.** `orderedEdges` (sort by predicate, then target; `slices.Compact` drops exact
  duplicates) runs on the relations `Neighbors` result in `collectEdges` and on every walk `Neighbors` result in
  `neighbors` (paths, impact, graph incoming). It sorts a copy, so a client's slice is never reordered.
- **The graph facet sorts before its caps too** (stop-1 review, AGENTS.md § 2). Its outgoing edges come from the seed's
  own triples, not `Neighbors`: `graphNodeFor` sorts them by (predicate, target), stably so one edge's evidence keeps
  triple order, before the 256-edge cap sees them. Facts are merged first, then sorted by their key (predicate,
  datatype, JSON value) and the first 64 kept; `FactsDropped` counts the rest. Facts therefore list in key order on
  the wire, not stored order. The per-fact and per-edge evidence caps (8) still keep the first entries in triple order:
  not in the review's scope, left as is.
- **Relations cap.** The label is set when an edge with a role arrives after its role already holds 12 refs. A target
  read that failed or found nothing also sets it, so an edge past the cap whose target would have been absent is
  labelled either way.
- **Paths cap.** The walk keeps going until it finds an 11th path, then stops; exactly 10 paths leave no label.
- **One cut path per node.** When several next nodes of the same node are unread, the path to that node is emitted once,
  truncated, after its readable branches; unread next nodes of the seed emit nothing and set `paths_truncated`. A failed
  `Neighbors` read at the seed also sets `paths_truncated` (a path was dropped, D4), which
  `TestFatalWalkReadSkipped/paths` now asserts. `nameOf` no longer falls back to the ID (F12).
- **Impact.** Only a failed file read truncates; a read that finds nothing counts the node with no file, as the spec
  says.
- **Graph.** A counterpart read that failed keeps the edge the index reported, without evidence, and sets
  `graph.truncated`; an absent counterpart keeps the pin's edge without evidence and no label.
- **Pin test replaced.** `TestEngine_NeighborGenuineError_Swallowed` is removed; `TestRelationsFaultLabelled` replaces
  it (D4).

Failing first: with only the `PathsTruncated` field added and the `Resolution` type in place, every new test failed
on its assertions (relations cap, fault and absent-target labels, unsorted refs, path cap, ID in a path, impact,
graph, the NL counts); `TestSymbolAnswerOmitsCounts` passed then, as it should (it guards against copying too much),
and is shown to fail by the mutant below.

Generated checks: not used. The law is "the same graph gives the same cut whatever order the reply lists its edges"; the
order is decided by one sort and one compact over a copy, so the interacting inputs are reply order and duplicates.
`TestEdgesSortedBeforeCap` covers both: one reply in order, one reversed with a duplicate of the first target, against
an expected list built from the fixture. Fuzzing: none; 2.2 parses no external bytes.
