# Task 2.2 notes: the vector cache on `graphview.View`

`graph/embedding/vector_cache_bench_test.go`: 50,000 generated records of 384 dimensions (the BM25 embedder's
default), vectors from a fixed seed, over the in-memory `replayKV` (no NATS). Apple M3 Pro, 12 CPUs, go1.26.10

- **Call time:** about 37 ms per `FindSimilar` (limit 10).
- **Lock hold time:** about 9.0 ms. `ListCounted` runs its whole body, the copy and the key sort, under the view's
  one mutex, so its uncontended call time is the hold time plus one uncontended lock and unlock. While it is held
  the view applies no write. The benchmark measures the call; it does not instrument the mutex.
- **What it means for graph-clustering** (arithmetic from the numbers above, not measured): one `similar` per entity
  per refresh at 50,000 entities is about 50,000 x 37 ms = 31 minutes of call time and 50,000 x 9 ms = 7.5 minutes of
  view lock per refresh. The design sets no gate; this is for graph-clustering's port to plan around (a batched
  read, or a `ListCounted` that does not sort keys the caller re-sorts by score).
- The cache this replaces held its own read lock for the whole call, scoring included (`dfe89d6`,
  `graph/embedding/vector_cache.go:151-152`); not benchmarked here.

## Choices the design leaves open

- **The last view stays after its Run.** `VectorCache` keeps the latest Run's view in an `atomic.Pointer` and
  replaces it on the next Run, so after Run returns `FindSimilar` reads the stopped view and maps `ErrViewStopped`
  to an error matching `ErrNotReady` (D2's wording), or the lost view's own error, which already matches. The
  cost is that a stopped view's vectors stay in memory until the next Run or until the cache is dropped.
  graph-query's community reader clears its pointer instead (`processor/graph-query/community.go:92`); here the
  mapping would then be unreachable by a test. No view at all (before the first Run) is its own error matching
  `ErrNotReady`.
- **The watch source.** `indexSource` adapts the storage's `natsclient.KVStore` to `graphview.WatcherSource`:
  `WatchAll` is `KVStore.Watch(ctx, jetstream.AllKeys)`, and the view passes no options. No new exported surface.
- **A limit of 0 or less** still reads the view, so the readiness error and the unreadable count are answered as
  for any limit; only the entities are none.
- **`errWatchLost` stays for the Worker** and moved to `worker.go`; the cache's Run now returns the view's error,
  which matches `graphview.ErrWatcherLost` (spec delta).
- **`Storage.ListGeneratedEntityIDs` had no test uses** to remove; it is deleted with its doc comment.
  `docs/admission-ledger.yaml:3806` still names it, for task 3.1. `graph/embedding/README.md:79` still says
  `(nil, false)`, for task 3.1.

## Tests changed beyond the four D2 names

- **`TestVectorCacheRunLeavesNoWatchDelivery`** kept its property and lost its mechanism: it stalled Run by
  holding the cache's read lock inside `keep`, and `FindSimilar` now calls `keep` after the view's lock is released.
  It now wraps the bucket so `Watch` hands the watcher over only after nats.go's delivery is blocked and the
  context has ended, the shape of `natsclient/storagereport`'s `backloggedWatchStore`. Ten cycles on one cache,
  each a new Run.
- **`TestVectorCacheInvalidationLinearizesWithActiveRead`** now proves the new rule: a read made while the view
  answered returns that answer even after Run has returned, and Run does not wait for it. It runs in a bubble; the
  goroutine-stack helper `runWaitsForCacheLock` is gone.
- **`TestFindSimilarReadsOneMoment`** (new): a delete and a poison applied after the read and before the call
  returns are not in its answer; the next call sees both.
- The unit tests' `feedKV` now shares one watcher so a test can close the channel under a live Run (`lose`).
