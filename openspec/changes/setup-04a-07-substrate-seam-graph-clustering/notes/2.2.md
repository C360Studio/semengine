# Task 2.2 notes: config, factory, `Register`, shell and feed

## Choices the design leaves open

- **A minimal piece of 2.3, `tick`.** `TestRefusedValueReportedNotWithheld` needs a tick: D2 takes `refused_entity`
  from the last tick's `*IncompleteError`. 2.2 adds the unexported `tick` (`component.go`): no tick while the
  follower's `QueryReady` refuses, then `BootstrapDone`, `Tick`, and the refused count kept for `Failed`. Only the tests
  call it, marked `// shortcut:`. Left for 2.3: the ticker on `detection_interval`, `publication_failed`, the counter,
  the stuck state. Until then a failed write only logs and keeps the last refused count, as D2 says.
  `BootstrapDone` runs on every tick that starts: it only sets a flag, so this matches "the first such tick calls
  `BootstrapDone` first".
- **Removed keys, with guidance.** Strict decoding alone would say `json: unknown field "batch_size"`; the spec wants
  the key and what replaces it. `decodeConfig` scans the top-level keys against `removedKeys` first and names every
  removed key present, in name order, as `"<key>" was removed: <what replaces it>`. A value that is not one object
  falls through to the strict decoder, which names its fault. A key in the wrong case (`BATCH_SIZE`) is refused as
  unknown, without guidance: encoding/json matches field names without regard to case, so only defined keys match
  that way.
- **`detection_interval` refuses what the pin ignored.** The pin parsed it and fell back to 30 s on a value it could
  not parse (`pin:component.go:405-410`); here `soon`, `30`, `0s` and `-1s` are refused naming the key. The field stays
  a string (the pin's JSON shape, so semsource's and semboids' values decode), parsed by the unexported
  `Config.interval` (inventory § 8: the pin's `DetectionInterval()` method is unexported). Negative
  `startup_attempts` and `startup_interval_ms` are refused; zero still means the default.
- **Exactly one input.** D3 says "one `ENTITY_STATES` input". A second input, a kv-read (the pin's default also read
  `ENTITY_STATES`, `OUTGOING_INDEX`, `INCOMING_INDEX`), a filtered or history watch, or no input is refused naming the
  port.
- **A value that does not decode.** `deliver` logs the decoder's error (it names the reason) and applies
  `Upsert(id, rev, nil)`, the maintainer's refusal, whose own error is dropped: it says less than the decoder's.
  Either way the revision is `Complete`d at once (D1). `Withhold` returns 0.
- **Package comment.** In `component.go` for now; `doc.go` is task 4.2's and takes it over.
- **`readiness.KeyGraphClustering`** is added next to the other keys, with a doc saying what its indexed revision
  counts, as `IndexStatusResponse.IndexedRevision`'s doc (task 2.1) does.

## The lifecycle suite runs on the real clock, not in `synctest`

The task's check names `synctest`. 2.2 starts one goroutine of its own, the follower's `Run`, and it needs a real
client and a real `ENTITY_STATES`. A bubble's clock does not advance while a goroutine waits on a socket read, and
nats.go's read loop always does: the reason task 3.2 of the graph-index change ran the follower's two `synctest` tests
on the real clock (`archive/2026-10-27-setup-04a-04-graph-roots-graph-index/notes/3.2.md`, accepted by the
orchestrator). So `TestStopLeavesNothing` is an integration test, as graph-index's and graph-embedding's suites
are. It runs `lifecycletest.Run`, and then `StopAfterATick`: the component publishes, `Stop` returns nil, and polled
reads find no goroutine in a `graphclustering.(*Component)` or `follower.(*Follower)` frame, no nats.go watch
delivery, and no consumer on `ENTITY_STATES`. The polls wait on `t.Context()` only (#554). A `synctest` test fits
task 2.3's ticker loop if that loop runs without a NATS client. **Open for the reviewer**: the check's `synctest`
label is not met by 2.2.

## Named examples, no generated checks, except the config fuzz target

The config is external bytes, so `FuzzResolveConfig` (seed corpus: one seed per class it accepts or refuses)
asserts its invariants. Seed replay runs in `task test:unit`. One exploratory run on this machine,
`go test -run '^$' -fuzz FuzzResolveConfig -fuzztime 30s`, made 2,236,768 executions and failed nothing. The shell
and the feed have no stated law beyond D1 and D2, so named examples cover them.
