# Task 2.3 notes: ticker, publication failures and #525

## Choices the design leaves open

- **The ticker calls 2.2's `tick`; the `// shortcut:` marker is gone.** `start` runs a second goroutine under the
  one run context, `c.runTicks(runCtx, c.tick)`, and `cleanup` joins it after the follower's `Run` (`ticks`, beside
  `feeds`). The first tick is one `detection_interval` after `Start`, as the pin's `time.NewTicker` loop
  (`pin:component.go:1449-1463`); a tick that outlasts the interval delays the next, so ticks never overlap.
- **`runTicks` takes the tick as an argument.** Production passes `c.tick`, once. `TestDetectionIntervalIsRead` passes
  a counter, so the interval reading runs in a `synctest` bubble with no NATS client (2.2's notes: the follower's
  `Run` cannot run in one). The interval is resolved once, in the factory (`Component.interval`), from
  `Config.interval`, which `Validate` already ran. **Open for the reviewer:** whether an unexported method taking its
  tick reads as a back door. It swaps nothing under a running object; the alternative, testing the interval only
  through the integration tests' wall clock, cannot tell 30 s from the configured value.
- **What a failed tick does.** Any error from `Maintainer.Tick` other than `*clustering.IncompleteError` sets
  `publicationFailed`, adds one to `semengine_graph_clustering_publication_failures_total` and logs a warning, in
  that order. The refused-entity count is kept (design D2). A successful tick, or one returning `*IncompleteError`,
  clears `publicationFailed`. `Failed` reports `publication_failed 1` beside `refused_entity N`, so the envelope reads
  `degraded` and the follower's `Stuck` sentence (`N unresolved failures: publication_failed 1`) makes `Health`
  unhealthy; `Withhold` stays 0. No new `Stuck` sentence was added: the follower's names the reason.
- **A tick the run context ends is not a failure.** When `Tick` fails and the run context has ended (`Stop` is under
  way), nothing is counted or kept. Not covered by a test (see below).
- **Metric name.** `Namespace: "semengine"`, subsystem from the key, as graph-embedding's collectors; the design's
  `graph_clustering_publication_failures_total` is the name below the namespace, as ADR-063 names graph-embedding's.
  Registered in the factory through `metric.RegisterOrGet` on `Dependencies.MetricsRegistry`, keeping the returned
  collector.
- **Tests that tick by hand.** `TestRecordsFollowChanges`, `TestLostFeedStopsPublication`,
  `TestResetStopsPublication` and 2.2's `TestRefusedValueReportedNotWithheld` set `detection_interval` to `1h`
  (`tickByHand`) and call `tick` themselves, so each tick runs at a point the test chose and none runs between a
  write and the reading that must come before its tick ("Applied before the tick"). The production ticker drives
  `TestNothingPublishedBeforeReplay` (`1ms`), `TestPersistentPublicationFailureIsStuck` and `TestStopWaitsForTick`
  (`20ms`); the last two fail if `start` runs no ticker (mutant `m7` below).
- **The lost feed's trigger.** The spec's scenario names a revision out of order. A real server cannot be made to
  deliver one, so `TestLostFeedStopsPublication` deletes `ENTITY_STATES` under the component, the trigger an
  operator causes; both set the follower's one lost-feed latch, and the out-of-order case is
  `TestFollowerDeclaresLostFeedOnOutOfOrderDelivery`. The test waits about 18 s for nats.go to close the watch.
- **How publication is made to fail.** `COMMUNITY_INDEX` is deleted under the running component, so every write
  fails, and created again for the success. No hook: the failure is the server's.
- **`TestStopWaitsForTick`** is added beyond the task's list: the join mutant (`m9`) survives `TestStopLeavesNothing`,
  whose polled stack read forgives a goroutine still exiting (#490), as 2.2 found for the follower's join. It holds a
  failed tick in its log line and checks that a `Stop` with a 200 ms deadline (the behaviour under test) returns
  `context.DeadlineExceeded` with its handles kept.
- **Named examples, no generated checks.** The ticker has one input, the interval; the outcome has three tick results
  (success, incomplete, other error) and the gate one answer from `QueryReady`. The tests name each.

## `TestWatchOrderAcrossKeys`: the observed order (#525)

An observation at nats.go v1.55.0 and the server image `nats:2.15.0-alpine@sha256:ac8f88a6...` (the pin in
`internal/harness/natsfixture/nats-image`), on 2026-11-10, not a promise. The probe opens the watch the follower
opens (`kvcatalog.CatalogReader.WatchAll`) after five interleaved rounds over four keys, the last round in reverse
key order, then makes twenty interleaved live writes with one delete:

```text
replay order: c1@17 a2@18 b1@19 a1@20
live order: a1@21 b1@22 a2@23 c1@24 c1@25 a2@26 b1@27 a1@28 a1@29 b1@30 a2@31 c1@32 c1@33 a2@34 b1@35 a1@36 a1@37 b1@38 a2@39 c1@40
```

The replay delivered each key's last write in revision order, not key order, and the live writes in revision order,
the delete (`b1@30`) among them. The probe fails if a version changes that. graph-clustering does not rely on it: the
follower declares a revision at or below one it has observed a lost feed, and no tick starts after
(`TestLostFeedStopsPublication`, design D4).

`TestNothingPublishedBeforeReplay` cannot hold the replay: every value the component's logger would hold on is one
the replay refuses, which latches the reset instead. So its detection rests on a tick landing inside a 2,000-entity
replay with the ticker at 1 ms; it detected in every run made (5 of 5 over `m1` and `m2`). Its assertion does not
depend on timing: with the gate in place no tick publishes before the replay, so every group's first record is whole.

Not covered: a tick ended by `Stop` counted as a publication failure (the `ctx.Err()` arm) has no test; it needs `Stop`
to land inside a failing write.
