# Task 2.2 notes: index memory before real data

Implemented by claude (opus, medium).

## What changed

`graph/lexical/index.go` holds each entity and each word once, under a number (`uint32`), and refers to them by
number everywhere else: an entity's word sequences are `[]uint32`, and each word's postings map entity numbers to
the weighted term frequency (`map[uint32]int32`). Numbers of removed entities and words are reused, so the numbers
stay as few as what is held. This is design D4's word-number layout, the one change 1's `sequence-probe` measured.
Scoring is unchanged: each entity's score sums the same terms in the same order (`Query.scored`), so scores are
bit-identical, and ties still break on entity ID. No exported name, signature or doc comment changed; no test was
edited.

## The entity count and text size the cost is accepted for

- Measured: 50,000 entities at about 1.2 KB of text each (2.2 KB of index per entity), and 32,000 entities at
  SemSource's sizes, about 640 B of text each (1.4 KB per entity, 44 MB in all).
- Projected, not measured: one million entities at SemSource's sizes, about 1.4 GB; at the scorecard's 1.2 KB, about
  2.2 GB, close to change 1's design figure of about 2 GB for a million 120-word entities (#623). The projection
  multiplies the per-entity figure, which is a floor: the corpus is repeated, so its vocabulary stops at 8,335
  words, where real data's keeps growing.
- Search time is not changed by this task: a common-word query over a million entities stays roughly 200 to 400 ms
  under the read lock (#623). That cost is the design's Risks item, not part of this acceptance.

## Why the harness is not in the tree

It asserts nothing, so it proves no behaviour, and it would run in every unit lane: the repository allows no build
tag but `integration` and no `Skip`, so a test file in `graph/lexical` runs in `task test:unit` (once, under the race
detector) and `task test:repeat` (five more times). A 50,000-entity build there costs seconds per run for figures
nobody reads. It stays beside these notes as `.go.txt`, as change 1's probes do.

## Tests

- Every `graph/lexical` test passes unchanged, with the race detector (`TestSearchDuringWrites` included), the
  generated checks (`TestPropIndexMatchesModel`, `TestPropRankingIgnoresHistory`, `TestPropAbsentWordsMatchNothing`)
  and `TestScorecardHoldsItsFloor`.
- Generated checks: no new ones. The change is a layout under an unchanged contract, and the order-dependent history
  it adds (numbers freed and reused across `Put` and `Delete`) is what `TestPropIndexMatchesModel` already drives:
  random histories of `Put`, replacement and `Delete` compared after each step against a test-owned model.
- Shown able to fail: `task mutate:check -- -pkg ./graph/lexical -test TestPropIndexMatchesModel -file
  graph/lexical/index.go -mutant <copy> -expect-text model`, the copy removing the `holders == nil` guard in `remove`
  so a word repeated in one entity frees its number twice. Verdict: detection, three of three runs failing at
  `index_prop_test.go:258` (`Search("alpha delta", ...): Matched = 1, model 2`), the after-run passing.
- Not covered by a kept test: that freed numbers are reused, a memory property no exported call can see. Checked
  once with a throwaway test in the package (not kept, as it reads private fields): 1,000 entities with unique words
  put and deleted three times; after each round `entities.items` stayed at 1,000 and `words.items` at 1,002, every
  number on the free list. As with the map layout before, the slices keep their peak length after a mass delete
  until new entities and words reuse the numbers.
