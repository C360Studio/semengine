## Choices the design leaves open

1. **The word gauge's count and source.** `semengine_graph_lexical_index_words` counts every word occurrence the
   index holds, name and body, as `lexical.Tokens` returns them; `semengine_graph_lexical_index_entities` is
   `Index.Len()`. `lexical.Index` exports no word count, and this task builds against its exported surface, so the
   applier tokenizes each document a second time and keeps a per-key count. A `Words()` method on `lexical.Index`
   would remove the second pass; it is a change to `graph/lexical`, which PR B is editing, so it is not made here.
2. **A delete forgets the key.** The applier keeps no revision for a deleted key, so memory does not grow with
   deletes. A delivery older than the delete is then applied: the spec ignores a delivery at or below "the revision
   the index holds for that key", and after a delete it holds none. That order only arrives when the watch delivers
   out of order, which the follower declares a lost feed and refuses queries for until restart.
3. **An ignored delivery is completed at once**, so a re-delivered or older revision never holds the floor.
4. **A value that is not a canonical entity state** latches the follower's reset with the state contract's reason,
   counts an error and leaves the revision pending, as graph-embedding and graph-index do. Nothing is applied.
5. **A failed body read leaves the inline text** and drops the waiting state. Whether `unread` keeps the state for
   the repair pass is task 2.4's.
6. **Until the body path exists**, `deliver` gives every offloaded body the outcome "not read" at once, marked
   `// shortcut:` in `component.go`; task 2.4 replaces it.
7. **`max_text_len` above 1,000,000 is refused**, graph-embedding's ceiling, spelled again in `config.go` rather
   than importing `graph/embedding` for the constant. One spelling in `graph/entitytext` would serve both; that
   moves an exported constant of `graph/embedding` and is left to the owner of that choice.
8. **Ports**: one input, the `ENTITY_STATES` kv-watch. Task 2.4 adds a store-read input if it needs one.
9. **`Failed` reports 0** and no `Withhold` is set: nothing is counted as a failure until task 2.4's `body_unread`.
10. **The applier completes through a function** the component sets to `follower.Complete`; the tests pass a
    `revlag.Watermark`'s `Complete` or a recorder. It is the applier's one dependency, set at construction; no
    production caller swaps it.

## Generated checks

Used, not examples alone, because two paths write one key and the order of their outcomes is the risk (design D2).

`TestStaleBodyReadDropped` is the named witness: it sits above the property in `apply_prop_test.go`, so it runs
first in file order, and its case is also the first of eight named witnesses `TestPropApplyMatchesModel` runs through
its own checks before `rapid.Check`. The floor in the witness is a `revlag.Watermark`, the follower's own.

The reference model (`history` in `apply_prop_test.go`) is filled from the requirement: each delivery's words are
unique to its key and revision, so a search per word says which revision's text the index holds. After every step it
checks the touched key's words, the entity count and both gauges, and that each delivered revision is complete
exactly when its own outcome, or a later outcome of a revision of the key at or above it, is in (the follower's
`Complete` rule), never before. Inside each completion it checks that the index already holds the completed
revision's text. Older deliveries, deletes, failed reads and reads returning late or out of order are generated;
each kind has a named witness, so every assertion runs on every run.
