# Task 2.5 notes: the quality bar (PR B)

Base commit `6fa27439`.

## What the test does

`TestSearchScorecard` (`processor/graph-query/scorecard_integration_test.go`) writes the word index's frozen
corpus (`graph/lexical/testdata/scorecard/corpus.jsonl.gz`, 2,000 sections) through real graph-ingest, indexed by
real graph-index and graph-lexical, and asks each of the 500 questions in `known.json` through `globalSearch` and
through `localSearch` from the answer's own entity ID at level 0, both with `limit` 100. It fails when either verb's
R@10 is more than one point (5 answers of 500) below a plain BM25 computed in the test, or below 55% global and
58% local. A refusal of any question, or a local reply whose `community_id` is not the answer's level-0 group, fails
it at once.

## Choices the design leaves open

- **The corpus and questions are the package scorecard's files**, read from `graph/lexical/testdata/scorecard`, so
  both scorecards ask the same questions of the same text. Only `known.json` is asked: the spec names "its 500
  questions". `questions.json` (behaviour questions) stays the package scorecard's; it checks the ranking, which
  this test does not re-prove.
- **The reference** is the probe's: Okapi BM25 with Lucene's idf, k1 1.2, b 0.75, over one field holding a
  section's name and body words, no name weight; ties go to the smaller ID; a score of zero is not a hit. Local
  is the same scores kept to the answer's group, so idf is corpus-wide in both, as the scoped index's is. Words come
  from `lexical.Tokens`, and the text from `entitytext`'s default rule over the triples written: the reference
  must read the same words the index reads, or the comparison measures tokenizing, not ranking. The ranking is the
  reference's own.
- **The level-0 group** is the ID's first four parts (`c360.semengine.<top directory>.markdown`), from the corpus
  README's ID shape, not from `clustering`; the local reply's `community_id` is checked against it.
- **Sections are written as `doc.section.title` and `doc.section.content`**, the probe's predicates, with no type
  triple, so the indexed text is exactly the section's. graph-ingest runs under platform `c360`/`semengine` to accept
  the corpus IDs: `startIngestAndIndex` now calls `startIngestAndIndexAs` with the test platform.
- **`limit` 100, not 10.** A wrong order inside the first hundred moves answers out of the first ten, which R@10
  sees; with `limit` 10 the "re-sorted by ID" mutant reorders only the first ten and R@10 cannot see it. MRR is
  therefore over the first hundred, for the reference too (a rank past 100 counts as not found), which is why the
  MRRs below are about 0.001 under the probe's uncapped ones. Cost: the test takes about 106 s under `-race`
  (ingest about 10 s; 1,000 replies of up to 100 hydrated entities the rest); with `limit` 10 it took 26 s.
- **No community records.** graph-clustering does not run, so local search answers with `record_state`
  `not_ready`; records do not change matches.

## Measured

On the commit of this note, `go test -race -tags integration -count=1 -run TestSearchScorecard -v`:

| Row | R@1 | R@10 | MRR (first 100) |
| --- | --- | --- | --- |
| global, plain BM25 | 25.4% | 56.0% | 0.363 |
| global, `globalSearch` | 24.6% | 56.0% | 0.357 |
| local, plain BM25 in the group | 29.0% | 60.0% | 0.399 |
| local, `localSearch` | 28.2% | 59.8% | 0.394 |

These match the probe's word-index rows (`notes/probes/search-quality-probe.log`, keyword phrasing) in R@1 and
R@10 exactly: the path through graph-ingest, graph-lexical and graph-query loses nothing.
