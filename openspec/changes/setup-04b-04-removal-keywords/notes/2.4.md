## Choices the task leaves open

- **Where `Start` builds the embedder.** First, before the follower opens. The design says "in `Start`, where the
  embedder is built today"; building it first means a product embedder that cannot be built fails `Start` before any
  watch or bucket is touched, and it makes "a `Start` failing after the build" reachable through production calls
  (no `ENTITY_STATES`, one startup attempt), which `TestEmbedderClosedOnStop` uses. Every step after it rolls back
  through cleanup, which closes it.
- **A failed close.** cleanup clears every other handle first, then closes the embedder; a failed close returns the
  error with only the embedder kept, so the next `Stop` does not re-drain subscriptions that are already gone and
  closes the embedder again. That second close is the "kept and closed by `Stop`" case; `Close` is called twice in it.
- **`CreateGraphEmbedding` stays exported, and always refuses** (task 2.7 later unexported it as
  `refuseWithoutEmbedder`; see `notes/2.7.md`). It is the factory plain `Register` adds.
  `processor/graph-query/embedding_integration_test.go:32,87` calls it, and this task does not edit graph-query, so
  removing it would stop graph-query's integration tests compiling. Once graph-query's tests build graph-embedding
  through `RegisterWithEmbedder`, it can become unexported.
- **`max_text_len` default** stays 4,000 (renamed `defaultMaxTextLen`); it was BM25's cap. The design does not move
  it, and it is part of the dedup key, so changing it re-embeds every entity.
- **Test path.** In-package tests create graph-embedding through `RegisterWithEmbedder` and the registry's
  `CreateComponent`, a fresh registry per component. Two tests call the unexported factory `RegisterWithEmbedder`
  wraps, because the registry's own checks would hide the factory's: `TestCreateGraphEmbeddingRequiresNATSClient`
  (the registry refuses a nil NATS client first) and `FuzzResolveConfig` (it compares the factory with
  `resolveConfig`, and the registry's input checks would refuse some bytes first).
- **The test embedder** (`wordEmbedder`) hashes each lower-cased word that is not a stop word into one of 1,024
  positions and scales the counts to unit length; it drops the same kind of stop words, so the existing tests' claims
  (a stop-word query has no hit, a word shared by no entity has no hit, an exact title outranks a title with one
  shared word) hold. The hashed BM25 embedder in `graph/embedding` is kept for task 2.5; nothing here uses it.
- **`TestEmbedderClosedOnStop`** is integration-tagged as a whole (its started and failed-start cases need a
  server); its "built and never started" case needs none but stays with the others under the one name.
- **Comments that described BM25's corpus statistics** in two test comments were reworded; the claims they made
  (a refused request changes nothing) still hold.

## A restart under a different embedder

A product that restarts graph-embedding with a different embedder, against the same NATS state, must not get answers
computed across two vector spaces. Before this, hop 1 kept every generated record at the replayed revision whatever
made it, so the old provider's vectors stood, readiness latched, and `search` scored a new query against them:
unequal widths scored 0 and every hit vanished; equal widths gave plausible scores for unrelated vectors.

**Choice: regenerate, not refuse.** The framework can see the mismatch and repair it, rather than refuse to start and
ask the operator to wipe the index. Changing embedders is an ordinary product decision; the cost is one regeneration
of every entity, the cost the dedup key already accepts for the same change.

**Which embedders count as the same: the dedup key's identity, unchanged.** `EmbedderIdentity` (registered type,
model, width, text cap) already decides when a deduplicated vector may be reused, and an embedder that has not
resolved its width gets no dedup key. Generated-record reuse now follows the same rule, so there is one answer to
"same vector space" instead of two:

- **The record stores its identity.** `Record` gains `EmbedderType` and `MaxTextLen` beside `Model` and
  `Dimensions`; `SaveGenerated` takes an `EmbedderIdentity` and stores all four (the width is the vector's own
  length). A record written before this has no type, so it matches no running identity and is regenerated. No
  migration: deployments start fresh.
- **One rule.** `Record.GeneratedBy(id)`: generated, the stored identity equals `id`, and `id`'s width is resolved.
  The cache uses the same unexported `sameSpace` check, so the rule is written once.
- **One builder.** `embedding.IdentityOf(type, embedder, maxTextLen)` builds the identity; the Worker's dedup key
  and graph-embedding's `identity()` (`component.go`) both call it, so hop 1, the cache and `similar` read exactly the
  identity the Worker writes.
- **Hop 1 re-pends.** `SavePendingGuarded(ctx, record, id)` holds back only when the stored record was made under
  `id` at a same-or-newer revision. Any other generated record is replaced by the pending one, and the Worker
  regenerates it before the revision completes, so readiness still means every replayed revision has a current
  vector.
- **The identity is read on each call, never frozen.** `NewVectorCache(storage, identity func() EmbedderIdentity)`:
  the cache keeps every generated vector with the identity it was made under, and `FindSimilar` reads the running
  identity once per call and scores only vectors made under it. An embedder that learns its width after Start is
  matched by the learned width; while its width is unresolved nothing is scored. `similar` refuses a source made
  under another identity with `embedding_unavailable`, as it refuses a pending one. This covers a mixed old/new
  index during regeneration, and a stale record with no `ENTITY_STATES` entry that nothing will regenerate.
- **The text cap is part of the identity.** It is in the dedup key because it changes the text embedded, so
  changing `max_text_len` now regenerates every vector at the next restart; the README's `max_text_len` row said a
  stored record kept its old text, and now says this.

**Cost, stated:** an embedder whose `Dimensions()` reports 0 until its first response cannot vouch for a stored
vector, so on a same-provider restart every entity hop 1 replays before that first response is embedded again (the
dedup bucket cannot help: it withholds a key for the same reason). The embedder contract asks for 0 rather than a
guess, so this is the honest outcome; an embedder that knows its width up front restarts with no re-embedding. The
README says so under "Changing the embedder".

**Not declared as a skip.** A vector made under another identity is left out of scoring exactly as a pending record
is (absent until generated), not as a dropped answer, so it gets no metric of its own; the regeneration is the
Worker's ordinary pending-to-generated path. A reviewer who reads the exclusion as a degrade needing its own signal
should say so.

**Exported surface changed:** `Storage.SavePendingGuarded` and `Storage.SaveGenerated` take an `EmbedderIdentity`;
`NewVectorCache` takes an identity function; `Record` gains `EmbedderType` and `MaxTextLen`; new
`Record.GeneratedBy` and `IdentityOf`. Every caller in this repository is updated; consumer callers were not
measured, and a consumer break is a migration line.
