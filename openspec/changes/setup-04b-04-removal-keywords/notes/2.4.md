## Choices the task leaves open

- **Where `Start` builds the embedder.** First, before the follower opens. The design says "in `Start`, where the
  embedder is built today"; building it first means a product embedder that cannot be built fails `Start` before any
  watch or bucket is touched, and it makes "a `Start` failing after the build" reachable through production calls
  (no `ENTITY_STATES`, one startup attempt), which `TestEmbedderClosedOnStop` uses. Every step after it rolls back
  through cleanup, which closes it.
- **A failed close.** cleanup clears every other handle first, then closes the embedder; a failed close returns the
  error with only the embedder kept, so the next `Stop` does not re-drain subscriptions that are already gone and
  closes the embedder again. That second close is the "kept and closed by `Stop`" case; `Close` is called twice in it.
- **`CreateGraphEmbedding` stays exported, and always refuses** (task 2.7 later unexported it as
  `refuseWithoutEmbedder`; see `notes/2.7.md`). It is the factory plain `Register` adds.
  `processor/graph-query/embedding_integration_test.go:32,87` calls it, and this task does not edit graph-query, so
  removing it would stop graph-query's integration tests compiling. Once graph-query's tests build graph-embedding
  through `RegisterWithEmbedder`, it can become unexported.
- **`max_text_len` default** stays 4,000 (renamed `defaultMaxTextLen`); it was BM25's cap. The design does not move
  it, and it is part of the dedup key, so changing it re-embeds every entity.
- **Test path.** In-package tests create graph-embedding through `RegisterWithEmbedder` and the registry's
  `CreateComponent`, a fresh registry per component. Two tests call the unexported factory `RegisterWithEmbedder`
  wraps, because the registry's own checks would hide the factory's: `TestCreateGraphEmbeddingRequiresNATSClient`
  (the registry refuses a nil NATS client first) and `FuzzResolveConfig` (it compares the factory with
  `resolveConfig`, and the registry's input checks would refuse some bytes first).
- **The test embedder** (`wordEmbedder`) hashes each lower-cased word that is not a stop word into one of 1,024
  positions and scales the counts to unit length; it drops the same kind of stop words, so the existing tests' claims
  (a stop-word query has no hit, a word shared by no entity has no hit, an exact title outranks a title with one
  shared word) hold. The hashed BM25 embedder in `graph/embedding` is kept for task 2.5; nothing here uses it.
- **`TestEmbedderClosedOnStop`** is integration-tagged as a whole (its started and failed-start cases need a
  server); its "built and never started" case needs none but stays with the others under the one name.
- **Comments that described BM25's corpus statistics** in two test comments were reworded; the claims they made
  (a refused request changes nothing) still hold.

## A restart under a different embedder

A product that restarts graph-embedding with an embedder of another model or width, against the same NATS state,
must not get answers computed across two vector spaces. Before this, hop 1 kept every generated record at the
replayed revision whatever made it, so the old provider's vectors stood, readiness latched, and `search` scored a
new-model query against them: unequal widths scored 0 and every hit vanished; equal widths gave plausible scores
for unrelated vectors.

**Choice: regenerate, not refuse.** A stored record already says which model and width made it (`Model`,
`Dimensions`), the same two facts the Worker already checks before reusing a deduplicated vector
(`dedupRecordUsable`). So the component can see the mismatch itself and repair it, rather than refuse to start and
ask the operator to wipe the index. Changing models is an ordinary product decision; the cost is one regeneration of
every entity, the same cost the dedup key already accepts for the same change.

- **One test of "made by this embedder".** `Record.GeneratedBy(model, dimensions)`
  (`graph/embedding/storage.go`): generated, same model, and same width unless the embedder has not learned its width
  yet (`Dimensions()` is 0), when the model alone decides. Exported because `processor/graph-embedding` calls it
  (`query.go`, `handleSimilar`).
- **Hop 1 re-pends.** `SavePendingGuarded` takes the running embedder's model and width and blocks only on a record
  that embedder generated at a same-or-newer revision (`hop1.go` passes `c.embedder.Model()` and
  `Dimensions()`). Any other generated record is replaced by the pending one, and the Worker regenerates it before
  the revision completes, so readiness still means every replayed revision has a current vector. The same-provider
  restart is unchanged: the record stands, nothing is rewritten.
- **Search and similar score only this embedder's vectors.** `NewVectorCache(storage, model, dimensions)` keeps only
  records `GeneratedBy` that embedder; another embedder's record is absent from the cache as a pending one is.
  `similar` refuses such a record as its source with `embedding_unavailable`, as it refuses a pending one. This
  covers a mixed old/new index: an entity whose vector is not regenerated yet, or one with no `ENTITY_STATES` entry
  that nothing will regenerate, is never scored against the new model.
- **Not declared as a skip.** An old-model record left out of the cache is treated exactly as a pending record is
  (absent until generated), not as a dropped answer, so it gets no metric of its own. The regeneration itself is the
  Worker's ordinary pending-to-generated path. A reviewer who reads the cache exclusion as a
  degrade needing its own signal should say so; that would be a counter on the cache's decode.
- **Exported signatures changed**: `Storage.SavePendingGuarded` gains `model string, dimensions int`;
  `NewVectorCache` gains the same two. Every caller in this repository is updated (`hop1.go`, `component.go`,
  tests); consumer callers were not measured, and a consumer break is a migration line.

Generated checks: none added. The guard gains one input (the embedder's identity) with three named cases in
`TestSavePendingGuarded_Decisions` (another model at the same revision, another width at a newer revision, same model
with the width unresolved); the revision history test `TestRevisionGuardHistoryMatchesModel` still runs with one
embedder throughout. A history mixing embedders is not generated: the identity check is an equality applied before
the existing revision rule, and the named cases cover each way it can differ.
