# Task 2.2: the merge in searchGraph

## What changed

- `graph/query_global_search_types.go`: `GlobalSearchData.Fallback` is `Merge` (JSON `merge`);
  `TextSearchMatch` gains `WordRank` (`word_rank`) and `VectorRank` (`vector_rank`), both omitted when 0; doc
  comments on `GlobalSearchData`, `GlobalSearchHint`, `TextSearchData` and `TextSearchMatch` say what they hold in
  a merged reply.
- `processor/graph-query/merge.go` (new): `mergeRanks` (D1), the word lists read back unmerged, `goSearch` (runs
  the embedding search beside the word search; `stop` cancels and waits for it to return), `semanticSearch` and
  `readSemantic`.
- `processor/graph-query/textsearch.go`: `globalText` keeps globalSearch and tier 0 as they were; `mergedText` is
  tier 1 searchGraph (D1-D4); both end in `answerText`, the batch read, hints, fit and encode that `globalText` did.
  `semanticAlone` reads the outcome already in flight. `textSearchAnswer` adds `, and {extra} more by meaning`.
- `processor/graph-query/query.go`: `ask` is split so its failure classification (`requestFailed`) can be applied
  only to an embedding outcome that is read. `globalsearch.go`: `semanticFallback` and the `no_matches` detail are
  gone.

## Choices the design leaves open

1. **Score in a failed merge.** When the embedding search fails, the matches carry the word index's score, not a
   merged one: the spec gives the merged score to "a searchGraph merged list" only, and a failed merge's list is the
   word list. `word_rank` is set, `vector_rank` omitted.
2. **Detail of a failed merge.** `merge.detail` is `merged` whether or not it is honoured (D2 names `merged` or
   `index_not_ready`); `honoured`, `code` and `reason` say what happened.
3. **An embedding hit whose ID names no group.** That is the embedding index's broken reply: counted as one error,
   `merge` not honoured naming it, and the word list answered. A broken word hit stays a refusal, as before.
4. **An ID listed twice in one list** keeps its first place (`TestMergeRanks`, "an ID listed twice"). Neither index
   sends one; the rule keeps "each entity once" true whatever arrives.
5. **Errors counted.** The cancelled embedding request (word refusal other than `index_not_ready`) counts none:
   its outcome is never read. An embedding failure that is graph-query's own (no answer, timeout, broken reply)
   counts one when it is read, as `ask` did. Mutation 7 below shows the test sees the difference.
6. **`index_not_ready` reply depth.** The embedding request is sent 100 deep before the word refusal is known
   (D1.1), so `semantic` in that reply holds up to 100 hits, not the request's limit. It is the reply's data as its
   bytes came, as the spec says.
7. **The embedding reply is decoded** as `graph.SemanticData` to read its hits; data that does not decode is a broken
   reply. Before, the `index_not_ready` path passed any JSON through.
8. **`TestStoppedSearchEndsWithoutItsReply` (added).** `TestSearchGraphOtherRefusalIsReturned` cannot tell a call
   that waits for the embedding reply from one that does not without a wall clock: graph-query's handler budget
   (natsclient's 30 s) would end a waiting call with the same refusal. The unit test proves "waits for the request to
   end, never its reply, leaving nothing running" in a `synctest` bubble; the integration test proves the reply and
   the error count.
9. **Degrade signal.** A failed merge is declared in the reply (`merge` not honoured, `code`, `reason`) and, when it
   is graph-query's own failure, by the error count, as the fallback was. No Warn line or dedicated metric is added;
   the design names none.
10. **How long `stop` can wait.** It waits for the embedding request to return after its context is cancelled. A
    blocked write on the connection is not bounded by the context (`ask`'s doc comment, ADR-112), so the same bound
    applies here as to every other downstream request.
