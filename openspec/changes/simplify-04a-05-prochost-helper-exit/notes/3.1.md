# Task 3.1 notes

Mechanism (design D1, `cmd.StdinPipe` variant):

- `Start` (`internal/harness/prochost/prochost.go:110`) calls `cmd.StdinPipe()` and discards the writer. `cmd` keeps
  the write end in its close-after-wait list, and the reaper goroutine holds `cmd` inside `cmd.Wait` until the child
  has exited, so the write end closes only when the helper is gone or the test process is. No field is added to
  `Process`.
- `Helper` (`prochost.go:52-59`), only once the marker names this helper, starts a goroutine that copies stdin to
  `io.Discard`. When the copy returns (end-of-file, or a read error) it writes
  `prochost: helper <name> exiting: test process ended (<how>)` to stderr and calls `os.Exit(1)`.

## Choices the design does not spell out

- **Exit code 1.** The design asks only for non-zero. 1 differs from `testing`'s panic exit (2) and from the
  helper-parent's own setup exits (2-4).
- **A read error also exits.** `io.Copy` ends on end-of-file (nil error) or on a read error; either way the helper
  can no longer see its test process, so it exits and names the error (fail closed).
- **No race with a clean SIGTERM exit.** While the test process runs it holds the write end, so the watcher stays
  blocked in its read; the hello helper's SIGTERM path still ends through `os.Exit(0)`
  (`TestStartedHelperHasItsOwnGroupAndCapturedOutput` passes). The pipe closes only after `cmd.Wait` has reaped the
  child.
- **Ordinary test runs untouched.** The watcher starts after the marker check, so `TestHelperProcess` in a normal
  `go test` run (stdin whatever the shell gave it) still returns at once (`TestHelperIsANoOpWithoutItsMarker`).
- **Doc comment.** Only `Helper` gains a minimal comment naming #208 and that `fn` must not read stdin; the package
  doc comment and `docs/testing.md` are task 4.1.
