As the task predicted: the valid-input nil-target row panics, the empty-input row returns nil, and the unknown key is
accepted. Two rows already held on the base commit and are kept as guards, not counted as failing-first evidence:

- *valid configuration, nil pointer*: `json.Unmarshal` returns `*json.InvalidUnmarshalError`, which the base wraps as
  invalid. The empty-configuration nil-pointer row did fail (nil returned).
- *data after the first value*: `json.Unmarshal` refuses trailing data itself. The row pins that the strict decoder
  that replaces it keeps the refusal (D2).

## Choices the design does not spell out

- The whole target check (nil, nil pointer, not a pointer) moves first, not only the nil check: one check on the
  target, before the config check and before the empty-input return. On the base commit a non-pointer target with an
  empty configuration was accepted; it is now refused like a nil one.
- Strict decoding reuses `decodeStrict` (`component/port_codec.go`), which the design names as the shape, rather than
  a copy. Its unknown-key error is `encoding/json`'s `json: unknown field "prot"`, which names the key.
