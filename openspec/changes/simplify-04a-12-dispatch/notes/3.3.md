# Task 3.3 notes

`metricsUpdater` removed; the queue-depth gauge counts waiting items (design D5, #136 item 1).

## Conformance

| Design statement | Where |
| --- | --- |
| The gauge goes up when an item is accepted | `internal/dispatch/keyed_pool.go:219`, after the send to the lane succeeds |
| The gauge goes down when a lane picks the item up | `keyed_pool.go:242`, first in `runOne`, before `Process` |
| No sampler goroutine, no `GaugeFunc` | `metricsUpdater` and the `stopMetrics` channel task 3.1 added (`notes/3.1.md`) are deleted; `NewKeyedPool` starts only the lanes (`:163`) |
| The shutdown coordinator stays | `keyed_pool.go:290` (`go p.drain()`) |
| Summed over pools of one `Name` | each pool writes the gauge `metric.RegisterOrGet` returns for that name (`newKeyedMetrics`), so pools of one name add to and take from one gauge |

## Choices the design does not spell out

- **Raise after the send, not before.** The gauge counts accepted items, so it rises only once the send succeeds: a
  submit parked on a full lane, or one whose context ends, never counts. The cost: between a send and its `Inc`, the
  lane can pick the item up and `Dec` first, so a scrape at that instant can read one low (even -1). The spec
  promises the count only "whenever no submit or lane pickup is in progress", which covers this. Raising before the
  send instead would count parked submits, which are not accepted.
- **Help text** now says what the gauge counts: "Items accepted and not yet passed to Process, across all lanes of
  every pool of this name".
