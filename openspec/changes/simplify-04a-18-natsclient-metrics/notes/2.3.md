# Task 2.3 notes

## Base failures

On the base commit `7132e4e` with only the test files changed, the two tables in
`natsclient/kv_watcher_ownership_test.go` run every row through `KeysByFilter` and `FilteredKeys`
(`filteredListings`). Every `KeysByFilter` row passes; every `FilteredKeys` row fails.

```text
go test -race -count=1 -run TestKVStoreFilteredCancellationFinishesNativeDelivery -v ./natsclient/
--- FAIL: TestKVStoreFilteredCancellationFinishesNativeDelivery (0.00s)
    --- PASS: TestKVStoreFilteredCancellationFinishesNativeDelivery/KeysByFilter (0.00s)
    --- FAIL: TestKVStoreFilteredCancellationFinishesNativeDelivery/FilteredKeys (0.00s)
        Messages: production must invoke native Stop once before public return (expected 1, actual 2)
        public listing returned with native Updates delivery pending
```

The cancellation row fails on what the design meant it to catch: base `FilteredKeys` returns while the watcher still
holds an undelivered update.

Each `TestKVStoreFilteredWatcherSnapshotAndStopErrors/FilteredKeys/<row>`, run alone
(`go test -race -count=1 -run 'TestKVStoreFilteredWatcherSnapshotAndStopErrors/FilteredKeys/<row>$' ./natsclient/`),
exits 1 with `panic: runtime error: invalid memory address or nil pointer dereference` in
`scriptedWatchBucket.ListKeysFiltered`, for all four rows (`snapshot_success_discards_post_marker`, `premature_close`,
`nonbenign_stop_after_closure`, `already_terminal_stop_requires_closure`). The scripted bucket offers only
`WatchFiltered`; base `FilteredKeys` reads through `ListKeysFiltered`, which the bucket does not implement. The same
four rows through `KeysByFilter` exit 0.

## Choices the design does not spell out

- The empty row has two states on one real bucket: empty, then holding one key (`other.one`) the filter `diag.>` does
  not match. The empty bucket is the state in which nats.go's own `Keys` returns `ErrNoKeysFound`, so it is the one
  most likely to reach the branch task 3.4 removes.
- Both tables keep their names; each body moved into a helper the table runs once per entry point, so the rows did
  not change.
