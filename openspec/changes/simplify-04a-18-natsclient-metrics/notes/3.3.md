# Task 3.3 notes

## Choices the design does not spell out

- `PublishToStreamWithAck` reaches the one path, as D3 says, so `publishToStream` must know which caller's errors to
  return. It takes a `classify` flag: with it (only `PublishToStreamWithAck`), a failure of the publish itself is
  counted as `publish_to_stream` and wrapped transient; without it, nats.go's error comes back unchanged. The
  not-connected and JetStream errors return unchanged either way. The alternative was a helper making the checks
  and the build, with each caller doing its own `PublishMsg`; it leaves two publish calls and a `publishToStream`
  with no use for the ack, against D3's "returning `(*jetstream.PubAck, error)`".
- The message builder is a free function, `streamMsg(ctx, subject, data, msgID)`. The async path calls it with an
  empty `msgID`, which builds the message it built before: no header unless a trace adds one.
- `publishToStreamAsync` keeps its order (status, `ctx.Err()`, JetStream), so only the builder is shared, as D3
  says.
- `PublishToStreamWithAck`'s doc comment loses the `AutoCreate` line and gains one saying which errors are counted
  and classified, the behaviour 2.2's oracle holds.
