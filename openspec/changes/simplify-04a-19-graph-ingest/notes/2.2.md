# Task 2.2 notes

The change is in `processor/graph-ingest/entity_writes.go`: each of the five writes calls a new unexported method,
`writeFailed`, when its write call returns an error. Choices the design does not spell out:

1. `writeFailed` re-checks the poison record before it invalidates the cache entry, the order `committed` uses. A
   concurrent query can run between the two steps and read the key; that is harmless, because the invalidation bumps
   the key's cache generation, so the query's repopulation is refused (`repopulateEntityCacheEntry`) and the next
   query reads the bucket.
2. The poison re-check is guarded by the same atomic load the clear paths use (`entityPoisonSize`), so on the healthy
   path a failed write costs one atomic load and one cache invalidation. `verifyEntityPoisonRecord` itself takes the
   inventory lock before it reads, so the guard keeps the lock off that path.
3. The replace and append writes can fail inside their callback after the seam's read check refused the stored value
   (`decodeStoredForWrite`), which already records and re-checks the key. `writeFailed` then re-checks it a second
   time: one more bucket read, only for a key the write just found poisoned. Telling that error apart from the
   others would be the sorting of errors D1 rejects.
4. The doc comment states no nats.go behaviour: it says natsclient does not promise that a write which returns an
   error stored nothing (`natsclient/kv.go`, the `UpdateWithRetryRev` comment), and names the lost reply as one case
   (#174). The tests inject the lost reply with `natsfixture.FaultKV`; they do not drive a real timeout.

## Post-review: `cacheGen` growth (owner decision 2026-10-18)

Codex's automated review (PR #299, inline on `entity_writes.go:506`) found that `writeFailed` adds a `cacheGen` entry
for a key that was never written, so the map grows past the bound its comment stated. A not-found skip would not bound
it: a probe against the fixture's NATS server (nats.go v1.54.0) showed `DeleteAtRevision` and `Update` on a
never-written key return a revision mismatch, not not-found, and the delete path does not read first. Skipping on a
revision mismatch too would sort errors into stored and not stored, which D1 rejects. The owner chose to keep D1 as
it is and correct the comment at `component.go:493-506`; removing or bounding the map is #300.
