Choices the design does not spell out:

1. The Health tests read through `awaitHealthAfterTick`: each `probe.Await` observation calls
   `refreshReadinessStatus` and then `Health()`. A compute the running loop began before the consumer was deleted can
   land after a single test call; the next observation's own tick replaces it, so no test waits on the loop's cadence
   (design D3, "Reading after a direct `refreshReadinessStatus` call").
2. The clearing test is named `TestIntegration_HealthClearsWhenObservationSucceeds_ConsumptionNotChecked`: the task
   names the prefix, and design D3 asks that the name say consumption recovery is not checked (Codex batch 2 review:
   the test never publishes after the consumer is recreated, and whether nats.go's consume loop resumes is not probed
   or promised; renamed from `_ConsumptionNotRestored`). The recreated consumer takes the
   configuration the server reported for the deleted one (`ConsumerInfo.Config`).
3. The lost-consumer test asserts unhealthy, `Status` `degraded`, and a `LastError` naming the backlog and the
   consumer; it does not recreate the consumer (#216).
4. `TestIntegration_UnconfirmedDeleteClearsPoison` builds an unstarted component, and `Health()` reads `running`; the
   test sets `c.running = true`, as `poisonScopingTestComponent` (`poison_scoping_test.go:38`) does.
5. The envelope test holds a backlog with the `consumeStream` barrier `TestIntegration_ReadinessEnvelope_BacklogIsNotReady`
   uses (owner question 2: the field stays), and reads the key with `probe.Await` until an envelope with `lag` above zero
   is there; every envelope published while the message is held has one.
