## The poison-accounting test, case by case

The test is `TestHandleMessage_RejectionsLandOnPoisonAccounting`. Design D7 says `handleMessage`'s two tests "drive
`processIngest` instead". Five of this test's six cases fail in `decodeEntity`, and the consume closure counts and
terminates those before anything reaches `processIngest` (`component.go`, the consume closure's decode branch), so it
could not be rewritten that way. The orchestrator ruled, after the first stop, on D7's intent (`handleMessage` goes;
its tests' outcomes stay proven): compare it with `TestStreamLane_FailingPayloadIsTerminated`, which drives the
consume closure Start wires; add what the old test asserts and the stream-lane test does not; delete the old test.
The comparison:

| Case | Old test asserted | `TestStreamLane_FailingPayloadIsTerminated` | Added |
| --- | --- | --- | --- |
| `invalid`, `panic-entity-id`, `panic-triples`, `panic-validate`, `panic-unmarshal` (each) | no panic escapes | the subtest runs the handler on the test goroutine; a panic fails it | none |
| the same five | error count is exactly 1 from a fresh component | error count rises by exactly 1, and stays there after the next message | none |
| the same five | the bucket holds no key at all (`storedKeyCount == 0`) | only that the fence entity is absent | yes: `c.entityBucket.Keys` is empty after the poison message |
| `conforming` (reaches `processIngest`) | error count 0; one key stored | the next conforming message is acked, the fence entity is stored, and the error count does not move | none: covered, so no new `processIngest` test |

The stream-lane test also asserts what the old one did not: the terminate disposition and the WARN line naming the
payload type and subject. `storedKeyCount` and `newFenceTestComponent`'s bucket return lost their last reader and
went. The added key assertion was not mutation-checked: making the poison branch store a key would itself be a new
write path, not a wrong change to an existing line.

## Choices the design does not spell out

1. **The stale-repopulation test** (`cache_stale_repopulation_integration_test.go`). The test-side wrapper is
   `pausingGetBucket`, a `jetstream.KeyValue` that pauses the first `Get` of the entity after the server has answered
   it, until the test releases it; every other `Get` (the concurrent append's included) passes through, chosen by a
   compare-and-swap rather than `sync.Once`, whose `Do` would hold the append's `Get` until the first returned. The
   reader captures the key's generation before its `Get` (`query.go`), so the pause holds it in the same window the
   hook did. The component is not started: as `TestIntegration_TypedClientPreservesCommitAmbiguity` does, the test
   gives an unstarted component the fixture's `ENTITY_STATES` (through the wrapper) and the cache Start would build
   (`cache.NewSimple`), so no running goroutine reads the store it replaces.
2. **The failed-start test** (`TestFailedRegistrationRunsNoRequestWork/query`). The hook and its `hookEntered`
   check go; the seeded entity stays, so a query that ran would succeed and only the refusal gives the error the test
   asserts (`errs.ErrNotStarted`, transient).
3. **`handleMessage`'s integration test** (`TestIntegration_HandleMessage_DoesNotClobber`) is renamed
   `TestIntegration_StreamIngest_DoesNotClobber`: it decodes with `decodeEntity` and applies with `processIngest` on
   a `keyedIngestTestMsg`, the two steps the consume closure runs, and also asserts the input is acknowledged.
4. **Comments that named `handleMessage`** (six, in `component.go`, `entity_validation_test.go`,
   `fact_lane_guards_test.go`, `ingest_metrics_test.go`, `interrupted_work_test.go`,
   `keyed_ingest_integration_test.go`) now name the step that does the work: `decodeEntity`, `applyIngest` or the stream
   lane; `decodeEntity`'s doc comment names its one caller.
5. **D6.** The help text is the design's sentence, with `internal` in single quotes inside the Go string; the
   constructor's doc comment no longer names `MutationResponse ErrorCode`.
