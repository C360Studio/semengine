# Task 5.2 notes

Ruling I (#91 comment 6062681355): `handlesMu` goes. The proof is the access list below, read from the code at the
task's commit; the race run is evidence only.

## Every handle access, and the goroutine it runs on

The handles are `cancel`, `ingestPoolCancel`, `ingestSubmitCancel`, `statusDone`, `consumers`, `subscriptions` and
`ingestPool`. Every production access is in one of five functions:

| Access (`processor/graph-ingest/`) | Function | Runs on |
| --- | --- | --- |
| `component.go:974-976` write `cancel`, `ingestPoolCancel`, `ingestSubmitCancel` | `start` | Start's caller |
| `keyed_ingest.go:198` write `ingestPool` | `buildIngestPool`, called only from `start` (`component.go:1005`) | Start's caller |
| `component.go:1515` read `ingestPool` into the callback's `pool` local | `setupJetStreamConsumer`, via `setupSubscriptions` from `start` (`:1008`) | Start's caller |
| `component.go:1592` append `consumers` | `setupJetStreamConsumer` | Start's caller |
| `query.go:54`, `mutation_runtime.go:30` append `subscriptions` | `setupQueryHandlers`, `setupMutationHandlers`, from `start` (`:1011`, `:1014`) | Start's caller |
| `component.go:1059` write `statusDone` | `startStatusMetricsLoop`, from `start` (`:1018`) | Start's caller |
| `component.go:1099-1132` read every handle | `cleanup`, called only from `release` (`:1088`) | Stop's caller, or Start's caller for a rollback |
| `component.go:1144-1150` clear every handle | `clearLifecycleHandles`, called only from `release` (`:1091`) | as `cleanup` |

`start` and `release` are passed only to `internal/lifecycleguard` (`component.go:964`, and `Stop`'s closure at
`:1072`). The guard runs `start`, and a failed start's rollback (`lifecyclecleanup.RollbackFailedStart`, synchronous),
on Start's caller, and closes `startDone` under its mutex afterwards; a `Stop` that arrives during `Start` waits on
that channel before it runs `release`, two `Stop`s cannot run `release` together (`stopping`), and each `Stop` takes
the guard's mutex before and after its cleanup. So every write above happens before every later read, with no lock
of graph-ingest's own.

No other goroutine touches a handle:

- The status loop goroutine (`component.go:1060`) closes the `statusDone` local it was started with and reads no
  handle field.
- Each consumer callback submits to its `pool` local (`component.go:1515`), never `c.ingestPool`.
- Request handlers, pool lanes and the exported methods read none of the seven fields (grep for each field name over
  the package's non-test files returns only the lines above).

`clearLifecycleHandles` also clears `entityCache` and `statusPublisher`, which are not on the list: they were cleared
under `handlesMu`, but their readers (request handlers, pool lanes, the status loop, exported `CreateEntity`) never
took it, so removing it changes nothing for them.

## Tests that read handles

- `lifecycle_integration_test.go` reads `consumers` while `Start` is blocked in its second consume: `start` appended
  the first handle before calling the stand-in that closed `secondEntered`, and the test reads after receiving from
  it, so the channel orders the two.
- `TestComponent_RespectsContext_Cancellation` reads `statusDone` after `Start` returned on the same goroutine.
- The lifecycle suite's `Observe` (`lifecycle_adapter_test.go`) runs after a `Start` or `Stop` returned its result to
  the suite over a channel. The one exception is the suite's report of a call that overran its bound
  (`internal/harness/lifecycletest`, `describe`), which reads while the call still runs; that check has already
  failed, and the lock never covered `ingestPool`, `subscriptions` or `entityCache` there either.
