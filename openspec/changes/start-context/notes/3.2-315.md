# Task 3.2 notes: #315, Start's context lost when handler registration fails

Codex's review at stop B of PR #310 (at `0faadcc`) found that `start` returned a failed query or mutation
registration's error before its final `ctx.Err()` check. The registrations run under the run context (D6), so a Start
context that ended during a failing registration was not reported, against ADR-113 ("if ctx ends first, Start returns
that error and holds nothing").

## Choices

- The fix joins the Start context's error to the registration error on both exits:
  `errs.Wrap(errors.Join(err, ctx.Err()), "Component", "Start", "<action>")`. `errors.Join` drops a nil, so a live
  context leaves the error as before. `errs.Wrap` wraps with `%w` (`pkg/errs/errs.go:360-365`), so `errors.Is` reaches
  both `context.Canceled` and the registration error.
- The comment above the final `ctx.Err()` check now covers both paths.
- The test, `TestGraphIngest_StartReportsItsContextWhenHandlerSetupFails` in `lifecycle_integration_test.go`, is the
  issue's reproduction made table-driven (rows `query`, `mutation`). The mutation row's failing call is not hard-coded:
  it is one past the number of `graph.QueryVerbs()` whose responder is graph-ingest, since `setupQueryHandlers`
  registers one subscription per such verb (`query.go:39-58`); today that is 3, so the mutation row fails call 4, as
  the issue said. The test also records the subject of the failed call and checks it is a query subject for the
  `query` row and not one for the `mutation` row, so a change in registration order fails the test instead of
  silently testing the wrong exit.
- Each row asserts `errors.Is(err, context.Canceled)`, `errors.Is(err, natsclient.ErrNotConnected)`, nothing held
  through the suite adapter's `Observe`, and a later `Stop` returns nil under a 30 s bound.
