# Task 2.3 notes: `TestSmoke_KillMidIngestKeepsAcknowledgedWrites`

Developer notes on the choices design D6, case 2, leaves open, and the "shown to fail" runs design D7 asks for.
**The design's mutant for this case survives (below); task 2.3 stays unticked until that is re-ruled.**

## Choices the design leaves open

- **How the hold is made.** The composition root's logger handler (`holdOnIngested`, in
  `stack_integration_test.go`) passes every record on, except graph-ingest's `Entity ingested` record for the
  entity whose ID ends in `.fleet.ops.<SMOKE_HOLD>`: there it receives from a channel nothing closes, so that lane
  stays between the entity write and the applied-sequence record until the SIGKILL
  (`processor/graph-ingest/ingest.go`, `keyed_ingest.go`, `applyIngest`). It is settlement_integration_test.go's
  `pauseOnRecord`, scoped to one entity. The match is on the ID's fixed positions 3 to 6, because positions 1 and 2
  are the platform ID `config.Manager` mints after the logger exists; setting the full ID later would race the
  goroutines already logging. No production change.
- **The held input** is a new entity, `drone.010` (`Gyrfalcon`, homed at `base.004`, which had no edge until then),
  published last, so the index must catch up on an edge only the redelivery's process can index.
- **"Mid-ingest" is three events, awaited together, never a time:** the held entity's key exists in `ENTITY_STATES`
  and the consumer's ack floor has reached the held sequence minus 1. Then the test requires the floor exactly at
  that, exactly one pending, delivery through the held sequence, the applied-sequence record of the input before it
  present (so an absent read cannot pass on a wrong key) and the held entity's record absent.
- **The kill:** `Alive`, `Kill`, `Wait` under `t.Context()`, and the exit status must name SIGKILL.
- **The short `ack_wait` is in both boots' configuration.** After the first boot `config.Manager` serves the
  configuration from its bucket (`notes/2.2.md`), so a value only the second boot's file carries would have no
  effect. graph-ingest's ports block is used as written, never merged with the defaults, so the test builds it
  from `graphingest.DefaultConfig()` with the stream port's `ack_wait` set to 2s (`killIngestConfig`); the child
  takes it from `SMOKE_INGEST_CONFIG`. In the first process the held lane's in-progress signal keeps the input
  pending; it comes again in the second process once the wait has passed.
- **After the restart** the test requires: the held input acknowledged, with more deliveries than before the kill
  (the redelivery) and its applied-sequence record present; the ordered waits of design D5; health; `checkAnswers`
  over the first batch plus the held input (each statement once, edges, path, summary, alias, an embedding record
  at each entity's current revision); then `checkWritesAfterRestart`.
- **The index and embedding records caught up on main**: the test passes on the worktree, so no defect to file.
- **"Appending statement" (design D6) has no stream-lane form.** The stream lane's only write mode is replace by
  (subject, predicate, source) (`graph-entity-writes` spec, "Each write mode has one identity rule";
  `processor/graph-ingest/entity_writes.go`); append is a mutation-lane mode only. A second application of the same
  message replaces its own sets with themselves. `statementsOf` keeps every stored statement, so a doubled one would
  show (supplementary mutant B shows it does).

Why it survives: the guard drops only a delivery whose sequence its record already covers. In this history the held
input has no record (the test asserts that before the kill), so the redelivery applies with the guard on or off;
every other input is acknowledged before the kill and is not delivered again. Exactly-once here rests on the
replace write mode being idempotent, not on the guard. The guard matters for a redelivery of an input whose record
was written and whose acknowledgement was lost, a history this hold cannot produce. Task 2.3's "Shown to fail:
graph-ingest's applied-sequence guard off" is therefore not met as written; it goes back for re-ruling.

## Not covered

- A redelivery of an input whose applied-sequence record exists (the guard's own case): the hold after the entity
  write cannot produce it. A hold after the record and before the acknowledgement needs a record graph-ingest does
  not log; adding one for the test would be a production change.
- A write lost because it was acknowledged before it was durable: the held entity's write lands before the hold, so
  this history cannot lose it.
- Examples, not generated checks, as design D6 states for the whole change.
